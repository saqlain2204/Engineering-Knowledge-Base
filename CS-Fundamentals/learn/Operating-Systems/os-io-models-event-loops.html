I/O Models & Event Loops

A web server spends most of its life waiting: for a request to arrive, for the database to answer, for a slow phone to accept the reply. This page explains what a program can do while it waits, and why that choice decides whether one machine can serve 10 users or 10,000. We build up from a single blocking server to an event loop you write by hand, and every number on this page comes from code you can run. It builds on processes and threads and the short overview in File Systems & Disk I/O.

1. The Problem: Programs Mostly Wait

Look at one request to a typical API:

receive request          ~0.05 ms of CPU
parse JSON               ~0.05 ms of CPU
ask the database         ~5 ms of WAITING (network + database work)
build the reply          ~0.1 ms of CPU
send the reply           ~0.05 ms of CPU (more waiting if the client is slow)

The CPU is busy for about 0.25 ms. The request takes about 5.25 ms. So the CPU is idle about 95% of the time for this request. If the program does nothing else while it waits, 95% of the machine is wasted.

Intuition. Think of a waiter in a restaurant. A bad waiter takes one order, walks to the kitchen, and stands there until the food is ready. A good waiter takes the order to the kitchen and goes to the next table. The kitchen rings a bell when food is ready. The good waiter is an event loop, and the bell is epoll.

There are two big ways to use the waiting time:

  1. Many workers. Use many threads. When one thread waits, the operating system runs another one.
  2. One clever worker. Use one thread that never waits on a single client. It keeps a list of all clients and only works on the ones that are ready.

2. Words You Need

WordPlain meaning
I/OInput/output: reading or writing data that lives outside the CPU and memory, such as a network socket, a disk file, or a keyboard.
SocketThe program's end of a network connection. You read bytes from it and write bytes to it (see TCP: sockets).
File descriptor (fd)A small number the kernel gives your program for each open file or socket, like a ticket number: 0, 1, 2, 3...
System callA request from your program to the kernel, such as read, write, accept. Each one costs a little time (roughly 0.1 to 1 microsecond).
Blocking callA call that puts your thread to sleep until it can finish. recv() on an empty socket blocks until data arrives.
Non-blocking callA call that returns at once. If it cannot finish, it says "try again later" (the error EAGAIN).
ReadyA socket is "ready to read" when a read would not block (data is waiting). It is "ready to write" when there is room in the kernel's send buffer.
Event loopA loop that asks the kernel "which sockets are ready?", handles each ready one a little, and asks again. Forever.
ConcurrencyMany tasks are in progress at the same time (they take turns). Parallelism means tasks really run at the same instant on different CPU cores. An event loop gives concurrency on one core.

3. Model 1: One Thread, Blocking

The simplest server. One thread does everything, one client at a time:

while True:
    conn = sock.accept()     # sleep until a client connects
    data = conn.recv(64)     # sleep until the client sends something
    reply = handle(data)     # maybe sleep again on the database
    conn.sendall(reply)      # sleep if the client reads slowly
    conn.close()

Each line can block. While the thread waits for client A's database answer, client B is stuck in the kernel's queue of not-yet-accepted connections (the listen backlog).

Worked example

200 clients arrive at the same moment. Each request waits 100 ms on the database. The server handles them one after another:

  • Client 1 finishes at 100 ms. Client 2 at 200 ms. Client k at k × 100 ms.
  • The last client finishes at 200 × 100 ms = 20 s.
  • The middle client (the median, p50) waits about 100 × 100 ms = 10 s.

The CPU did almost nothing during those 20 seconds. In the lab we measured exactly this: 20.1 s total, p50 10.1 s.

4. Model 2: One Thread per Client

Fix: start a new thread for each client. While one thread sleeps on the database, the kernel's scheduler runs another thread (see scheduling).

while True:
    conn = sock.accept()
    threading.Thread(target=handle_one_client, args=(conn,)).start()

Now 200 clients wait at the same time, so all of them finish after about 100 ms. This is how classic Apache (prefork/worker), Java servlet servers, and many database servers (PostgreSQL uses one process per connection) work.

What threads cost

  • Memory. Each thread has its own stack. Linux reserves up to 8 MB of address space per stack, but only the pages actually touched use real memory. In our lab, 10,000 Python threads that only wait used about 157 MB of real memory (about 16 KB each). Java reserves 1 MB of stack per thread by default, and threads that run deep code touch more of it.
  • Context switches. Switching the CPU from one thread to another costs a few microseconds, plus cold CPU caches afterwards. With 10,000 busy threads, this adds up.
  • Limits. Operating systems cap threads per process and processes per user (ulimit -u, /proc/sys/kernel/threads-max). Containers often cap them too (the cgroup pids.max).
  • Shared data. Threads run in parallel, so shared data needs locks, and locks bring races and deadlocks.

The C10K problem. Around 1999, people asked: how can one server handle 10,000 connections at once? With one thread per connection, memory and switching costs were too high on the machines of that time. The answer was event loops, which is why nginx, Node.js, Redis and HAProxy are built on them.

A common middle ground is a thread pool: a fixed number of threads (say 50) and a queue of work. It caps memory but brings back waiting when all 50 threads are busy. That is the same math as a database connection pool (see Little's law).

5. Non-Blocking Sockets: "Not Ready Yet"

You can tell the kernel: "never put this socket's calls to sleep". In Python, sock.setblocking(False). In C, the O_NONBLOCK flag.

Now recv() on an empty socket returns at once with the error EAGAIN ("try again"). Your thread is free to do other work.

But how do you know when to try again? A bad idea is to ask every socket in a tight loop:

# BAD: busy polling
while True:
    for conn in all_connections:
        try:
            data = conn.recv(1024)      # returns at once
            handle(conn, data)
        except BlockingIOError:         # EAGAIN: nothing yet
            pass

With 10,000 mostly-idle connections, this makes 10,000 system calls per loop, and the CPU sits at 100% doing nothing useful. We need the kernel to tell us which sockets are ready.

6. Asking the Kernel: select, poll, epoll

These are system calls that say: "Here are many file descriptors. Put me to sleep until at least one of them is ready, then tell me which."

CallHow you use itCost per callNotes
select (1983)Pass bit masks of fds. The kernel marks the ready ones.Checks all fds you passed: O(n)Limited to fd numbers below 1024 on Linux. You must rebuild the masks every call.
pollPass an array of fds. The kernel fills in which are ready.O(n)No 1024 limit, but still copies and checks the whole list every time.
epoll (Linux, 2002)Register each fd once with epoll_ctl. Then epoll_wait returns only the ready ones.O(number of ready fds)The kernel keeps the interest list. Used by nginx, Node.js (libuv), Python asyncio, Redis, Go's runtime.
kqueueLike epoll, on macOS and BSD.O(ready)Python's selectors.DefaultSelector picks epoll or kqueue for you.

Worked example: why epoll wins at scale

A chat server has 10,000 connections. In each moment, about 10 of them have new messages.

  • poll: each call hands 10,000 entries to the kernel and the kernel checks all 10,000. Work per call: about 10,000 units.
  • epoll: the 10,000 sockets were registered once. When data arrives on a socket, the kernel adds it to a "ready list" at that moment. epoll_wait just hands back the ready list. Work per call: about 10 units.

That is a 1,000× difference in this example, and it grows as connections grow.

  your program                     kernel
  ────────────                     ──────
  epoll_create()  ───────────────► new epoll instance (interest list + ready list)
  epoll_ctl(ADD, fd 7, READ) ────► watch fd 7
  epoll_ctl(ADD, fd 8, READ) ────► watch fd 8
  epoll_wait() ──── sleeps ...
                                   packet arrives for fd 8
                                   fd 8 put on ready list, wake the waiter
  epoll_wait() returns [fd 8] ◄─── 
  recv(fd 8)  (will not block)

7. An Event Loop by Hand

Here is a complete echo server (it sends back what you send, in capitals) using one thread and Python's selectors module, which uses epoll on Linux:

# sel.py - a tiny event loop by hand with the selectors module (epoll on Linux)
import selectors, socket
sel = selectors.DefaultSelector()          # EpollSelector on Linux
srv = socket.socket(); srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("127.0.0.1", 9000)); srv.listen(100); srv.setblocking(False)
sel.register(srv, selectors.EVENT_READ, data="listener")
print("selector:", type(sel).__name__)
while True:
    for key, _ in sel.select():            # sleep until at least one socket is ready
        if key.data == "listener":
            conn, addr = srv.accept()      # will not block: the kernel said it is ready
            conn.setblocking(False)
            sel.register(conn, selectors.EVENT_READ, data="client")
        else:
            conn = key.fileobj
            data = conn.recv(1024)         # will not block either
            if data:
                conn.sendall(data.upper()) # echo back in capitals (fine for small replies)
            else:                          # empty read = the client closed
                sel.unregister(conn); conn.close()

Read it slowly. There is only one place where the thread sleeps: sel.select(). Every other call is made only after the kernel said it will not block. A new connection on the listening socket counts as "ready to read".

Watching the system calls

We ran this server under strace (a tool that prints every system call a program makes) and connected 3 clients, each sending one line:

$ strace -f -c -e trace=epoll_wait,epoll_ctl,accept4,recvfrom,sendto python3 sel.py
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 42.73    0.000047           4        10         1 epoll_wait
 29.09    0.000032          10         3           sendto
 12.73    0.000014           4         3           accept4
  8.18    0.000009           1         7           epoll_ctl
  7.27    0.000008           1         6           recvfrom

Let us explain every count:

  • epoll_ctl = 7: 1 to register the listener, 3 to register each client, 3 to unregister each client when it closed.
  • accept4 = 3: one per client.
  • recvfrom = 6: two per client: one read with the data, one empty read that means "closed".
  • sendto = 3: one reply per client.
  • epoll_wait = 10: the loop woke up about 3 times per client, plus one call that was cut short when we stopped the server (the 1 error).

No busy polling, no threads, and the process used almost no CPU while idle.

Simplification. sendall on a non-blocking socket can fail if the send buffer is full. A real event loop keeps unsent bytes per connection and also watches for "ready to write". That is exactly what asyncio's writer.drain() does for you (see backpressure).

8. Level-Triggered vs Edge-Triggered

epoll can report readiness in two ways. Imagine 3,000 bytes arrive and you read only 1,024 of them.

ModeRuleWhat happens next
Level-triggered (default)"Tell me every time I ask, as long as data is waiting."The next epoll_wait reports the socket again, because 1,976 bytes are still there. Safe and simple. select and poll work this way.
Edge-triggered (EPOLLET)"Tell me once, when new data arrives."No new report until more data arrives. If you stop reading early, the 1,976 bytes can sit there forever. You must read in a loop until you get EAGAIN.

Intuition. Level-triggered is a light that stays on while there is mail in the box. Edge-triggered is a doorbell that rings once when the postman comes. If you take only one letter after the doorbell, nobody reminds you about the rest.

Edge-triggered saves some wake-ups and is used by high-performance servers like nginx, but it is easy to get wrong. Start with level-triggered.

9. async/await: Event Loops Made Readable

The hand-written loop works, but real handlers do many steps: read the request, call the database, call another API, write the reply. Writing every step as "register a callback and come back later" is hard to read (people call it callback hell).

async/await lets you write code that looks blocking but gives control back to the loop at every await:

async def handle(reader, writer):
    request = await reader.read(64)        # pause here; loop serves others
    row = await db.fetch("SELECT ...")    # pause here too
    writer.write(render(row))
    await writer.drain()                   # pause until the reply fits in the buffer
    writer.close()

What happens at an await:

  1. The function (called a coroutine) saves where it is, like a bookmark.
  2. It tells the loop: "wake me when this socket is ready" (the loop registers it with epoll).
  3. It returns control to the loop. The loop runs other coroutines that are ready.
  4. When epoll reports the socket ready, the loop resumes the coroutine right after the await.

This is called cooperative multitasking: tasks give up the CPU only when they choose to (at an await). Threads use preemptive multitasking: the kernel can pause a thread at any moment.

ThreadsEvent loop + async
Who switches tasksThe kernel, at any instructionYour code, only at await
Memory per waiting taskA stack (KBs to MBs)A small object (about 1 KB)
Uses many CPU coresYes (except Python's GIL for pure Python code)No, one loop uses one core. Run one loop per core.
Data racesPossible anywhereOnly across await points
A slow CPU taskSlows only its threadFreezes every client

Languages differ in how they hide this. Node.js runs one event loop (libuv) and everything is async. Go starts cheap "goroutines" that look like threads but are scheduled by Go's runtime on top of epoll, so blocking-looking code is fine. Java 21 added virtual threads that do the same.

10. The Lab: Four Servers, 200 Clients

We wrote four servers and hit each with 200 clients at once. Each request waits 100 ms (like a database call). The full program is below; run it with python3 iolab.py (Python 3.10+).

# iolab.py - four ways to serve 200 clients whose requests each wait 100 ms on I/O.
import asyncio, socket, statistics, sys, threading, time

WAIT = 0.1          # each request waits 100 ms (think: a database call)
CLIENTS = 200

def handle_blocking(conn):
    conn.recv(64)
    time.sleep(WAIT)                 # blocking wait: this thread can do nothing else
    conn.sendall(b"done\n")
    conn.close()

def server_one_thread(sock):         # A: one thread, one client at a time
    while True:
        conn, _ = sock.accept()
        handle_blocking(conn)

def server_thread_per_conn(sock):    # B: a new thread for every client
    while True:
        conn, _ = sock.accept()
        threading.Thread(target=handle_blocking, args=(conn,), daemon=True).start()

async def handle_async(reader, writer, bad=False):
    await reader.read(64)
    if bad:
        time.sleep(WAIT)             # D: a blocking call inside the event loop (bug!)
    else:
        await asyncio.sleep(WAIT)    # C: give control back to the loop while waiting
    writer.write(b"done\n")
    await writer.drain()
    writer.close()

def server_event_loop(sock, bad=False):
    async def main():
        srv = await asyncio.start_server(lambda r, w: handle_async(r, w, bad), sock=sock)
        await srv.serve_forever()
    asyncio.run(main())

def run_clients(port):
    lat = []
    def one():
        t0 = time.time()
        s = socket.create_connection(("127.0.0.1", port))
        s.sendall(b"hi\n"); s.recv(64); s.close()
        lat.append(time.time() - t0)
    t0 = time.time()
    ts = [threading.Thread(target=one) for _ in range(CLIENTS)]
    for t in ts: t.start()
    for t in ts: t.join()
    lat.sort()
    return time.time() - t0, statistics.median(lat), lat[int(0.99 * len(lat)) - 1]

if __name__ == "__main__":
    kinds = {"A one thread, blocking": lambda s: server_one_thread(s),
             "B thread per connection": lambda s: server_thread_per_conn(s),
             "C event loop (asyncio)": lambda s: server_event_loop(s),
             "D event loop + time.sleep": lambda s: server_event_loop(s, bad=True)}
    for name, fn in kinds.items():
        sock = socket.socket(); sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
        sock.bind(("127.0.0.1", 0)); sock.listen(512)
        threading.Thread(target=fn, args=(sock,), daemon=True).start()
        time.sleep(0.2)
        total, p50, p99 = run_clients(sock.getsockname()[1])
        print(f"{name:28s} total {total:6.2f} s   p50 {p50*1000:7.0f} ms   p99 {p99*1000:7.0f} ms")

Results (8-core Linux machine, Python 3.13)

A one thread, blocking       total  20.08 s   p50   10065 ms   p99   19855 ms
B thread per connection      total   0.16 s   p50     106 ms   p99     128 ms
C event loop (asyncio)       total   0.16 s   p50     102 ms   p99     104 ms
D event loop + time.sleep    total  20.13 s   p50   10117 ms   p99   19916 ms

What this shows:

  • A matches our hand math: 200 × 100 ms = 20 s, median about 10 s.
  • B and C both finish in about 0.16 s. Each client waits about its own 100 ms, plus a little overhead. Threads have a slightly worse p99 (128 ms vs 104 ms) because creating 200 threads and switching between them takes time. (A second run gave B a p99 of 220 ms: thread start-up cost varies.)
  • D uses an event loop, but it is exactly as bad as A. One wrong line made the whole server single-file. The next section explains why.

Memory: 10,000 waiting clients

We also started 10,000 threads that all wait on an event, and then 10,000 asyncio tasks that all wait on an event, and measured how much real memory (RSS) grew:

10000 threads: +157 MB
10000 asyncio tasks: +9 MB

About 16 KB per thread vs about 1 KB per task. For 10,000 connections both are fine on a modern server. For 1,000,000 long-lived connections (chat, push notifications, IoT devices), only the event loop is practical.

11. The Classic Bug: Blocking the Loop

In server D, the handler called time.sleep(0.1) instead of await asyncio.sleep(0.1). time.sleep puts the whole thread to sleep. The event loop runs in that thread. So for 100 ms, the loop cannot accept, read, or write for anyone.

time ─────────────────────────────────────────────────►
loop thread:  [client 1 sleeps 100ms][client 2 sleeps 100ms][client 3 ...
other clients: waiting      waiting        waiting

In real code the blocking call is rarely time.sleep. It is usually one of these:

  • A normal (non-async) database driver or HTTP library, like requests.get() or psycopg2, called from an async def.
  • Heavy CPU work: parsing a 50 MB JSON file, resizing an image, running a machine learning model, a slow regular expression.
  • Reading a big file from disk (remember: regular files always look "ready" to epoll, see File Systems).
  • DNS lookups through the C library's blocking getaddrinfo.

How to fix it

  1. Use the async version of the library (httpx/aiohttp instead of requests, asyncpg or async psycopg instead of psycopg2).
  2. Move blocking calls to a thread pool: await asyncio.to_thread(slow_function, arg). In Node.js, use worker threads.
  3. Move heavy CPU work to a process pool or a separate service, so it can use other cores.

How to detect it

  • Python: run with PYTHONASYNCIODEBUG=1. asyncio then logs any step that holds the loop for more than 100 ms: Executing <Task ...> took 0.105 seconds.
  • Node.js: measure event loop lag (perf_hooks.monitorEventLoopDelay()). If a timer set for 0 ms fires after 200 ms, something blocked the loop for 200 ms.
  • Symptom in production: latency of every endpoint jumps together, even health checks, while CPU on one core is at 100%.

12. Real Servers Mix Models

Almost nothing in production is purely one model:

SystemDesign
nginxOne event loop per worker process, one worker per CPU core. Each worker handles thousands of connections.
Node.jsOne event loop for your JavaScript, plus a small thread pool (libuv, 4 threads by default) for file I/O, DNS and crypto.
Gunicorn + Uvicorn (Python)Several worker processes (to use all cores), each running an asyncio event loop.
RedisOne main event loop thread runs all commands, which is why one slow command (like KEYS *) stalls everyone.
PostgreSQLOne process per client connection. That is why it needs a pooler like PgBouncer for thousands of clients.
GoMany goroutines multiplexed onto a few OS threads; the runtime uses epoll underneath.

The common rule: one event loop per core for waiting on the network, plus pools of threads or processes for work that would block or burn CPU.

Newer still is io_uring on Linux: instead of asking "which sockets are ready?" and then making a system call for each, the program puts whole requests ("read from fd 8 into this buffer") in a ring shared with the kernel and collects the results later. It works for files too. See the overview in File Systems.

13. Backpressure: When Clients Are Slow

Backpressure means a slow receiver pushes back on a fast sender, so data does not pile up without limit.

Example: your server streams a 1 GB file to a phone on a slow network. Your disk reads at 500 MB/s, but the phone takes 1 MB/s. If you keep calling writer.write() without waiting, the unsent data piles up in your process's memory: after 2 seconds, about 1 GB is queued. With 50 such phones, the server runs out of memory.

The fix is to wait for the buffer to drain:

async def stream_file(path, writer):
    with open(path, "rb") as f:
        while chunk := f.read(64 * 1024):
            writer.write(chunk)
            await writer.drain()     # pauses this task while the send buffer is full

Underneath, TCP's flow control stops the kernel from sending faster than the phone can receive. When the kernel's send buffer is full, the socket is no longer "ready to write", so drain() waits. The same idea applies to queues between services: always put a size limit on a queue, and decide what happens when it is full (wait, drop, or return 503).

14. Practice Problems

Answers follow each one.

Problem 1: how long?

A single-threaded blocking server gets 50 requests at the same moment. Each takes 2 ms of CPU and 38 ms waiting on a database. How long until the last one finishes? What if the server is a correct event loop instead?

Answer: Blocking: each takes 40 ms one after another, so 50 × 40 = 2,000 ms. Event loop: the waits overlap, but the CPU work still runs one at a time on one core: 50 × 2 ms = 100 ms of CPU, plus one 38 ms wait at the end, so about 138 ms.

Problem 2: how many threads?

A thread-per-request server gets 400 requests per second. Each request takes 250 ms, almost all of it waiting. How many threads are busy at once on average? (Hint: Little's law, busy = arrival rate × time in system.)

Answer: 400 × 0.25 = 100 threads. A pool of 50 threads would make requests queue up, and the queue would grow forever because the pool can only finish 50 / 0.25 = 200 requests per second.

Problem 3: find the bug

@app.get("/report")
async def report():
    data = requests.get("https://slow-partner.example/api").json()   # takes 2 s
    return summarize(data)

Under load, every endpoint of this service (even /health) becomes slow. Why, and give two fixes.

Answer: requests.get is a blocking call inside an async def, so it freezes the event loop for 2 s per call. Fix 1: use an async client, async with httpx.AsyncClient() as c: data = (await c.get(url)).json(). Fix 2: data = await asyncio.to_thread(lambda: requests.get(url).json()). (Or declare the route as a plain def, which frameworks like FastAPI then run in a thread pool.)

Problem 4: select or epoll?

A proxy holds 20,000 connections. In each loop round, about 20 are ready. Roughly how many fd checks does each round cost with poll, and with epoll? Could select even be used?

Answer: poll: about 20,000 per round. epoll: about 20 (only the ready list). select cannot be used on Linux, because fd numbers go above its limit of 1024.

Problem 5: edge-triggered trap

With EPOLLET, a client sends 10 KB. Your code reads 4 KB once and goes back to epoll_wait. The client now waits for a reply that never comes. Why?

Answer: Edge-triggered mode reports readiness only when new data arrives. The remaining 6 KB is still in the buffer, but no new data comes, so epoll never reports the socket again. Fix: in edge-triggered mode, keep reading until recv returns EAGAIN, or use level-triggered mode.

15. Common Pitfalls

  • Blocking calls inside async code. One time.sleep, sync database driver, or big JSON parse stalls every client (our lab: 0.16 s became 20 s).
  • Thinking async makes CPU work faster. An event loop only overlaps waiting. CPU-heavy work needs more cores (processes) or a faster algorithm.
  • Unlimited concurrency. An event loop can accept 50,000 requests, then open 50,000 database connections and crash the database. Limit with a semaphore or pool.
  • Forgetting backpressure. Writing without drain() or with unbounded queues uses unbounded memory with slow clients.
  • Busy polling. A loop of non-blocking calls with no select/epoll burns 100% CPU.
  • Edge-triggered without draining. Read until EAGAIN, or data gets stuck.
  • Huge thread pools as a fix. 5,000 threads hide a slow dependency for a while, then cost memory and context switches. Find the slow dependency.
  • Assuming files are async. epoll does not help with regular files; use a thread pool or io_uring.

Memory Allocation & Garbage Collection

Every time your code makes a list, a string, or an object, someone has to find room for it in memory. Later, someone has to give that room back. This page shows who does that and how: the stack, the heap, malloc and free, and the garbage collectors in Python, Java, Go and Node. It builds on Virtual Memory & Paging, and every number comes from a run you can repeat.

1. Why This Matters

Three real problems come straight from this topic:

  • A service frees most of its data after a busy hour, but its memory graph never goes down. The team thinks it is a leak. It is not. It is fragmentation (section 6).
  • A Java or Go API has a fine average latency, but every few seconds a request takes 300 ms. That is often a garbage collection pause (section 11).
  • A container is killed with OOMKilled even though the language runtime "thinks" it has plenty of room. The runtime did not know about the container limit (section 14, and the OOMKilled scenario).

You can only fix these if you know where memory comes from and who gives it back.

2. Words You Need

  • Allocate. Ask for a piece of memory to hold some data.
  • Free (or release). Say "I am done with this piece; it can be reused."
  • Stack. A region of memory for function calls. Each call gets a slice; the slice is thrown away when the call returns. Fast and automatic, but small.
  • Heap. A big region for data that must live longer than one function call, or whose size is only known at run time. You (or a garbage collector) must free it.
  • Allocator. The code that hands out heap memory. In C it is malloc and free, usually from glibc on Linux.
  • Pointer (or reference). A value that holds the address of some data. "A points to B" means A knows where B lives.
  • Leak. Memory you no longer need but never freed. It stays used until the process dies.
  • Garbage. Heap data that nothing can reach any more. No pointer leads to it.
  • Garbage collector (GC). Code inside a language runtime that finds garbage and frees it for you.
  • RSS (resident set size). How much real RAM a process is using right now. This is what top shows and what container limits count.
  • Pause (or stop-the-world). A moment when the GC stops your code so it can work safely.

3. The Memory Map of a Process

From virtual memory you know that each process sees its own private address space. Here is how that space is laid out on Linux, low addresses at the bottom:

high addresses
 +-----------------------------+
 |  stack                      |  grows DOWN, one frame per call
 |      |                      |  (default limit often 8 MB per thread)
 |      v                      |
 |                             |
 |  mmap area                  |  big malloc blocks, shared libraries,
 |                             |  memory-mapped files
 |      ^                      |
 |      |                      |
 |  heap                       |  grows UP (brk), small malloc blocks
 +-----------------------------+
 |  data / bss                 |  global variables
 +-----------------------------+
 |  text                       |  your machine code (read-only)
 +-----------------------------+
low addresses

You can see this for any running process: cat /proc/<pid>/maps lists every region, and [heap] and [stack] are labeled. The stack limit is shown by ulimit -s (in KB).

4. The Stack, Traced by Hand

Each function call gets a stack frame: a slice of the stack that holds its local variables, its arguments, and the address to go back to when it returns. Take this C code:

int square(int x) {
    int r = x * x;
    return r;
}

int main(void) {
    int a = 3;
    int b = square(a);
    return b;
}

Here is the stack at each step. Each box is a frame; the newest frame is on top.

step 1: main starts      step 2: main calls square   step 3: square returns
                         +--------------------+
                         | square             |
                         |   x = 3            |
                         |   r = 9            |
                         |   return to main   |
+------------------+     +--------------------+      +------------------+
| main             |     | main               |      | main             |
|   a = 3          |     |   a = 3            |      |   a = 3          |
|   b = ?          |     |   b = ?            |      |   b = 9          |
+------------------+     +--------------------+      +------------------+

When square returns, its frame is simply "popped". Nothing is erased; the stack pointer (a CPU register that marks the top) just moves back. That is why stack allocation is almost free: making room is one subtraction, and freeing is one addition.

Two limits follow:

  • Data on the stack dies when the function returns. If square returned the address of r, the caller would hold a pointer into a dead frame. The next call would overwrite it. This is a classic C bug.
  • The stack is small. A recursion that is 1,000,000 calls deep, or a 50 MB local array, runs past the end. You get a stack overflow (on Linux, a segmentation fault; in Python, a RecursionError first, because Python limits depth to 1,000 by default).

Intuition. The stack is a pile of plates. You can only add or remove the top plate, which makes it very fast and very tidy. The heap is a big warehouse. You can store anything of any size for as long as you like, but someone must keep track of what is where and clear out what is no longer needed.

5. The Heap: How malloc and free Work

When data must outlive a function, or its size is only known at run time (a file you just read, a list that grows), it goes on the heap:

char *buf = malloc(100);   /* ask for 100 bytes          */
/* ... use buf ... */
free(buf);                 /* give them back             */

5.1 Where the allocator gets memory

The allocator gets big pieces from the kernel and cuts them into small pieces for you. It uses two system calls:

  • brk moves the top of the heap region up, to grow it. glibc uses this for small requests.
  • mmap asks for a brand new region anywhere in the address space. glibc uses this for big requests: by default anything of 128 KB or more (this threshold can grow on its own, up to 32 MB on 64-bit systems).

System calls are slow compared with normal code, so the allocator asks the kernel rarely and reuses freed pieces as much as it can.

5.2 Chunks and headers

Each piece the allocator hands out is a chunk. Just before your bytes, it keeps a small header that records the chunk size. That is how free(buf) knows how much to give back, even though you only passed a pointer.

      header        your 100 bytes                 padding
   +----------+-------------------------------------+------+
   | size=112 |  buf points here                    |      |
   +----------+-------------------------------------+------+
     8 bytes              100 bytes                  4 bytes

On 64-bit glibc, a chunk is the request plus an 8-byte header, rounded up to a multiple of 16. So malloc(100) uses 100 + 8 = 108, rounded up to 112 bytes. Keep that number; the lab uses it.

5.3 Free lists, worked by hand

Freed chunks are kept on free lists, so the next malloc can reuse them. Here is a tiny 64-byte heap, to see the idea (real allocators are fancier, but the logic is the same). We use first fit: take the first free piece that is big enough.

start:            [ free 64                                        ]
A = malloc(16):   [ A 16 ][ free 48                                ]
B = malloc(24):   [ A 16 ][ B 24          ][ free 24               ]
C = malloc(16):   [ A 16 ][ B 24          ][ C 16 ][ free 8 ]
free(B):          [ A 16 ][ free 24       ][ C 16 ][ free 8 ]
D = malloc(20):   [ A 16 ][ D 20      ][f4][ C 16 ][ free 8 ]
E = malloc(12):   fails! 4 + 8 = 12 bytes are free, but not in one piece

The last line is the key. There are 12 free bytes in total, but they are split in two holes, so a 12-byte request cannot be served. This is external fragmentation (next section).

When two free neighbors sit side by side, a good allocator coalesces them (joins them into one bigger free piece). That is why freeing in big solid runs works much better than freeing scattered pieces.

5.4 Size classes and per-thread caches

Real allocators keep separate free lists for common sizes (16, 32, 48 ... bytes). These are size classes or bins. A request for 100 bytes goes straight to the 112-byte list: no searching. glibc also keeps a small cache per thread (the tcache), so most malloc/free pairs never touch a lock. Other allocators, like jemalloc and tcmalloc (used by many databases, browsers and Go-style runtimes), push this idea further to cut fragmentation and lock contention.

6. Fragmentation

There are two kinds of waste:

KindWhat it meansExample
InternalWaste inside a chunk: you got more than you asked formalloc(100) uses 112 bytes; 12 bytes (about 11%) are header and padding
ExternalWaste between chunks: free space exists but is split into holes too small to useThe failed 12-byte request in section 5.3

There is a third effect that surprises people in production. The kernel gives memory to a process in pages of 4 KB. The allocator can only give a page back to the kernel if the whole page is free. One live 112-byte chunk in a 4 KB page keeps the whole page in RAM. So "I freed half my objects" can mean "I gave back zero pages". The lab shows this.

7. Lab: Speed and Fragmentation in C

We ran a small C program on Linux (glibc, compiled with gcc -O0 so the compiler cannot remove the work). It reads its own RSS from /proc/self/status after each step.

7.1 Stack vs heap speed

Ten million calls of each:

OperationTime per call (two runs)
Function with a 64-byte local array (stack)1.86 to 2.06 ns
malloc(64), touch it, free6.88 to 7.62 ns

The heap is about 3 to 4 times slower here, and this is the best case: one thread, the same size again and again, always served from the tcache. With many threads, mixed sizes and cache misses, heap allocation costs much more. That is why hot loops avoid allocating, and why reusing buffers is a common speed-up.

7.2 Freeing half the data gave back nothing

int M = 1000000;
for (i = 0; i < M; i++) a[i] = malloc(100);   /* 1,000,000 chunks of 112 bytes */
for (i = 0; i < M; i += 2) free(a[i]);         /* free every OTHER chunk        */
malloc_trim(0);                                 /* ask glibc to return free pages */
StepRSS
Start1,716 KB
After 1,000,000 × malloc(100)118,904 KB
After freeing every other chunk (half the data)118,904 KB
After malloc_trim(0)118,904 KB
After freeing the rest, then malloc_trim(0)9,528 KB
Allocate 1,000,000 again, free the first half (one solid run), trim64,220 KB
One malloc of 200 MB, touched269,024 KB
After freeing that one block64,220 KB

Check the first number: 1,000,000 × 112 bytes = 112,000,000 bytes, about 109,000 KB. Add 7,800 KB for the array of pointers (a itself, 8 bytes × 1,000,000) and a little for the program: about 118,900 KB. It matches.

Now the lesson:

  • Freeing every other chunk freed half the data but 0 KB of RSS. Each 4 KB page holds about 36 chunks, and every page still had live chunks in it. Even malloc_trim could not return a single page.
  • Freeing the first half as one solid run returned about half the memory (118,904 to 64,220 KB), because whole pages became empty and could be given back.
  • The 200 MB block came from mmap (it is above the 128 KB threshold), so free handed it straight back to the kernel.

The headline. "Memory did not go down after the spike" is not proof of a leak. If the live objects are scattered across many pages, the allocator cannot return those pages. The memory is free inside the process and will be reused for new allocations, but RSS stays high. A real leak keeps growing under the same load; fragmentation goes up and then stays flat.

8. Bugs of Manual Memory

In C and C++ you free memory yourself. Four bugs come from that:

BugWhat happensTiny example
LeakYou lose the last pointer without freeing. Memory grows forever.p = malloc(10); p = malloc(20); (the first 10 bytes are lost)
Use after freeYou keep using memory after freeing it. Someone else may now own it. Data gets corrupted, or an attacker takes control.free(p); p[0] = 1;
Double freeYou free the same chunk twice. The free list gets corrupted.free(p); free(p);
Buffer overflowYou write past the end of a chunk and smash the next chunk's header or data.p = malloc(8); strcpy(p, "much longer than 8");

Tools catch these: compile with -fsanitize=address (AddressSanitizer) and run your tests, or run the program under valgrind. Both report the exact line. A large share of serious security bugs in big C and C++ projects are memory-safety bugs like these, which is why newer systems code is often written in memory-safe languages.

9. Reference Counting

The simplest automatic scheme: every object keeps a count of how many references point to it. Add a reference: count up. Remove one: count down. When the count hits 0, nobody can reach the object, so free it right away. CPython (the normal Python), Swift and C++ shared_ptr work this way.

a = Node()      # Node count = 1  (a)
b = a           # Node count = 2  (a, b)
del b           # Node count = 1
del a           # Node count = 0  -> freed immediately

Good: memory is freed at once, in small steps, so there are no long pauses. Bad: every assignment does extra work, and it has one big hole: cycles.

x = Node(); y = Node()
x.other = y          # y count = 2 (y, x.other)
y.other = x          # x count = 2 (x, y.other)
del x, y             # both counts drop to 1, never 0

   +------+  other   +------+
   |  X   | -------> |  Y   |      nothing outside points to X or Y,
   |  1   | <------- |  1   |      but each keeps the other at count 1
   +------+  other   +------+

The two nodes are garbage (no variable can reach them), but their counts never reach 0. Pure reference counting leaks them forever. Python adds a second tool, a cycle-finding GC, to clean these up. The lab in section 12 shows it.

10. Tracing GC: Mark and Sweep by Hand

Most runtimes (Java, Go, JavaScript, C#) do not count references. They trace: start from things that are surely alive, follow every pointer, and treat everything not reached as garbage.

The starting points are the roots: global variables, local variables on every thread's stack, and CPU registers.

Worked example

roots: [ r1 ]  [ r2 ]
          |       |
          v       v
          A ----> B ----> C          E ----> F
                  |                  ^       |
                  v                  |       |
                  D                  +-------+   (E and F point to each other)

Mark phase. Start at the roots and color everything you can reach.

  1. From r1, reach A. Mark A.
  2. From A, reach B. Mark B. (r2 also points to B; it is already marked, so skip.)
  3. From B, reach C and D. Mark both.
  4. No more pointers to follow. Marked: A, B, C, D.

Sweep phase. Walk the whole heap. Anything not marked is garbage: E and F. Free them, and clear the marks for next time.

Notice that E and F form a cycle, and tracing handles it with no special effort. Being in a cycle does not matter; only being reachable from a root matters.

Variations

  • Mark-compact. After marking, slide the live objects together so free space is one solid block. This removes fragmentation, but pointers must be updated, so the program must pause (or the GC must be clever).
  • Copying. Split memory into two halves. Copy live objects from the full half to the empty half, then treat the old half as empty. Cost depends on live data, not on garbage, which is great when most objects die young.
  • Concurrent. Do most of the marking while your program keeps running, using a "write barrier" (a few extra instructions on each pointer write) so the GC is told about changes. Go and modern Java collectors work this way to keep pauses short.

11. Generational GC

People measured real programs and found the weak generational hypothesis: most objects die young. A request handler makes hundreds of small objects (strings, dicts, temporary lists), and nearly all are garbage when the request ends. A few objects (caches, config, connection pools) live for hours.

So the heap is split into generations:

  new objects
       |
       v
 +-------------+   survives a few   +-------------+   survives more   +-------------+
 |   young     | -----------------> |   middle    | ----------------> |    old      |
 | (collected  |                    | (collected  |                   | (collected  |
 |  very often,|                    |  less often)|                   |  rarely,    |
 |  cheap)     |                    |             |                   |  expensive) |
 +-------------+                    +-------------+                   +-------------+

Collecting only the young generation is quick, because there is little live data in it. Objects that survive are promoted to an older generation, which is collected rarely. The trap: an object in the old generation that points to a young one must still keep the young one alive. Runtimes track this with a write barrier and a "remembered set" (a list of old objects that point into the young area).

Python's cycle GC has three generations. In Python 3.13 (used in the lab), gc.get_threshold() returns (2000, 10, 10): a young collection runs after about 2,000 new tracked objects, a middle one after 10 young ones, and an old one after 10 middle ones.

12. Lab: Python's Collector at Work

Run with Python 3.13.5 on Linux:

import gc, sys, weakref

class Node:
    def __init__(self):
        self.other = None
        self.data = bytearray(1000)

a = Node()
print(sys.getrefcount(a))   # 2  (a, plus the temporary argument)
b = a
print(sys.getrefcount(a))   # 3
del b
print(sys.getrefcount(a))   # 2

r = weakref.ref(a)          # a weak reference does not keep it alive
del a
print(r() is not None)      # False: freed the moment the count hit 0

gc.disable()
x, y = Node(), Node()
x.other, y.other = y, x
rx = weakref.ref(x)
del x, y
print(rx() is not None)     # True: the cycle is still in memory
print(gc.collect())         # 9 unreachable objects found
print(rx() is not None)     # False: the cycle GC freed it

Then we built many cycles and timed a full collection (gc.collect()):

Cycles (2 objects each)Full collect, all still aliveFull collect after dropping themObjects freed
100,00013 ms19 ms199,998
1,000,000169 ms200 ms1,999,998

Three lessons:

  • Cost grows with the number of objects. Ten times the objects took about ten times as long. A full collection over millions of objects is a pause your users feel.
  • Live objects cost time too. Even when nothing was garbage, the GC spent 169 ms walking 2,000,000 live objects. Big long-lived caches of small Python objects make every full collection slower.
  • Why 1,999,998 and not 2,000,000? The loop variables p and q still pointed at the last pair, so those two were still reachable. The GC is exact about reachability.

A common trick in big Python services: after loading a large, permanent data set at startup, call gc.freeze(). This moves everything into a permanent generation that later collections skip.

13. Java, Go, Node and Rust

RuntimeHow memory is freedMain knob
CPythonReference counting, plus a generational cycle collectorgc.set_threshold, gc.freeze()

Go's GOGC rule, worked: after a GC, 200 MB is live. With GOGC=100, the next cycle starts at 200 + 100% × 200 = 400 MB. With GOGC=50, at 300 MB (more GC work, less memory). With GOGC=200, at 600 MB (less GC work, more memory). It is always a trade of CPU for RAM.

14. GC in Production and in Containers

14.1 Pauses show up in p99, not in the average

Say a service handles 1,000 requests per second, each in 5 ms. Every 10 seconds the GC pauses for 150 ms. In those 150 ms, about 150 requests arrive and wait. That is 150 out of 10,000, or 1.5% of requests, each delayed by up to 150 ms. The average barely moves. The p99 (the time that 99% of requests beat) jumps from about 5 ms to well over 100 ms. When p99 has a spike pattern every few seconds, check GC logs first.

14.2 Tell the runtime about the container limit

A container limit is enforced by the kernel through a cgroup. If the runtime's own heap limit is bigger than the container limit, the runtime happily grows past the limit and the kernel kills it (OOMKilled). Leave room for things outside the heap too: thread stacks, native libraries, buffers, and the allocator's own fragmentation.

RuntimeSetting for a 1 GiB container
Java-XX:MaxRAMPercentage=75 (heap up to about 768 MiB). Modern JVMs read the cgroup limit; the default is only 25%.
GoGOMEMLIMIT=800MiB. The GC works harder as it nears this number instead of growing past it.
Node.js--max-old-space-size=768
PythonNo heap cap. Watch RSS, avoid giant caches of small objects, and consider gc.freeze() after startup.

14.3 Leak or fragmentation? A quick test

  1. Put the service under steady, constant load for an hour.
  2. If RSS keeps climbing in a straight line, it is a leak. Find it with a heap profiler (tracemalloc in Python, a heap dump in Java, pprof in Go). The OOMKilled scenario walks through one.
  3. If RSS jumps during a spike and then stays flat, it is likely fragmentation or the runtime keeping freed memory for reuse. Fixes: reuse buffers, avoid many tiny long-lived objects, try jemalloc (for C/C++/Python with LD_PRELOAD), or set MALLOC_ARENA_MAX=2 for glibc programs with many threads.

15. Common Pitfalls

  • Returning a pointer to a local variable in C. The frame is gone when the function returns.
  • Calling "it did not go down" a leak. Check whether it keeps going up under steady load.
  • Unbounded caches. A dict used as a cache with no size limit is a leak with a nice name. Use an LRU cache with a maxsize.
  • Calling gc.collect() in a request path. A full collection over millions of objects took 200 ms in our lab.
  • Heap limit equal to the container limit. The heap is not the only memory. Leave 20 to 25% for everything else.
  • Allocating in a hot loop. Making a new buffer per item is slower than reusing one, and it feeds the GC.
  • Forgetting that closures and listeners hold references. An event listener that is never removed keeps its whole object graph alive, even in GC languages.

16. Practice Problems

Problem 1: chunk sizes

On 64-bit glibc, what chunk size does malloc(24) use? And malloc(40)? (Hint: add 8, round up to a multiple of 16, and the smallest chunk is 32.)

Solution

malloc(24): 24 + 8 = 32, already a multiple of 16, so 32 bytes. (glibc can also borrow 8 bytes from the next chunk's header area, which is why 24 fits exactly.) malloc(40): 40 + 8 = 48, so 48 bytes.

Problem 2: first fit

A 100-byte heap. Run: A = malloc(30), B = malloc(30), C = malloc(30), free(A), free(C), D = malloc(40). Ignore headers. Does D succeed?

Solution

After the frees the layout is [free 30][B 30][free 30][free 10]. The last two holes are neighbors, so a coalescing allocator joins them: [free 30][B 30][free 40]. D = 40 fits in that last hole. Yes, but only because of coalescing. Without it, the biggest hole is 30 and D fails, even though 70 bytes are free.

Problem 3: mark and sweep

Roots point to P. P points to Q. Q points to P. R points to S. S points to Q. Which objects are freed?

Solution

Marked from the root: P, then Q (and Q back to P, already marked). Not reached: R and S. They are freed. S points to Q, but that does not matter: pointers into live objects do not keep the pointer's owner alive.

Problem 4: reference counting

Which of these does pure reference counting free? (a) A list that nothing points to. (b) A list that contains itself (L.append(L)) after del L. (c) Two objects that point to each other while a global variable points to one of them.

Solution

(a) Yes, count 0. (b) No: the list points to itself, so its count stays 1. It is a cycle of one; the cycle GC must clean it. (c) Neither is garbage: the global keeps one alive, and that one keeps the other alive. Nothing should be freed.

Problem 5: Go GOGC

After a GC, 300 MB is live. GOGC=100 and GOMEMLIMIT=500MiB. When does the next cycle start, roughly?

Solution

GOGC alone says 300 + 300 = 600 MB. But the memory limit is about 500 MiB, so the GC starts earlier to stay under it, at roughly 500 MiB (a little less, since other runtime memory counts too). The limit wins when it is lower.

Problem 6: leak or not

A Python service: RSS goes from 300 MB to 900 MB during a nightly import, then stays at 900 MB all day with normal traffic. Leak?

Solution

Probably not. A leak would keep growing during the day. Flat after a spike points to memory that was freed inside the process but not returned (fragmentation, like the lab), or to objects the import left in a global. Check with tracemalloc snapshots before and after the import. If the import keeps a reference to its data, drop it. If not, run the import in a separate worker process that exits when done, so all its memory goes back to the kernel.

Virtual Memory & Paging

How every process gets its own private, huge, tidy memory while sharing one small, messy pool of RAM. With hex translations, page-table math, and page replacement traced by hand.

1. Why Virtual Memory Exists

Imagine the early days: every program used real RAM addresses directly. Three problems appear immediately:

  1. No protection. A bug in one program can overwrite another program's data, or the OS itself.
  2. No relocation. A program compiled to live at address 0x10000 cannot run if another program already sits there.
  3. Fragmentation. Free RAM ends up in small scattered holes. A program needing 100 MB in one piece may fail even if 500 MB is free in total.

Virtual memory solves all three with one idea: programs never see real addresses. Each process uses virtual addresses. The hardware (the MMU, Memory Management Unit, inside the CPU) translates each virtual address to a physical address in RAM on every memory access, using tables the OS maintains.

Intuition: Virtual addresses are like apartment numbers in a building directory. "Apartment 4B" is what you tell your friends. The directory (page table) says 4B is actually the third door on the second floor of the east wing. The landlord (OS) can move you to another physical room and just update the directory. Your friends never notice.

Bonus wins: processes can share read-only pages (one copy of libc in RAM for hundreds of processes), memory can be loaded lazily from disk, and a process can use more virtual memory than physical RAM exists.

2. Pages, Frames, and Offsets

Translating every single byte separately would need a gigantic table. So memory is split into fixed-size chunks:

  • A page is a fixed-size block of virtual memory. The common size is 4 KiB (4096 bytes).
  • A frame (page frame) is a block of physical RAM of the same size.
  • The page table maps page numbers to frame numbers. One entry per page is a PTE (page table entry).

Because pages and frames are the same size, the position inside the page never changes during translation. So a virtual address splits in two parts:

  virtual address  =  [ virtual page number (VPN) | offset ]
  physical address =  [ physical frame number (PFN) | offset ]   (same offset)

  offset bits = log2(page size)      4 KiB = 2^12  ->  12 offset bits

A PTE stores more than the frame number. It has flag bits: present (is the page in RAM?), writable, user/kernel, accessed (used recently), dirty (modified since loaded), and on x86-64 an NX (no-execute) bit.

3. Translating an Address by Hand

Setup: 32-bit virtual addresses, 4 KiB pages. So 12 bits of offset and 32 - 12 = 20 bits of VPN.

Problem: translate virtual address 0x00403A7C. The page table says VPN 0x00403 maps to frame 0x001F2, present.

Step by step

  1. Split the address. 12 offset bits = 3 hex digits (each hex digit is 4 bits). So the last 3 hex digits are the offset: 0xA7C. The rest is the VPN: 0x00403.
  2. Look up the VPN. PTE for 0x00403 gives PFN 0x001F2. Present bit is 1, so no fault.
  3. Glue frame and offset. Physical address = PFN followed by the offset = 0x001F2 and A7C = 0x001F2A7C.

In formula form: PA = PFN * page_size + offset = 0x1F2 * 0x1000 + 0xA7C = 0x1F2A7C.

Shortcut: with 4 KiB pages the offset is exactly 3 hex digits, and with 64 KiB pages it is exactly 4, so you can split the address by counting hex digits from the right. For sizes like 8 KiB (13 offset bits), write the address in binary first.

Try another (solution right below)

Same system. Translate 0x0040_3FFF and 0x0040_4000, if VPN 0x404 maps to frame 0x7AB.

  • 0x00403FFF: VPN 0x403, offset 0xFFF, the last byte of the page. PA = 0x1F2FFF.
  • 0x00404000: one byte later, but it is a new page. VPN 0x404, offset 0x000. PA = 0x7AB000. Neighbouring virtual bytes can live in completely different physical places.

4. Page Table Size and Multi-Level Tables

The problem with one flat table

32-bit addresses, 4 KiB pages, 4-byte PTEs:

number of pages  = 2^32 / 2^12 = 2^20 = 1,048,576
table size       = 2^20 * 4 bytes = 4 MiB   per process

4 MiB for every process, even a tiny one, is wasteful. For 64-bit it is impossible: x86-64 uses 48-bit virtual addresses, so 2^48 / 2^12 = 2^36 pages times 8-byte PTEs = 512 GiB of page table per process.

The fix: a tree of tables

Most of the address space is unused. A multi-level page table only allocates the parts that are used. x86-64 with 4 levels splits a 48-bit address like this:

 47        39 38        30 29        21 20        12 11          0
+------------+------------+------------+------------+-------------+
|  PML4 (9)  |  PDPT (9)  |   PD (9)   |   PT (9)   | offset (12) |
+------------+------------+------------+------------+-------------+
   level 4      level 3      level 2      level 1

Each level: 9 bits -> 512 entries x 8 bytes = 4096 bytes = exactly one page.

The CPU starts at the top table (its address lives in the CR3 register), uses 9 bits to pick an entry, which points to the next table, and so on 4 times, then adds the offset. If a whole region is unused, the upper-level entry is simply empty and no lower tables exist. Newer CPUs support 5 levels (57-bit addresses) for machines with huge memory.

The cost: one memory access by the program can need 4 extra memory reads just to walk the tables. That would make everything 5 times slower. Which brings us to the TLB.

5. The TLB: Making Translation Fast

The Translation Lookaside Buffer (TLB) is a small, very fast cache inside the CPU that remembers recent VPN to PFN translations. Typical sizes are tens of entries (level 1) to a couple of thousand (level 2).

  • TLB hit: translation is found instantly. No page walk.
  • TLB miss: the hardware walks the page table (on x86), then stores the result in the TLB.

Programs touch memory with strong locality: the same and nearby addresses again and again. So hit rates above 99% are normal.

Worked example: effective access time

Memory access takes 100 ns. TLB lookup time is negligible. The TLB hit ratio is 98%. A miss needs a 4-level walk (4 memory reads) plus the real access.

hit cost  = 100 ns                       (just the data access)
miss cost = 4 * 100 + 100 = 500 ns      (walk + data access)

EAT = 0.98 * 100 + 0.02 * 500
    = 98 + 10
    = 108 ns     -> only 8% slower than no translation at all

Drop the hit ratio to 90% and EAT = 90 + 50 = 140 ns, 40% slower. TLB hit rate really matters. (Real CPUs also cache page-table entries in the normal data caches, which shortens walks.)

Context switches and the TLB: translations belong to one address space. Old CPUs flushed the whole TLB on every process switch. Modern CPUs tag entries with an address-space ID (PCID on x86, ASID on ARM) so entries can survive switches.

6. Page Faults and Demand Paging

A page fault is a trap into the kernel when the MMU cannot complete a translation: the PTE is not present, or the access breaks the permissions. A fault is not always an error. It is how lazy loading works.

Demand paging, step by step

  1. You start a program. The kernel sets up page tables but loads almost nothing. All PTEs are "not present".
  2. The CPU tries the first instruction. Not present: page fault.
  3. The kernel checks: is this address part of a valid region (code of the binary, heap, stack)? If not, the process gets SIGSEGV (segmentation fault).
  4. If valid: find a free frame (evicting another page if RAM is full), read the page from disk if needed, fill in the PTE, mark it present.
  5. Return to the process and re-run the same instruction. It now succeeds.
Fault typeMeaningCost
Minor (soft)Page is already in RAM (for example in the page cache, or a fresh zero page) and just needs mappingAround a microsecond
Major (hard)Page must be read from disk or swapAround 100 microseconds on NVMe, around 10 ms on a spinning disk
InvalidAddress not in any valid region, or a write to read-only memoryProcess gets SIGSEGV

Copy-on-write (used by fork(), see Processes) is also built on faults: shared pages are read-only, and the first write faults, so the kernel copies just that page.

Worked example: how much does a fault rate hurt?

Memory access is 100 ns. A major fault costs 8 ms = 8,000,000 ns. Let p be the fault probability per access.

EAT = (1 - p) * 100 + p * 8,000,000

p = 1 in 1000:     EAT = 99.9 + 8000     = ~8100 ns  (81x slower!)
For <10% slowdown: 110 > 100 + 7,999,900p  ->  p < 0.0000013  (about 1 in 800,000)

Lesson: the fault rate for hot data must be tiny. This is why running out of RAM feels like the machine freezing.

$ /usr/bin/time -v ./myprogram 2>&1 | grep -i fault
  Major (requiring I/O) page faults: 0
  Minor (reclaiming a frame) page faults: 1532

7. Page Replacement: FIFO, LRU, OPT

When RAM is full and a fault needs a frame, the OS must evict some page. If that page is dirty, it must be written to disk first. Which page to evict? We compare three policies on a classic reference string (the sequence of pages a program touches) with 3 frames:

7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1     (20 references)

FIFO: evict the oldest loaded page

Simple, but "loaded long ago" does not mean "not needed". Result: 15 faults.

LRU: evict the least recently used page

Uses the recent past to predict the near future. Full trace below. The frames column lists pages from least recently used (left, next victim) to most recently used (right).

OPT (Belady's optimal): evict the page used furthest in the future

Look ahead and evict the page whose next use is the latest (or never). This gives the fewest faults possible: 9 faults here. It is impossible in a real OS (it needs to know the future), but it is the yardstick for judging other policies.

Example decision at reference #4 (page 2 arrives, frames hold 7, 0, 1): the future is 0 3 0 4 2 3 0 3 2 1 2 0 1 7 .... Page 0 is needed next at once, page 1 at position 14, page 7 not until position 18. So OPT evicts 7.

(All three counts were verified with a simulator.)

Belady's anomaly: more RAM, more faults?

With FIFO, adding frames can increase faults. Reference string 1 2 3 4 1 2 5 1 2 3 4 5 gives 9 faults with 3 frames but 10 faults with 4 frames. LRU and OPT never do this (they are "stack algorithms": the pages kept with n frames are always a subset of those kept with n + 1).

What real kernels do: approximate LRU

Tracking exact recency for every memory access is too expensive. Instead, the hardware sets the accessed bit in the PTE when a page is used. The clock (second-chance) algorithm sweeps pages in a circle: if the accessed bit is 1, clear it and move on (second chance); if it is 0, evict. Linux keeps active and inactive lists, and since kernel 6.1 offers MGLRU (multi-generational LRU), which sorts pages into age generations and is used by default on Android, ChromeOS, and several Linux distributions.

8. Thrashing and the Working Set

The working set of a process is the set of pages it actively uses in a recent time window. If the sum of all working sets is bigger than RAM, every process keeps evicting pages that another process (or itself) needs a moment later. The system spends nearly all its time on page faults and disk I/O. CPU utilization drops, which can trick a naive OS into starting even more work. This collapse is thrashing.

Signs on Linux: high si/so (swap in/out) in vmstat 1, many major faults, high I/O wait, and Pressure Stall Information showing memory pressure:

$ cat /proc/pressure/memory
some avg10=42.17 avg60=30.02 avg300=12.50 total=81726354
full avg10=18.40 avg60=11.73 avg300=4.02 total=31277120

"some" = percent of time at least one task stalled on memory; "full" = all non-idle tasks stalled. Fixes: add RAM, run fewer things at once, reduce memory use, or kill something (which is what the OOM killer and tools like systemd-oomd do).

9. Linux in Practice: Huge Pages, Overcommit, OOM

Huge pages and TLB reach

TLB reach = number of TLB entries times page size. With 1536 entries:

4 KiB pages:  1536 * 4 KiB = 6 MiB of memory covered
2 MiB pages:  1536 * 2 MiB = 3 GiB of memory covered

A database with a 64 GiB buffer pool will miss the TLB constantly with 4 KiB pages. x86-64 supports 2 MiB and 1 GiB huge pages. Linux offers explicit hugetlbfs pages (reserved in advance; used by databases and DPDK) and Transparent Huge Pages (THP), which merges pages automatically. THP helps many workloads but can cause latency spikes from background compaction, which is why some databases recommend madvise mode instead of always.

Overcommit

malloc(1 GB) usually succeeds instantly even on a small machine. Linux hands out virtual memory optimistically and only assigns frames when pages are touched. This is overcommit. It works because programs often reserve more than they use. The risk: if everyone touches their memory, RAM runs out.

The OOM killer

When memory cannot be reclaimed, the kernel's OOM (out-of-memory) killer picks a process (largest memory, adjusted by /proc/<pid>/oom_score_adj) and kills it with SIGKILL. In containers, each cgroup has its own limit (memory.max). Exceeding it triggers an OOM kill inside that cgroup only.

Kubernetes connection: a container killed this way shows Reason: OOMKilled and exit code 137 (128 + signal 9). Note that the page cache counts toward the cgroup too, but the kernel reclaims clean cache before killing. See Kubernetes Workloads for memory requests and limits.

RSS vs VSZ

ps shows VSZ (virtual size: everything mapped, including never-touched reservations) and RSS (resident set size: pages actually in RAM now, counting shared libraries fully in every process). Neither is perfect. PSS in /proc/<pid>/smaps_rollup splits shared pages fairly among sharers.

10. Modern Twist: Paging for the LLM KV Cache

The same idea that freed operating systems from fragmentation in the 1960s now powers LLM serving. An LLM keeps a KV cache per request that grows one token at a time, and nobody knows in advance how long an answer will be. Early servers reserved one big contiguous block per request for the maximum length. Most of it sat unused, just like external and internal fragmentation in RAM.

PagedAttention (the vLLM paper, 2023) applies paging directly:

OS conceptvLLM equivalent
Page (4 KiB)KV block (for example 16 tokens)

Page table per processBlock table per request
Demand pagingAllocate a new block only when the previous one is full
Copy-on-write shared pagesShared prefix blocks for parallel sampling and prefix caching
Swapping to diskPreempting a request and swapping or recomputing its KV blocks

11. Common Pitfalls

  • Confusing page and frame. Page = virtual, frame = physical. Offsets are identical in both.
  • Counting offset bits wrong. Offset bits come from the page size only: 4 KiB means 12 bits, no matter how big memory is.
  • Forgetting the data access in EAT. A TLB miss costs the page walk plus the actual access.
  • Thinking a page fault means a bug. Most faults are normal (lazy loading, COW). Only invalid accesses crash.
  • Trusting free memory numbers. Linux uses idle RAM for the page cache. Look at available in free -h, not free.
  • Assuming more frames always helps FIFO. Belady's anomaly says no.

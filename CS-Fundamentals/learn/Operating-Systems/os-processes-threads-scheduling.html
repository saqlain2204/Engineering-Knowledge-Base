1. The Big Picture

Your laptop may have 8 CPU cores. Yet it runs a browser, a music player, a chat app, and hundreds of background services at once. How?

The answer is time sharing. The operating system (OS) gives each program a tiny slice of CPU time, a few milliseconds. Then it pauses that program and gives the CPU to another one. It switches so fast that, to a human, everything looks simultaneous.

To do this, the OS needs answers to three questions:

  1. What exactly is a "running program"? That is a process (and inside it, threads).
  2. How do we pause one program and resume another without losing anything? That is a context switch.
  3. Who runs next, and for how long? That is CPU scheduling.
Intuition: Think of one chef (the CPU) and many recipes being cooked (processes). The chef works on one dish for a minute, writes a sticky note saying exactly where they stopped ("added salt, stirring step 4"), then moves to another dish. The sticky note is the saved context. The rule for choosing the next dish is the scheduler.

2. What Is a Process?

A program is a file on disk, for example /usr/bin/python3. It is passive. It does nothing by itself.

A process is a program in execution. It is the program plus everything needed to run it right now. If you open three terminal windows and run python3 in each, you have one program and three processes.

What a process owns

  • A process ID (PID): a number that names it, for example 4182.
  • Its own virtual address space: its private view of memory. Process A cannot read process B's memory by accident.
  • CPU state: the values in the CPU registers, including the program counter (the address of the next instruction to run) and the stack pointer.
  • Open resources: open files, network sockets, pipes. Each is referenced by a small number called a file descriptor (0 = stdin, 1 = stdout, 2 = stderr).
  • Credentials and limits: which user it runs as, how much memory it may use, and so on.

The kernel stores all of this in a data structure called the Process Control Block (PCB). In Linux the PCB is struct task_struct.

The memory layout of a process

High addresses
 +--------------------------+

Every address in this picture is virtual. The OS and hardware translate it to real RAM. See Virtual Memory & Paging for how.

You can look at a live process on Linux:

$ cat /proc/self/status | head -n 9   # info about the 'cat' process itself
$ ls -l /proc/$$/fd                   # open file descriptors of your shell
$ cat /proc/$$/maps                   # its memory regions (text, heap, stack, libraries)

3. Process States

A process is not always running. At any moment it is in one of a few states:

              admitted                    exit()
   [ NEW ] -----------> [ READY ] <----+     [ TERMINATED ]
                          |    ^        |           ^
          scheduler picks |    | time   |           |
                    it    v    | slice  |           |
                        [ RUNNING ] ----+-----------+
                          |       used up / preempted
       waits for I/O,     |
       a lock, or sleep   v
                       [ WAITING ]  (also called BLOCKED)
                          |
                          +---- I/O done -----> back to READY
StateMeaning in plain words
NewBeing created. The kernel is setting up its PCB and memory.
ReadyCould run right now, but is waiting for a free CPU. It sits in the run queue.
RunningInstructions are executing on a CPU core. At most one process per core is in this state.
Waiting / BlockedCannot run even if a CPU is free. It waits for something: a disk read, a network packet, a timer, a lock.
TerminatedFinished. Some bookkeeping remains until the parent collects the exit code.

The key insight: a blocked process uses no CPU. While your web server waits for the database, the CPU runs something else. This is why one core can serve many I/O-heavy programs.

On Linux, ps and top show these as letters: R (running or runnable, so Linux merges Ready and Running), S (sleeping, interruptible), D (uninterruptible sleep, usually disk I/O), Z (zombie), T (stopped).

4. Context Switches

A context switch is the act of saving the state of the running process and loading the state of the next one.

Step by step

  1. Something gives control to the kernel. Either a timer interrupt fires (the time slice is over), or the process makes a system call that blocks (for example read() on a socket with no data).
  2. The kernel saves the CPU registers of process A (program counter, stack pointer, general registers) into A's PCB.
  3. The scheduler picks process B.
  4. The kernel switches the memory mapping to B's address space (on x86 this means loading a new page table base into the CR3 register).
  5. The kernel restores B's registers from B's PCB. The CPU continues exactly where B stopped.

Why switches cost something

The direct cost is small, typically a few microseconds. The hidden cost is bigger: B's data is probably not in the CPU caches and TLB (the cache of address translations). So B runs slowly for a while until the caches "warm up" again. This is why a scheduler should not switch too often.

Two kinds of switch you can measure: voluntary (the process blocked on I/O or a lock) and involuntary (the scheduler preempted it). Run grep ctxt /proc/<pid>/status. Many involuntary switches mean CPU contention. Many voluntary switches mean the program waits a lot.

5. Creating Processes: fork, exec, wait

On Unix-like systems (Linux, macOS), new processes are created in two steps:

  • fork() makes a copy of the calling process. After it, there are two almost identical processes. The only visible difference is the return value: the child gets 0, and the parent gets the child's PID.
  • exec() (a family: execlp, execvp, ...) replaces the current program with a new program. The PID stays the same. The code, data, heap, and stack are replaced.
  • wait() / waitpid() lets the parent pause until a child finishes and read its exit code.

This is exactly what your shell does when you type ls: it forks, the child execs /bin/ls, and the shell waits.

A complete, tested example

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    printf("parent: my pid is %d\n", getpid());
    fflush(stdout);                 /* empty the buffer before fork */

    pid_t pid = fork();             /* one call, two returns */
    if (pid < 0) {
        perror("fork");
        return 1;
    }
    if (pid == 0) {
        /* Child: fork() returned 0 here */
        printf("child: pid=%d, parent=%d\n", getpid(), getppid());
        fflush(stdout);
        execlp("echo", "echo", "child: now running the echo program", (char *)NULL);
        perror("execlp");           /* only reached if exec failed */
        _exit(127);
    }
    /* Parent: fork() returned the child's pid */
    int status;
    waitpid(pid, &status, 0);       /* reap the child, no zombie */
    if (WIFEXITED(status))
        printf("parent: child %d exited with code %d\n", pid, WEXITSTATUS(status));
    return 0;
}
$ gcc -Wall -o fork fork.c && ./fork
parent: my pid is 989355
child: pid=989356, parent=989355
child: now running the echo program
parent: child 989356 exited with code 0

Copy-on-write: why fork is cheap

Copying gigabytes of memory on every fork() would be slow. Instead, the kernel lets parent and child share the same physical pages and marks them read-only. Only when one of them writes to a page does the kernel copy that single page. This trick is called copy-on-write (COW). Redis uses it to take snapshots: it forks, and the child writes the frozen memory to disk while the parent keeps serving.

Worked problem: how many processes?

int main(void) {
    fork();
    fork();
    fork();
    printf("hi\n");
}

Walk through it. Before the first fork there is 1 process. Each fork() is executed by every process that exists at that point, and each one doubles.

  • After fork #1: 2 processes.
  • After fork #2: each of the 2 forks, so 4.
  • After fork #3: 8.

So "hi" prints 8 times. In general, n sequential forks give 2n processes, which means 2n - 1 new ones were created. (We ran this on Linux and counted 8 lines.)

Zombies and orphans

  • Zombie: a child has exited but the parent has not called wait() yet. The process uses no memory or CPU, but its PID and exit code stay in the process table. Thousands of zombies can exhaust PIDs. Fix: the parent must reap children (or handle SIGCHLD).
  • Orphan: the parent exits first. The child is adopted by PID 1 (init/systemd), or by a "subreaper", which reaps it later.
Containers connection: Inside a container your app is often PID 1. PID 1 has special duties: it must reap orphaned zombies, and it does not get default signal handlers, so SIGTERM may be ignored. That is why tools like tini (or docker run --init) exist. See Advanced Docker.

6. Threads

A thread is one sequence of instructions running inside a process. A process starts with one thread. It can create more.

Shared by all threads of a processPrivate to each thread
MemoryCode, global data, heapIts own stack
CPURegisters, program counter
ResourcesOpen files, sockets, PIDThread ID, signal mask

Why use threads instead of processes?

  • Cheap sharing: threads see the same heap, so passing data is just passing a pointer. Processes need pipes, sockets, or shared memory.
  • Cheaper to create and switch: switching between threads of the same process does not change the address space, so the TLB stays useful.

The price: shared memory is dangerous

If two threads update the same variable without coordination, updates get lost. counter++ looks like one step but is three: load, add, store. Two threads can both load 5, both add 1, and both store 6. One increment vanished. This is a race condition. Fixes are locks (mutexes), atomic operations, or not sharing mutable data.

How Linux implements threads

Linux does not have a separate "thread" object. Both processes and threads are tasks created by the clone() system call. A thread is simply a task that shares its address space, files, and signal handlers with its creator. Each thread is scheduled independently, so a process with 4 threads can use 4 cores at once. Run ps -eLf to see one line per thread.

Intuition: A process is a house. Threads are people living in the house. They share the kitchen and the fridge (heap), each has their own notebook (stack), and if two people cook in the same pot at once without talking, dinner is ruined (race condition).

Concurrency vs parallelism

Concurrency means several tasks are in progress during the same period, possibly by taking turns on one core. Parallelism means tasks literally execute at the same instant on different cores. A single-core machine can be concurrent but never parallel.

7. Scheduling Vocabulary

Before solving scheduling problems, learn these terms. Every exam and every real tuning discussion uses them.

TermPlain meaningFormula

Turnaround time (TAT)Total time from arrival to finishTAT = CT - AT
Waiting time (WT)Time spent ready but not runningWT = TAT - BT

Two more words matter:

  • Non-preemptive: once a process gets the CPU it keeps it until it finishes or blocks.
  • Preemptive: the OS can take the CPU away in the middle (for example when the time slice ends or a more urgent process arrives).

A Gantt chart is just a timeline showing which process ran when. We will draw one for every algorithm.

8.2 Shortest Job First (SJF), non-preemptive

Rule: when the CPU becomes free, pick the ready process with the smallest burst. Break ties by arrival time.

SJF gives the minimum possible average waiting time among non-preemptive schedules for a known set of jobs. The catch: the OS does not know burst times in advance. Real systems estimate the next burst from past bursts, often with an exponential average: next_guess = a * last_actual + (1 - a) * previous_guess.

8.3 Shortest Remaining Time First (SRTF), preemptive SJF

Rule: at every moment, run the process with the least remaining time. When a new process arrives, compare it with the running one and preempt if the new one is shorter.

  1. t = 0: P1 starts (remaining 7).
  2. t = 2: P2 arrives with 4. P1 has 5 left. 4 < 5, so P2 preempts P1.
  3. t = 4: P3 arrives with 1. P2 has 2 left. 1 < 2, so P3 runs.
  4. t = 5: P3 finishes. P4 arrives with 4. Remaining: P1 = 5, P2 = 2, P4 = 4. Run P2.
  5. t = 7: P2 finishes. Remaining: P1 = 5, P4 = 4. Run P4 until 11.
  6. t = 11: only P1 is left. Run until 16.

8.4 Round Robin (RR), time quantum = 2

Rule: keep a FIFO ready queue. Each process runs for at most one quantum (here 2 ms), then goes to the back of the queue. This is the basis of interactive time sharing.

RR has the worst average turnaround here, but good response time and no starvation: every process gets the CPU within (n - 1) * quantum of joining the queue, where n is the number of processes in the queue. It also caused 8 context switches versus 5 for SRTF.

Choosing the quantum

  • Too large (bigger than every burst): RR becomes FCFS.
  • Too small (close to the context switch cost): the CPU spends most of its time switching instead of working. With a 1 ms quantum and 0.1 ms switch cost, about 1/11, roughly 9%, of CPU time is overhead.

8.6 Priority scheduling and multilevel queues

Priority scheduling runs the highest-priority ready process. SJF is a special case where priority = shorter burst. Low-priority work can starve; the classic fix is aging: slowly raise the priority of processes that have waited a long time.

Multilevel Feedback Queue (MLFQ) uses several queues with different priorities and quanta. New processes start at the top. A process that uses its whole quantum (CPU-hungry) is moved down. A process that blocks early (interactive, I/O-bound) stays high. So the scheduler learns which jobs are interactive without being told. Periodically, everything is boosted to the top to prevent starvation.

9. How Linux Actually Schedules (CFS, EEVDF, sched_ext)

Textbook algorithms are building blocks. Real kernels combine them.

Scheduling classes

Linux has several scheduling classes checked in priority order. Real-time classes (SCHED_FIFO, SCHED_RR, and the deadline class SCHED_DEADLINE) always beat normal tasks. Almost every ordinary program runs in the normal class, SCHED_OTHER (also called SCHED_NORMAL).

CFS: the idea of fair share

From Linux 2.6.23 (2007) the normal class used the Completely Fair Scheduler (CFS). Its core idea:

  • Each task has a virtual runtime (vruntime): how much CPU it has had, scaled by its weight.
  • The scheduler always picks the task with the smallest vruntime, the one that has been treated least fairly so far. Tasks are kept in a red-black tree sorted by vruntime, so finding the minimum is fast.
  • Nice values from -20 (high priority) to +19 (low) change the weight. Each nice step changes the CPU share by roughly 10%. A higher weight makes vruntime grow more slowly, so the task gets picked more often.

EEVDF: the current default

In Linux 6.6 (late 2023) CFS's picking logic was replaced by EEVDF (Earliest Eligible Virtual Deadline First). It keeps the fairness accounting but adds two ideas:

  • Eligibility: a task that has received more than its fair share ("negative lag") must wait until it is owed time again.
  • Virtual deadline: among eligible tasks, pick the one whose deadline (roughly: when it should finish its next slice) is earliest. Tasks that ask for shorter slices get earlier deadlines, which helps latency-sensitive work without special heuristics.

sched_ext: schedulers written in eBPF

Linux 6.12 (late 2024) merged sched_ext. It lets you load a whole scheduling policy as an eBPF program at runtime, and the kernel falls back to the default scheduler if the BPF scheduler misbehaves. Companies use it to experiment with policies tuned for games, cloud hosts, or specific services without rebuilding the kernel. This is a big trend: the scheduler is no longer one fixed algorithm.

Try it

$ chrt -p $$                  # scheduling policy of your shell
$ nice -n 10 ./batch-job      # start with lower priority
$ renice -n 5 -p 4182         # change priority of a running process
$ cat /proc/4182/sched        # vruntime, switch counts, etc.
$ taskset -c 0,1 ./app        # pin a process to cores 0 and 1

10. Scenario: Why Is My Container Slow at 30% CPU?

Situation. A Java API runs in Kubernetes with resources.limits.cpu: 500m (half a core). Dashboards show average CPU around 30% of the limit. Yet p99 latency is terrible: some requests take an extra 80 to 90 ms for no visible reason.

Step 1: understand how a CPU limit works

A CPU limit is enforced by the CFS bandwidth controller in cgroups. It is not "half a core at all times". It is a budget: quota per period. The default period is 100 ms. A limit of 500m becomes:

$ cat /sys/fs/cgroup/cpu.max        # cgroup v2, inside the container
50000 100000                         # 50 ms of CPU time per 100 ms period

Step 2: do the math for a burst

A request arrives and the app uses 4 threads in parallel (GC threads, a thread pool). Four threads burn CPU 4 times faster than wall-clock time.

  • The 50 ms budget is used up after 50 / 4 = 12.5 ms of wall time.
  • All threads are then throttled (not allowed to run) until the period ends: 100 - 12.5 = 87.5 ms of forced waiting.

Averaged over a minute, usage looks low (30%). But within individual 100 ms windows, the app hits the wall. That matches the extra ~85 ms latency.

Step 3: confirm with data

$ cat /sys/fs/cgroup/cpu.stat
usage_usec 81234567
nr_periods 51234
nr_throttled 9120            # periods in which we hit the limit
throttled_usec 612345678     # total time spent throttled

If nr_throttled / nr_periods is more than a few percent, throttling is hurting you. In Prometheus, the cAdvisor metric is container_cpu_cfs_throttled_periods_total.

Step 4: fix options

  • Raise the limit, or remove CPU limits and rely on requests for fair sharing (a common practice for latency-sensitive services; requests map to CPU weight, which only matters under contention).
  • Reduce parallelism to match the budget (for example size thread pools and GC threads for 1 core, not for the host's 64 cores).
  • Make sure the runtime sees the right CPU count. Modern JVMs, Go (from 1.25, GOMAXPROCS respects the cgroup CPU limit), and others read cgroup limits; older ones size thread pools for the whole machine.
Lesson: averages hide bursts. Scheduling problems are about what happens inside each small time window, which is exactly what the Gantt charts above trained you to think about.

11. Common Pitfalls

  • Forgetting to flush before fork. printf output sits in a user-space buffer. fork() copies the buffer, so text printed before the fork can appear twice. Try it: printf("hello "); fork(); then print a newline in both processes. You will see "hello" twice. Call fflush(stdout) before forking.
  • Not reaping children. Leads to zombies. Always wait/waitpid, or handle SIGCHLD.
  • Confusing load average with CPU usage. Linux load average counts runnable tasks and tasks in uninterruptible sleep (D state). Slow disks or NFS can push load to 50 while CPUs are idle.
  • More threads is not always faster. Beyond the number of cores, CPU-bound threads only add context switches and cache misses.
  • Mixing up WT and RT. Waiting time is total time spent waiting; response time is only until the first run. They are equal only for non-preemptive algorithms.
  • Ignoring tie-breaking rules in RR. Different conventions give different Gantt charts. State your convention.

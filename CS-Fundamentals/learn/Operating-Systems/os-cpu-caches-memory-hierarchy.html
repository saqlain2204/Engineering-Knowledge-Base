CPU Caches & the Memory Hierarchy

Why the same loop can run 10 times faster just by swapping two lines, and why two threads that never touch the same variable can still slow each other down 5 times. We build the ideas from zero, work the address math by hand, and measure everything on a real Linux machine. All timings on this page come from the C programs shown here.

1. Why Caches Exist: the Speed Gap

A modern CPU core can do a simple step (add two numbers) in well under a nanosecond. But fetching one number from main memory (RAM) takes around 80 to 150 nanoseconds. In that time the core could have done hundreds of steps. If every read went to RAM, the CPU would spend almost all its time waiting.

The fix is a cache: a small, very fast memory that sits on the CPU chip and keeps copies of data that was used recently. When the data you need is in the cache, that is a hit, and it is fast. When it is not, that is a miss: the CPU must fetch it from a slower level, and it waits.

Intuition: Think of studying for an exam. The book you are reading is on your desk (cache). Other books are on the shelf across the room (RAM). Books you have not opened this year are in the library across town (disk). You keep the books you use most on the desk, because walking to the shelf every time would waste the whole evening.

Fast memory is expensive and takes chip space, so we cannot make the cache as big as RAM. Instead, computers stack several levels, each one bigger and slower than the one before. That stack is the memory hierarchy.

2. The Memory Hierarchy and Locality

              faster, smaller, costlier per byte
                          ^
   +-----------------+    |   ~0.3 ns   a few hundred bytes   (inside the core)
   |    Registers    |    |
   +-----------------+    |
   |    L1 cache     |    |   ~1 ns     32-64 KiB per core
   +-----------------+    |
   |    L2 cache     |    |   ~4 ns     1-2 MiB per core
   +-----------------+    |
   |    L3 cache     |    |   ~10-40 ns tens to hundreds of MiB, shared by all cores
   +-----------------+    |
   |   RAM (DRAM)    |    |   ~80-150 ns  gigabytes
   +-----------------+    |
   |   SSD / disk    |    |   ~20-100 us (SSD), ~5-10 ms (spinning disk)
   +-----------------+    v
              slower, bigger, cheaper per byte

These are rough, typical numbers. Your machine will differ a bit, and section 4 shows how to measure your own.

Caches work because real programs are not random. They show locality:

  • Temporal locality (locality in time): if you used a piece of data just now, you will probably use it again soon. Example: a loop counter, or the top of the stack.
  • Spatial locality (locality in space): if you used one address, you will probably use the addresses right next to it soon. Example: walking through an array from start to end.

Caches use temporal locality by keeping recent data, and spatial locality by fetching data in blocks, not single bytes. That block is the next idea.

3. Cache Lines: Memory Moves in 64-Byte Blocks

The cache never fetches just one byte. It fetches a whole cache line (also called a cache block). On almost all current x86 and ARM CPUs a line is 64 bytes. When you read one byte, the 63 bytes around it come along for free.

RAM addresses (each box = 4 bytes = one int)

 line 0: [a0][a1][a2][a3][a4][a5][a6][a7][a8][a9][a10][a11][a12][a13][a14][a15]   bytes 0-63
 line 1: [a16][a17] ...                                                [a31]   bytes 64-127

Read a0  -> MISS, the whole line 0 (a0..a15) is copied into the cache
Read a1  -> HIT  (already there)
...
Read a15 -> HIT
Read a16 -> MISS, line 1 is fetched

Worked example: counting misses in a sum

You sum an array of 1,000,000 int values (4 bytes each, so 4,000,000 bytes) from start to end. The cache starts empty. How many misses?

  1. Ints per line = 64 / 4 = 16.
  2. Lines touched = 1,000,000 / 16 = 62,500.
  3. Each line misses once (the first time), then gives 15 hits. So 62,500 misses out of 1,000,000 reads: a miss rate of 1/16 = 6.25%.

In practice it is even better. The CPU has a hardware prefetcher: a circuit that notices you are walking forward through memory and starts fetching the next lines before you ask. For simple forward or backward walks, it hides most of the miss time.

Now change the element to a 64-byte struct and read only one 4-byte field from each. Every read lands on a new line, so every read is a miss: 1,000,000 misses, a miss rate of 100%, while using only 4 of every 64 bytes fetched. Same number of reads, 16 times more memory traffic. This is why data layout matters.

4. Measuring the Hierarchy Yourself

We can see the levels with a pointer-chasing test. We fill a block of memory with a chain of jumps in random order: each 64-byte line stores the address of the next line to visit. The CPU cannot guess the next address (random order defeats the prefetcher), and it cannot start the next read before the current one ends (it needs the value to know where to go). So the time per step is the true latency of whatever level holds the block.

// chase.c  (build: gcc -O2 chase.c -o chase)
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
double now(){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);return t.tv_sec+t.tv_nsec*1e-9;}
int main(){
  size_t sizes[]={16<<10,32<<10,256<<10,1<<20,4<<20,16<<20,64<<20,256<<20,1024L<<20};
  for(int k=0;k<9;k++){
    size_t n=sizes[k]/sizeof(size_t), lines=n/8;      // 8 words = 64 bytes
    size_t *p=malloc(n*sizeof(size_t)), *perm=malloc(lines*sizeof(size_t));
    for(size_t i=0;i<lines;i++) perm[i]=i;
    srand(1);                                            // shuffle the visit order
    for(size_t i=lines-1;i>0;i--){size_t j=((size_t)rand()*RAND_MAX+rand())%(i+1);
      size_t t=perm[i];perm[i]=perm[j];perm[j]=t;}
    for(size_t i=0;i<lines;i++) p[perm[i]*8]=perm[(i+1)%lines]*8;   // build the chain
    size_t idx=perm[0]*8; long steps=20000000;
    double t0=now(); for(long s=0;s<steps;s++) idx=p[idx]; double t1=now();
    printf("%8zu KiB: %.2f ns per load (%zu)\n",sizes[k]>>10,(t1-t0)*1e9/steps,idx&1);
    free(p); free(perm);
  }
}

Output on our test machine (an 8-core Intel Xeon VM with 48 KiB of L1 data cache and 2 MiB of L2 per core, and a large shared L3):

      16 KiB: 1.34 ns per load
      32 KiB: 1.38 ns per load
     256 KiB: 4.44 ns per load
    1024 KiB: 5.77 ns per load
    4096 KiB: 33.06 ns per load
   16384 KiB: 38.91 ns per load
   65536 KiB: 125.24 ns per load
  262144 KiB: 141.02 ns per load
 1048576 KiB: 210.41 ns per load

Read it like stairs:

Block sizeFits inTime per load
16-32 KiBL1about 1.4 ns
256 KiB-1 MiBL2about 4-6 ns
4-16 MiBL3 (bigger than one core's L2)about 33-39 ns
64 MiB and upmostly RAM125-210 ns

The biggest sizes are slower than "pure RAM" because they also miss in the TLB, the small cache of address translations. Each miss there adds a page-table walk on top of the data fetch. See the TLB section of Virtual Memory.

The lesson in one line: the same instruction (idx = p[idx]) costs 1.4 ns or 210 ns depending only on where the data lives. That is a 150x range.

5. Where Can a Line Go? Direct-Mapped and Set-Associative

A cache has room for a fixed number of lines. When a new line arrives, the hardware needs a fast rule for where to put it and how to find it again. There are three designs:

  • Direct-mapped: each memory line can go in exactly one slot. Very fast to check, but two hot lines that map to the same slot keep kicking each other out.
  • Fully associative: a line can go in any slot. No clashes, but checking every slot on every access is too slow and power-hungry for big caches.
  • Set-associative (the real-world middle ground): slots are grouped into sets. A line can go only in one set, but in any slot (called a way) inside that set. An "8-way" cache has 8 slots per set.
8-way set-associative cache with 64 sets

            way0  way1  way2  way3  way4  way5  way6  way7
 set 0   [     ][     ][     ][     ][     ][     ][     ][     ]
 set 1   [     ][     ][     ][     ][     ][     ][     ][     ]
 ...
 set 63  [     ][     ][     ][     ][     ][     ][     ][     ]

 A memory line picks its set from a few bits of its address,
 then may use any free way in that set. If all 8 are full,
 the cache evicts one (usually the least recently used).

Each slot also stores a tag: the leftover high bits of the address. The tag tells the cache which of the many possible memory lines is sitting in that slot right now.

6. Splitting an Address by Hand

To find a byte, the cache cuts the address into three parts:

  [          tag          |   set index   |  offset  ]
     which line is it?       which set?     which byte inside the line?

Setup: a 32 KiB L1 cache, 8-way set-associative, with 64-byte lines.

  1. Number of lines = 32 KiB / 64 B = 32,768 / 64 = 512 lines.
  2. Number of sets = lines / ways = 512 / 8 = 64 sets.
  3. Offset bits = log2(line size) = log2(64) = 6.
  4. Index bits = log2(number of sets) = log2(64) = 6.
  5. Tag bits = all the remaining high bits.

Problem: which set and which byte does address 0x7FFE12345678 use?

  1. Offset + index = 12 bits, so only the last 3 hex digits matter here: 0x678.
  2. In binary: 0x678 = 0110 0111 1000.
  3. The low 6 bits are the offset: 111000 = 56. So it is byte 56 of its line.
  4. The next 6 bits are the set index: 011001 = 25. So it lives in set 25.
  5. Everything above bit 12 (0x7FFE12345) is the tag.

Check with plain arithmetic: 0x678 = 1656. 1656 mod 64 = 56 (offset). 1656 / 64 = 25, rounded down (set). Both match.

A useful fact: here, 64 sets × 64 bytes = 4096 bytes. So the set depends only on the address mod 4096. Any two addresses exactly 4 KiB apart (or 8 KiB, 16 KiB, ...) land in the same set. Touch 9 such addresses over and over in an 8-way cache and they keep evicting each other, even though the other 63 sets sit empty. Section 9 shows this hurting real code.

7. The Three Kinds of Misses and AMAT

Every miss has one of three causes (often called "the three C's"):

KindPlain meaningHow to reduce it
Compulsory (cold)The first time you ever touch a line. It cannot already be there.Use bigger lines well (spatial locality); prefetching.
CapacityYour working data is bigger than the cache, so lines get evicted before you come back.Work on smaller pieces at a time (tiling or blocking); use smaller data types.
ConflictThe cache has room, but too many hot lines map to the same set.Change strides or add padding so addresses spread over sets; more ways.

Average memory access time (AMAT)

To judge a cache with one number, we use the average memory access time:

AMAT = hit time + miss rate × miss penalty

The miss penalty of one level is the AMAT of the next level down, so the formula nests.

Worked example. L1 hit time is 1 ns and 5% of accesses miss L1. L2 hit time is 4 ns and 20% of the accesses that reach L2 also miss there. RAM takes 80 ns.

  1. Time for an access that reaches L2: 4 + 0.20 × 80 = 4 + 16 = 20 ns.
  2. AMAT = 1 + 0.05 × 20 = 1 + 1 = 2 ns.

Now say a bad loop order pushes the L1 miss rate to 25%: AMAT = 1 + 0.25 × 20 = 6 ns, three times slower, with the exact same hardware. A small change in miss rate has a big effect because the miss penalty is so large.

8. What Happens on a Write

Reading is simple: copy the line in. Writing raises a question: when does RAM get the new value?

  • Write-through: every write goes to the cache and to the next level right away. Simple and always up to date, but it creates a lot of traffic.
  • Write-back (what CPU data caches use): the write changes only the cached copy, and the line is marked dirty (changed). The line is written down to the next level only when it is evicted. Ten writes to the same line cost one write to RAM, not ten.

And if you write to a line that is not in the cache? Data caches use write-allocate: first bring the line in, then change it. This is why writing one byte can still cost a full 64-byte read.

Same idea, other places: the OS page cache is write-back too. write() only changes RAM and marks the page dirty; the disk gets it later, which is why fsync() exists. See File Systems & Disk I/O.

9. Loop Order: a 10x Speedup from Two Lines

In C (and in NumPy by default) a 2D array is stored row by row ("row-major"). a[0][0], a[0][1], a[0][2] sit next to each other in memory; a[1][0] comes after the whole first row.

// rowcol.c  (build: gcc -O1 rowcol.c -o rowcol)
#include <stdio.h>
#include <time.h>
#define N 4096
static int a[N][N];                      // 4096 x 4096 ints = 64 MiB
double now(){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);return t.tv_sec+t.tv_nsec*1e-9;}
int main(){
  for(int i=0;i<N;i++) for(int j=0;j<N;j++) a[i][j]=1;
  long s=0; double t0,t1;
  t0=now(); for(int i=0;i<N;i++) for(int j=0;j<N;j++) s+=a[i][j]; t1=now();
  printf("row-major    (j inner): %.1f ms\n",(t1-t0)*1e3);
  t0=now(); for(int j=0;j<N;j++) for(int i=0;i<N;i++) s+=a[i][j]; t1=now();
  printf("column-major (i inner): %.1f ms\n",(t1-t0)*1e3);
  printf("%ld\n",s);
}

Output (a typical run; three runs gave 11.0-11.2 ms and 117-131 ms):

row-major    (j inner): 11.0 ms
column-major (i inner): 117.3 ms

Same additions, same answer, more than 10 times slower. Why?

  • Row order walks memory forward 4 bytes at a time. One miss brings 16 useful ints, and the prefetcher sees the pattern.
  • Column order jumps one full row each step: 4096 × 4 bytes = 16 KiB. Every read is on a new line, and only 4 of its 64 bytes are used before it is evicted.
  • It is worse than that. 16 KiB is a multiple of 4 KiB, so (as in section 6) every element of a column maps to the same L1 set. Only 8 to 12 of the 4096 lines in a column can stay in L1 at once: conflict misses on top of capacity misses.

Fixes

  1. Make the inner loop walk memory in order (swap the loops). This is the fix 95% of the time.
  2. Tiling (also called blocking): when you truly need both directions, as in matrix multiply or a transpose, work on small square tiles (say 64 × 64) that fit in cache, and finish each tile before moving on.
  3. Pick the right layout. If you always read one field of many records, store each field in its own array ("struct of arrays") instead of an array of big structs.
Python note: NumPy follows the same rule. For a C-ordered array, a.sum(axis=1) (along rows) streams memory, while a Python loop over a[:, j] columns jumps around. You can check the layout with a.flags['C_CONTIGUOUS'].

10. Many Cores: Coherence and MESI

Each core has its own L1 and L2. So two cores can each hold a copy of the same line. If core 0 writes to its copy, core 1 must never keep reading the old value. Keeping all copies in agreement is called cache coherence. The hardware does it for you, using a protocol. The classic one is MESI, named after the four states a line can be in, inside one core's cache:

StatePlain meaning
ModifiedOnly I have it, and I changed it. RAM is out of date.
ExclusiveOnly I have it, and it matches RAM.
SharedOthers may have it too. Read-only for now.
InvalidMy copy is useless. Fetch it again before use.

The main rule: before a core may write a line, every other copy must become Invalid. The writer sends an "invalidate" message, waits for the others to drop the line, and moves to Modified.

Two cores take turns writing to the same 64-byte line X

time  core 0                         core 1
 t1   write X: owns it (M)           -
 t2   -                              write X: send invalidate
      copy -> I                      fetch line from core 0, now M
 t3   write X: send invalidate       copy -> I
      fetch line from core 1, now M
 t4   -                              write X: ...and so on

The line "ping-pongs" between the cores. Every write is now a
cross-core transfer (tens of ns) instead of an L1 hit (about 1 ns).

This is fine and necessary when threads really share a value. The trap is when they do not, which is the next section.

11. False Sharing: Slow Without Sharing Anything

Coherence works on whole lines, not single variables. If two threads write to two different variables that happen to sit in the same 64-byte line, the hardware still ping-pongs the line. This is false sharing: the program shares nothing, but the cache line is shared.

// fs2.c  (build: gcc -O2 -pthread fs2.c -o fs2)
#define _GNU_SOURCE
#include <stdio.h>
#include <pthread.h>
#include <sched.h>
#include <time.h>
#define ITERS 50000000L
struct same   { long a; long b; } s;                  // a and b: 8 bytes apart, same line
struct padded { long a; char pad[120]; long b; } p;   // a and b: 128 bytes apart
double now(){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);return t.tv_sec+t.tv_nsec*1e-9;}
struct arg{long*c;int cpu;};
void* inc(void* x){ struct arg*a=x; cpu_set_t m; CPU_ZERO(&m); CPU_SET(a->cpu,&m);
  pthread_setaffinity_np(pthread_self(),sizeof m,&m);       // pin to one core
  for(long i=0;i<ITERS;i++) __atomic_fetch_add(a->c,1,__ATOMIC_RELAXED);
  return 0; }
double run(long*x,long*y){ pthread_t t1,t2; struct arg A={x,0},B={y,2}; double t0=now();
  pthread_create(&t1,0,inc,&A); pthread_create(&t2,0,inc,&B);
  pthread_join(t1,0); pthread_join(t2,0); return now()-t0; }
int main(){
  printf("same cache line:          %.2f s\n",run(&s.a,&s.b));
  printf("padded (different lines): %.2f s\n",run(&p.a,&p.b));
  struct arg A={&p.a,0}; double t0=now(); inc(&A);
  printf("one thread alone:         %.2f s\n",now()-t0);
}

Each thread adds 1 to its own counter 50 million times. Output (three runs were all close to this):

same cache line:          1.27 s
padded (different lines): 0.23 s
one thread alone:         0.23 s

With padding, two threads finish in the time one thread needs for its half: perfect scaling. Without padding, the same work is more than 5 times slower than with it, and slower than doing everything on one thread.

Where it shows up and how to fix it

  • Per-thread counters or stats in one array (long hits[NUM_THREADS]): neighbours share lines. Fix: pad each slot to 64 bytes, or keep counters in thread-local variables and add them up at the end.
  • Hot fields of different threads in one struct (a queue's head written by the consumer and its tail written by the producer). Fix: put them on separate lines. In C11 use _Alignas(64), in C++ alignas(64) or std::hardware_destructive_interference_size, in Java @Contended, in Rust #[repr(align(64))] or crossbeam's CachePadded.
  • How to spot it: adding threads makes things slower, and a profiler (for example perf c2c on Linux) shows heavy contention on one cache line.

Real sharing (many threads updating one counter) has the same cost, for the same reason. The fix there is to share less: give each thread its own counter and combine later. The page on Concurrency & Deadlocks covers locks and atomics; this section explains why even correct atomic code can be slow.

12. NUMA: Near and Far Memory

Big servers often have two or more CPU sockets (physical chips). Each socket has its own RAM attached. A core can read any RAM, but its own socket's RAM is faster than the other socket's, which must be reached over a link between the chips. This design is NUMA: non-uniform memory access. Each socket plus its RAM is a NUMA node.

   +---------------- node 0 ----------------+      +---------------- node 1 ----------------+
   |  cores 0-31   L3 cache    RAM 256 GiB  |<---->|  cores 32-63  L3 cache    RAM 256 GiB  |
   +----------------------------------------+ link +----------------------------------------+
     local access: about 80-100 ns              remote access: often 1.5-2x slower

Linux places a page on the node of the core that first touches it ("first touch"). So if one thread fills a big array and then threads on the other socket do all the work, every access is remote.

  • See the layout: lscpu (NUMA lines) or numactl --hardware.
  • Keep a process and its memory together: numactl --cpunodebind=0 --membind=0 ./app.
  • In Kubernetes, the kubelet's CPU Manager and Topology Manager can give a pod whole cores on one NUMA node. This matters for databases, low-latency services, and GPU jobs (each GPU is also attached closer to one socket).

14. Practice Problems

Try each one before reading the answer.

Problem 1: address split

A 64 KiB, 4-way set-associative cache uses 64-byte lines. How many sets are there, how many offset and index bits, and which set does address 0x0001F7C4 use?

Answer: Lines = 65,536 / 64 = 1024. Sets = 1024 / 4 = 256. Offset bits = log2(64) = 6; index bits = log2(256) = 8. Offset + index = 14 bits. Take the low 14 bits of 0x1F7C4: 0x1F7C4 = 128,964; 128,964 mod 16,384 = 14,276. Offset = 14,276 mod 64 = 4; set = 14,276 / 64 = 223.06, so set 223.

Problem 2: misses in a loop

You read every element of an array of 2,000,000 double values (8 bytes each) in order, with no prefetcher and a cold cache. Lines are 64 bytes. How many misses? Now you read only every 8th element. How many misses, and how does the time per element change?

Answer: 8 doubles per line, so 2,000,000 / 8 = 250,000 misses (miss rate 12.5%). Reading every 8th element still touches every line once: still 250,000 misses, but for only 250,000 reads, so every read misses. You do 8 times less work but it takes about as long, because time is set by lines fetched, not by elements read.

Problem 3: AMAT

L1 hit time is 1 ns, L1 miss rate 10%. L2 hit time 5 ns, L2 local miss rate 30%. RAM is 100 ns. What is the AMAT? Which helps more: cutting the L1 miss rate to 5%, or cutting RAM time to 70 ns?

Answer: L2 time = 5 + 0.3 × 100 = 35 ns. AMAT = 1 + 0.1 × 35 = 4.5 ns. With 5% L1 misses: 1 + 0.05 × 35 = 2.75 ns. With 70 ns RAM: L2 time = 5 + 21 = 26 ns, AMAT = 1 + 2.6 = 3.6 ns. Halving L1 misses helps more.

Problem 4: find the false sharing

A web server keeps struct { long requests; long errors; } stats[16]; and each of 16 worker threads updates only stats[my_id]. Adding threads beyond 4 makes it slower. Why, and what is the fix?

Answer: Each struct is 16 bytes, so 4 workers' slots share one 64-byte line. Every update invalidates the line in the other 3 cores: false sharing. Fix: align and pad each slot to 64 bytes (for example struct { _Alignas(64) long requests; long errors; }, which makes the struct 64 bytes), or use thread-local counters that are added up when stats are read.

Problem 5: which kind of miss?

Name the kind of miss: (a) the first call to a function after the program starts; (b) a 50 MiB hash table looked up at random on a CPU with 2 MiB of L2; (c) two arrays, each 64 KiB long and starting exactly 64 KiB apart, read together element by element on a direct-mapped 32 KiB cache.

Answer: (a) Compulsory: never touched before. (b) Capacity: the data is much bigger than the cache. (c) Conflict: A[i] and B[i] are 64 KiB apart, a multiple of the 32 KiB cache size, so they map to the same slot and evict each other every step, even though the cache has other free space.

15. Common Pitfalls

  • Counting operations, not memory. Two loops with the same number of additions can differ 10x in speed. Ask "how many cache lines does this touch?"
  • Benchmarking with tiny inputs. A 1 MiB test fits in L2 and looks great; the 1 GiB production input lives in RAM. Test with real sizes.
  • Strides that are powers of two. Rows of 1024 or 4096 elements line up on the same sets. Padding a row by one cache line (for example 4096 + 16 ints) can remove conflict misses.
  • Per-thread data packed side by side. That is false sharing waiting to happen. Pad hot per-thread data to 64 bytes.
  • Assuming more threads means more speed. If threads fight over one line (real or false sharing), more threads make it slower.
  • Ignoring NUMA on big servers. The thread that first touches memory decides where it lives.
  • Confusing CPU caches with the page cache. CPU caches are hardware, tiny, and measured in nanoseconds. The page cache is the OS keeping disk data in RAM, measured in GiB.

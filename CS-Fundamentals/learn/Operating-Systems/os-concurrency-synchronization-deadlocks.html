1. Why Concurrency Is Hard

Concurrency means several tasks are in progress at the same time. They may truly run at the same moment on different CPU cores (this is called parallelism), or one core may switch between them very fast. Either way, you do not control the exact order in which their steps happen.

That is fine when tasks share nothing. Trouble starts when two threads (two paths of execution inside one program) read and write the same memory. The result can depend on timing. A bug that depends on timing may show up once in a million runs, vanish when you add a print statement, and then appear in production on a busy day.

Intuition: Two people share one notebook that holds a bank balance. Each one reads the number, does the math in their head, and writes the new number. If they both read "100" before either writes, and each adds 50, both write "150". One deposit is lost. Nobody did anything wrong alone. The bug lives in the overlap.

This page gives you the words and tools to reason about that overlap:

  • Race condition: the result depends on the timing of threads.
  • Synchronization: rules and tools that control the order threads may run in.
  • Deadlock: threads wait for each other forever because of those very rules.

2. A Race Condition, Step by Step

Here is a tiny C program. Two threads each add 1 to a shared counter one million times. The right answer is 2,000,000.

#include <pthread.h>
#include <stdio.h>

long counter = 0;

void *work(void *arg) {
    for (int i = 0; i < 1000000; i++) {
        counter++;              /* load, add, store: NOT atomic */
    }
    return NULL;
}

int main(void) {
    pthread_t a, b;
    pthread_create(&a, NULL, work, NULL);
    pthread_create(&b, NULL, work, NULL);
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    printf("counter = %ld (expected 2000000)\n", counter);
    return 0;
}

Compile with gcc -O0 -pthread race.c -o race and run it three times. On an 8-core Linux machine we got:

counter = 1156636 (expected 2000000)
counter = 1109601 (expected 2000000)
counter = 1026926 (expected 2000000)

Almost half the updates vanished, and the number changes every run. Why?

counter++ is really three steps

The CPU cannot change memory in place for this line. It does three separate steps:

  1. Load: copy counter from memory into a register (a tiny storage slot inside the CPU).
  2. Add: add 1 to the register.
  3. Store: write the register back to memory.

A thread can be paused, or another core can act, between any two steps. Here is one bad interleaving (an order in which the steps of two threads mix together). The counter starts at 5.

TimeThread AThread Bcounter in memory
1load 5 into register5
2load 5 into register5
3add: register = 65
4add: register = 65
5store 66
6store 66 (should be 7)

Both threads did one increment, but the counter only went up by one. This is called a lost update. The same bug exists in databases, where two transactions read and then write the same row.

How to spot a race: look for shared data + at least one writer + no rule that orders the accesses. All three must be true. Remove any one of them and the race is gone.

Try it yourself: count the outcomes

Two threads each run x = x + 1 once, starting from x = 0. Each is load, add, store. What final values are possible?

  • If one thread finishes all three steps before the other starts: x = 2.
  • If both load before either stores (like the table above): x = 1.
  • x = 0 is impossible, because at least one store of a value of 1 or more always happens last.

So the answer is {1, 2}. Doing this small "list every interleaving" exercise is the best way to build intuition.

3. Critical Sections and the Three Rules

A critical section is a piece of code that touches shared data and must not be run by two threads at once. In the example, counter++ is the critical section.

Any correct solution to the "critical section problem" must give three guarantees:

RulePlain meaningWhat breaks without it
Mutual exclusionAt most one thread is inside the critical section at any time.Lost updates and corrupt data
ProgressIf nobody is inside and some threads want in, one of them gets in soon. Threads outside cannot block the choice.Everyone waits even though the room is empty
Bounded waitingA waiting thread gets its turn after a limited number of other threads go first.Starvation: one unlucky thread waits forever

Code is shaped like this:

while (true) {
    entry section       // ask permission (lock)
        critical section    // touch shared data
    exit section        // give permission back (unlock)
    remainder section   // other work, no shared data
}

Why a simple flag does not work

A first idea is a shared variable busy:

while (busy) { }   // wait until free
busy = true;       // claim it
counter++;
busy = false;

This fails for the same reason as before. Both threads can see busy == false, and both can set it to true and enter. Checking and setting are two steps, and a thread can be interrupted between them. We need a way to check and set in one unbreakable step.

There are clever software-only fixes, such as Peterson's algorithm for two threads. It uses two flags and a "turn" variable. It is great for learning, but modern CPUs reorder memory operations for speed, so Peterson's algorithm is not safe on real hardware without extra "memory barrier" instructions. In practice, we use help from the hardware.

4. Atomic Instructions: Help From the Hardware

An atomic operation happens all at once from the point of view of every other thread. No one can see it half done. CPUs offer a few atomic instructions. Two are the building blocks of almost every lock.

Test-and-set

It sets a memory word to true and returns the old value, in one step.

// What the hardware does, all as ONE step:
bool test_and_set(bool *target) {
    bool old = *target;
    *target = true;
    return old;
}

// A lock built on it:
while (test_and_set(&lock)) { }   // old was true? someone holds it, keep trying
/* critical section */
lock = false;

If two threads call it at once, the hardware orders them. Exactly one sees false (and wins). The other sees true and keeps trying.

Compare-and-swap (CAS)

"If the value is still what I expect, replace it with my new value. Tell me if it worked." Again, one step.

// Hardware, ONE step:
bool cas(int *addr, int expected, int new_value) {
    if (*addr != expected) return false;
    *addr = new_value;
    return true;
}

// Lock-free increment:
int old;
do {
    old = counter;                     // read
} while (!cas(&counter, old, old + 1)); // retry if someone changed it meanwhile

CAS powers lock-free data structures (structures where threads never wait on a lock; they just retry). In C you get it as atomic_fetch_add or atomic_compare_exchange_strong from <stdatomic.h>. Java has AtomicInteger, Go has sync/atomic, and Rust has AtomicUsize.

Rule of thumb: for one number (a counter, a flag), use an atomic type. For anything bigger (two fields that must change together, a list, a map), use a lock. Hand-written lock-free code is very hard to get right.

Correct is not the same as fast: when many cores update one atomic counter, or even different variables that share a 64-byte cache line, the hardware bounces that line between cores. CPU Caches: False Sharing measures a 5x slowdown from this and shows the fix.

5. Mutexes and Spinlocks

A mutex (short for "mutual exclusion") is a lock with two operations: lock() and unlock(). Only the thread that locked it may unlock it. Here is the race program fixed with a mutex:

long counter = 0;
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void *work(void *arg) {
    for (int i = 0; i < 1000000; i++) {
        pthread_mutex_lock(&lock);    /* enter critical section */
        counter++;
        pthread_mutex_unlock(&lock);  /* leave critical section */
    }
    return NULL;
}

Output, every time: counter = 2000000 (expected 2000000).

What happens while you wait?

There are two ways to wait for a lock:

SpinlockSleeping mutex
How it waitsLoops ("spins") and checks again and againAsks the OS to put the thread to sleep until the lock is free
CPU use while waiting100% of a core, doing nothing usefulNear zero
Cost to wake upNone; it notices in nanosecondsA context switch, a few microseconds
Good whenThe lock is held for a very short time and threads run on different cores (common inside OS kernels)The lock may be held for a while, or there are more threads than cores

Real mutexes mix both. On Linux, pthread_mutex_lock is built on a futex ("fast user-space mutex"). If the lock is free, it is taken with one atomic instruction and no system call. Only when there is a fight does the thread ask the kernel to sleep. Many runtimes also spin for a short moment before sleeping.

Lock granularity

Granularity is how much data one lock protects.

  • Coarse-grained: one big lock for a whole data structure. Simple and safe, but threads queue up behind each other. Python's old global interpreter lock (GIL) is the most famous example. Python 3.13 added an optional "free-threaded" build without it, and 3.14 made that build officially supported, which is exactly why Python code now has to care more about fine-grained locks.
  • Fine-grained: many small locks, such as one per bucket of a hash table. More parallel, but more chances for deadlock (section 9).

Reader-writer locks

Many structures are read often and written rarely. A reader-writer lock lets many readers in at once, but a writer gets the lock alone. Examples: pthread_rwlock_t, Go's sync.RWMutex, Java's ReentrantReadWriteLock.

6. Semaphores

A semaphore is an integer counter with two atomic operations. It was invented by Edsger Dijkstra in the 1960s.

  • wait() (also called P, down, or acquire): if the value is above 0, subtract 1 and continue. If it is 0, sleep until it is above 0.
  • signal() (also called V, up, or release): add 1, and wake one sleeping thread if any.
Intuition: a semaphore is a bowl of tokens at a parking lot gate. Each car takes a token to enter (wait). If the bowl is empty, cars wait in line. A car leaving puts a token back (signal). The starting number of tokens is the number of parking spots.

Two kinds

  • Binary semaphore (starts at 1): works like a lock. Only one thread can be inside.
  • Counting semaphore (starts at N): lets up to N threads in. Good for "at most 10 database connections" or "at most 4 GPU jobs at once".

Worked example: tracing a semaphore

A semaphore S starts at 2. Threads T1, T2, T3 each call wait(S), work, then signal(S).

StepEventS afterSleepingInside
1T1 wait1noneT1
2T2 wait0noneT1, T2
3T3 wait (S is 0, so sleep)0T3T1, T2
4T1 signal (wakes T3, which takes the token)0noneT2, T3
5T2 signal1noneT3
6T3 signal2nonenone

A quick check: the value always returns to its start value when every wait has a matching signal. If it does not, some path forgot to release.

Semaphores for ordering

A semaphore that starts at 0 makes one thread wait for another. "Run B only after A is done":

done = Semaphore(0)

Thread A:            Thread B:
  do_step_a()          done.wait()     # sleeps until A signals
  done.signal()        do_step_b()

7. Condition Variables and Monitors

Often a thread needs to wait until some condition is true: "the queue is not empty", "the job is finished". A condition variable is a place to sleep until another thread says "something changed, check again". It is always used together with a mutex.

  • wait(cv, mutex): unlock the mutex and sleep, as one atomic step. When woken, lock the mutex again before returning.
  • signal(cv) (or notify): wake one sleeper.
  • broadcast(cv) (or notify_all): wake all sleepers.
import threading

items = []
lock = threading.Lock()
not_empty = threading.Condition(lock)

def consumer():
    with not_empty:                 # lock the mutex
        while len(items) == 0:      # WHILE, not IF
            not_empty.wait()        # unlock + sleep, relock on wake
        item = items.pop(0)
    print("got", item)

def producer(x):
    with not_empty:
        items.append(x)
        not_empty.notify()          # wake one waiting consumer
Always check the condition in a while loop. A thread can wake up and find the condition false again. Another consumer may have taken the item first, or the OS may wake a thread for no reason (a spurious wakeup). With if, the thread would run on with a false belief and crash on an empty list.

A monitor is a language feature that bundles data, a lock, and condition variables together, so the lock is taken automatically. Java's synchronized methods with wait() and notify() are a monitor. Python's with lock: block is a small step toward the same idea: the lock is always released, even if an exception happens.

8. Three Classic Problems

These three problems appear in every OS course because real systems are full of them. Learn the pattern, and you will recognise it in a web server, a message queue, or a GPU job scheduler.

8.1 Producer-consumer (bounded buffer)

Producers put items into a buffer with N slots. Consumers take items out. Producers must wait when the buffer is full. Consumers must wait when it is empty. This is the shape of every work queue, log pipeline, and LLM request queue.

  producers                buffer (N = 3 slots)             consumers
  +--------+     put     +------+------+------+     take     +--------+
  |   P    | ----------> |  i1  |  i2  |      | -----------> |   C    |
  +--------+             +------+------+------+              +--------+
       empty = free slots (starts at N)    full = filled slots (starts at 0)

The classic solution uses three semaphores. This Python version runs as written:

import threading, time

N = 3                                  # buffer size
buffer = []
mutex = threading.Lock()               # protects the buffer list
empty = threading.Semaphore(N)         # counts free slots
full  = threading.Semaphore(0)         # counts filled slots

def producer():
    for item in range(6):
        empty.acquire()                # wait for a free slot
        with mutex:
            buffer.append(item)
            print(f"produced {item}  buffer={buffer}")
        full.release()                 # one more filled slot

def consumer():
    for _ in range(6):
        full.acquire()                 # wait for a filled slot
        with mutex:
            item = buffer.pop(0)
            print(f"consumed {item}  buffer={buffer}")
        empty.release()                # one more free slot
        time.sleep(0.05)               # consumer is slower

p = threading.Thread(target=producer); c = threading.Thread(target=consumer)
p.start(); c.start(); p.join(); c.join()

One real run (the exact order can change):

produced 0  buffer=[0]
produced 1  buffer=[0, 1]
produced 2  buffer=[0, 1, 2]
consumed 0  buffer=[1, 2]
produced 3  buffer=[1, 2, 3]
consumed 1  buffer=[2, 3]
...

Notice the buffer never grows past 3. The producer is forced to wait on empty. This is called backpressure: a slow consumer slows the producer down instead of letting memory fill up.

Order matters: if the producer took mutex before empty.acquire(), a full buffer would make it sleep while holding the mutex. The consumer could then never get the mutex to free a slot. That is a deadlock. Always wait on the counting semaphore first, then take the mutex.

8.2 Readers-writers

Many threads read shared data. A few write it. Readers can share; a writer needs the data alone. The tricky part is fairness:

  • Reader preference: a new reader may join while other readers are inside. A steady stream of readers can starve the writer forever.
  • Writer preference: once a writer is waiting, new readers must wait. Now readers can starve.

Real reader-writer locks pick a policy. For example, Go's sync.RWMutex blocks new readers once a writer is waiting, so writers do not starve.

8.3 Dining philosophers

Five philosophers sit at a round table. Between each pair is one fork, so there are five forks. To eat, a philosopher needs both the left and the right fork.

              P0
         F4        F0
      P4              P1
         F3        F1
          P3   F2   P2

  Pi needs fork Fi (right) and fork F(i-1) (left), with F(-1) = F4.

If every philosopher picks up their left fork at the same moment, each one holds one fork and waits for the other. No one can eat, ever. This is the simplest picture of a deadlock, and it leads straight to the next section.

Fixes, each of which breaks one deadlock condition:

  • Number the forks and always take the lower number first. P1 to P4 each take their left fork first (F0, F1, F2, F3). But P0 needs F4 and F0, so it takes F0 first, which is its right fork. Because one philosopher reaches in the other direction, the circle of waiting cannot close.
  • Allow at most four philosophers at the table at once (a counting semaphore of 4).
  • Pick up both forks together or none (take a lock that guards both).

9. Deadlock: The Four Conditions

A deadlock is a state where a group of threads each wait for something that another thread in the same group holds. Nobody can move, and nothing outside will help.

Here is a real deadlock in Python. Two transfers lock two accounts, but in opposite orders:

import threading, time

lock_a = threading.Lock()   # protects account A
lock_b = threading.Lock()   # protects account B

def transfer(first, second, name):
    with first:
        print(name, "holds its first lock")
        time.sleep(0.1)          # widen the window so the bug shows every time
        with second:
            print(name, "holds both locks, moving money")

t1 = threading.Thread(target=transfer, args=(lock_a, lock_b, "T1"), daemon=True)
t2 = threading.Thread(target=transfer, args=(lock_b, lock_a, "T2"), daemon=True)
t1.start(); t2.start()
t1.join(timeout=2); t2.join(timeout=2)
print("deadlocked!" if t1.is_alive() and t2.is_alive() else "finished")

Output:

T1 holds its first lock
T2 holds its first lock
deadlocked!

The resource allocation graph

We can draw who holds what. Circles are threads, boxes are resources. An arrow from a resource to a thread means "held by". An arrow from a thread to a resource means "waiting for".

        holds                waits for
  [lock_a] -----> (T1) ---------------+
     ^                                |
     |                                v
     +-------- (T2) <----------- [lock_b]
     waits for          holds

  Follow the arrows: T1 -> lock_b -> T2 -> lock_a -> T1.  A cycle.

When every resource has only one instance (like a lock), a cycle in this graph means deadlock. When resources have several instances (like 3 printers), a cycle means deadlock is possible, but not certain.

The four Coffman conditions

A deadlock can only happen when all four of these are true at the same time (Coffman and others, 1971):

ConditionPlain meaningIn the transfer example
1. Mutual exclusionA resource can be held by only one thread at a time.A lock has one owner.
2. Hold and waitA thread holds one resource while waiting for another.T1 holds lock_a and waits for lock_b.
3. No preemptionNobody can take a resource away; the holder must give it up.Python will not force T2 to drop lock_b.
4. Circular waitThere is a cycle of threads, each waiting for the next.T1 waits on T2, T2 waits on T1.
Intuition: four cars reach a four-way crossing at once. Each one has moved a little into the middle (hold), each needs the space in front (wait), nobody will reverse (no preemption), and each blocks the next one around the square (circular wait). Remove any one of these and traffic flows.

10. Handling Deadlock: Prevent, Avoid, Detect

There are four overall strategies. Real systems usually mix the first and third.

10.1 Prevention: make one condition impossible

Break thisHowCost
Mutual exclusionUse data that can be shared: read-only data, atomics, copy-on-writeNot possible for most real resources
Hold and waitRequest every resource at once at the start, or release everything before asking for moreResources sit idle; you must know your needs up front
No preemptionUse trylock or a timeout; if you cannot get the next lock, release what you hold and retry laterWasted work; can cause livelock (section 12)
Circular waitGive every lock a number. Always take locks in increasing order.You must agree on the order across the whole codebase

Lock ordering is by far the most used fix. Here is the transfer code with a fixed global order. It finishes every time:

def transfer(first, second, name):
    # Rule: always lock in a fixed global order (here: by id()).
    lo, hi = sorted([first, second], key=id)
    with lo:
        time.sleep(0.1)
        with hi:
            print(name, "holds both locks, moving money")

In a real bank you would sort by account number. Why does it work? A cycle needs someone to hold a "higher" lock while waiting for a "lower" one. The rule forbids that, so no cycle can form.

10.2 Avoidance: only grant safe requests

The system knows the maximum each thread may ever ask for. Before granting a request, it checks whether the system would still be in a safe state: a state where there is some order in which every thread can still finish. If not, the request waits even though the resource is free. The classic method is the Banker's algorithm (next section). It is mostly used in teaching and in some embedded and batch systems, because real programs rarely know their maximum needs.

10.3 Detection and recovery

Let deadlocks happen, look for cycles every so often, then break them. To recover, you can:

  • Kill one thread or abort one transaction in the cycle (the "victim"), often the one that did the least work.
  • Roll a thread back to an earlier checkpoint.

Databases do exactly this. PostgreSQL checks for a cycle when a lock wait lasts longer than deadlock_timeout (1 second by default), then aborts one transaction with ERROR: deadlock detected. Your app must catch that error and retry. See Locks, Two-Phase Locking, and Deadlocks.

10.4 Ignore it

Most general-purpose operating systems do not try to prevent deadlocks between user programs. They assume deadlocks are rare and leave it to programmers and to a reboot. This is sometimes called the "ostrich algorithm". It sounds silly, but the cost of the other methods is often higher than the cost of a rare restart.

11. The Banker's Algorithm, Worked by Hand

The name comes from a bank that never lends out so much cash that it could not satisfy all customers' maximum needs in some order. We use the standard textbook example, so you can check your answer against any OS book.

Setup

Five processes (P0 to P4) and three resource types (A, B, C). Total instances: A = 10, B = 5, C = 7.

  • Allocation: what each process holds right now.
  • Max: the most each process will ever need.
  • Need = Max - Allocation: what it may still ask for.
  • Available: free right now = Total - sum of Allocation = (3, 3, 2).
ProcessAllocation (A B C)Max (A B C)Need (A B C)
P00 1 07 5 37 4 3
P12 0 03 2 21 2 2
P23 0 29 0 26 0 0
P32 1 12 2 20 1 1
P40 0 24 3 34 3 1

The safety check, step by step

Start with Work = Available = (3, 3, 2). Repeatedly find a process that is not finished and whose Need ≤ Work in every column. Pretend it runs to the end and returns everything it holds: Work = Work + Allocation. Scan from P0 each time.

StepCheckResultWork after
1P0: need (7,4,3) ≤ (3,3,2)? No (7 > 3). P1: need (1,2,2) ≤ (3,3,2)? YesP1 finishes, returns (2,0,0)(5, 3, 2)
2P0: (7,4,3) ≤ (5,3,2)? No. P2: (6,0,0)? No (6 > 5). P3: (0,1,1)? YesP3 finishes, returns (2,1,1)(7, 4, 3)
3P0: (7,4,3) ≤ (7,4,3)? YesP0 finishes, returns (0,1,0)(7, 5, 3)
4P2: (6,0,0) ≤ (7,5,3)? YesP2 finishes, returns (3,0,2)(10, 5, 5)
5P4: (4,3,1) ≤ (10,5,5)? YesP4 finishes, returns (0,0,2)(10, 5, 7)

Every process can finish, so the state is safe. One safe sequence is <P1, P3, P0, P2, P4>. Other orders also work (for example <P1, P3, P4, P0, P2>). Any valid order is a correct answer. The final Work equals the total (10, 5, 7), which is a good self-check.

Handling a request

Now P1 asks for (1, 0, 2). The algorithm runs three checks:

  1. Is the request ≤ P1's Need (1,2,2)? Yes.
  2. Is the request ≤ Available (3,3,2)? Yes.
  3. Pretend to grant it: Available becomes (2,3,0), P1's Allocation becomes (3,0,2), P1's Need becomes (0,2,0). Run the safety check on this pretend state.

Starting from Work = (2,3,0): P1 needs (0,2,0), yes, Work becomes (5,3,2). From here the steps match the table above, so the state is safe. Grant the request.

Next, in that new state, P0 asks for (0, 2, 0). Available is (2,3,0), so it fits. Pretend: Available becomes (2,1,0). Now check: P0 needs (7,2,3), no. P1 needs (0,2,0), no (2 > 1). P2 needs (6,0,0), no. P3 needs (0,1,1), no (C: 1 > 0). P4 needs (4,3,1), no. Nobody can finish, so the state is unsafe. P0 must wait, even though the resources are free right now.

Unsafe is not the same as deadlocked. An unsafe state means a deadlock could happen if processes ask for their maximum. It might not. The Banker's algorithm plays it safe and refuses.

Cost: each check looks at n processes and m resource types, up to n times, so it takes about m × n² steps. That is fine for 5 processes, but too slow to run on every lock request in a big system.

12. Starvation, Livelock, and Priority Inversion

A program can be free of deadlock and still fail to make progress.

Starvation

A thread waits forever because others keep getting chosen first. Example: the reader-preference lock above, where the writer never gets in. Fix: fair queues (first come, first served), or aging (raise the priority of anything that has waited a long time, as in CPU scheduling).

Livelock

Threads are not blocked. They keep running, but they keep undoing each other's work. Picture two people in a corridor who both step left, then both step right, again and again. In code, this happens when two threads use "trylock, release on failure, retry" with the exact same timing. Fix: wait a random amount of time before retrying (random backoff). Ethernet and Wi-Fi use the same trick when two machines talk at once.

Priority inversion

A high-priority task waits for a lock held by a low-priority task. A medium-priority task, which needs no lock, keeps the CPU busy, so the low task never runs and never releases the lock. In effect, the high task is now stuck behind the medium one.

time  --->
High   :  ......... wants lock L .... blocked ..............................
Medium :                 runs runs runs runs runs runs (no lock needed)
Low    :  holds L .. (never gets CPU, never releases L) ....................

This really happened on NASA's Mars Pathfinder lander in 1997. A watchdog timer kept resetting the computer. Engineers fixed it from Earth by turning on priority inheritance: while a low task holds a lock that a high task wants, the low task temporarily gets the high priority, so it finishes and releases the lock quickly. Linux offers this for pthread mutexes with the PTHREAD_PRIO_INHERIT setting.

13. Scenario: The Frozen Payments Service

Situation. A small payments API runs fine in testing. On the first busy sale day, a few requests start hanging. After 20 minutes, all worker threads are stuck. CPU use is near 0%. Restarting fixes it for a while, then it happens again.

Step 1: read the clues

  • CPU near 0% while requests hang means threads are waiting, not working. That points to locks, I/O, or a pool that ran dry. A busy loop or livelock would show high CPU.
  • Only under load means a timing problem. Two requests must overlap in a special way.

Step 2: look at what threads are waiting on

Take a thread dump: a list of every thread and the line of code it is stopped on. Tools: jstack <pid> for Java, py-spy dump --pid <pid> for Python, sending SIGQUIT to a Go program, or gdb -p <pid> then thread apply all bt for C. The JVM even prints "Found one Java-level deadlock" for you.

Thread "worker-7":  waiting to lock  account:1042   held by "worker-3"
                    holding          account:2210
Thread "worker-3":  waiting to lock  account:2210   held by "worker-7"
                    holding          account:1042

That is the cycle from section 9. One request sent money from 2210 to 1042. Another sent from 1042 to 2210 at the same moment. Each locked "from" first, then "to".

Step 3: fix the cause

  1. Lock in a fixed order. Always lock the smaller account number first, whatever the direction of the transfer. This breaks circular wait.
  2. Add a timeout to every lock wait, so a future mistake causes one failed request (with a clear log line) instead of a frozen server.
  3. Keep critical sections short. The code was also calling a fraud-check API while holding both locks. Moving the network call outside the locked region cut lock hold time from 300 ms to under 1 ms, which also made collisions far rarer.

Step 4: prove the fix

Write a stress test: 50 threads making random transfers between 3 accounts (few accounts means many collisions) for 60 seconds. Check two things at the end: no thread is stuck, and the total money across all accounts is unchanged. Run it in CI. The broken version freezes within seconds; the fixed one passes every time.

Databases have the same problem with row locks, and they detect the cycle for you. Scenario: Requests Stuck on Database Locks reproduces it in PostgreSQL: 105 of 200 unordered transfers deadlocked, and 0 once rows were locked in id order.

If the locks live in the database (SELECT ... FOR UPDATE), the same lesson applies: lock rows in a fixed order (for example ORDER BY id), and retry on a deadlock error. The OS idea and the database idea are the same idea.

14. Common Pitfalls

  • Forgetting to unlock on an error path. An early return or an exception skips the unlock, and the next thread waits forever. Use with lock: (Python), defer mu.Unlock() (Go), try/finally (Java), or RAII guards like std::lock_guard (C++).
  • Doing slow work while holding a lock. Network calls, disk reads, and sleep inside a critical section turn a lock into a traffic jam.
  • Checking a condition with if instead of while before wait().
  • Protecting a variable with a lock in one place but not in another. A lock only helps if every access takes it.
  • "It passed the test, so it is safe." Races hide. Use tools: ThreadSanitizer (gcc -fsanitize=thread), Go's go test -race, and Java's jcstress.
  • Locking the same non-reentrant mutex twice in one thread. A thread can deadlock with itself. Either restructure the code, or use a reentrant lock (Python's threading.RLock) on purpose.
  • Assuming x += 1 is atomic in a high-level language. It is not in C, Java, Go, or free-threaded Python.
  • Mixing up semaphore order in producer-consumer (taking the mutex before waiting on the counting semaphore).

15. Cheat Sheet

NeedTool
Share one number safelyAtomic integer / CAS
Only one thread in a block of codeMutex (with with / defer / RAII)
Many readers, few writersReader-writer lock
At most N at once (connections, GPUs)Counting semaphore
Wait until something becomes trueCondition variable, checked in a while loop
Hand work between threadsBounded queue (producer-consumer)
Avoid deadlock with many locksGlobal lock order; timeouts
Avoid livelockRandom backoff before retry
Avoid priority inversionPriority inheritance

File Systems & Disk I/O

What really happens when a program saves a file. How the operating system turns names like /home/asha/notes.txt into blocks on a disk, why a "saved" file can still vanish after a power cut, and how to debug a full or slow disk. The command outputs on this page come from a Linux machine running ext4 on 19 November 2026.

1. The Big Picture: the I/O Stack

A disk only understands one thing: "read or write block number N". It has no idea what a file, a folder, or a name is. A file system is the part of the operating system that builds files and folders on top of those numbered blocks. Common ones are ext4 and XFS on Linux, APFS on macOS, and NTFS on Windows.

I/O means input/output: moving data in or out of the program, for example to a disk or a network.

When your program calls write(), the data passes down through several layers:

  your program          write(fd, "hello", 5)
       |                         (a system call: a request to the kernel)
  -----+---------------------------------------------------------- user space / kernel
       v
  VFS                   one common front door for every file system
       |
  page cache            copies of file data kept in RAM          (section 7)
       |
  file system (ext4)    maps "byte 5,000,000 of notes.txt" to "block 81,233"
       |                and keeps the journal                     (sections 6, 9)
  block layer           queues and merges requests, picks an order
       |
  device driver         speaks NVMe, SATA, or a cloud disk protocol
       v
  disk (SSD/HDD)        stores bits. Has its own small cache too.
  • A system call (syscall) is how a program asks the kernel to do something it is not allowed to do itself, such as touching hardware. See Processes & Threads for user space and kernel space.
  • The VFS (Virtual File System) is a shared layer that gives every file system the same set of operations: open, read, write, close. That is why the same cat works on ext4, on a USB stick, and on a network share.

The most important idea on this page: most layers lie a little to be fast. The page cache says "done" before the data reaches the disk. The disk may say "done" while the data is still in its own cache. Section 8 shows how to get the truth when you need it.

2. Disks: Blocks, HDDs, and SSDs

Storage is cut into fixed-size pieces:

  • A sector is the smallest piece the hardware reads or writes. Usually 512 bytes or 4 KiB.
  • A block is the smallest piece the file system hands out. On ext4 it is almost always 4 KiB (4,096 bytes). Even a 6-byte file uses one whole 4 KiB block.

A KiB is 1,024 bytes. (KB is sometimes 1,000 bytes. With disks the difference adds up, so this page uses KiB, MiB, GiB.)

Hard disks and solid-state drives

HDD (spinning disk)SSD (NVMe flash)RAM, for comparison
How it worksA metal plate spins. An arm moves a head to the right track and waits for the data to spin under it.Flash memory chips. No moving parts.Electronic memory, lost on power off
One random 4 KiB readabout 5–10 msabout 0.05–0.1 ms (50–100 µs)about 0.0001 ms (100 ns)
Random reads per second (IOPS)about 100–200hundreds of thousands 
Reading in order (sequential)about 150–250 MiB/sabout 2–7 GiB/stens of GiB/s

IOPS means I/O operations per second: how many separate small reads or writes a disk can do each second. Throughput is how many bytes per second it can move.

Worked example: random versus sequential

You must read 10,000 small 4 KiB records (40 MiB in total) from an HDD.

  • Scattered randomly: 10,000 reads × 8 ms = 80 seconds.
  • Stored next to each other: 40 MiB ÷ 200 MiB/s = 0.2 seconds. That is 400 times faster.

On an SSD the random case is about 10,000 × 0.08 ms = 0.8 s, so the gap is much smaller, but sequential access still wins. This is why databases log changes by appending to the end of a file (see write-ahead logging), and why LSM trees exist (see Indexing).

Cloud disks: a cloud "disk" is usually storage on other machines reached over the network. It often has a fixed IOPS and throughput limit that you pay for. When you hit the limit, requests simply wait in a queue. A slow cloud disk is often a disk that is working perfectly but is capped.

3. File Descriptors: How Programs Talk to Files

A program does not pass a file name to every read and write. It opens the file once and gets back a small number called a file descriptor (fd). After that it uses the number.

int fd = open("notes.txt", O_RDONLY);  // the kernel returns, say, 3
char buf[100];
ssize_t n = read(fd, buf, 100);        // read up to 100 bytes; n = how many arrived
close(fd);                             // give the number back

Every process starts with three file descriptors already open:

fdNameUsually connected to
0standard input (stdin)the keyboard, or a pipe
1standard output (stdout)the terminal
2standard error (stderr)the terminal

That is why the first file you open gets fd 3. It is also why 2>&1 in a shell means "send fd 2 to wherever fd 1 goes".

What the kernel keeps for each open file

  process A's fd table          open file table (kernel)             inode
  fd 0 -> terminal              +---------------------------+
  fd 1 -> terminal              | offset: 4096              |       notes.txt
  fd 3 ------------------------>| mode: read                |-----> size, owner,
                                +---------------------------+       block list ...

The offset is the current position in the file. Each read starts there and moves it forward. Two programs that open the same file separately each have their own offset.

"Everything is a file"

On Linux, many things that are not files on disk still use file descriptors: network connections (sockets), pipes between programs, the terminal, and even timers. One set of calls (read, write, close) works on all of them. You can see a process's open fds in /proc/<pid>/fd.

Each process has a limit on open fds (check with ulimit -n; 1,024 is a common default). A server that opens a connection per user and forgets to close them hits the error "Too many open files" (EMFILE).

4. Inodes and Directories

Here is the surprise that explains most of this page: a file's name is not stored with the file.

Each file has an inode (index node): a small record that holds everything about the file except its name and its data:

  • size, owner, permissions
  • times: last read, last data change, last inode change
  • the link count: how many names point to this inode
  • where the data blocks are (section 6)

Each inode has a number. A directory (folder) is just a special file whose content is a list of "name → inode number" pairs.

  directory /home/asha            inode 553404                  data blocks
  +-------------+--------+        +------------------------+      +-------+
  | name        | inode  |        | size: 6 bytes          |      |hello\n|
  | .           | 553390 |        | owner: asha, mode 0644 |----->+-------+
  | ..          | 2048   |        | links: 1               |      block 81233
  | notes.txt   | 553404 |------->| blocks: [81233]        |
  +-------------+--------+        +------------------------+

Looking up a path, step by step

To open /home/asha/notes.txt, the kernel does this:

  1. Start at the root directory /. Its inode number is fixed and known (2 on ext4).
  2. Read the root directory's content. Find the entry home and its inode number.
  3. Read that inode, then its content. Find asha.
  4. Read that directory. Find notes.txt → inode 553404.
  5. Read inode 553404. Check permissions. Return a file descriptor.

That could be many disk reads, so the kernel keeps recent lookups in RAM in the dentry cache (directory entry cache).

See it yourself

$ echo hello > notes.txt
$ stat notes.txt
  File: notes.txt
  Size: 6           Blocks: 8          IO Block: 4096   regular file
Device: 254,16      Inode: 553404      Links: 1
Access: (0644/-rw-r--r--)  Uid: ( 1000/     box)   Gid: ( 1000/     box)

"Size: 6" is the real content. "Blocks: 8" counts 512-byte units, so 8 × 512 = 4,096 bytes: one full 4 KiB block is used for 6 bytes.

Running out of inodes

Many file systems, ext4 included, create a fixed number of inodes when the disk is formatted. Millions of tiny files (cache files, session files, mail) can use up every inode while plenty of space is left. New files then fail with "No space left on device", even though df -h shows free space. Check with df -i:

$ df -i /
Filesystem      Inodes  IUsed   IFree IUse% Mounted on
/dev/vdb       2048000 239234 1808766   12% /

5. Hard Links, Soft Links, and Deleting Files

Because names are only directory entries, one inode can have several names.

  • A hard link is a second directory entry pointing to the same inode. Both names are equally real. The link count goes up by one.
  • A soft link (symbolic link, symlink) is a tiny separate file that contains a path. Opening it makes the kernel follow that path. If the target is deleted, the symlink is left "dangling" and broken.
$ ln notes.txt hard.txt        # hard link
$ ln -s notes.txt soft.txt     # soft link
$ ls -li notes.txt hard.txt soft.txt
553404 -rw-r--r-- 2 box box 6 Nov 19 14:23 hard.txt
553404 -rw-r--r-- 2 box box 6 Nov 19 14:23 notes.txt
553406 lrwxrwxrwx 1 box box 9 Nov 19 14:23 soft.txt -> notes.txt

The first column is the inode number. hard.txt and notes.txt share inode 553404, and the link count (third column) is now 2. soft.txt has its own inode, and its size is 9 bytes: the length of the text "notes.txt".

Hard linkSoft link
Points toAn inodeA path (text)
Works across file systems / disksNo (inode numbers are per file system)Yes
Can point to a directoryNo (to avoid loops)Yes
Target deletedThe data stays; this name still worksThe link breaks

Deleting is really "unlinking"

The system call that deletes a file is called unlink. It removes one name and lowers the link count. The space is freed only when both are true:

  1. the link count reaches 0 (no names left), and
  2. no process still has the file open.

Rule 2 causes a classic production mystery. A log file grows to 500 MiB. Someone deletes it to free space. df still shows the disk as full, but du cannot find any big files. Here is that exact case, reproduced:

$ dd if=/dev/zero of=big.log bs=1M count=500    # make a 500 MiB file
$ df -h --output=used /                          # used: 41G
$ sleep 600 3< big.log &                         # a process holds it open on fd 3
$ rm big.log
$ df -h --output=used /                          # used: still 41G!
$ du -sh .                                       # 12K: du only counts names, and the name is gone
$ ls -l /proc/$!/fd | grep deleted
lr-x------ 1 box box 64 Nov 19 14:23 3 -> /tmp/lab/big.log (deleted)
$ kill $!                                        # the holder exits
$ df -h --output=used /                          # used: 40G. The space is back.

The fix in production is to restart (or signal) the program holding the file, or to empty the file in place with truncate -s 0 big.log instead of deleting it. lsof +L1 lists every open-but-deleted file on the machine.

6. Finding a File's Blocks: Pointers and Extents

A file's data is spread over many blocks, not always next to each other. The inode must record which blocks, in order. There are two classic ways.

Way 1: direct and indirect pointers (ext2/ext3 style)

The inode has 15 slots, each holding a 4-byte block number:

  • Slots 0–11: direct pointers. Each points straight to a data block.
  • Slot 12: single indirect. Points to a block that is full of more block numbers.
  • Slot 13: double indirect. Points to a block of pointers to blocks of pointers.
  • Slot 14: triple indirect. One more level.
  inode
  [0] ----------------------------> data block 0
  ...
  [11] ---------------------------> data block 11
  [12] --> [ptr block: 1024 ptrs] --> data blocks 12 .. 1035
  [13] --> [1024 ptrs] --> [1024 ptrs each] --> data blocks 1036 .. 1,049,611
  [14] --> [1024] --> [1024] --> [1024] --> data blocks ...

Worked example: the biggest possible file

Block size 4 KiB, block numbers 4 bytes. One pointer block holds 4,096 ÷ 4 = 1,024 pointers.

  direct:           12 blocks             x 4 KiB =        48 KiB
  single indirect:  1,024 blocks          x 4 KiB =         4 MiB
  double indirect:  1,024^2 = 1,048,576   x 4 KiB =         4 GiB
  triple indirect:  1,024^3               x 4 KiB =         4 TiB
                                                    total ~ 4 TiB (+ 4 GiB + 4 MiB + 48 KiB)

Small files only need direct pointers, so they are fast. Huge files pay for extra pointer lookups.

Worked example: where is byte 5,000,000?

  1. Which block of the file? 5,000,000 ÷ 4,096 = 1,220 remainder 2,880. So it is file block 1,220, at byte 2,880 inside it.
  2. 1,220 ≥ 12, so not direct. Subtract: 1,220 − 12 = 1,208.
  3. 1,208 ≥ 1,024, so not in the single indirect range. Subtract: 1,208 − 1,024 = 184.
  4. It is in the double indirect range, at position 184. First-level index = 184 ÷ 1,024 = 0. Second-level index = 184 mod 1,024 = 184.
  5. With nothing cached, reading this byte takes 4 disk reads: the inode, the double indirect block, its entry 0 (a pointer block), then the data block found at entry 184.

Way 2: extents (ext4, XFS, and most modern file systems)

Pointer lists waste space and time for big files that sit in one long run of blocks. An extent says "starting at file block X, the next N blocks are at disk blocks Y to Y+N−1". One extent can describe up to 128 MiB on ext4.

  pointer style for a 1 GiB file in one run:  262,144 separate block numbers
  extent style for the same file:             8 extents of 128 MiB
                                              e.g. (file block 0, length 32768, disk block 500000)

See a file's extents on Linux with filefrag -v file. Many extents for a file means it is fragmented: its pieces are scattered.

Free space

To know which blocks are free, ext4 keeps a bitmap: one bit per block, 1 = used, 0 = free. One 4 KiB bitmap block covers 4,096 × 8 = 32,768 blocks, which is 128 MiB of disk. There is another bitmap for free inodes.

7. The Page Cache

The page cache is RAM that the kernel uses to keep copies of file data. It uses the same 4 KiB pages as virtual memory (see Virtual Memory & Paging).

  • Reads: the first read of a block goes to disk, and the kernel keeps a copy. The next read of the same block comes from RAM, which is about 1,000 times faster than an SSD.
  • Read-ahead: if you read a file in order, the kernel guesses you want the next part and loads it early.
  • Writes: write() copies your data into the page cache, marks those pages dirty (changed but not yet on disk), and returns at once. A kernel thread writes dirty pages to disk later, usually within about 30 seconds. This is called writeback.

Worked example

A 1 GiB file on an SSD that reads at 2 GiB/s, on a machine with plenty of free RAM.

  • First cat big.file > /dev/null: about 1 ÷ 2 = 0.5 s, from disk.
  • Second time: from the page cache at RAM speed, roughly 0.1 s or less.

This is why the first run of a benchmark is often slower ("cold cache") and later runs are faster ("warm cache"). Be careful which one you are measuring.

"My server has no free memory!"

$ free -h
               total        used        free      shared  buff/cache   available
Mem:            15Gi       4.1Gi       0.6Gi       0.2Gi        10Gi        11Gi

Only 0.6 GiB is "free", but 10 GiB is buff/cache. The kernel fills spare RAM with cached files because empty RAM does nothing useful. It gives that memory back as soon as programs need it. The number to watch is available (11 GiB here), not free.

In containers this matters too: page cache used by a container's files is counted towards its memory limit, but the kernel reclaims it before deciding to kill the container. The kills come from memory that cannot be reclaimed (see OOM kills).

8. write() Is Not Saved: fsync and the Safe-Save Pattern

Since write() only reaches RAM, a power cut in the next few seconds loses the data, even though the program was told "success".

fsync(fd) is the system call that says: "push all of this file's dirty data and its inode to the disk, and do not return until the disk confirms it is stored safely". The kernel also tells the disk to empty its own cache. After fsync returns, the data survives a power cut.

The cost of fsync, with numbers

An fsync must wait for the device. Say it takes about 2 ms on a typical SSD (enterprise SSDs with power-loss protection can be much faster; HDDs and some cloud disks are slower).

  • An app saves 1,000 records, calling fsync after each one: 1,000 × 2 ms = 2 seconds.
  • The same app writes all 1,000, then calls fsync once: about 2 ms plus the write time.

Databases use this idea, called group commit: transactions that finish at about the same time share one fsync of the log. That is how a database can commit thousands of transactions per second on a disk that can only do a few hundred flushes.

The safe-save pattern

How do you replace a settings file so that, after a crash, you have either the complete old version or the complete new version, never half of each?

Writing over the file directly is unsafe: a crash in the middle leaves a mix. The standard answer uses rename, which the file system does as one atomic step (it fully happens or does not happen at all):

import os

def save_atomically(path, data: bytes):
    tmp = path + ".tmp"
    with open(tmp, "wb") as f:
        f.write(data)          # 1. write the new version to a temporary file
        f.flush()              #    move Python's own buffer into the kernel
        os.fsync(f.fileno())   # 2. make sure the new data is on disk
    os.replace(tmp, path)      # 3. atomically swap the name to the new file
    dir_fd = os.open(os.path.dirname(path) or ".", os.O_RDONLY)
    try:
        os.fsync(dir_fd)       # 4. make the rename itself durable (it lives in the directory)
    finally:
        os.close(dir_fd)

Why each step:

  1. Readers keep seeing the old file while the new one is being written.
  2. Without this fsync, the rename could reach the disk before the data. After a crash you would have the new name pointing at an empty or partial file. This really happened to many apps on early ext4.
  3. os.replace calls rename. Anyone who opens the path gets either the old file or the new file.
  4. The rename is a change to the directory, so the directory must be synced too.
There are also several buffers before the kernel. Python's file object, C's FILE*, and Java's BufferedWriter keep data in the program's own memory first. flush() moves it into the kernel (the page cache). Only fsync moves it to the disk. Three different steps.

9. Surviving Crashes: Journaling and Copy-on-Write

Even a tiny file change updates several places on disk. Appending one block to a file needs:

  1. the new data block,
  2. the inode (new size, new block pointer),
  3. the free-space bitmap (mark that block as used).

The disk writes these one at a time. If power fails after only some of them:

What reached the diskResult after reboot
Only the data blockHarmless: nothing points to it. The new data is simply lost.
Only the inodeThe file points to a block holding old garbage, and the bitmap says the block is free, so it may be given to another file too.
Only the bitmapA block is marked used but nothing owns it: leaked space.

Old file systems fixed this by scanning the whole disk after a crash with fsck (file system check). On a large disk that could take hours.

Journaling

A journal is a small area of the disk used as a diary. Before changing the real locations, the file system writes a note: "I am about to do these 3 changes". This is the same idea as a database's write-ahead log.

  1. write to journal:   [BEGIN tx 52] [inode] [bitmap] [data?] [COMMIT tx 52]
  2. wait until the journal is on disk
  3. write the changes to their real places ("checkpoint")
  4. mark tx 52 as done in the journal

  After a crash:
  - journal has COMMIT for tx 52  -> replay it (do steps 3-4 again). Safe to repeat.
  - journal has no COMMIT         -> ignore it. The real places were never touched.

Recovery now takes seconds, because only the journal is read. ext4 has three modes:

  • ordered (default): only metadata (inodes, bitmaps, directories) goes into the journal, but data blocks are written before the metadata that points to them is committed. So a file never points at garbage.
  • writeback: metadata only, no ordering. Faster, but after a crash a file can contain old garbage.
  • journal: data also goes through the journal. Safest, but every block is written twice.

Copy-on-write

File systems such as Btrfs and ZFS never overwrite live data. They write new versions of the changed blocks to free space, then switch one top-level pointer to the new tree in a single step. A crash leaves either the old tree or the new tree, both complete. As a bonus, snapshots are almost free: keep the old top pointer and you have the old version of everything.

10. Ways to Do I/O: Blocking, epoll, io_uring, mmap

A disk or network read takes a long time compared with the CPU. What the thread does while it waits is a big design choice.

ModelHow it worksUsed by
Blockingread() puts the thread to sleep until data arrives. Simple. To serve 10,000 users you need about 10,000 threads.Simple scripts, thread-per-request servers
Non-blocking + readiness (epoll)One thread asks the kernel "tell me which of these 10,000 sockets have data". epoll_wait returns only the ready ones, and the thread handles each without waiting.nginx, Node.js, Redis, Python asyncio
Completion-based (io_uring)The program puts requests in a ring shared with the kernel ("read 4 KiB at offset X"). The kernel does them and puts results in a second ring. Very few system calls.Newer high-performance databases and storage engines

One gap to know: classic epoll readiness works well for network sockets, but regular files always report "ready", because the kernel assumes disk reads are short. That is why event-loop systems often send file I/O to a pool of helper threads. io_uring fixes this by handling files and sockets the same way.

Two ways to skip steps

  • mmap maps a file into the program's memory. Reading ptr[5000000] reads the file; the first touch of each page causes a page fault that loads it from the page cache or disk (see page faults). It avoids copying data and is great for read-mostly files. It is harder to control exactly when changes are saved, and an I/O error becomes a crash signal instead of an error code.
  • Direct I/O (O_DIRECT) skips the page cache and moves data straight between the program's memory and the disk. Databases that keep their own cache (for example the InnoDB buffer pool in MySQL) use it so that data is not cached twice.

11. File Systems in Containers

A container image is made of read-only layers, one for each build step (see Docker Fundamentals). When a container starts, Linux's overlay file system (overlayfs) stacks them and adds one thin writable layer on top:

  what the container sees:   /app/server.py   /etc/config.yml   /tmp/cache.db
                                   |                |                 |
  writable layer (per container)   |          config.yml (edited) cache.db (new)
  image layer 3: COPY app          server.py        |
  image layer 2: pip install       ...              |
  image layer 1: base OS           ...          config.yml (original, now hidden)
  • Reading a file finds the top-most layer that has it.
  • Changing a file from a lower layer first copies the whole file up into the writable layer. This is called copy-up. Editing one byte of a 2 GiB file in an image copies 2 GiB.
  • Deleting a file from a lower layer adds a hidden marker (a "whiteout"). The image does not get smaller.
  • The writable layer is thrown away when the container is removed.

So databases, uploads, and anything you want to keep belong on a volume: a normal directory or disk mounted into the container, without overlay layers. In Kubernetes that is a PersistentVolume (see Kubernetes Storage). Also watch the writable layer and logs: a container that writes big logs to its own file system can fill the node's disk, and Kubernetes then starts evicting pods with the reason "DiskPressure".

12. Debugging Disk Problems

"No space left on device"

  1. df -h: which file system is full?
  2. df -i: is it really out of inodes, not bytes?
  3. du -xh --max-depth=1 /var | sort -h: which folder is big? (-x stays on one file system.)
  4. If du adds up to much less than df: look for open-but-deleted files with lsof +L1 (section 5).
  5. Also check for space reserved for the root user: ext4 keeps 5% by default, so normal users see "full" a little earlier.

"The disk is slow"

iostat -x 1 (from the sysstat package) prints one line per disk every second. The columns that matter:

Device   r/s     w/s    rkB/s    wkB/s  r_await  w_await  aqu-sz  %util
nvme0n1  850.0  2400.0  27200   96000     0.21    14.80   35.6   99.6
  • r/s, w/s: IOPS for reads and writes. Compare with what the disk (or your cloud plan) allows.
  • r_await, w_await: average milliseconds per request, including time waiting in the queue. Here writes take 14.8 ms on an SSD that should take well under 1 ms, so they are queuing.
  • aqu-sz: average number of requests waiting. 35 means a long queue.
  • %util: share of time the disk was busy. Near 100% on an HDD means saturated. On SSDs and cloud disks, which do many requests in parallel, it can show 100% while there is still room; trust await and the IOPS limit more.

This disk is doing 2,400 writes per second. If the cloud plan allows 3,000 IOPS in total, then 850 + 2,400 = 3,250 means it is over the cap, and every request queues. Next step: find who is writing with sudo iotop -o or pidstat -d 1.

A high wa (I/O wait) number in top or vmstat means CPUs are idle while threads wait for the disk. The slow-API scenario shows how to fit this into a full investigation.

13. Practice Problems

Try each on paper first. Answers follow.

Problem 1: block math

A file system has 1 KiB blocks and 4-byte block numbers, with 12 direct pointers, one single indirect, and one double indirect. What is the largest file it can hold?

Answer: One pointer block holds 1,024 ÷ 4 = 256 pointers. Direct: 12 × 1 KiB = 12 KiB. Single: 256 × 1 KiB = 256 KiB. Double: 2562 = 65,536 × 1 KiB = 64 MiB. Total = 64 MiB + 256 KiB + 12 KiB = about 64.3 MiB.

Problem 2: which pointer?

With 4 KiB blocks and the layout from section 6, which pointer finds byte 100,000 of a file, and how many disk reads does it take with nothing cached?

Answer: 100,000 ÷ 4,096 = 24 remainder 1,696, so file block 24. 24 ≥ 12, and 24 − 12 = 12 < 1,024, so it is in the single indirect block at entry 12. Reads: inode, single indirect block, data block = 3.

Problem 3: link counts

You run: echo hi > a; ln a b; ln -s a c; rm a. What does cat b print? What about cat c? What is the link count of b's inode?

Answer: cat b prints hi: b is a hard link to the same inode, which still has one name. cat c fails with "No such file or directory": c holds the path "a", which no longer exists. The link count is 1.

Problem 4: fsync budget

A logging service receives 5,000 events per second. Each fsync takes 3 ms. Can it fsync after every event? If it batches, what is the smallest batch that keeps up, and what is the most data it could lose in a crash?

Answer: One thread can do at most 1 ÷ 0.003 ≈ 333 fsyncs per second, so no: 5,000 per second is 15 times too many. A batch must hold at least 5,000 ÷ 333 = 15 events. In practice you flush on a timer, for example every 10 ms (about 50 events, 100 fsyncs per second, well within budget). The most you could lose is the batch not yet synced: about 10 ms of events.

Problem 5: df versus du

df -h /var says 95% used (190 GiB of 200 GiB). du -sh /var says 40 GiB. Give two possible causes and a command to check each.

Answer: (1) Deleted files still held open by a process: check with lsof +L1, then restart that process. (2) Files hidden under a mount point: something wrote into /var/data before a disk was mounted on top of it, so du cannot see them. Check by bind-mounting the parent somewhere else (mount --bind /var /mnt/check) and running du there. (Another possibility: a different file system is actually mounted at a sub-path, which du -x would show.)

Problem 6: container copy-up

An image has a 1.5 GiB SQLite file baked into a layer. At start-up, the app opens it and updates one row. What happens, and what is the fix?

Answer: The first write triggers a copy-up of the whole 1.5 GiB file into the container's writable layer, which slows start-up and uses 1.5 GiB more disk per container. The change is also lost when the container is removed. Fix: put the database on a volume, and copy the starting file there once if it is not present.

14. Common Pitfalls

  • Thinking write() means saved. It means "in RAM". Use fsync when the data matters.
  • Overwriting important files in place. Use the temp file + fsync + rename + fsync-the-directory pattern.
  • Deleting a log file that a program still writes to. The space is not freed. Truncate it, or tell the program to reopen its logs (most support a signal for this, and tools like logrotate do it for you).
  • Reading "free" memory instead of "available". The page cache is supposed to fill RAM.
  • Benchmarking with a warm cache and believing the disk is that fast. Clear caches for tests (echo 3 | sudo tee /proc/sys/vm/drop_caches), or use files larger than RAM.
  • Millions of tiny files in one directory. Inodes run out and directory operations get slow. Spread files into sub-folders (for example by the first two letters of a hash), or use a database or object store.
  • Writing app data into the container's own file system. It is slow (copy-up), it fills the node, and it disappears. Use volumes.
  • Ignoring the cloud disk's IOPS cap. High await with modest load often means you hit the paid limit, not a broken disk.

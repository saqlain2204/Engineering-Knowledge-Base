System Calls & the Kernel Boundary

Your program cannot talk to the disk, the network, or even the clock by itself. It has to ask the operating system. That ask is a system call (syscall). This page explains the two worlds a program lives in, what a syscall costs, and why writing one megabyte as a million tiny writes can be hundreds of times slower than writing it once. It builds on Processes, Threads & CPU Scheduling.

1. Two Worlds: User Space and Kernel Space

A CPU has a privilege switch. In everyday language: some instructions are allowed only for the operating system. The usual names are user mode (also called ring 3 on x86) and kernel mode (ring 0).

user space                         kernel space
+---------------------------+      +------------------------------+
| your process              |      | the operating system         |
|  - your code and data     |      |  - talks to devices          |
|  - libraries (libc)       |      |  - owns files, memory, net   |
|  - cannot talk to disks   |      |  - switches between processes|
|    or change page tables  |      |  - enforces permissions      |
+--------------+------------+      +--------------^---------------+
               |                                  |
               |  system call (a controlled door) |
               +----------------------------------+

This split is not a fashion. If every program could write any sector on the disk, or change any other process's memory, a bug in a calculator could wipe the machine. The kernel sits in the middle and allows only well-defined requests: "read this file," "send these bytes," "give me more memory."

Intuition. Think of a bank. You cannot walk into the vault. You fill in a form at the counter (the system call). The teller (the kernel) checks your identity, does the work, and hands back a result or an error. The form is standardized. You cannot invent a new form that says "give me everyone else's money."

2. Words You Need

  • System call (syscall). A request from a program to the kernel. On Linux, examples are read, write, open, mmap, fork, clone, poll, and getpid.
  • User space. The memory and mode your process runs in. It cannot run privileged instructions.
  • Kernel space. The memory and mode the operating system runs in.
  • Trap (or exception, or software interrupt). The CPU event that switches from user mode to kernel mode in a controlled way. Modern x86-64 Linux uses the syscall instruction for this.
  • ABI (application binary interface). The contract for how arguments are passed (which registers, which numbers identify which call) and how results come back.
  • libc. The C library (on Linux often glibc or musl). Your Python or Go or Java program usually does not issue the raw instruction itself. A library wraps the syscall and gives you a function like open() or os.read().
  • vDSO (virtual dynamic shared object). A small page of kernel-provided code mapped into every process. A few "syscalls" run there, in user space, with no mode switch. clock_gettime is the usual example.
  • Context switch. The kernel stops one thread and starts another. A syscall is not always a context switch to another process. Many syscalls run in the kernel and return to the same thread. A blocking syscall (wait for disk, wait for the network) often does cause a context switch, because the thread has nothing to do until the event arrives.
  • File descriptor (fd). A small integer the kernel gives your process to refer to an open file, socket, or other object. See File Systems & Disk I/O.

3. What Happens During a System Call

Suppose your program calls write(fd, buf, 13) to send hello, world\n. Under the hood, roughly this happens:

1. libc puts the syscall number for write in a register
   (on x86-64 Linux, rax = 1) and the arguments in others
   (rdi = fd, rsi = pointer to the bytes, rdx = 13).
2. It runs the syscall instruction.
3. The CPU switches to kernel mode, and jumps to a kernel
   entry point. User registers are saved.
4. The kernel checks the number, copies (or looks at) the
   arguments, checks permissions, and does the work:
   find the file, copy bytes toward the destination.
5. It puts the result in rax: 13 on success, or a negative
   error code on failure.
6. The CPU switches back to user mode and returns to libc.
7. libc turns a negative code into errno and a -1 return,
   or returns 13 to your program.

Two costs matter. The first is the mode switch itself: save state, change privilege, look up the call, come back. That is a few tens of nanoseconds on a modern machine, not millions, but it is still tens to hundreds of times a normal add. The second is the work of the call: writing a byte to a disk is much heavier than asking for the process id.

If the data is not ready (a read from a socket with no incoming bytes), the kernel puts the thread to sleep and runs something else. That is the link to I/O models and event loops: a blocking syscall waits, a non-blocking one comes back at once with "try again," and epoll is itself a syscall that waits for many file descriptors at once.

4. The Main Families

Linux has hundreds of syscalls. Almost all of the ones you meet fall into a few groups.

FamilyExamplesWhat you are asking
Files and directoriesopenat, read, write, close, lseek, fsync, statx, mkdir, unlinkCreate, read, write, and remove files
Memorymmap, munmap, brk, mprotect, madviseGive me address space, change permissions
Processes and threadsclone, fork, execve, exit, wait4, kill, getpidStart, stop, wait, signal
Timeclock_gettime, nanosleepWhat time is it? Sleep until then.
Networksocket, bind, listen, accept, connect, sendto, recvfromTalk to the network
I/O readinesspoll, epoll_wait, io_uring_enterWhich fds are ready? Submit a batch of I/O.
Identity and permissionsgetuid, setuid, capset, prctlWho am I, and what am I allowed to do?

You rarely pick the syscall by name in a high-level language. You call f.write(...) or socket.send(...), and the runtime decides whether to make one syscall or many. That decision is the difference between a fast program and a slow one, which the lab below measures.

5. The Lab: Measuring the Cost

We compiled a small C program with -O2 and ran it on a Linux machine with 8 logical CPUs. Each figure below is from a representative run. A second run was within a few percent.

A userspace add vs getpid vs the clock

const int N = 2000000;
volatile int x = 0;
for (int i = 0; i < N; i++) x += 1;          /* userspace add */
for (int i = 0; i < N; i++) (void) getpid(); /* real syscall */
for (int i = 0; i < N; i++) clock_gettime(CLOCK_MONOTONIC, &ts);
Operation, 2,000,000 timesTotalTime each
Userspace add (x += 1)0.55 ms0.28 ns
getpid() (enters the kernel)132 ms66 ns
clock_gettime (vDSO, see next section)50 ms25 ns

On this machine, getpid is about 240 times slower than a single add. It is still fast in human terms: you can do about 15 million getpid calls in a second. The trouble starts when you do a heavier syscall, or when you do a cheap one once per byte.

Writing one megabyte, three ways

We opened a file and wrote 1,048,576 bytes (1 MiB) of the letter A.

HowSyscallsTimeThroughput
One write() of 1 byte, 1,048,576 times1,048,576260 ms4.0 MB/s
One write() of 4 KB, 256 times2560.56 ms1,862 MB/s
One write() of the whole megabyte10.44 ms2,365 MB/s

The one-byte loop was about 590 times slower than a single write (260 ms vs 0.44 ms). Almost all of that gap is the syscall boundary, not the disk: these writes hit the page cache (see File Systems & Disk I/O). Going from 4 KB writes to one large write only shaved a little more off, because 256 calls is already a small number.

Open and close vs reuse

Opening a file 50,000 times and closing it each time took 35 ms (0.69 µs each). Reusing one file descriptor, seeking to the start, and reading one byte 50,000 times took 11 ms (0.23 µs each). Open and close are not free. Long-running servers keep files and sockets open and reuse them.

The same lesson in Python

Python is slower per operation because of the interpreter, but the syscall count is still visible. Linux exposes it in /proc/self/io as syscw (write syscalls) and syscr (read syscalls).

with open(path, "wb", buffering=0) as f:   # unbuffered
    for i in range(1 << 20):
        f.write(b"A")
# 421 ms, 1,048,576 write syscalls

with open(path, "wb") as f:                # default buffered
    for i in range(1 << 20):
        f.write(b"A")
# 74 ms, 256 write syscalls

with open(path, "wb") as f:
    f.write(b"A" * (1 << 20))              # one write
# 1.5 ms, 1 write syscall

The default buffered writer already did the important fix: it turned a million calls into 256. One write of the whole buffer was faster still. This is why print in a tight loop, or logging one line per request without buffering, can show up as a hot syscall in production.

6. The vDSO: Some Calls Never Enter the Kernel

Look back at the lab: clock_gettime was 25 ns, and getpid was 66 ns. Both look like system calls in the manual. Why is the clock faster?

The kernel maps a tiny shared page, the vDSO, into every process. For a few functions, libc jumps to that page instead of running the syscall instruction. The page holds data the kernel updates (such as the current time) and a short function that reads it. There is no mode switch.

gettimeofday and clock_gettime with the usual clocks take this path on modern Linux. getpid does not: it still enters the kernel (the kernel is the authority on which process you are). The 25 ns vs 66 ns gap we measured is that difference.

You usually do not need to think about the vDSO, except for this: do not assume every function in section 2 of the manual pays a full syscall. If you are counting entries with strace, clock_gettime may barely appear, while read and write will.

7. Watching a Program Talk to the Kernel

strace (and ltrace for library calls, and bpftrace / perf for lower overhead) is how you see the conversation. We did not have strace on the lab machine; these are the commands you run on yours, and the kind of output they produce.

# follow every syscall of a command (noisy, slow)
strace -o /tmp/trace.txt ls /tmp

# count syscalls and time spent, then print a summary
strace -c python3 -c 'open("/tmp/x","w").write("a"*1000000)'

# a typical summary line (your counts will differ):
#   % time     seconds  usecs/call     calls    errors syscall
# ------ ----------- ----------- --------- --------- ----------------
#   40.00    0.000120          12        10           openat
#   25.00    0.000075          75         1           write
#   ...

Useful flags:

  • -f follows children (needed for programs that start workers).
  • -p PID attaches to a process that is already running.
  • -e trace=file or -e write,read,openat keeps only the calls you care about.
  • -c counts instead of printing every call. Start here. A full trace of a busy server is huge and will slow the process down.

When a service is "mysteriously slow" and CPU is low, a syscall count is often the missing picture: millions of tiny reads, a stat per request on the same config file, or a process that opens and closes a connection every time instead of reusing it.

Linux also lets you read counts without strace:

cat /proc/$(pidof yourapp)/io     # syscr, syscw, bytes
cat /proc/$(pidof yourapp)/status | grep ctxt   # voluntary / nonvoluntary context switches

8. Too Many Syscalls: The N+1 I/O Problem

The one-byte write loop is a small case of a general bug: doing a syscall once per item, instead of once per batch.

  • Reading a file line by line with unbuffered 1-byte reads.
  • Querying a database once per row of a web page (the classic N+1 query, which is the same idea one layer up; see SQL Joins).
  • A server that getaddrinfos the same hostname on every request, instead of caching the result (and honoring DNS TTLs; see DNS & HTTP).
  • Logging with a flush after every line on a hot path.

The fix is almost always buffering, batching, or reuse:

  • Let the standard library buffer, or write in chunks of 4 KB or more.
  • Reuse file descriptors, HTTP connections, and database connections.
  • Use sendfile or splice to copy data without pulling it into user space, when you are just moving bytes from a file to a socket.
  • For many tiny I/O operations, look at io_uring, which lets you submit a batch of requests in one syscall. The event loop page has the wider picture.

9. How Errors Come Back

On success, most syscalls return a useful number: bytes written, a new file descriptor, 0. On failure, the kernel returns a negative error code. libc stores the positive version in errno and returns -1 from the wrapper. Python turns those into exceptions such as FileNotFoundError or PermissionError.

CodeNameTypical meaning
EPERM, EACCES1, 13You are not allowed to do that
ENOENT2No such file or directory
EINTR4A signal arrived; retry the call (good libraries do this for you)
EAGAIN / EWOULDBLOCK11 / 11Non-blocking I/O, nothing is ready yet
EPIPE32The other end of the pipe or socket is gone
ECANCELED125The request was cancelled (common with io_uring)

man 2 write documents the syscall. man 3 write documents the libc wrapper. The numbers are in man errno. You do not need to memorize them. You do need to know that a short write (write returned 4 when you asked to write 13) is not an error: you must write the rest. Network sockets do this often.

10. Containers Can Limit Which Calls You Make

The kernel can filter syscalls with seccomp (secure computing). A process provides a short program (a BPF filter) that says "allow," "deny," or "kill" for each syscall number. Docker and Kubernetes apply a default profile that blocks rare and dangerous calls. Your own profile can be tighter.

If a container fails with "operation not permitted" on something that works on your laptop, a syscall filter is one of the first places to look, along with capabilities and AppArmor or SELinux. The page on how containers really work walks through the other walls around a container (namespaces, cgroups, capabilities).

This is the same door as section 1, just with a narrower opening: the process may still enter the kernel, but only for the calls the filter allows.

11. Common Pitfalls

  • One syscall per byte (or per row, or per request). Buffer, batch, or reuse. The lab: 260 ms vs 0.44 ms for the same megabyte.
  • Ignoring short reads and short writes. Loop until you have all the bytes, or use a library that does.
  • Treating every man-page "syscall" as a mode switch. clock_gettime may be a vDSO call. Measure if it matters.
  • Running strace -p on a hot process in production for a long time. It slows the process. Start with -c, or use perf / eBPF.
  • Forgetting -f when the work happens in a child process. The parent looks idle.
  • Busy-looping on EAGAIN without waiting with poll / epoll. You will burn a core. See the event loop page.
  • Not checking errors. A failed close or fsync can mean the last write never hit durable storage.

12. Practice Problems

Problem 1: roughly how much slower?

Using the lab numbers (0.28 ns per add, 66 ns per getpid), how many userspace adds can you do in the time of one getpid?

Answer: 66 / 0.28 ≈ 236 adds (we rounded this to about 240 in the lab write-up).

Problem 2: why is this log line expensive?

def handle(request):
    with open("/var/log/app.log", "a") as f:
        f.write(json.dumps(request) + "\n")
        f.flush()

The handler runs 20,000 times per second. Which syscalls are you paying for on each request, and what is a cheaper shape?

Answer: Each request at least openat, write (maybe more than one), flush (which may call write again), and close. At 20,000 requests per second that is tens of thousands of open/close pairs. Open a logger once at startup (or use the standard logging library with a buffered handler), write to the same fd, and flush on a timer or when the buffer fills, not on every line, unless you have a hard durability requirement.

Problem 3: read the counts

A Python script writes 1 MB with default buffering and /proc/self/io reports syscw: 256. About how many bytes did each write syscall carry, and what would syscw be if the script passed buffering=0?

Answer: 1,048,576 / 256 = 4,096 bytes per write. Unbuffered, syscw would be about 1,048,576, as in the lab (421 ms vs 74 ms).

Problem 4: blocking or not?

A thread calls read on a socket and sits there for 80 ms until a packet arrives. Did this syscall also cause a context switch? Why does that matter for a server with 10,000 waiting clients?

Answer: Yes, almost certainly: the thread had nothing to do, so the kernel ran another thread (or went idle). 10,000 threads each blocked in read means 10,000 stacks and many context switches when data arrives. An event loop uses one (or a few) threads and one epoll_wait (or similar) to wait on all of those sockets at once. That is the subject of the I/O models page.

13. Cheat Sheet

strace -c <cmd>                 # count syscalls for a command
strace -f -c -p <pid>           # attach, include children, summarize
cat /proc/<pid>/io              # syscr / syscw and byte counts
man 2 write                     # the syscall
man 3 write                     # the libc wrapper
man errno                       # error names

# C: one write of a whole buffer, not one write per byte
write(fd, buf, len);

# Python: let buffering work, or write a large chunk
open(path, "wb").write(data)
# unbuffered (usually not what you want on a hot path):
open(path, "wb", buffering=0)

QUIC and HTTP/3

The web still speaks HTTP: a method, some headers, a body. HTTP/3 is the same language on a new transport, QUIC, which runs over UDP instead of TCP. This page explains why that change exists, what it fixes, and what it does not. It builds on TCP, DNS & HTTP, and TLS.

1. The Problem TCP Does Not Fix

TCP gives you a reliable, ordered stream of bytes. HTTP/1.1 used one stream per connection, so a page with many files opened many connections. HTTP/2 put many request/response streams on one TCP connection, which is kinder to the network. But TCP still delivers bytes in order. If packet 5 is lost, packets 6, 7, and 8 wait in the receiver, even if they belong to a completely different image.

That wait is TCP head-of-line (HOL) blocking. HTTP/2 removed HOL blocking at the HTTP layer (one slow response no longer holds up the next on the same connection), then bumped into it again at the TCP layer.

Three other TCP limitations show up on phones and on long paths:

  • Handshake cost. A new TCP connection plus TLS 1.3 takes two or three round trips before the first request gets an answer. The TCP page budgets this.
  • A new IP address is a new connection. Move from Wi-Fi to mobile data and the four-tuple (your IP, your port, server IP, server port) changes. TCP cannot follow you. The connection dies, and TLS starts again.
  • The transport headers are in the clear. A middlebox can see and tinker with sequence numbers and window sizes. That made the internet work in the 1990s. It also made TCP itself hard to change: if you invent a new option, some middlebox may drop the packet.

QUIC's answer: put reliability, streams, and TLS together in user space, carry them over UDP, and encrypt almost everything.

2. Words You Need

  • QUIC. A transport protocol, standardized as RFC 9000 (with TLS in RFC 9001 and recovery in RFC 9002). It provides reliable, ordered streams, congestion control, and encryption. It runs over UDP, usually on port 443.
  • HTTP/3. HTTP semantics (methods, headers, status codes, bodies) over QUIC. It is not a new meaning for GET. It is a new mapping of that meaning onto QUIC streams.
  • Stream. An independent ordered sequence of bytes inside one QUIC connection. One request/response typically gets one stream. Loss on stream 7 does not stall stream 8.
  • Connection ID (CID). A value in the QUIC packet header that identifies the connection, even if the client's IP or port changes.
  • Round trip time (RTT). The time for a packet to go to the other side and for a reply to come back. Many "how long does setup take?" answers are just "this many RTTs."
  • 0-RTT. Sending application data (for example an HTTP request) in the first flight of a resumed connection, without waiting for the handshake to finish. Faster, with a replay risk described below.
  • Head-of-line blocking. A lost piece at the front of a queue holds up everything behind it.
  • Middlebox. A firewall, NAT, or other device between the two ends that may inspect or drop packets.

3. Head-of-Line Blocking, Worked by Hand

Two files share one connection. Each file is two packets. Packet 2, which belongs only to file A, is lost. The one-way delay is 40 ms, and a lost packet is retransmitted after one RTO of 160 ms (we use these same numbers in the lab).

Send order on the wire (packet, which file):
  1:A1   2:B1   3:A2   4:B2
                 ^
                 this packet is lost

TCP / HTTP/2 (one ordered byte stream):
  A1 arrives, B1 arrives, B2 arrives... but the TCP stack
  cannot hand B1 or B2 to HTTP/2 until A2 is retransmitted
  and placed in order. File B waits for file A's loss.

QUIC / HTTP/3 (two streams):
  Stream A waits for A2.
  Stream B delivers B1 and B2 as soon as they arrive.
  The image in file B can render while A is still recovering.

Intuition. TCP is one checkout line at a shop. If the person at the front of the line forgot their wallet, everyone waits. QUIC is one shop with many checkout lines (streams) under one roof (the connection). A delay in one line does not stop the others. The roof still has rules (congestion control) so the shop as a whole does not flood the street.

Two honest limits: QUIC does not make the lost stream itself faster. File A still waits for the retransmission. And if the lost packet was the only packet you needed, there is no other stream to save you. The win is when a page or an API call uses several streams at once, which is the common case in a browser.

4. Why QUIC Runs on UDP

Could we have changed TCP instead? In theory, yes. In practice, TCP is implemented in the kernel, and the path between two hosts is full of devices that expect TCP to look a certain way. A new TCP option may be dropped. A new delivery rule may never be deployed to every kernel your users run.

UDP is a thin envelope: ports, a length, a checksum, and the payload. Middleboxes have to allow UDP for other things (video, VPNs, games, and now HTTP/3). QUIC puts its own packet format and its own reliability inside that payload, in user space. Browsers and servers can ship a new QUIC version without waiting for an operating-system update.

HTTP/2:   HTTP frames  |  TLS  |  TCP  |  IP
HTTP/3:   HTTP frames  |  QUIC (includes TLS 1.3)  |  UDP  |  IP

Because QUIC includes TLS 1.3, there is no "cleartext QUIC" in normal use. Packet numbers, stream data, and most headers are encrypted. A middlebox can still see UDP ports and some connection-ID bytes. It cannot tweak the receive window the way it could with TCP.

The cost of using UDP: some office networks and old firewalls still block UDP on port 443, or treat it badly. Browsers then fall back to HTTP/2 over TCP. That is a feature, not a failure, as long as you do not assume every client will complete an HTTP/3 handshake.

5. 1-RTT and 0-RTT Handshakes

Setup time is measured in round trips. Take an RTT of 80 ms, a long but realistic path between continents, and ignore DNS for a moment (DNS is extra, and is the same for both designs; see the DNS page).

TCP + TLS 1.3, first visit (no connection reuse):
  1. TCP SYN -> SYN-ACK -> ACK              1 RTT
  2. TLS ClientHello -> ServerHello+certs
     + Finished, then the HTTP request      1 RTT
  3. HTTP response starts                   1 more RTT
  Time to first byte of the response:       3 RTT = 240 ms

QUIC + HTTP/3, first visit:
  1. QUIC Initial + TLS ClientHello ->
     Server reply (keys, certs) + handshake
     The HTTP request can go once keys are
     in place, in this same 1-RTT exchange  1 RTT
  2. HTTP response starts                   1 RTT
  Time to first byte:                       2 RTT = 160 ms

QUIC, returning visitor with a session ticket (0-RTT):
  1. Client sends 0-RTT data (the HTTP request)
     along with the first handshake flight
  2. Server answers with the response       1 RTT = 80 ms

The first-visit saving is one RTT (80 ms here). The returning-visitor saving can be another RTT, but only if 0-RTT is accepted. TLS 1.3 on a reused TCP connection can also send 0-RTT data; QUIC's extra win on the first visit is that it does not spend a separate RTT on a TCP handshake.

The 0-RTT catch: replay

0-RTT data is sent before the server has proved that this handshake is fresh. An attacker who captured the first flight can send it again. If the request was GET /style.css, a replay is usually harmless. If the request was POST /pay and the server is not careful, a replay could try to pay twice.

The safe rule, which the TLS page also uses: only send idempotent, replay-safe requests as 0-RTT data (typically GET of public or cacheable resources). Servers should reject 0-RTT for anything with a side effect, or protect those handlers with an idempotency key and replay detection. Browsers already follow this rule for many requests.

6. Connection IDs and a Changing IP

TCP names a connection by the four-tuple of IP addresses and ports. Change one of those, and it is a different connection. QUIC names a connection by a connection ID carried in the packet. The client and server can also agree on new IDs during the connection, so an observer cannot follow a user across networks by a single stable ID.

on Wi-Fi:   client 192.0.2.10:54123  ->  server 203.0.113.5:443
            connection ID  a1b2...

switch to mobile data: the client IP becomes 198.51.100.77
            same connection ID  a1b2...
            the server keeps the stream state, the TLS keys,
            and the HTTP requests that were in flight

This is why a video or a large download can survive walking out of a building, at least when both ends and the path support the change. NAT and firewalls still have to allow the new UDP flow. Connection migration is a QUIC feature, not a guarantee from the network.

7. Streams, Frames, and Loss

A QUIC packet can carry several frames: stream data, acknowledgements, crypto handshake bytes, connection close, and others. Each stream has its own offset, like a private sequence number. If packet 9 is lost and it only held bytes for stream 3, only stream 3 is missing a range. Stream 4's bytes in packet 10 can be delivered as soon as they arrive.

Streams are cheap to open. HTTP/3 typically uses:

  • One bidirectional stream per request/response.
  • A few control streams for settings and QPACK (the HTTP/3 header compressor).
  • Optional unidirectional streams for other control data.

QPACK is designed so a lost header packet does not stall every other request the way HPACK on HTTP/2 could. That was another, quieter form of HOL blocking.

Loss recovery and congestion control still exist. QUIC acknowledgements are richer than classic TCP SACK, and the sender can decide to retransmit quickly. Algorithms such as CUBIC or BBR can run on a QUIC connection the same way they run on TCP (the TCP congestion section is still the right mental model). QUIC does not magically get more bandwidth. It wastes less of the bandwidth you already have when loss is on a different stream than the one the user is waiting for.

8. The Lab: Four Streams, 2% Loss

We wrote a small discrete-event simulation of four parallel responses. Each response is 50 packets (about 60 KB at 1,200 bytes per packet). Packets are sent in round-robin order across the four streams, 0.1 ms apart. The RTT is 80 ms. A lost packet is retransmitted after an RTO of 160 ms (2 × RTT). There is no extra bandwidth limit, on purpose: we wanted to isolate head-of-line blocking, not congestion control.

In the TCP / HTTP/2 model, a packet can be delivered to the application only when every earlier packet on the connection has arrived. In the QUIC model, a packet can be delivered when every earlier packet on its own stream has arrived.

No loss, both designs agree

With zero loss, every stream finished in 59.6 to 59.9 ms in both models: one one-way delay (40 ms) plus a little pacing of the 200 packets. There is nothing for QUIC to fix when nothing is lost.

One seed at 2% loss, told in full

Seed 27 dropped 4 of the 200 packets: stream 1 packet 5, stream 3 packets 10 and 19, and stream 0 packet 22. Stream 2 lost nothing.

Stream 0Stream 1Stream 2Stream 3First stream doneAll done
TCP / HTTP/2208.8 ms208.8 ms208.8 ms208.8 ms208.8 ms208.8 ms
QUIC / HTTP/3208.8 ms202.1 ms59.8 ms207.9 ms59.8 ms208.8 ms

The last stream finished at the same time in both models, 208.8 ms, because the last lost packet needs the same retransmission wait. QUIC does not rewrite physics. What changed is stream 2: it had no loss, so QUIC delivered it in 59.8 ms, the no-loss time. Under TCP, stream 2 sat behind the other streams' losses for an extra 149 ms.

If stream 2 was the CSS or the first JSON response the page needed, the user can go forward 149 ms earlier, even though some images are still recovering.

Twenty random seeds

We repeated the 2% loss run with 20 different seeds.

2% loss223.7 ms74.0 ms223.7 ms (same in both)

At 2% loss, the first usable stream arrived about 3 times earlier with QUIC (74 ms vs 224 ms). At 5% loss the gap is still there, but smaller in ratio, because more streams themselves are hit by loss.

What this lab is not. It is not a speed test of a real browser against a real CDN. It does not model congestion windows, delayed acks, or application-limited senders. It is a microscope on one idea: shared sequence numbers stall everyone; per-stream sequence numbers stall only the victim. The handshake math in section 5 is a separate, real saving that this loss lab does not include.

9. HTTP/3: The Same Meaning, a New Pipe

A GET /index.html still means "give me this resource." Status 304 Not Modified still means "your cache is fine." Cookies, authorization headers, and CORS do not change their meaning. If you know HTTP/1.1 text, you already know HTTP/3's vocabulary. The DNS & HTTP page is the right place for that vocabulary.

What changes is how that message is carried:

  • Headers are compressed with QPACK, not HPACK or gzip of the whole message.
  • Each request lives on its own QUIC stream, not as TCP bytes on a shared connection, and not as a new TCP connection per file.
  • Priorities and server push have a different (and, in practice, more modest) story than early HTTP/2 hopes. Do not plan a product around server push.

For an API you built, "support HTTP/3" usually means "put a load balancer or CDN that speaks HTTP/3 in front, keep your application as HTTP." The application still sees a method, a path, headers, and a body. The load balancing page is the next place to read about that front door.

10. How a Browser Finds HTTP/3

The first visit to a site often still starts over TCP. The server then advertises HTTP/3 in one of two ways:

  • An Alt-Svc header, for example alt-svc: h3=":443"; ma=86400, which says "I also speak HTTP/3 on port 443, remember this for a day."
  • A DNS HTTPS (or SVCB) record that lists alpn=h3,h2 up front, so the browser can start with QUIC on the first visit and skip a wasted TCP attempt.

The DNS page shows a real HTTPS record. If HTTP/3 fails (UDP is blocked, a middlebox eats the packets, the handshake times out), a good client falls back to HTTP/2 or HTTP/1.1 and remembers not to keep trying QUIC for a while.

11. Debugging When UDP Is Blocked

When a site "works on my phone and not on the office Wi-Fi," or a client spends a second then falls back, think about UDP.

# does this host advertise HTTP/3?
dig +short example.com HTTPS
curl -sI --http3 https://example.com     # if your curl was built with HTTP/3
curl -sI --http2 https://example.com     # fallback path

# look for Alt-Svc
curl -sI https://example.com | grep -i alt-svc

# a packet capture (needs permission): UDP port 443
# tcpdump -i any udp port 443

Signs of trouble: lots of QUIC Initial packets and no reply; a long gap then a TCP connection; a corporate firewall that allows TCP 443 only. qlog (a JSON event log some stacks can emit) is the detailed trace, similar in spirit to a TLS key log plus a TCP dump, but built for QUIC events.

Do not block UDP 443 on your own servers if you want HTTP/3 to work. Do keep a TCP listener for the fallback. Health checks should cover both, or you will "prove" the service is up while half of your browsers take the slow path.

12. Common Pitfalls

  • Expecting HTTP/3 to make a single large download much faster on a clean path. With no loss and a warm connection, TCP and QUIC are often close. The big wins are setup time and loss on multiplexed streams.
  • Sending unsafe 0-RTT requests. No POST /pay in 0-RTT without replay protection.
  • Forgetting the UDP fallback. Some networks will always use HTTP/2. Measure both.
  • Assuming a new IP keeps the connection on TCP. Only QUIC connection IDs do that, and only when migration is allowed.
  • Looking at a TCP dump for HTTP/3. You will see UDP. Use a QUIC-aware tool or qlog.
  • Turning on HTTP/3 at a load balancer and checking only TCP health. Test UDP 443 too.
  • Confusing HTTP/3 with a new application protocol. Your handlers, status codes, and auth headers stay the same.

13. Practice Problems

Problem 1: first-byte time

RTT is 40 ms. Ignore DNS and the download itself. How long until the first byte of the response on a first visit with TCP+TLS 1.3, and with QUIC? How about a QUIC 0-RTT resume?

Answer: TCP+TLS 1.3 first visit: 3 × 40 = 120 ms. QUIC first visit: 2 × 40 = 80 ms. QUIC 0-RTT resume: 40 ms.

Problem 2: who waits?

A page fetches four images on one connection. The packet that holds the middle of image 2 is lost. Under HTTP/2 over TCP, which images can be fully delivered before the retransmission arrives? Under HTTP/3?

Answer: Under HTTP/2 over TCP, none of the later packets can be delivered to HTTP/2 until the lost packet is filled in, so images 2, 3, and 4 all wait (image 1 only finishes if every one of its packets was sent and received before the loss). Under HTTP/3, images 1, 3, and 4 can finish as soon as their own packets have arrived; only image 2 waits for the retransmission.

Problem 3: is 0-RTT safe here?

A client wants to retry POST /v1/orders as 0-RTT after a disconnect. The handler creates a paid order. Should the server accept this as 0-RTT data? What should it do instead?

Answer: No. A replay could create a second paid order. Reject 0-RTT for this path (force a 1-RTT handshake) and, separately, require an idempotency key so even a legitimate retry after a lost response does not double-charge. See the retry-storm scenario for the wider retry story.

Problem 4: the lab's honest limit

In the lab, "all streams done" was the same for TCP and QUIC (208.8 ms on seed 27). Someone says "then QUIC did not help." What did it help, and when would "all done" also improve?

Answer: It helped the streams that were not hit by the loss (stream 2 finished in 59.8 ms instead of 208.8 ms). "All done" would also improve if the last stream itself had no loss, or if you care about a metric like "time until the first needed resource," not "time until every resource is here." Handshake savings (section 5) improve even a single-stream first visit, which this loss lab does not measure.

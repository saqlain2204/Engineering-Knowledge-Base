Load Balancing & Reverse Proxies

One server can only do so much. To serve more users, and to survive when a server dies, we run many copies of an app and put something in front that spreads the requests. That "something" is a load balancer. This page explains how load balancers decide where each request goes, how they notice broken servers, and the mistakes that cause real outages. We compare balancing rules with a small simulation you can run. It builds on TCP, DNS & HTTP (which has a short overview of proxies) and TLS.

1. Why We Need Load Balancers

Say one copy of your API can handle 200 requests per second (rps). At lunch time you get 900 rps. You start 5 copies. Now you have three problems:

  1. One address. Users only know api.example.com. Something must turn one address into five servers.
  2. Fair sharing. If 600 rps go to one copy and 75 to each of the others, the busy one falls over while the others relax.
  3. Failure. When one copy crashes, requests must stop going to it within seconds.

A load balancer solves all three. It also becomes a natural place for shared jobs: TLS, logging, rate limits, and safe deploys.

                       ┌──────────► app-1  10.0.1.11:8080
  clients ──► LB  ─────┼──────────► app-2  10.0.1.12:8080
   (one address:       ├──────────► app-3  10.0.1.13:8080
   api.example.com)    └──────────► app-4  10.0.1.14:8080   (the "backends" or "upstreams")

Words: the servers behind the load balancer are called backends, upstreams, or targets. The group of them is a pool (nginx calls it an upstream block; AWS calls it a target group).

2. Proxies: Forward and Reverse

A proxy is a program that sits in the middle of a conversation and passes messages along. There are two kinds, and the difference is who it works for.

Forward proxyReverse proxy
Works forThe clientsThe servers
Who knows it existsThe client is set up to use itThe client thinks it is the server
Typical usesCompany web filter, caching for an office, hiding the client's addressLoad balancing, TLS, caching for a website, routing /api and /images to different apps
ExamplesSquid, a corporate HTTP proxynginx, HAProxy, Envoy, Traefik, AWS ALB, Kubernetes Ingress controllers

A load balancer is a reverse proxy that spreads requests over many backends. In daily speech the two words are used almost the same way.

Intuition. A reverse proxy is the receptionist at a big office. Visitors talk only to the receptionist. The receptionist decides which person inside should help, walks the question over, and brings back the answer. Visitors never learn the inside room numbers.

3. Layer 4 vs Layer 7

The "layer" says how much of the traffic the load balancer understands (see where TCP fits).

Layer 4 (transport)Layer 7 (application)
SeesIP addresses and ports only. The data is just bytes.Full HTTP requests: method, path, headers, cookies.
Decides perConnection. All bytes of one TCP connection go to the same backend.Request. Each HTTP request can go to a different backend.
Can route by path or headerNoYes: /api/* to the API, /static/* to a file server
TLSUsually passes it through untouchedUsually decrypts it (TLS termination) so it can read the request
SpeedVery fast, very cheapMore CPU per request
ExamplesAWS NLB, Linux IPVS, Kubernetes Services (kube-proxy), HAProxy in TCP modeAWS ALB, nginx, Envoy, HAProxy in HTTP mode, Ingress controllers

What actually happens with a Layer 7 proxy

A Layer 7 proxy uses two separate TCP connections: one from the client to the proxy, and one from the proxy to the backend. It reads a full request from the first, picks a backend, and writes the request to the second.

client ══TCP+TLS══► proxy ══TCP══► app-2
          conn #1    reads "GET /orders/42"
                     picks app-2 (least busy)
                     reuses an idle keep-alive conn #2 to app-2

The backend sees the proxy's IP address as the source, not the client's. We fix that with headers in section 10. TLS at the proxy is covered in TLS at load balancers.

4. Balancing Rules, One by One

Each new connection (Layer 4) or request (Layer 7) needs a backend. These are the common rules:

RuleHow it picksGoodBad
RandomAny backend, at randomNeeds no memory or shared stateBad luck piles requests onto one server for a while
Round robin1, 2, 3, 4, 1, 2, 3, 4...Simple, even count of requestsIgnores how busy each server is and how long each request takes
Weighted round robinLike round robin, but a weight-2 server gets twice as many turnsMixed machine sizesWeights are set by hand and go stale
Least connections (least outstanding requests)The backend with the fewest requests in progress right nowAdapts to slow servers and slow requestsNeeds an exact count; with many load balancers, each sees only its own traffic
Power of two choicesPick 2 backends at random; send to the one with fewer requests in progressAlmost as good as least connections, cheap, works well with many load balancersSlightly worse than a perfect least-connections choice
Hash (of client IP, cookie, or URL)The same key always goes to the same backendCaches and sticky sessionsHot keys overload one backend; see section 9

Worked example: least connections

Four backends have this many requests in progress: [3, 1, 4, 1]. A new request arrives.

  • Round robin (last one used was backend 2): goes to backend 3, which has 4 already. Now [3, 1, 5, 1].
  • Least connections: backends 2 and 4 tie at 1; pick one, say backend 2. Now [3, 2, 4, 1].
  • Power of two choices: pick 2 at random, say backends 1 and 3 (counts 3 and 4); send to backend 1. Now [4, 1, 4, 1]. Not perfect, but it avoided the worst one.

5. A Simulation: Which Rule Wins?

We simulated 10 backends. Each handles one request at a time (extra requests wait in its queue). A request takes 50 ms of work on average, with natural variation (some take 5 ms, some 200 ms). Requests arrive at random times at 90% of the total capacity. We sent 200,000 requests through each rule. Run it yourself with python3 lbsim.py:

# lbsim.py - compare load-balancing rules on 10 servers.
# Each server does one request at a time; extra requests wait in its queue.
import heapq, random

def simulate(rule, slow=(), n_servers=10, load=0.9, n_req=200_000, seed=1):
    rng = random.Random(seed)
    speed = [1/3 if i in slow else 1.0 for i in range(n_servers)]
    mean_work = 0.050                            # 50 ms of work on a normal server
    rate = load * sum(speed) / mean_work         # arrivals per second (90% of capacity)
    free_at = [0.0] * n_servers                  # when each server finishes its queue
    open_reqs = [0] * n_servers                  # requests sent but not finished
    ends = []                                    # heap of (finish time, server)
    t, rr, lat = 0.0, 0, []
    for _ in range(n_req):
        t += rng.expovariate(rate)               # next request arrives
        while ends and ends[0][0] <= t:          # forget requests that already finished
            open_reqs[heapq.heappop(ends)[1]] -= 1
        if rule == "random":
            s = rng.randrange(n_servers)
        elif rule == "round robin":
            s = rr % n_servers; rr += 1
        elif rule == "least connections":
            fewest = min(open_reqs)
            s = rng.choice([i for i, n in enumerate(open_reqs) if n == fewest])
        elif rule == "power of two choices":
            a, b = rng.sample(range(n_servers), 2)
            s = a if open_reqs[a] <= open_reqs[b] else b
        start = max(t, free_at[s])               # wait for the server to be free
        free_at[s] = start + rng.expovariate(1 / mean_work) / speed[s]
        heapq.heappush(ends, (free_at[s], s)); open_reqs[s] += 1
        lat.append(free_at[s] - t)
    lat.sort()
    return lat[len(lat) // 2] * 1000, lat[int(0.99 * len(lat))] * 1000

for slow in [(), (0,)]:
    print("server 0 is 3x slower" if slow else "all 10 servers equal")
    for rule in ["random", "round robin", "least connections", "power of two choices"]:
        p50, p99 = simulate(rule, slow)
        print(f"  {rule:21s} p50 {p50:8.0f} ms   p99 {p99:10.0f} ms")

Results

all 10 servers equal
  random                p50      325 ms   p99       1908 ms
  round robin           p50      195 ms   p99       1243 ms
  least connections     p50       70 ms   p99        381 ms
  power of two choices  p50      123 ms   p99        510 ms
server 0 is 3x slower
  random                p50      245 ms   p99    1585876 ms
  round robin           p50      145 ms   p99    1631778 ms
  least connections     p50       75 ms   p99        511 ms
  power of two choices  p50      134 ms   p99        858 ms

(p50 is the median time a request took, waiting plus working. p99 means 99% of requests were faster than this.)

What the numbers teach

  • Even with identical servers, the rule matters a lot. Random lets queues form by bad luck: p99 is 1.9 s. Least connections sends work to whoever is free: p99 is 0.38 s, five times better.
  • Round robin beats random, because it spreads the count evenly. But it is blind to the fact that some requests are 4 times longer than others.
  • Power of two choices gets most of the benefit by looking at only 2 servers. That is why Envoy's "least request" mode uses it by default.
  • One slow server breaks random and round robin completely. Their p99 is about 1,600,000 ms, which is 27 minutes. The next section shows why.

Limits of this model. Real servers handle several requests at once, and real traffic is burstier. The exact numbers will differ, but the ranking (least-busy rules beat blind rules, and the gap grows when servers differ) is what you see in production.

6. One Slow Server: the Math

Why did one slow server make round robin's waits explode? Do the math by hand:

  1. A normal server does one 50 ms request at a time: 1 / 0.05 = 20 rps. The slow one is 3× slower: 6.7 rps.
  2. Total capacity: 9 × 20 + 6.7 = 186.7 rps. We send 90% of that: 168 rps.
  3. Round robin gives each server 1/10 of the traffic: 16.8 rps each.
  4. The slow server gets 16.8 rps but can finish only 6.7 rps. Its queue grows by about 10 requests every second, forever.
  5. After 20 minutes the queue holds about 12,000 requests. A new request must wait for all of them: 12,000 × 150 ms = 1,800 s. That matches the 27-minute p99.

Meanwhile the other 9 servers are only at 16.8 / 20 = 84% busy. The fleet has spare capacity, but the blind rule cannot use it. Least connections notices that the slow server's count keeps climbing and stops sending to it.

Intuition. Round robin is like a supermarket manager who sends every 10th customer to lane 1, even though the cashier in lane 1 is a trainee. The line at lane 1 goes out the door while other cashiers stand idle. Customers choosing the shortest line (least connections) fix it on their own.

In real life, "one slow server" happens all the time: a noisy neighbor on the same host, a bad disk, a garbage collection pause, a node with throttled CPU (see container CPU throttling), or a new pod with a cold cache.

7. Health Checks

A load balancer must stop sending to dead backends. There are two ways to find them.

Active health checks

The load balancer itself asks each backend every few seconds, for example GET /healthz, and expects a 200. Typical settings:

interval            5s     # ask every 5 seconds
timeout             2s     # no answer in 2 s counts as a failure
unhealthy_threshold 3      # 3 failures in a row: remove the backend
healthy_threshold   2      # 2 successes in a row: add it back

Worked example: how many errors before removal?

A backend crashes right after passing a check. Checks run at 5 s, 10 s and 15 s after the crash, and each fails. After the third failure the backend is removed. So for about 15 s it still gets traffic. At 500 rps spread over 10 backends, it gets 50 rps: 15 × 50 = about 750 failed requests.

Making the interval smaller helps, but costs more check traffic. That is why we add passive checks.

Passive health checks (outlier detection)

The load balancer watches real traffic. If a backend refuses connections or returns errors several times in a row, it is taken out for a while. In nginx, max_fails=3 fail_timeout=10s does this. Envoy calls it outlier detection. Passive checks react within a few requests instead of 15 seconds.

What should a health check test?

  • Too shallow: "the process is running". A server stuck in a deadlock still passes.
  • Too deep: "the database answered". If the database has a short hiccup, every backend fails its check at once, the load balancer removes all of them, and a small problem becomes a full outage.
  • Good: "this process can serve requests": its own threads and event loop respond, and it has finished starting. Report dependency problems in metrics, not in the health check. Kubernetes splits this into liveness and readiness probes (see probes and rollouts).

When removing a backend on purpose (a deploy), first stop sending it new requests, then let in-flight ones finish: connection draining. Getting this wrong causes 502s on every release; the full story is in Scenario: Errors During Every Deploy.

8. Timeouts and Retries

A proxy has several separate timeouts. Each answers a different question:

TimeoutQuestionTypical value
ConnectHow long to wait for the TCP handshake to a backend?1 to 3 s (a healthy backend in the same data center answers in under 1 ms)
Read / responseAfter sending the request, how long to wait for the reply?Slightly above your slowest normal request
Idle (keep-alive)How long to keep an unused connection open for reuse?60 s or so; the side that receives requests must wait longer than the side that sends them

When is a retry safe?

If a backend fails, the proxy can try another one. But only when the first backend surely did not act on the request, or when acting twice is harmless:

  • Connection refused or connect timeout: the request was never sent. Safe to retry anywhere.
  • Error after the request was sent (reset, read timeout): the backend may have done the work. Retry only if the request is idempotent (doing it twice has the same effect as once: GET, PUT, DELETE), or if it carries an idempotency key. See HTTP methods and idempotency.

Retry storms

Retries multiply load. Suppose the client retries 3 times, the load balancer retries 3 times, and the app retries its database call 3 times. One user request can become 3 × 3 × 3 = 27 database calls, exactly when the database is struggling. Rules: retry at one layer, add random delay between tries (jitter), and use a retry budget (for example, retries may add at most 10% extra traffic). The slow API scenario shows a storm in action, and the retry-storm scenario measures how a queue cap and a retry policy change the success rate.

9. Sticky Sessions and Hashing

Sometimes we want the same user to reach the same backend every time. This is called session affinity or sticky sessions.

  • Why: the backend keeps something in memory for that user: a login session, a shopping cart, a WebSocket, or a warm cache.
  • How: the load balancer sets a cookie naming the backend (SERVERID=app-3), or hashes the client IP.
  • The cost: load is no longer spread by the balancing rule. One very busy customer can overload one server. When a server dies, all its users lose their sessions.

Better: keep sessions in a shared store (Redis, a database) or in a signed cookie, so any backend can serve any request. Then stickiness is only an optimization, not a requirement.

Hashing and adding servers

Simple hashing picks backend = hash(key) % N. If N changes from 4 to 5, most keys move to a different backend (about 80% of them), and every cache goes cold at once. Consistent hashing moves only about 1/N of the keys. It is explained with a real experiment in Replication & Sharding.

10. Who Is the Real Client? X-Forwarded-For

Behind a Layer 7 proxy, every request reaches the app from the proxy's IP address. The app still needs the real client address for logs, rate limits and fraud checks. Proxies add headers:

X-Forwarded-For: 203.0.113.7, 10.0.0.5     # client, then each proxy it passed
X-Forwarded-Proto: https                   # the client used HTTPS (the proxy-to-app hop may be HTTP)
X-Forwarded-Host: api.example.com
Forwarded: for=203.0.113.7;proto=https      # the standard version (RFC 7239)

Each proxy appends the address it received the connection from.

Security trap. Anyone can send a fake X-Forwarded-For: 1.2.3.4. Only trust the entries added by your own proxies. If you have one proxy in front, the real client is the last entry added by that proxy, which is the right-most one. Reading the left-most entry lets attackers pick any IP they like and skip your rate limits.

A Layer 4 load balancer cannot add HTTP headers. It can either keep the client's IP as the packet's source (some cloud NLBs do this) or use the PROXY protocol, a short line sent at the start of the TCP connection that carries the original addresses.

11. An nginx Config, Line by Line

upstream orders_api {
    least_conn;                                   # rule: fewest active requests
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.13:8080 max_fails=3 fail_timeout=10s weight=2;   # a bigger machine
    keepalive 32;                                 # keep up to 32 idle connections per worker
}

server {
    listen 443 ssl;
    server_name api.example.com;
    ssl_certificate     /etc/ssl/api.crt;
    ssl_certificate_key /etc/ssl/api.key;

    location / {
        proxy_pass http://orders_api;
        proxy_http_version 1.1;                   # needed for keep-alive to backends
        proxy_set_header Connection "";           # ... together with this line
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 2s;
        proxy_read_timeout 30s;
        proxy_next_upstream error timeout;        # retry another backend on these errors
        proxy_next_upstream_tries 2;              # at most 2 backends per request
    }
}
  • upstream is the pool. least_conn chooses the rule; without it nginx uses weighted round robin.
  • max_fails=3 fail_timeout=10s is a passive health check: 3 failures within 10 s mark the server down for 10 s. (Active checks need nginx Plus, or a different proxy such as HAProxy or Envoy.)
  • weight=2: this server gets twice the share.
  • keepalive 32 plus the two proxy_http_version/Connection lines reuse TCP connections to backends instead of opening a new one per request. This saves a handshake each time and avoids running out of ports (lots of short connections leave many sockets in TIME_WAIT).
  • ssl_certificate: TLS ends here. Traffic to the backends is plain HTTP on a private network (or re-encrypted, if you need encryption inside too).
  • proxy_next_upstream error timeout: on a connection error or timeout, try the next backend. Since nginx 1.9.13, requests like POST are not retried by default if they were already sent, which protects you from double actions.

12. Scenario: All gRPC Traffic Hits One Pod

A team moves a service from REST to gRPC on Kubernetes. They have 6 pods. The dashboard shows one pod at 95% CPU and five pods nearly idle. Scaling to 12 pods changes nothing.

Why

  1. gRPC runs on HTTP/2. HTTP/2 sends many requests over one long-lived TCP connection (this is called multiplexing).
  2. A Kubernetes Service (kube-proxy) is a Layer 4 load balancer. It picks a pod once, when the connection opens (see Kubernetes Services).
  3. The client opened one connection at startup. So every request for hours goes to the pod chosen at that moment. New pods never receive anything.

With REST over HTTP/1.1, clients open many connections, so per-connection balancing looked fine by accident.

Fixes

  • Layer 7 balancing: put an HTTP/2-aware proxy in the path (Envoy, Linkerd, Istio, or a gRPC-aware Ingress), which balances each request.
  • Client-side balancing: use a headless Service so DNS returns all pod IPs, and let the gRPC client open a connection to each pod and spread requests (round_robin policy).
  • Recycle connections: set the server's MAX_CONNECTION_AGE (for example 5 minutes), so clients reconnect and get re-balanced. This is a simple partial fix.

The same trap appears with WebSockets, database connection pools, and any long-lived connection behind a Layer 4 balancer.

13. Across Regions: DNS and Anycast

Load balancers inside one data center are not enough for a worldwide service. Two tools spread users across regions:

  • DNS-based balancing (GeoDNS): the DNS server returns a different IP depending on where the user is: Mumbai users get the Mumbai load balancer. Health checks remove a dead region from DNS answers. The catch is TTL: clients cache answers, so a failover takes at least one TTL to reach everyone (see DNS TTLs).
  • Anycast: many locations announce the same IP address. Internet routing sends each user to the nearest one. Failover is fast because routes change in seconds. Cloudflare, Google's global load balancer, and the DNS root servers use anycast.
user in Chennai ──DNS──► "api.example.com = 13.200.1.1"  (Mumbai LB)
                    └──► Mumbai LB ──► Mumbai pods
user in Berlin  ──DNS──► "api.example.com = 3.120.5.5"   (Frankfurt LB)
                    └──► Frankfurt LB ──► Frankfurt pods

14. Practice Problems

Answers follow each one.

Problem 1: Layer 4 or Layer 7?

For each, choose: (a) send /api/* to one service and /blog/* to another; (b) balance a PostgreSQL read pool; (c) block requests whose User-Agent is a known bad bot; (d) pass end-to-end encrypted traffic you are not allowed to decrypt.

Answer: (a) L7, needs the path. (b) L4, the database protocol is not HTTP. (c) L7, needs a header. (d) L4, TLS passthrough; an L7 proxy would have to decrypt.

Problem 2: weights

You have 2 servers that each handle 100 rps and 1 server that handles 300 rps. Traffic is 400 rps. What happens with plain round robin? What weights fix it?

Answer: Round robin sends 400 / 3 = 133 rps to each. The two small servers can do only 100, so they overload and their queues grow. Use weights proportional to capacity: 1, 1, 3. Shares become 80, 80 and 240 rps: each server at 80% busy.

Problem 3: health check math

Checks run every 10 s with an unhealthy threshold of 2. Traffic is 1,200 rps over 8 backends. One backend freezes. About how many requests fail before it is removed? How could you lower that number without checking more often?

Answer: Up to 2 × 10 = 20 s of traffic. It gets 1,200 / 8 = 150 rps, so about 20 × 150 = 3,000 failed requests (fewer if timeouts are retried elsewhere). Lower it with passive checks (outlier detection), which notice errors in real traffic within a few requests, and with safe retries of connect failures.

Problem 4: real client IP

Your app sits behind exactly one trusted proxy. A request arrives with X-Forwarded-For: 6.6.6.6, 198.51.100.20. Which is the real client, and what is 6.6.6.6?

Answer: Your proxy appended the address it saw, which is the right-most entry: 198.51.100.20 is the real client. 6.6.6.6 was in the header the client sent, so it may be fake. Never use it for rate limits or security decisions.

Problem 5: why did scaling not help?

A WebSocket chat service runs behind a Layer 4 load balancer with 4 servers, all busy. You add 4 more servers. An hour later the new servers have almost no connections. Why, and what would you do?

Answer: WebSockets are long-lived connections. An L4 balancer only chooses a server when a connection opens, and existing users stay connected for hours. Only new connections go to the new servers (and with round robin, only half of them). Use least-connections so new connections prefer the empty servers, and ask some clients to reconnect slowly over time (close a few percent of old connections per minute) to rebalance.

15. Common Pitfalls

  • Round robin with unequal servers or requests. One slow server can build an endless queue (our simulation: 27 minutes at p99). Prefer least connections or power of two choices.
  • Health checks that test the database. One database blip removes every backend at once.
  • Retries at every layer. 3 × 3 × 3 = 27 times the load during an outage. Retry at one layer, with jitter and a budget.
  • Retrying non-idempotent requests after they were sent: double payments.
  • Trusting the left-most X-Forwarded-For. Attackers choose it.
  • Long-lived connections behind Layer 4. gRPC, WebSockets and connection pools stick to one backend.
  • No keep-alive to backends. A new TCP (and maybe TLS) handshake per request wastes time and fills TIME_WAIT.
  • Idle timeout mismatch. If the backend closes idle connections before the proxy does, the proxy sometimes sends a request on a connection that was just closed: random 502s.
  • The load balancer as a single point of failure. Run at least two, with a shared virtual IP or a managed cloud LB.

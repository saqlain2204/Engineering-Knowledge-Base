DNS & HTTP: From a Name to a Web Page

What really happens between typing a web address and seeing the page: how a name becomes an IP address, and what the browser and server say to each other. The DNS answers and HTTP headers on this page come from real lookups and requests made on 17 November 2026.

1. The Big Picture

You type https://engineering.msaqlain.com/ and press Enter. Roughly six things happen:

  1. Parse the URL         "https", host "engineering.msaqlain.com", path "/"
  2. DNS lookup            host name  -->  IP address          (this page)
  3. TCP connection        3-way handshake to IP, port 443      (TCP page)
  4. TLS handshake         check certificate, agree on keys     (TCP page)
  5. HTTP request/reply    "GET /"  -->  "200 OK" + HTML         (this page)
  6. Render                parse HTML, fetch CSS/JS/images (more HTTP requests), draw

Steps 3 and 4, plus the speed of each step, are covered in TCP Deep Dive (see its page-load budget). This page covers the two "language" layers around them: DNS, which finds the server, and HTTP, which is what you say once you reach it.

Two words first:

  • An IP address is the number that identifies a machine on the internet, like a phone number. IPv4 looks like 104.20.23.154. IPv6 is longer, like 2606:4700::6810:84e5. (Full details: IP Addressing, Subnetting & Routing.)
  • A port picks which program on that machine you want, like an extension number. HTTPS uses port 443, plain HTTP uses 80, and DNS uses 53.

2. Reading a URL

  https://user@shop.example.com:8443/orders/42?sort=new&page=2#reviews
  \___/   \__/ \______________/ \__/\________/\________________/\______/

PortOptional. Default 443 for https, 80 for httpUsed to connect

Special characters are written with percent-encoding: a space becomes %20. That is why a folder named AI Engineer shows up in a link as AI%20Engineer.

3. Why DNS Exists

Computers connect using IP addresses. People remember names. The Domain Name System (DNS) is the internet's phone book: it turns a name like github.com into an address like 140.82.112.3.

Names also let the owner change servers without telling anyone. The address behind a name can change every day. Big sites even hand out different addresses to different users, to send each one to a nearby or less busy server.

In the 1970s, every computer on the early internet had one shared file, HOSTS.TXT, copied from a central server. It did not scale. DNS (1983) replaced it with a distributed database: no single server knows every name. Each part of the name is managed by someone different. Your machine still has a tiny leftover of the old idea: the /etc/hosts file, which is checked before DNS.

4. The DNS Tree

Read a domain name from right to left. Each dot is a step down a tree.

                               . (root)
                 /               |                 \
              com               org                 in       <- top-level domains (TLDs)
            /     \               |               /    \
       github    msaqlain     wikipedia        co      gov    <- second level
                    |                           |
               engineering                   example          <- subdomain
                                              (example.co.in)

  "engineering.msaqlain.com." = engineering -> msaqlain -> com -> . (root)

The full name really ends with a dot for the root: engineering.msaqlain.com. Browsers hide it.

  • A zone is a part of the tree managed by one owner. The com zone is run by a registry. The msaqlain.com zone is run by whoever owns that domain.
  • An authoritative name server is a server that holds the official answers for a zone. It does not guess or remember; it simply knows.
  • Each level delegates to the next: the com servers do not know the address of github.com, but they know which servers are authoritative for github.com and point you there.
  • There are 13 named root server addresses (a.root-servers.net to m.root-servers.net). Each one is really hundreds of machines around the world sharing one address, a trick called anycast. Your packets reach the nearest copy.

5. A Lookup, Step by Step

Three kinds of DNS programs take part:

  • Stub resolver: a tiny client inside your operating system. It just asks one server and waits.
  • Recursive resolver: the server that does the real work and remembers answers. Your home router, your internet provider, or a public one like 1.1.1.1 (Cloudflare) or 8.8.8.8 (Google).
  • Authoritative servers: root, TLD, and the domain's own servers.

Here is a full lookup of www.github.com when nothing is cached yet:

  your laptop               recursive resolver                 the DNS tree
  (stub)                    (e.g. 1.1.1.1)
     |  1. www.github.com A?      |
     |--------------------------> |  2. www.github.com A?
     |                            |-------------------------------> root server
     |                            |  3. "I don't know. Ask com: a.gtld-servers.net"
     |                            |<-------------------------------
     |                            |  4. www.github.com A?
     |                            |-------------------------------> com TLD server
     |                            |  5. "Ask github's servers: ns-1283.awsdns-32.org ..."
     |                            |<-------------------------------
     |                            |  6. www.github.com A?
     |                            |-------------------------------> github.com authoritative
     |                            |  7. "www.github.com is an alias (CNAME) for github.com,
     |                            |      and github.com A 140.82.112.3, short TTL"
     |                            |<-------------------------------
     |  8. 140.82.112.3           |  (saves the answer in its cache)
     |<-------------------------- |

Two different styles of asking happen here:

  • Your laptop sends a recursive query: "please give me the final answer, do whatever it takes."
  • The resolver sends iterative queries: each server only says "I don't know, but ask that one", and the resolver walks down the tree itself.

A cold lookup takes 3 or more round trips from the resolver. That is slow (often 50 to 200 ms). So caching (section 7) is what makes DNS feel instant. In real life the root and com answers are almost always already cached, so most lookups go straight to step 6, or are answered from the cache at step 1.

Where your machine looks, in order

  1. The browser's own DNS cache (Chrome: chrome://net-internals/#dns).
  2. The operating system: /etc/hosts, then its own cache (for example systemd-resolved on Linux).
  3. The recursive resolver listed in /etc/resolv.conf or your network settings.

Try it yourself

# Ask your normal resolver
dig github.com A
nslookup github.com

# Ask a specific resolver
dig @1.1.1.1 github.com A

# Watch the whole walk from the root, like the diagram above
dig +trace www.github.com

# Short answer only
dig +short gmail.com MX

No dig installed? Use DNS over HTTPS with plain curl. This is how the answers in the next section were collected:

curl -s -H 'accept: application/dns-json' \
  'https://cloudflare-dns.com/dns-query?name=www.github.com&type=A'

6. Record Types, With Real Answers

A DNS zone is a list of resource records. Each record has a name, a type, a TTL (how long it may be cached, in seconds), and data.

TypePlain meaningExample answer (real lookups on 17 Nov 2026, unless marked "typical")
AName to IPv4 addressexample.com. 89 A 104.20.23.154 and 172.66.147.243
AAAAName to IPv6 addressTypical: AAAA 2606:4700::6810:84e5
CNAME"This name is an alias. Look up that other name instead."www.github.com. 3392 CNAME github.com. then github.com. 37 A 140.82.112.3
NSWhich servers are authoritative for this zoneexample.com. 82500 NS hera.ns.cloudflare.com.
MXWhere to deliver email. Lower number = try firstgmail.com. MX 5 gmail-smtp-in.l.google.com., then 10, 20, 30, 40 (backups)
TXTFree text. Used for proof of domain ownership and email security (SPF, DKIM, DMARC)Typical: "v=spf1 include:_spf.google.com ~all"
SOA"Start of authority": facts about the zone, including how long to cache a "no such name" answerexample.com SOA ends in ... 10000 2400 604800 1800; the last number, 1800 s, is the negative-cache time
CAAWhich certificate authorities may issue HTTPS certificates for this nameTypical: 0 issue "letsencrypt.org"
HTTPS / SVCBNewer: tells the browser up front that the site supports HTTP/3 and other options, saving a round tripcloudflare.com. 300 HTTPS 1 . alpn=h3,h2 ipv4hint=104.16.132.229,...

Things worth noticing in these real answers:

  • example.com returned two A records. The client may pick either. This spreads load and gives a backup if one fails.
  • www.github.com is a CNAME with a long TTL (3,392 s, cached nearly an hour), but the final A record has a very short TTL (37 s). GitHub can move github.com to another IP within a minute, while the alias rarely changes.
  • NS records often have long TTLs (82,500 s, almost a day), because the list of name servers almost never changes.
CNAME rule: a name that has a CNAME cannot have any other record. That is why the bare domain (example.com, called the apex) usually cannot be a CNAME: it must also have NS and SOA records. DNS providers work around this with "ALIAS" or "CNAME flattening", which look up the target for you and serve plain A records.

7. TTL and Caching

TTL (time to live) is how many seconds a resolver may keep an answer before it must ask again. When a resolver hands you a cached answer, it counts the TTL down. That is why the real answer above said 89 seconds: it had been cached for a while already.

Worked example: how long until a change is seen?

Your A record has TTL 3600 (1 hour). At 10:00 you change the IP from 203.0.113.10 (old server) to 198.51.100.20 (new server).

  • A resolver that cached the old answer at 09:59 keeps serving the old IP until 10:59.
  • A resolver that never cached it sees the new IP right away.
  • So the worst case is that some users reach the old server until 10:00 + TTL = 11:00.

Rule: a DNS change takes up to the old TTL to reach everyone. The word "propagation" makes it sound like the change spreads out. It does not. Old copies simply expire. (A few badly behaved resolvers and apps ignore TTLs and keep answers longer, so keep the old server running a bit past the TTL.)

Choosing a TTL

TTLGood forCost
30 to 300 sRecords you may need to change fast (failover, migrations)More queries, slightly slower first visits
3600 s (1 hour)Most normal recordsA change takes up to an hour
86400 s (1 day)Records that almost never change (NS, MX)Mistakes take a day to undo

Negative caching

"This name does not exist" is cached too, for the time given in the zone's SOA record (1,800 s in the real answer above). If you look up a name before you create it, resolvers may keep saying "does not exist" for 30 minutes after you create it. Create records first, then test.

8. DNS in Practice: Transport, Privacy, Failures, Kubernetes

How DNS travels

  • Classic DNS uses UDP port 53: one small packet out, one back, no handshake. If the answer is too big, the server sets a "truncated" flag and the client retries over TCP port 53.
  • Classic DNS is not encrypted. Anyone on the network path can see which names you look up, and could fake answers.
  • DNS over HTTPS (DoH) and DNS over TLS (DoT, port 853) encrypt the query between you and the resolver. Modern browsers can use DoH by default.
  • DNSSEC adds digital signatures to records, so a resolver can prove an answer really came from the zone owner and was not changed. (The "AD": true flag in the real example.com answer means the resolver checked those signatures.)

When DNS fails

ResultMeaningUsual cause
NXDOMAINThe name does not existTypo, record not created yet, wrong search domain
NOERROR but no answerThe name exists but has no record of this type (often called NODATA)Asking for AAAA when only A exists
SERVFAILThe resolver could not get a good answerAuthoritative servers down, broken DNSSEC signatures
TimeoutNo reply at allFirewall blocks port 53, resolver overloaded

A saying among engineers is "It's always DNS." Many big outages started with a bad DNS change, because almost everything depends on it and caches hide mistakes for a while.

Kubernetes: the ndots trap

Inside a Kubernetes pod, /etc/resolv.conf usually looks like this:

nameserver 10.96.0.10
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

ndots:5 means: "if a name has fewer than 5 dots, first try it with each search domain added on the end." api.example.com has 2 dots, so a lookup tries, in order:

api.example.com.default.svc.cluster.local   -> NXDOMAIN
api.example.com.svc.cluster.local           -> NXDOMAIN
api.example.com.cluster.local               -> NXDOMAIN
api.example.com                             -> the real answer

That is 4 lookups instead of 1, and twice that if the app asks for both A and AAAA. Under heavy traffic, this can overload the cluster DNS (CoreDNS) and add latency to every outgoing call. Fixes: write external names with a trailing dot (api.example.com.), which means "this is already complete"; lower ndots in the pod's dnsConfig; or run NodeLocal DNSCache.

9. HTTP Messages

Once connected, the browser and server speak HTTP (HyperText Transfer Protocol). The model is simple: the client sends a request, the server sends back a response. Every request stands alone, so HTTP is called stateless: the server does not have to remember earlier requests.

Here is a real exchange, printed with curl -v https://example.com/ (lines with > are sent, < are received):

> GET / HTTP/2                         <- request line: method, path, version
> Host: example.com                    <- headers: name: value
> User-Agent: curl/8.14.1
> Accept: */*
>                                      <- blank line ends the headers
< HTTP/2 200                           <- status line: version, status code
< date: Tue, 17 Nov 2026 08:48:38 GMT
< content-type: text/html; charset=utf-8
< server: cloudflare
< last-modified: Mon, 16 Nov 2026 00:30:20 GMT
< age: 7
< cf-cache-status: HIT
< alt-svc: h3=":443"; ma=86400
<
<!doctype html> ...                    <- body (the HTML)

The parts of every HTTP message:

  1. Start line. Request: method + path + version. Response: version + status code.
  2. Headers. Extra facts as Name: value lines. Names are not case sensitive.
  3. Blank line.
  4. Body (optional). The HTML, JSON, image, or form data.

In HTTP/1.1 this is literally plain text sent over the connection. HTTP/2 and HTTP/3 send the same information in a compact binary form (and header names are lowercase, as above), but the meaning is identical. Learn the text form and you understand all versions. See the TCP page for why HTTP/2 and HTTP/3 exist.

Notice alt-svc: h3=":443"; ma=86400: the server says "I also speak HTTP/3 on port 443, remember this for a day." The next visit can use HTTP/3. See QUIC and HTTP/3 for how that transport works, and for the DNS HTTPS record that can advertise it on the first visit.

10. Methods, Safety, and Idempotency

The method says what you want to do with the resource.

MethodPurposeSafe?Idempotent?Has body?
GETRead a resourceYesYesNo
HEADLike GET, but headers onlyYesYesNo
POSTCreate something, or run an actionNoNoYes
PUTReplace the resource with this exact contentNoYesYes
PATCHChange part of a resourceNoNot by defaultYes
DELETERemove the resourceNoYesUsually no
OPTIONSAsk what is allowed (used by browsers for CORS checks)YesYesNo
  • Safe means the request does not change anything on the server. Crawlers and prefetchers may send safe requests freely.
  • Idempotent means sending it once or ten times leaves the server in the same state. "Set my balance to 100" is idempotent. "Add 100 to my balance" is not.

Why idempotency matters: retries

Networks fail. A request can reach the server and succeed, and then the reply is lost. The client cannot tell the difference between "never arrived" and "done, but the answer got lost".

client                         server
  |  POST /payments  amount=100   |
  |-----------------------------> |  charges the card
  |       200 OK  (lost!)          |
  |   x <------------------------- |
  |  (timeout... retry)            |
  |  POST /payments  amount=100   |
  |-----------------------------> |  charges the card AGAIN

Retrying a GET or PUT is fine. Retrying a POST can charge a customer twice. The standard fix is an idempotency key: the client makes a unique ID for each logical action and sends it in a header such as Idempotency-Key: 7f3c.... The server remembers the keys it has seen, and if the same key comes again, it returns the saved result instead of charging again. Payment APIs such as Stripe work this way. On the server, "remember the key" must itself be safe from race conditions, usually by a unique constraint in the database.

11. Status Codes

The first digit tells you the class:

ClassMeaningCodes you will see most
1xxInfo, keep going101 Switching Protocols (WebSockets), 103 Early Hints
2xxSuccess200 OK, 201 Created, 204 No Content
3xxGo somewhere else, or use your copy301 Moved Permanently, 302 Found, 304 Not Modified, 307/308 (redirect, keep the method)
4xxThe client made a mistake400 Bad Request, 401 Unauthorized (not logged in), 403 Forbidden (logged in, not allowed), 404 Not Found, 409 Conflict, 429 Too Many Requests
5xxThe server failed500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout

The difference between 4xx and 5xx matters a lot in practice. A 4xx usually should not be retried: the same request will fail again. A 503 or a 429 often should be retried, after the delay in the Retry-After header if there is one, with growing waits between tries (exponential backoff).

502 vs 504: reading the error from the middle

Most sites have a proxy or load balancer in front of the app (section 14). These codes come from that middle box:

  • 502 Bad Gateway: the proxy reached the app, but got a broken reply or the connection was refused. Often the app crashed or is restarting.
  • 504 Gateway Timeout: the proxy waited for the app and gave up. The app is alive but too slow, often stuck on a database query. See Scenario: Debugging a Slow API.

12. Headers, Cookies, and State

Headers you should know

HeaderDirectionMeaning
HostRequestWhich site you want. One IP can host many sites, so this is required
Content-TypeBothWhat the body is: text/html, application/json...
Content-LengthBothBody size in bytes
Accept, Accept-EncodingRequestWhat formats and compression (gzip, br, zstd) the client can handle
AuthorizationRequestCredentials, such as Bearer <token>
LocationResponseWhere to go, for redirects and newly created resources
Cache-Control, ETagResponseCaching rules (section 13)
Set-Cookie / CookieResponse / RequestStore and send back small pieces of state
Strict-Transport-SecurityResponse"Only ever use HTTPS for this site" (HSTS)

Cookies: memory for a stateless protocol

If HTTP forgets every request, how does a site know you are logged in? With a cookie: a small named value the server asks the browser to store and send back on every later request to that site.

1. POST /login   (username + password)
   <- 200 OK
      Set-Cookie: session=9f8e7d...; HttpOnly; Secure; SameSite=Lax; Max-Age=86400

2. GET /orders
   -> Cookie: session=9f8e7d...        (browser adds it automatically)
   <- 200 OK  (server looks up session 9f8e7d... and knows who you are)

The cookie options are security settings:

  • HttpOnly: JavaScript on the page cannot read it, which limits damage from injected scripts.
  • Secure: only sent over HTTPS.
  • SameSite=Lax: not sent on most requests started by other sites, which blocks a class of attacks called CSRF (cross-site request forgery).
  • Max-Age: how long to keep it, in seconds.

APIs used by mobile apps and other servers often skip cookies and send a token in the Authorization header instead.

13. HTTP Caching: Cache-Control, ETag, 304

The fastest request is one you never send. HTTP caching lets browsers and CDNs reuse earlier responses.

Cache-Control

DirectiveMeaning
max-age=3600Fresh for 3,600 seconds. Use it without asking the server
no-cacheYou may store it, but must check with the server before each use
no-storeNever store it (bank pages, private data)
public / privateShared caches (CDNs) may / may not store it
must-revalidateOnce stale, never use without checking
immutableThis URL's content will never change

Revalidation with ETag: a real example

An ETag is a fingerprint of a version of a file. If the file changes, the ETag changes. Here is this very site's stylesheet:

$ curl -sI https://engineering.msaqlain.com/styles.css
HTTP/2 200
cache-control: public, max-age=0, must-revalidate
content-type: text/css; charset=utf-8
etag: "4c3894ae9469f1a7e8fc574abad9bd40"
content-length: 15575

$ curl -sI -H 'If-None-Match: "4c3894ae9469f1a7e8fc574abad9bd40"' \
    https://engineering.msaqlain.com/styles.css
HTTP/2 304

Step by step:

  1. First visit: the browser downloads 15,575 bytes and saves the ETag.
  2. max-age=0, must-revalidate means "check every time before using it".
  3. Next visit: the browser sends If-None-Match with the saved ETag.
  4. The file has not changed, so the server replies 304 Not Modified with no body. The browser uses its saved copy. Only a few hundred bytes of headers moved.

This is a safe default for a site that changes often: users always see the newest version, but unchanged files are not downloaded again. The cost is one round trip per file. The other common strategy is cache busting: put a version or hash in the file name (app.3f9a1c.js) and serve it with max-age=31536000, immutable. The browser never asks again, and a new release simply uses a new file name.

Last-Modified with If-Modified-Since does the same job as ETag, using a date instead of a fingerprint.

14. Proxies, Load Balancers, and CDNs

Your request rarely goes straight to the program that builds the page.

  browser --> CDN edge (near you) --> load balancer --> app server 1
                 |  cache HIT?                     \-> app server 2
                 |  answer from cache                \-> app server 3 --> database
  • A reverse proxy sits in front of servers and forwards requests to them. Examples: Nginx, Envoy, HAProxy. It can handle TLS, compression, and rate limits so the app does not have to.
  • A load balancer is a reverse proxy that spreads requests over several servers, and stops sending to servers that fail health checks. In Kubernetes, this is the job of Services and Ingress. How it picks a server and finds broken ones is covered in Load Balancing & Reverse Proxies.
  • A CDN (content delivery network) is a big network of caching proxies in many cities. In the real example.com reply above, server: cloudflare, cf-cache-status: HIT, and age: 7 mean a Cloudflare server near the client answered from its cache, and that copy was 7 seconds old.

Because of these middle boxes, the app sees the proxy's IP, not the user's. Proxies add headers like X-Forwarded-For (the original client IP) and X-Forwarded-Proto (was it https?). Only trust these headers when they come from your own proxy, because clients can fake them.

Where the TLS connection ends (at the load balancer, again at the app, or only at the app) is a design choice with real trade-offs; see TLS at Load Balancers and Proxies. What goes wrong when servers behind a load balancer start and stop is walked through in Scenario: Errors During Every Deploy.

15. Scenario: Moving a Site Without Downtime

Situation. shop.example.com points to an old server, 203.0.113.10, with an A record TTL of 86,400 seconds (1 day). You must move to a new server, 198.51.100.20, on Saturday at 10:00, with no visible downtime.

The naive plan, and why it hurts

Change the A record at 10:00 Saturday and turn off the old server. Resolvers that cached the old answer on Friday at 10:01 keep sending users to the dead server until Saturday 10:01. Some users see errors for almost a full day.

The safe plan

WhenActionWhy
Thursday 09:00 (at least one old TTL before the move)Lower the TTL to 300 s. Keep the same IPBy Friday 09:00 every cached copy with the 1-day TTL has expired. From then on, caches hold the answer for at most 5 minutes
FridaySet up the new server. Test it directly with curl --resolve shop.example.com:443:198.51.100.20 https://shop.example.com/--resolve skips DNS, so you test the new server with the real name and certificate before anyone else uses it
Saturday 10:00Change the A record to 198.51.100.20The worst-case switch-over time is now 5 minutes, not 1 day
Saturday 10:00 to 11:00Keep the old server running. Watch traffic on bothTraffic on the old server should fall to near zero within minutes. Some clients ignore TTLs
Saturday 11:00 onwardTurn off the old server once its traffic stays at zero. Raise the TTL back to 3600 sFewer DNS queries again

Check during the move: dig +short shop.example.com @1.1.1.1 and @8.8.8.8 show what big public resolvers currently return, and the second column of a full dig answer shows how many seconds of TTL are left.

The general lesson: DNS changes are not instant; they are bounded by the TTL that was in caches before you made the change. Lower the TTL first, wait one old TTL, then make the change.

16. Common Pitfalls

  • Testing a DNS change from one laptop and assuming the world sees it. Your machine, your browser, and your resolver all cache. Test against several public resolvers.
  • Looking up a name before creating it, then waiting for the negative-cache time.
  • Long-lived programs that look up a name once at start-up and never again. When the IP changes, they keep calling the old one. Some HTTP clients and connection pools do this. Make sure they respect TTLs or reconnect now and then.
  • Retrying POST requests without an idempotency key. Double charges, double orders.
  • Returning 200 with an error message in the body. Monitoring, caches, and retry logic all read the status code. Use the right 4xx or 5xx.
  • Caching private pages in a CDN because Cache-Control: private or no-store was missing. One user's page can be shown to another.
  • Long max-age on a file name that never changes (app.js). Users keep the old version after a release. Use hashed file names for long caching.
  • Trusting X-Forwarded-For from the open internet for rate limits or security decisions.
  • Forgetting the trailing dot or ndots in Kubernetes, multiplying DNS traffic.

TCP Deep Dive: From Handshake to Congestion Control

How two computers turn an unreliable network that loses, duplicates, and reorders packets into a clean, ordered byte stream. With real numbers, worked latency math, and debugging recipes.

1. Where TCP Fits

Networking is built in layers. Each layer solves one problem and relies on the layer below.

 Layer            Example         Job                                   Unit
 ---------------  --------------  ------------------------------------  ---------
 Application      HTTP, DNS, SSH  what the data means                   message
 Transport        TCP, UDP, QUIC  process-to-process delivery           segment
 Network          IP              host-to-host delivery across networks packet
 Link             Ethernet, WiFi  delivery to the next device on a link frame

IP delivers packets between machines on a "best effort" basis. Packets can be lost (a router queue was full), reordered (they took different paths), duplicated, or corrupted. IP does not care. (How IP addresses, subnets, and routing tables work is covered in IP Addressing, Subnetting & Routing.)

TCP (Transmission Control Protocol) runs on top and gives applications a promise: the bytes you write arrive at the other side complete, in order, without duplicates, or you get an error. It does this entirely in the two endpoints. Routers in the middle know nothing about TCP connections.

UDP is the opposite: it just adds ports to IP and sends. No connection, no ordering, no retransmission. It is used where speed matters more than perfection (DNS lookups, games, voice), and as the base of QUIC, which rebuilds reliability in user space.

2. Ports, Sockets, and the 4-Tuple

An IP address finds a machine. A port (a 16-bit number, 0 to 65535) finds a program on that machine. Servers listen on well-known ports (443 for HTTPS, 5432 for PostgreSQL). Clients use a random ephemeral port (on Linux by default 32768 to 60999).

A TCP connection is identified by the 4-tuple:

(source IP, source port, destination IP, destination port)
(192.168.1.20, 51544, 93.184.215.14, 443)

This is why one server port can serve millions of clients: each connection has a different 4-tuple. A socket is the operating system object (a file descriptor) your program uses to talk over one connection, or to listen for new ones.

$ ss -tn                 # established TCP connections, numeric
$ ss -tlnp               # listening TCP sockets and the owning process

3. The TCP Segment

TCP cuts your byte stream into segments. Each has a header (20 bytes minimum) with these important fields:

FieldMeaning
Source / destination portWhich programs
Sequence numberPosition in the byte stream of the first byte in this segment
Acknowledgment number"I have received everything before this byte number; send me this one next"
FlagsSYN (start), ACK (ack field valid), FIN (I am done sending), RST (abort), PSH
WindowHow many more bytes the sender of this segment can receive (flow control)
OptionsMSS, window scale, SACK permitted, timestamps

The MSS (maximum segment size) is the largest payload per segment. On normal Ethernet the link MTU is 1500 bytes; minus 20 bytes IPv4 header and 20 bytes TCP header gives an MSS of 1460 bytes.

4. The Three-Way Handshake

Before sending data, both sides must agree to talk and pick starting sequence numbers. Each side chooses a random Initial Sequence Number (ISN). Randomness prevents old stray packets from a previous connection being mistaken as new, and makes it hard for attackers to inject fake segments.

  Client (ISN = 1000)                              Server (ISN = 5000)
     |                                                   |
     |---- SYN, seq=1000 ------------------------------->|   "I want to talk; my bytes start after 1000"
     |                                                   |
     |<--- SYN+ACK, seq=5000, ack=1001 ------------------|   "OK. Mine start after 5000. Next I expect your 1001"
     |                                                   |
     |---- ACK, seq=1001, ack=5001 --------------------->|   "Got it. Next I expect your 5001"
     |                                                   |
     |========== connection ESTABLISHED =================|

Why the +1?

A SYN carries no data but consumes one sequence number, so it can be acknowledged like data. The same is true of FIN. That is why the ack is 1001, not 1000.

Why three messages, not two?

Each side must send its own ISN and hear confirmation that the other side received it. Client's ISN is confirmed in message 2. Server's ISN is confirmed in message 3. Message 2 combines the server's SYN with its ACK, so three messages are enough.

Cost

The client can send data right after sending the final ACK. So the handshake costs 1 round-trip time (RTT) before the first request byte leaves. With a 100 ms RTT, that is 100 ms of pure waiting, which is why connection reuse (keep-alive, pooling) matters so much.

SYN flood: an attacker sends many SYNs from fake addresses and never completes the handshake, filling the server's queue of half-open connections. SYN cookies defend against this: the server encodes the connection state in its ISN and stores nothing until the final ACK arrives.

5. Reliable Delivery: Sequence Numbers, ACKs, Retransmission

Sequence numbers count bytes

Continuing from the handshake, the client sends a 3000-byte request in segments of up to 1460 bytes:

segment A: seq=1001, 1460 bytes   (bytes 1001..2460)
segment B: seq=2461, 1460 bytes   (bytes 2461..3920)
segment C: seq=3921,   80 bytes   (bytes 3921..4000)

server ACKs: ack=2461, ack=3921, ack=4001

The ACK number is cumulative: "I have everything up to (not including) this byte". The receiver uses sequence numbers to put segments back in order and drop duplicates.

What happens when a segment is lost

Suppose segment B is lost, but A and C arrive.

  1. A arrives: receiver ACKs 2461.
  2. C arrives, but there is a hole at 2461. The receiver buffers C and ACKs 2461 again (a duplicate ACK). With the SACK option it also says "I additionally have 3921..4000".
  3. The sender eventually retransmits B. Once it arrives, the receiver ACKs 4001 in one go.

There are two ways the sender notices the loss:

  • Retransmission timeout (RTO): a timer per outstanding data. If no ACK arrives in time, resend. The RTO is computed from measured RTT and its variance (RFC 6298), and it doubles after each timeout (exponential backoff). Linux uses a minimum RTO of 200 ms.
  • Fast retransmit: after 3 duplicate ACKs for the same number, resend immediately without waiting for the timer. This works when later segments keep arriving.
Intuition: you mail chapters of a book numbered by page. Your friend replies "I have everything up to page 41". If they keep replying "up to page 41" while you are sending pages 60, 80, 100, page 41 clearly got lost, so you resend it without waiting a week.

A checksum in the header catches corrupted segments, which are dropped and later retransmitted.

6. Flow Control: Don't Drown the Receiver

The receiving application might read slowly. TCP must not send more than the receiver's buffer can hold. Every segment advertises the receive window (rwnd): free space in the receiver's buffer. The sender keeps the amount of unacknowledged data at most rwnd.

If the app stops reading, the window shrinks to 0 and the sender stops (it sends small "window probes" to learn when space opens).

Window scaling and the bandwidth-delay product

The header window field is 16 bits, so at most 65,535 bytes. That is too small for fast, long links. The window scale option, agreed in the handshake, multiplies it by 2shift (shift up to 14, so windows up to about 1 GiB).

How big must the window be? To keep a link full, you need enough data "in flight" to cover one round trip. That amount is the bandwidth-delay product (BDP).

Worked example

Link: 100 Mbit/s, RTT 50 ms

BDP = bandwidth * RTT
    = 100,000,000 bit/s * 0.050 s
    = 5,000,000 bits
    = 625,000 bytes  (about 610 KiB)

Max throughput with a 64 KiB window (no scaling):
    window / RTT = 65,535 B / 0.050 s = 1,310,700 B/s  = about 10.5 Mbit/s

Without window scaling you would use about 10% of the link no matter how fast it is. General rule: throughput ≤ window / RTT.

7. Congestion Control: Don't Drown the Network

Flow control protects the receiver. Congestion control protects the network between. If every sender blasted at full speed, router queues would overflow, packets would drop, everyone would retransmit, and throughput would collapse. (This actually happened on the early Internet in 1986, leading to Van Jacobson's congestion control algorithms.)

The sender keeps a second limit, the congestion window (cwnd), its own guess of how much the network can handle. The real limit on data in flight is:

in_flight ≤ min(cwnd, rwnd)

Slow start

A new connection does not know the network's capacity. It starts small (modern stacks use an initial cwnd of 10 segments, about 14.6 KB) and increases cwnd by one segment for every ACK. Since each full window of segments is acknowledged in one RTT, cwnd doubles every RTT. "Slow" only refers to the small start; the growth is exponential.

Worked example: how many round trips to send a 100 KB response?

MSS = 1460 bytes. 100,000 / 1460 = 68.5  ->  69 segments needed.

RTT 1: cwnd = 10  ->  sent 10   (total 10)
RTT 2: cwnd = 20  ->  sent 20   (total 30)
RTT 3: cwnd = 40  ->  sent 39   (total 69, done)

So a fresh connection needs 3 round trips just to deliver 100 KB, regardless of bandwidth. On a 100 ms RTT that is 300 ms of data transfer for a small page. This is why reusing warm connections (HTTP keep-alive, HTTP/2 multiplexing) and making responses smaller both help latency so much.

Congestion avoidance and AIMD

When cwnd reaches the slow start threshold (ssthresh), growth becomes linear: about +1 segment per RTT. When loss is detected, the sender assumes congestion and cuts back:

  • Loss detected by duplicate ACKs (mild): classic Reno halves cwnd (multiplicative decrease) and continues in congestion avoidance.
  • Loss detected by timeout (severe): ssthresh = cwnd / 2, cwnd resets to a small value, and slow start begins again.

This "Additive Increase, Multiplicative Decrease" (AIMD) pattern produces the classic sawtooth graph, and it makes competing flows converge to a fair share.

cwnd
  ^        /|        /|        /|
  |       / |       / |       / |
  |      /  |      /  |      /  |      linear growth, halve on loss
  |     /   |     /   |     /   |
  |    /    |____/    |____/    |____
  |   /  (slow start)
  |  /
  +---------------------------------------> time

Modern algorithms

AlgorithmSignalIdea
Reno / NewRenoLossTextbook AIMD
CUBICLossWindow grows as a cubic function of time since the last loss, so it recovers quickly on fast long links. Reduces by a factor of 0.7 on loss. Default in Linux, Windows, and macOS.
BBR (Google)Measured bandwidth and min RTTBuilds a model of the path's bottleneck bandwidth and RTT, and paces sending to match it, instead of filling buffers until loss. Helps on lossy links (mobile, long distance). Used widely at Google.
 
$ sysctl net.ipv4.tcp_congestion_control          # usually: cubic
$ sysctl net.ipv4.tcp_available_congestion_control
$ ss -ti dst example.com                            # per connection: cwnd, rtt, retrans

8. Closing a Connection and TIME_WAIT

TCP is full duplex: each direction is closed separately with a FIN.

  Active closer (A)                         Passive closer (B)
     |---- FIN -------------------------------->|   A: "I am done sending"
     |<--- ACK ---------------------------------|
     |              (B may still send data)     |
     |<--- FIN ---------------------------------|   B: "I am done too"
     |---- ACK -------------------------------->|
  TIME_WAIT                                   CLOSED
  (wait 2 x MSL, 60 s on Linux)
     |
  CLOSED

The side that closes first enters TIME_WAIT. It keeps the 4-tuple reserved for twice the Maximum Segment Lifetime for two reasons:

  1. If its final ACK is lost, B will resend FIN, and A must still be able to answer.
  2. Delayed segments from this connection must die out before a new connection reuses the same 4-tuple.

RST is the abrupt alternative: "this connection does not exist / abort now". You get one when connecting to a port nobody listens on, or when a program exits with unread data.

Practical note: a busy client opening thousands of short connections to the same server can run out of ephemeral ports because of TIME_WAIT. Fixes: reuse connections (pooling, keep-alive), and on Linux net.ipv4.tcp_tw_reuse for outgoing connections. Never use the long-removed tcp_tw_recycle advice you may find online.

9. Scenario: Budgeting a Page Load (TLS 1.3, HTTP/2, HTTP/3)

Question: a user in Mumbai opens https://shop.example, hosted in Frankfurt. RTT is 120 ms. Nothing is cached. Server processing takes 40 ms. How long until the first byte of HTML arrives?

Step 1: DNS

The browser asks its resolver for the IP. Assume the resolver is nearby and has the answer cached: about 10 ms. (If not cached, add round trips to root, TLD, and authoritative servers.)

Step 2: TCP handshake = 1 RTT = 120 ms

Step 3: TLS 1.3 handshake = 1 RTT = 120 ms

(For what each message contains, certificates, and a hands-on lab, see TLS, HTTPS & Certificates.) The client sends ClientHello with its key share. The server replies with ServerHello, its key share, certificate, and Finished. Now both sides can derive keys, and the client sends its Finished together with the HTTP request. (TLS 1.2 needed 2 RTTs here.)

Step 4: HTTP request and response = 1 RTT + server time = 160 ms

HTTP/1.1 or HTTP/2 over TLS 1.3 over TCP:
  DNS 10 + TCP 120 + TLS 120 + HTTP (120 + 40) = 410 ms to first byte

HTTP/3 over QUIC (UDP), first visit:
  QUIC merges transport and TLS 1.3 setup into ONE round trip
  DNS 10 + QUIC/TLS 120 + HTTP (120 + 40)     = 290 ms

HTTP/3 with 0-RTT resumption (returning visitor):
  request rides in the very first flight
  DNS 10 + (120 + 40)                          = 170 ms

Then the 100 KB HTML needs about 3 RTTs of slow start (section 7), plus CSS, JS, and images. A CDN edge in Mumbai (RTT 10 ms) shrinks every term. Latency is mostly round trips times RTT, so engineers fight round trips: connection reuse, TLS 1.3, HTTP/3, CDNs, fewer redirects, and preconnect hints.

Measure it yourself

$ curl -o /dev/null -s -w \
  'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  https://example.com
dns=0.001378 connect=0.001902 tls=0.024213 ttfb=0.039511 total=0.039601

All curl times are cumulative from the start. TCP took connect - dns, TLS took tls - connect, and the server plus one RTT took ttfb - tls. (Output above is a real run from a data center close to a CDN edge, hence the tiny numbers.)

Why HTTP/2 and HTTP/3 exist

  • HTTP/1.1: one request at a time per connection, so browsers open about 6 connections per host.
  • HTTP/2: many requests multiplexed as streams on one TCP connection. But one lost TCP segment stalls all streams until it is retransmitted, because TCP delivers bytes strictly in order. This is head-of-line blocking at the transport layer.
  • HTTP/3: runs over QUIC on UDP. QUIC handles streams itself, so a loss only stalls the stream it belongs to. It also encrypts transport headers and lets connections survive IP changes (WiFi to mobile) via connection IDs.

Walkthrough: "my service can't reach the database"

  1. Name resolution: getent hosts db.internal (or dig). Wrong IP? Fix DNS first.
  2. Is anything listening? On the DB host: ss -tlnp | grep 5432. If it shows 127.0.0.1:5432, it only accepts local connections. Change the bind address (listen_addresses in PostgreSQL).
  3. Can packets get there? From the client: nc -vz db.internal 5432. "Refused" means routing works but no listener; "timed out" points to a firewall, security group, or Kubernetes NetworkPolicy.
  4. Look at the packets if still unclear: sudo tcpdump -nn -i any host db.internal and port 5432. Repeated SYNs with no SYN-ACK means drops. SYN followed by RST means refused.

In Kubernetes, also check that the Service selector matches the Pod labels and that endpoints exist (kubectl get endpointslices). See Kubernetes Networking.

Nagle and delayed ACK, explained

Nagle's algorithm holds back small writes while earlier data is unacknowledged, to avoid flooding the network with tiny packets. Delayed ACK makes the receiver wait briefly (Linux: from 40 ms) hoping to piggyback the ACK on a reply. Together, a "write header, write body" pattern can stall: the second small write waits for an ACK the peer is deliberately delaying. Fix: set TCP_NODELAY on latency-sensitive sockets (many HTTP clients, database drivers, and gRPC already do), or write the whole message in one call.

11. Common Pitfalls

  • Thinking TCP preserves message boundaries. It is a byte stream. Two send()s of 100 bytes may arrive as one 200-byte recv(), or as 50 + 150. Protocols must add framing (length prefixes, delimiters).
  • Ignoring that bandwidth is not latency. A 1 Gbit/s link does not make a 3-round-trip handshake faster.
  • Opening a new connection per request. Pays handshake, TLS, and slow start every time. Use pooling.
  • Treating "connection refused" and "timeout" as the same. They point to completely different layers.
  • Forgetting the SYN and FIN each use a sequence number when computing ACK numbers.
  • Long idle connections through load balancers and NAT. Middleboxes drop idle state (often after 350 s to a few minutes). Use TCP keepalives or application pings shorter than that timeout.

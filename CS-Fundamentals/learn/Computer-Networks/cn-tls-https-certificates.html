TLS, HTTPS & Certificates

The small lock icon in your browser means the page came over TLS (Transport Layer Security). TLS lets two computers that have never met talk privately over a network that anyone could be listening to, and lets your browser check that it is really talking to your bank and not to someone pretending. This page builds TLS from zero, then runs a real lab: we make our own certificate authority, run a TLS server, and break it on purpose to see every common error. It builds on TCP and DNS & HTTP.

1. What Could Go Wrong Without TLS

When you send a request over plain HTTP, the bytes pass through many machines: your Wi-Fi router, your internet provider, several routers between cities, and the website's data center. Any of them could do three bad things:

AttackExampleWhat TLS gives you
Read (eavesdrop)Someone on café Wi-Fi sees your passwordConfidentiality: the bytes are encrypted, so they look like random noise
Change (tamper)A network inserts ads into a page, or changes a bank account numberIntegrity: any change is detected and the connection is closed
Pretend (impersonate)A fake server answers for mybank.comAuthentication: the server proves it owns the name, using a certificate

HTTPS is just HTTP sent inside a TLS connection, usually on port 443. TLS sits between TCP and HTTP:

  HTTP        GET /account  (readable only at the two ends)
  ─────────────────────────────────────────────
  TLS         encrypts + protects + proves identity
  ─────────────────────────────────────────────
  TCP         reliable byte stream (port 443)
  ─────────────────────────────────────────────
  IP          packets between addresses

Intuition. Encryption alone is not enough. If you encrypt perfectly but to the wrong person, the attacker just reads it. That is why authentication (certificates) is the hardest and most important part of TLS.

A note on names: the old name was SSL. SSL and TLS 1.0 and 1.1 are all broken or retired. Use TLS 1.2 or, better, TLS 1.3. People still say "SSL certificate"; it means the same thing as a TLS certificate.

2. Two Kinds of Locks: Symmetric and Public-Key

Symmetric encryption: one shared key

In symmetric encryption, the same key locks and unlocks. Both sides must have it. It is very fast: modern CPUs have special instructions for AES (the Advanced Encryption Standard), so they can encrypt gigabytes per second. TLS uses symmetric encryption for all the real data.

The problem: how do two strangers get the same secret key, when everything they send can be read?

Public-key (asymmetric) cryptography: a key pair

Here each side has two keys that belong together:

  • a private key, kept secret, never sent anywhere;
  • a public key, given to anyone.

What one key does, only the other can check or undo. This gives two powers: other people can create a shared secret with you (section 3), and you can sign things so anyone can check you wrote them (section 4). Public-key math is much slower than AES, so TLS uses it only during the start of the connection, the handshake.

Symmetric (AES, ChaCha20)Public-key (ECDHE, RSA, ECDSA)
KeysOne shared secretA private and public pair
SpeedVery fastSlow
Used in TLS forAll application dataAgreeing on keys, and proving identity

TLS also adds a tag to every encrypted record, a short code computed from the key and the data. If even one bit is changed in transit, the tag no longer matches. Ciphers that encrypt and tag in one step are called AEAD (authenticated encryption with associated data), for example AES-GCM and ChaCha20-Poly1305. This is how TLS gives integrity.

3. Agreeing on a Secret in Public: Diffie-Hellman by Hand

Diffie-Hellman (DH) is a trick that lets two people create the same secret number while an eavesdropper sees every message and still cannot work it out. Let us do it with tiny numbers. ("mod 23" means "the remainder after dividing by 23".)

  1. Everyone agrees on two public numbers: p = 23 and g = 5.
  2. Alice picks a secret a = 6. She sends A = 56 mod 23. 56 = 15,625, and 15,625 mod 23 = 8. She sends 8.
  3. Bob picks a secret b = 15. He sends B = 515 mod 23 = 19.
  4. Alice computes Ba mod 23 = 196 mod 23 = 2.
  5. Bob computes Ab mod 23 = 815 mod 23 = 2.

Both get 2. It works because both are really computing 56 × 15 mod 23. The eavesdropper saw 23, 5, 8 and 19, but never 6 or 15. To find the secret they would have to undo "5 to the power of something mod 23", which is easy for 23 but practically impossible for the huge numbers used in real life. You can check the numbers yourself in Python:

p, g, a, b = 23, 5, 6, 15
A, B = pow(g, a, p), pow(g, b, p)
print(A, B, pow(B, a, p), pow(A, b, p))   # prints: 8 19 2 2

Real TLS uses the same idea on elliptic curves (a different kind of math where the same "easy one way, hard to undo" property holds with smaller keys). The curve named X25519 is the common choice. In TLS 1.3, both sides make a fresh random secret for every connection and throw it away afterwards. This is called ephemeral DH (the "E" in ECDHE). It gives forward secrecy: even if the server's private key is stolen next year, recorded old traffic still cannot be decrypted, because those session secrets no longer exist anywhere.

Post-quantum key exchange. In our lab below, the connection used a group called X25519MLKEM768. That is a hybrid: it combines classic X25519 with ML-KEM, a newer method designed to resist attacks by future quantum computers. The secret is safe if either part holds. Recent browsers and OpenSSL 3.5 pick it by default.

But DH alone has a hole: Alice does not know that "19" really came from Bob. A person in the middle could do one DH exchange with Alice and another with Bob, and read everything. Fixing that needs signatures and certificates.

4. Digital Signatures: Proving Who Wrote It

A digital signature works like this:

  1. The signer takes a message, makes a short fingerprint of it with a hash function (like SHA-256, which turns any input into a fixed 32-byte value that changes completely if the input changes at all).
  2. They compute a signature from that hash using their private key.
  3. Anyone with the public key can check that the signature matches the message. Nobody without the private key can make a valid signature.

In the TLS handshake, the server signs the handshake messages so far (including its DH value) with its private key. The client checks the signature with the server's public key. Now the person in the middle cannot swap the DH value, because they cannot sign as the server.

One question remains: how does the client know which public key belongs to mybank.com? That is what certificates are for.

5. Certificates and the Chain of Trust

A certificate is a small signed document that says: "the public key K belongs to the name shop.test, valid from date X to date Y". It is signed by a certificate authority (CA): an organization that checks you really control the name before signing.

Here are the main fields of the certificate from our lab, printed with openssl x509 -noout -subject -issuer -dates -ext subjectAltName,extendedKeyUsage (real output; the dates are in GMT):

subject=CN=shop.test
issuer=CN=Demo Intermediate CA
notBefore=Nov 21 08:53:06 2026 GMT
notAfter=Feb 19 08:53:06 2027 GMT
X509v3 Subject Alternative Name:
    DNS:shop.test, DNS:www.shop.test
X509v3 Extended Key Usage:
    TLS Web Server Authentication
FieldMeaning
Subject / CNWho the certificate is for. CN means "common name". Clients today ignore CN for checking the name.
Subject Alternative Name (SAN)The list of names the certificate is valid for. This is what clients check. *.shop.test would match www.shop.test but not shop.test or a.b.shop.test.
IssuerWhich CA signed it.
notBefore / notAfterThe dates it is valid. Outside them, clients reject it.
Public keyThe server's public key.
Key usage, extended key usageWhat the key may be used for (for example, "TLS server", or "may sign other certificates").
SignatureThe issuer's signature over all of the above.

The chain of trust

Your computer and browser come with a list of about 150 trusted root CAs, the trust store. Root CA private keys are kept offline in safes, so roots rarely sign servers directly. Instead, a root signs an intermediate CA, and the intermediate signs servers (the leaf certificates).

  Demo Root CA              (in the client's trust store; signs itself)
       │ signs
       ▼
  Demo Intermediate CA      (sent by the server)
       │ signs
       ▼
  shop.test                 (the leaf, sent by the server)

To check a leaf, the client walks up: is the leaf signed by the intermediate? Is the intermediate signed by a root I trust? Are all of them within their dates? Does the leaf's SAN list contain the name I typed? If every answer is yes, the certificate is trusted.

The server must send the intermediate. The client has the roots but usually not the intermediates. If the server sends only its leaf, the client cannot connect the leaf to a root, and fails with "unable to get local issuer certificate". Some browsers hide this mistake by fetching or caching intermediates, so the site "works in Chrome" but fails in curl, Python, or Java. Always serve the full chain: leaf first, then intermediates. Do not send the root.

Revocation

If a private key is stolen, the certificate should be revoked (cancelled) before it expires. CAs publish lists of revoked certificates (CRLs) and answer live checks (OCSP). In practice these checks are slow and often skipped, which is one reason the industry is moving to short-lived certificates: a stolen certificate that expires soon does less harm.

6. The TLS 1.3 Handshake, Step by Step

After the TCP handshake, TLS needs one round trip before the client can send its HTTP request. We captured the real messages with openssl s_client -msg (lines shortened):

>>> TLS 1.3, Handshake [length 05f8], ClientHello
<<< TLS 1.3, Handshake [length 04ba], ServerHello
<<< TLS 1.3, ChangeCipherSpec [length 0001]
<<< TLS 1.3, Handshake [length 0006], EncryptedExtensions
<<< TLS 1.3, Handshake [length 01c2], Certificate
<<< TLS 1.3, Handshake [length 004e], CertificateVerify
<<< TLS 1.3, Handshake [length 0034], Finished
>>> TLS 1.3, ChangeCipherSpec [length 0001]
     (then the client's Finished and the first HTTP request)

(>>> is client to server, <<< is server to client. Lengths are in hex: 05f8 = 1,528 bytes. The ClientHello is big here because the post-quantum key share is large.)

  1. ClientHello. The client lists the TLS versions and cipher suites it supports, sends its DH key share (it guesses which group the server likes), and names the site it wants in the SNI field (Server Name Indication). SNI lets one IP address host many HTTPS sites: the server reads the name and picks the matching certificate.
  2. ServerHello. The server picks the cipher suite and sends its key share. Now both sides do the DH math and get the same secret. From here on, all handshake messages are encrypted.
  3. Certificate carries the leaf and intermediates. CertificateVerify is the server's signature over the handshake so far, made with the private key matching the certificate. This proves the server owns the certificate and that nobody changed the key shares.
  4. Finished (both sides) is a check value over the whole handshake. If an attacker changed any message (for example, removed the strongest cipher from the list), the Finished values do not match and the connection fails.

The ChangeCipherSpec lines are empty leftovers kept only so old middleboxes (firewalls that expect TLS 1.2) do not break the connection.

openssl's summary for this connection (real output, -brief):

CONNECTION ESTABLISHED
Protocol version: TLSv1.3
Ciphersuite: TLS_AES_256_GCM_SHA384
Peer certificate: CN=shop.test
Hash used: SHA256
Signature type: ecdsa_secp256r1_sha256
Verification: OK
Verified peername: shop.test
Negotiated TLS1.3 group: X25519MLKEM768

Read it as: TLS 1.3; data encrypted with AES-256 in GCM mode; the server signed with an ECDSA key on the P-256 curve; the chain and the name checked out; the key exchange used the hybrid post-quantum group.

Why TLS 1.3 is faster than 1.2

TLS 1.2 needed two round trips before data could flow, because the client first learned which key exchange the server wanted, and only then sent its share. TLS 1.3 sends the key share in the first message, saving a round trip. On a link with a 120 ms RTT, that is 120 ms saved on every new connection. (The page-load budget on the TCP page adds this up end to end.)

7. Resumption and 0-RTT

After a handshake, the server can give the client a session ticket: an encrypted blob that lets the client resume later with a shared key (a PSK, pre-shared key) instead of checking the full certificate chain again. Resumption still takes one round trip, but less CPU work.

We measured both on the same machine, client and server both on localhost (so there is almost no network delay and the numbers show only CPU and memory work), with Python's ssl module, 200 handshakes each, two runs:

full handshake  median 0.89 ms over 200
resumed         median 0.54 ms, reused=200/200
full handshake  median 0.90 ms over 200
resumed         median 0.58 ms, reused=200/200

So on this machine, a full handshake cost under 1 ms of computer time, and resumption cut that by roughly a third. Over a real network, the round trip (tens or hundreds of milliseconds) is far bigger than this CPU time. That is why reusing connections (HTTP keep-alive and connection pools) matters much more than tuning crypto.

0-RTT (early data)

With a ticket, a TLS 1.3 client may send its first request inside the very first message, with zero round trips of waiting. The catch: an attacker who records that first message can replay it (send it again). So 0-RTT is only safe for requests that do no harm when repeated, like GET /logo.png, never for "pay ₹500". Servers usually allow early data only for safe, idempotent methods (see HTTP methods). QUIC uses the same 0-RTT idea, without a separate TCP handshake; that is covered on the QUIC and HTTP/3 page.

8. Lab: Make a CA, Run a Server, Break It on Purpose

Everything below was run with OpenSSL 3.5 on Linux. You can copy it into a terminal in an empty folder. We use the made-up name shop.test (the .test ending is reserved for testing and never exists on the internet).

Step 1: a root CA

openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout ca.key -out ca.crt -days 3650 -subj "/CN=Demo Root CA" \
  -addext "basicConstraints=critical,CA:TRUE" \
  -addext "keyUsage=critical,keyCertSign,cRLSign"

-x509 makes a self-signed certificate (a root signs itself). -nodes means "do not password-protect the key" (fine for a lab, not for real CAs). basicConstraints CA:TRUE marks it as allowed to sign other certificates.

Step 2: an intermediate CA, signed by the root

openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout int.key -out int.csr -subj "/CN=Demo Intermediate CA"
printf "basicConstraints=critical,CA:TRUE,pathlen:0\nkeyUsage=critical,keyCertSign,cRLSign\n" > int.cnf
openssl x509 -req -in int.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out int.crt -days 1825 -extfile int.cnf

A CSR (certificate signing request) is the public key plus the requested name, signed by the requester. The CA turns it into a certificate. pathlen:0 means this intermediate may sign leaves but not more CAs.

Step 3: the server's leaf certificate

openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout leaf.key -out leaf.csr -subj "/CN=shop.test"
printf "subjectAltName=DNS:shop.test,DNS:www.shop.test\nextendedKeyUsage=serverAuth\n" > ext.cnf
openssl x509 -req -in leaf.csr -CA int.crt -CAkey int.key -CAcreateserial \
  -out leaf.crt -days 90 -extfile ext.cnf

Step 4: check the chain offline

$ openssl verify -CAfile ca.crt leaf.crt
CN=shop.test
error 20 at 0 depth lookup: unable to get local issuer certificate
error leaf.crt: verification failed

$ openssl verify -CAfile ca.crt -untrusted int.crt leaf.crt
leaf.crt: OK

Real output. The first check fails because nothing links the leaf to the root. Giving the intermediate (-untrusted means "use this to build the chain, but do not trust it by itself") fixes it.

Step 5: run servers and connect

# server that sends only the leaf (a common mistake)
openssl s_server -accept 8444 -cert leaf.crt -key leaf.key -www -quiet &
# server that sends leaf + intermediate (correct)
openssl s_server -accept 8445 -cert leaf.crt -cert_chain int.crt -key leaf.key -www -quiet &

echo | openssl s_client -connect 127.0.0.1:8445 -verify_hostname shop.test \
  -CAfile ca.crt -verify_return_error

Real results, trimmed to the verification lines:

port 8444 (leaf only):
  depth=0 CN=shop.test
  verify error:num=20:unable to get local issuer certificate
  Verification error: unable to get local issuer certificate

port 8445 (full chain):
  depth=2 CN=Demo Root CA           verify return:1
  depth=1 CN=Demo Intermediate CA   verify return:1
  depth=0 CN=shop.test              verify return:1
   0 s:CN=shop.test              i:CN=Demo Intermediate CA
   1 s:CN=Demo Intermediate CA   i:CN=Demo Root CA

"depth" counts up from the leaf (0). s: is the subject and i: the issuer of each certificate the server sent. Each i: must match the next line's s:.

Step 6: break it three more ways

We also made a leaf signed directly by the root (server.crt, on port 8443) and one whose dates had already passed (-not_before 20260101000000Z -not_after 20260301000000Z, on port 8446). Real results:

# 1. wrong name: asked for api.other.test, certificate says shop.test
verify error:num=62:hostname mismatch

# 2. unknown CA: we did not pass -CAfile, so our demo root is not trusted
verify error:num=20:unable to get local issuer certificate

# 3. expired certificate
verify error:num=10:certificate has expired
curl: (60) SSL certificate problem: certificate has expired

# curl, connecting by IP instead of name
curl: (60) SSL: no alternative certificate subject name matches target ipv4 address '127.0.0.1'

# curl, correct CA and correct name (the --resolve flag maps shop.test to 127.0.0.1)
$ curl -s -o /dev/null -w "%{http_code}\n" --cacert ca.crt \
    --resolve shop.test:8443:127.0.0.1 https://shop.test:8443/
200

A surprise from Python 3.13

Our first attempt made the root CA without the keyUsage line. openssl and curl accepted it. Python 3.13 refused it:

ssl.SSLCertVerificationError: [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed:
CA cert does not include key usage extension (_ssl.c:1029)

Python 3.13 turned on strict checking (VERIFY_X509_STRICT) in its default settings. A CA certificate that is missing the fields the standard requires now fails, even though older tools allowed it. This is why the root in Step 1 has a keyUsage line. Lesson: different TLS clients check different things. Test your certificates with the actual clients your users run.

9. Reading TLS Errors

Error (typical wording)What it meansUsual fix
"unable to get local issuer certificate" (openssl 20), "PKIX path building failed" (Java)The client cannot link the certificate to a root it trustsServe the full chain; or add your private CA to the client's trust store
"self-signed certificate" (openssl 18 or 19)The server sent a certificate that signs itself, or a chain ending in an untrusted rootUse a real CA, or trust the private root on purpose
"hostname mismatch" (62), "no alternative certificate subject name matches"The name you connected to is not in the SAN listAdd the name to the SAN; connect by name, not IP; check SNI is sent
"certificate has expired" (10), "not yet valid" (9)Outside the date range. "Not yet valid" often means the client's clock is wrongRenew; fix the clock (NTP)

The fastest debugging command is:

openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

It shows every certificate the server sends, the chain it built, and the verification result. Always pass -servername, or a server that hosts many sites may send the wrong certificate.

10. Getting and Renewing Certificates

Public certificates usually come from Let's Encrypt or another CA using ACME, an automatic protocol. The CA checks you control the name by asking you to prove it, for example by serving a token at http://yoursite/.well-known/acme-challenge/... (HTTP-01) or by creating a DNS TXT record (DNS-01, needed for wildcard names like *.shop.test).

Certificate lifetimes keep getting shorter. Let's Encrypt certificates have long lasted 90 days (and it has announced plans to shorten them further), and the CA/Browser Forum (the group of browsers and CAs that sets the rules) has voted to cut the maximum lifetime of public certificates in steps, down to 47 days by 2029. At that pace, renewing by hand is not an option: renewal must be automatic, and there must be an alert if it fails.

In Kubernetes, cert-manager does this: you declare a Certificate resource, it talks ACME, stores the result in a Secret, and renews before expiry. (See Kubernetes Config, Secrets & Security.)

Checking expiry from a script

# exit code 1 if the certificate expires within 90 days (7,776,000 seconds)
$ openssl x509 -in leaf.crt -noout -checkend 7776000; echo $?
Certificate will expire
1
# exit code 0 if it is still valid 30 days (2,592,000 s) from now
$ openssl x509 -in leaf.crt -noout -checkend 2592000; echo $?
Certificate will not expire
0

Real output for our 90-day leaf. A daily job that runs this against every live site, and alerts when fewer than 14 days remain, prevents the most common TLS outage of all: a certificate that silently expired.

11. Mutual TLS: When the Server Checks the Client Too

Normal TLS only proves the server's identity. The client proves who it is later, with a password or a token inside HTTP. In mutual TLS (mTLS), the server also asks for a client certificate during the handshake (a CertificateRequest message), and the client answers with its certificate and a signature.

  • Where it is used: service-to-service traffic inside a company, banking APIs, IoT devices. Service meshes such as Istio and Linkerd give every pod a short-lived certificate and turn on mTLS between all pods automatically.
  • What it gives: a stolen password is not enough; the attacker would also need the private key. And each service has a strong identity ("this request came from payments").
  • What it costs: you must run a private CA, hand out certificates, and rotate them. That is exactly the boring work meshes automate.

With openssl, the lab server would add -Verify 1 -CAfile ca.crt to require client certificates, and the client would add -cert client.crt -key client.key.

12. TLS at Load Balancers and Proxies

Most sites do not run TLS in the app itself. A load balancer (a machine that spreads incoming connections over many servers, see Proxies, Load Balancers, and CDNs and the deep dive Load Balancing & Reverse Proxies) usually handles it. There are three layouts:

1. TLS termination        client ══TLS══► LB ──plain HTTP──► app
2. Re-encryption          client ══TLS══► LB ══new TLS════► app
3. TLS passthrough (L4)   client ══════════TLS═════════════► app
                                   (LB only sees TCP + SNI)
LayoutGoodWatch out
TerminationOne place for certificates; the LB can read HTTP, so it can route by path, add headers, cacheTraffic inside the network is plain text. Fine only if that network is trusted.
Re-encryptionRouting by path and encrypted all the wayTwo sets of certificates; a little more CPU
PassthroughOnly the app holds the private key; works for any protocol over TLSThe LB cannot see paths or headers. It can only route by SNI or IP.

Two details that cause real bugs:

  • After termination, the app sees the LB's IP, not the user's, and sees plain HTTP. The LB passes the real details in headers like X-Forwarded-For and X-Forwarded-Proto: https. An app that ignores X-Forwarded-Proto may think the request was HTTP and redirect to HTTPS forever (a redirect loop).
  • Tell browsers to always use HTTPS with the header Strict-Transport-Security: max-age=31536000 (HSTS). After the first visit, the browser will not even try plain HTTP for a year, so nobody can quietly downgrade the user.

13. Common Pitfalls

  • Turning verification off (curl -k, verify=False in Python requests, InsecureSkipVerify in Go) "just to make it work". You still get encryption, but to anyone. It removes the whole point. Add the right CA instead.
  • Serving only the leaf. Works in some browsers, fails in curl, Python, Java and mobile apps.
  • Forgetting a name in the SAN. shop.test and www.shop.test are different names. A wildcard covers one level only.
  • Manual renewals. The certificate expires on a holiday. Automate and alert.
  • Wrong clocks. A device with its clock set to 2020 rejects every certificate as "not yet valid".
  • Committing private keys to Git or baking them into container images. Treat them as secrets; store them in a secret manager.
  • Allowing TLS 1.0/1.1 for "old clients". They have known weaknesses. Use TLS 1.2 as the minimum, prefer 1.3.
  • Using 0-RTT for non-idempotent requests. Early data can be replayed.
  • Assuming all clients check the same things. Our lab showed Python 3.13 rejecting a CA that openssl and curl accepted.

14. Practice Problems

Work these out first. Answers follow each one.

Problem 1: Diffie-Hellman by hand

p = 23, g = 5. Alice's secret is a = 4, Bob's is b = 3. What do they send, and what shared secret do they get?

Answer: A = 54 mod 23 = 625 mod 23 = 4 (23 × 27 = 621). B = 53 mod 23 = 125 mod 23 = 10 (23 × 5 = 115). Alice: 104 mod 23 = 10,000 mod 23 = 18 (23 × 434 = 9,982). Bob: 43 mod 23 = 64 mod 23 = 18. Both get 18.

Problem 2: does the name match?

A certificate has SAN DNS:*.shop.test, DNS:shop.test. Which of these pass: shop.test, api.shop.test, v2.api.shop.test, shop.test.evil.com?

Answer: shop.test passes (listed). api.shop.test passes (wildcard covers one label). v2.api.shop.test fails (two labels). shop.test.evil.com fails (a completely different name).

Problem 3: read the chain

openssl s_client -showcerts shows only 0 s:CN=api.shop.test i:CN=R11 and then "unable to get local issuer certificate". The site works in Chrome. What is wrong and how do you fix it?

Answer: The server sends only the leaf. Chrome found the intermediate "R11" on its own; other clients do not. Configure the server with the full chain file (leaf followed by the R11 intermediate), not just the leaf.

Problem 4: how many round trips?

RTT is 80 ms. A new HTTPS request needs a TCP handshake, a TLS handshake, then one round trip for the request and response. How long before the first byte arrives with TLS 1.3? With TLS 1.2? (Ignore DNS and server time.)

Answer: TLS 1.3: TCP 1 RTT + TLS 1 RTT + HTTP 1 RTT = 3 × 80 = 240 ms. TLS 1.2: 1 + 2 + 1 = 4 RTTs = 320 ms. A reused connection needs only the HTTP round trip: 80 ms.

Problem 5: which layout?

You run an API on Kubernetes. Security rules say traffic must be encrypted on every network hop. You also want the load balancer to send /v2/ to new pods and everything else to old pods. Which TLS layout do you choose?

Answer: Re-encryption. Termination would leave the LB-to-pod hop in plain text. Passthrough would hide the path, so the LB could not route on /v2/.

Problem 6: renewal alert

Write the openssl command that exits with an error if site.crt expires in the next 14 days.

Answer: 14 days = 14 × 86,400 = 1,209,600 seconds. openssl x509 -in site.crt -noout -checkend 1209600. It exits with 1 if the certificate will expire within that time.

openssl verify -CAfile root.pem -untrusted intermediate.pem leaf.pem

# expires within 14 days? (exit code 1 = yes)
openssl x509 -in cert.pem -noout -checkend 1209600

# curl: show the TLS handshake time
curl -so /dev/null -w 'tcp=%{time_connect} tls=%{time_appconnect}\n' https://HOST/

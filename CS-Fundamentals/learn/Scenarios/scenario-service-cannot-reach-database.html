Scenario: A Service Cannot Reach Its Database

A team moves its checkout service to a new Kubernetes cluster. Every pod fails to start with "Connection timed out" when it connects to PostgreSQL, even though the database is healthy and the old servers still connect fine. This page follows the investigation step by step, the way an on-call engineer would, and uses ideas from the IP addressing, DNS, and TCP pages. The company, names, and addresses are made up, but every step and error message is real.

1. The Situation

A shop's network in the cloud looks like this:

  • Network A (the old one), range 10.0.0.0/16. It holds the PostgreSQL database at 10.0.12.34, port 5432, with the private DNS name db.internal. The old checkout servers also live here.
  • Network B (new), range 10.1.0.0/16. A new Kubernetes cluster runs here. Network A and Network B are joined with peering, a cloud feature that routes traffic between two private networks. Peering only works if the two ranges do not overlap, and 10.0.0.0/16 and 10.1.0.0/16 do not. So far, so good.

On Tuesday at 11:05 IST, the team deploys the checkout service to the new cluster. Every pod crashes at start-up. The log says:

psycopg.OperationalError: connection failed: connection to server at "10.0.12.34",
port 5432 failed: Connection timed out
        Is the server running on that host and accepting TCP/IP connections?

Meanwhile, the old checkout servers in Network A talk to the same database with no problem. The database dashboard shows normal CPU and normal connections.

A pod is Kubernetes' smallest unit: one or more containers that share a network address. A node is a machine in the cluster that runs pods. (See Kubernetes Architecture.)

2. Read the Error First: What Each Message Means

The exact wording of a connection error tells you how far the attempt got. Learning this table saves hours.

Error message (typical wording)What happened on the wireUsual causes
"could not translate host name", "Name or service not known", NXDOMAINNever got an IP address. No packet was sent to the database.Typo in the name, private DNS zone not visible from this network, DNS server unreachable
"Connection refused"The packet reached the machine, and it answered "no" right away (a TCP reset, RST).Nothing listening on that port, server listening only on 127.0.0.1, wrong port, a firewall set to REJECT
"Connection timed out"The client sent SYN packets and nothing ever came back.A firewall that silently DROPs, a missing or wrong route, the reply going somewhere else, host down
"No route to host"The local machine has no route, or a router sent back an "unreachable" message.Missing route, a firewall REJECT that uses ICMP, the target down on the local subnet (ARP fails)
"Connection reset by peer" (after working a while)A connection existed, then something killed it.Idle timeout on a NAT or load balancer, server restarted, proxy limits
"certificate verify failed", "SSL is required"TCP works. The TLS handshake failed.Missing CA certificate, wrong host name in the certificate, TLS turned off on one side
"password authentication failed", "no pg_hba.conf entry"TCP and TLS worked. The database rejected the login.Wrong secret, the server's access rules do not allow this source address or user
"sorry, too many clients already"Everything worked, but the database is out of connection slots.Too many pods × too big a pool (section 11)
Intuition: "refused" means you knocked and someone said "go away". "Timed out" means you knocked and heard nothing: the door might not exist, someone might be ignoring you, or the answer went to the wrong house. Our error is a timeout, so we are looking for packets that are dropped or lost, not for a stopped database.

3. Draw the Path

Before running commands, write down every hop the connection should take. Each arrow is a place it can fail.

  checkout pod          node (VM)           Network B           peering          Network A
  10.0.3.17 (?)   ->   10.1.20.15     ->   route table   ->   connection  ->   route table
                                                                                    |
                                                                                    v
                                                        security group  ->  PostgreSQL 10.0.12.34:5432

  Layers to check, in order:
    name   ->  DNS gives 10.0.12.34?
    route  ->  does each hop send the packet the right way, and can the reply come back?
    filter ->  do firewalls allow it both ways?
    port   ->  is PostgreSQL listening?
    TLS, login, limits  ->  only after TCP works

Notice the question mark on the pod's address. The pod's IP looks like 10.0.3.17. That is odd: Network A uses 10.0.0.0/16, and this pod lives in Network B. Keep that in mind; it will matter.

4. Step 1: Does the Name Resolve?

The error already shows the IP address (10.0.12.34), so DNS probably worked. But it is cheap to check, and it rules out a whole layer. Start a temporary debug pod in the same namespace (the netshoot image is a common toolbox for this):

$ kubectl run netdebug -it --rm --image=nicolaka/netshoot -n checkout -- bash

netdebug$ getent hosts db.internal
10.0.12.34      db.internal

getent hosts asks the same resolver the app uses (including /etc/hosts and the Kubernetes search list), which makes it a better test than dig for "what does my app see". DNS is fine.

5. Step 2: Can We Open a TCP Connection?

Take the app out of the picture. If a plain TCP connection fails, no amount of app debugging will help.

netdebug$ nc -vz -w 3 10.0.12.34 5432
nc: connect to 10.0.12.34 port 5432 (tcp) timed out: Operation now in progress
  • nc (netcat) tries a raw TCP connection. -z means "just connect, send nothing". -v prints the result. -w 3 gives up after 3 seconds.

It times out, just like the app. The problem is below the app: somewhere in routing or filtering.

6. Step 3: Narrow It Down by Changing One Thing

The fastest way to find a network problem is to repeat the same test from different places and see where it starts failing.

Test fromSource addressResult
Old checkout server, Network A10.0.4.21Connects
A plain VM in Network B (not part of the cluster)10.1.5.10Connects
A cluster node, Network B (logged in with SSH)10.1.20.15Times out
A pod on that node10.0.3.17Times out

This one table rules out a lot:

  • The database is up and listening (Network A connects).
  • Peering works, and the database's firewall allows Network B (the plain VM connects).
  • The failure starts at the cluster nodes. Something on the nodes themselves is different from a plain VM in the same network.

7. Step 4: Firewalls and Security Groups

A security group is a cloud firewall attached to a machine or database. It has rules like "allow TCP 5432 from 10.1.0.0/16". Anything not allowed is silently dropped, which produces exactly a timeout. So it is always worth checking, even though step 3 suggests it is fine here.

  • The database's security group allows TCP 5432 from 10.0.0.0/16 and 10.1.0.0/16. The node 10.1.20.15 is inside 10.1.0.0/16. Allowed.
  • The nodes' security group allows all outbound traffic. Allowed.
  • Kubernetes NetworkPolicies (firewall rules between pods, see Kubernetes Networking) could block pods, but the node itself also fails, and policies do not apply to the node.

Firewalls are not the cause. What else is different on a cluster node? Its routing table: the cluster's network plugin adds routes for pod traffic.

8. Step 5: Follow the Packet with ip route get and tcpdump

First, ask the node's kernel where it would send a packet to the database. This runs the real longest prefix match:

node$ ip route get 10.0.12.34
10.0.12.34 via 10.0.12.0 dev flannel.1 src 10.0.3.0 uid 1000

Compare with the plain VM in the same network:

vm$ ip route get 10.0.12.34
10.0.12.34 via 10.1.0.1 dev eth0 src 10.1.5.10 uid 1000

The VM sends the packet to the network's gateway (10.1.0.1) on eth0, the real network card. The node sends it into flannel.1. flannel is the cluster's network plugin: it builds a private "overlay" network for pods, and flannel.1 is its tunnel interface. The node thinks 10.0.12.34 is a pod on another node.

Look at the full table to see why:

node$ ip route
default via 10.1.0.1 dev eth0
10.0.0.0/24 via 10.0.0.0 dev flannel.1 onlink
10.0.1.0/24 via 10.0.1.0 dev flannel.1 onlink
10.0.2.0/24 via 10.0.2.0 dev flannel.1 onlink
10.0.3.0/24 dev cni0 proto kernel scope link src 10.0.3.1      <- this node's own pods
...
10.0.12.0/24 via 10.0.12.0 dev flannel.1 onlink                <- pods on node #13
...
10.1.0.0/16 dev eth0 proto kernel scope link src 10.1.20.15

Apply longest prefix match by hand for the destination 10.0.12.34:

RouteMatches 10.0.12.34?Prefix length
default (0.0.0.0/0) via 10.1.0.1Yes0
10.1.0.0/16 dev eth0No 
10.0.12.0/24 via flannel.1Yes24, wins

The /24 pod route is more specific than the default route, so the packet goes into the tunnel to node #13, which has no database on it. It is dropped there. No reply ever comes: timeout.

Confirm with tcpdump

tcpdump prints the packets crossing a network interface. Watch both interfaces while running nc again in another terminal:

node$ sudo tcpdump -ni any host 10.0.12.34 and port 5432
11:52:01.204 flannel.1 Out IP 10.0.3.0.40312 > 10.0.12.34.5432: Flags [S], seq 1803321377, length 0
11:52:02.230 flannel.1 Out IP 10.0.3.0.40312 > 10.0.12.34.5432: Flags [S], seq 1803321377, length 0
11:52:04.278 flannel.1 Out IP 10.0.3.0.40312 > 10.0.12.34.5432: Flags [S], seq 1803321377, length 0

How to read it: [S] is a SYN, the first packet of the TCP handshake (see TCP handshake). The same SYN is resent after 1 second, then 2 seconds later: TCP's retry timer doubling. There is never a [S.] (SYN-ACK) coming back. And every packet leaves on flannel.1, never on eth0. That proves the routing theory.

9. The Root Cause: Overlapping Address Ranges

The cluster's pod range was set to 10.0.0.0/16. That is the same range as Network A, where the database lives. Each node gets a /24 slice of it for its pods: node #1 gets 10.0.0.0/24, node #4 gets 10.0.3.0/24 (our node), and node #13 gets 10.0.12.0/24, which happens to contain the database's address.

  10.0.0.0/16  as Network A sees it:    db subnet 10.0.12.0/24   (database 10.0.12.34)
  10.0.0.0/16  as the cluster sees it:  pod slice 10.0.12.0/24   (pods on node #13)
                                        same numbers, two different places

How did it happen? The cluster's configuration was copied from a test cluster where 10.0.0.0/16 was free. The cloud did not complain, because the pod range only exists inside the cluster; the cloud only checks the network ranges it manages (10.1.0.0/16).

Why it fails in both directions

Even destinations that do not hit a pod route would break. Suppose the database were at 10.0.200.5, a slice no node owns yet. The packet would go out through the default route correctly. But pods send packets from their pod address (like 10.0.3.17). Normally the node replaces the pod address with its own node address on the way out (a form of NAT called masquerading, see NAT). But the plugin does not masquerade traffic to addresses inside the pod range, because it assumes those are other pods. So the database would see a packet from 10.0.3.17 and send its reply to Network A's own local 10.0.3.0/24 subnet. The reply would never return.

And it would get worse with time: as the cluster grows, more nodes take more /24 slices, and more of Network A becomes unreachable.

The lesson: a router cannot tell two places apart if they use the same numbers. Overlapping ranges do not fail loudly; they fail as timeouts that depend on exactly which address you try. This is why address planning matters.

10. Mitigate Now, Fix Properly Later

On-call work has two separate goals. Mitigation stops the harm quickly, even if it is ugly. The fix removes the cause.

Mitigation (same day)

The plain VM at 10.1.5.10 can reach the database, and its address is not in the pod range. So the team runs PgBouncer (a small connection proxy for PostgreSQL) on that VM, and points the checkout pods at it:

  pod 10.0.3.17  -->  PgBouncer 10.1.5.10:6432  -->  PostgreSQL 10.0.12.34:5432
       (10.1.5.10 is in 10.1.0.0/16: normal route via eth0, and masqueraded to the node IP)
node$ ip route get 10.1.5.10
10.1.5.10 dev eth0 src 10.1.20.15 uid 1000
netdebug$ nc -vz -w 3 10.1.5.10 6432
Connection to 10.1.5.10 6432 port [tcp/*] succeeded!

It is a single extra machine in the path, so it is a temporary step, but checkout runs on the new cluster by 13:40 IST. The old servers keep running as a fallback.

Proper fix (planned)

The pod range of a running cluster usually cannot be changed in place. The team:

  1. Picks a new pod range that overlaps with nothing in the company's address list. They choose 100.64.0.0/16, part of the shared range many teams use for pod networks because it is rarely used by offices or clouds (see special ranges).
  2. Builds a new cluster with that range, moves the workloads over, and deletes the old cluster.
  3. Checks from a node: ip route get 10.0.12.34 now goes via 10.1.0.1 dev eth0.
  4. Removes the PgBouncer workaround, or keeps it on purpose for the reason in the next section.

11. The Next Errors: TLS and Connection Limits

Fixing a network problem often reveals the next problem up the stack, because now the connection gets further. Two came up during the move. (For how TLS certificates are checked, and every common certificate error reproduced on purpose, see TLS, HTTPS & Certificates.)

"no pg_hba.conf entry ... no encryption"

FATAL: no pg_hba.conf entry for host "10.1.20.15", user "checkout", database "shop", no encryption

This is good news: TCP works now. PostgreSQL's access file (pg_hba.conf) only accepts connections from Network B if they use TLS (hostssl lines). The new deployment had dropped sslmode=require from its connection string. Adding it back fixed the error. Better still is sslmode=verify-full with the database's CA certificate, which also checks that you are talking to the real server.

"sorry, too many clients already"

A day later, during a sale, the cluster scaled the checkout service to 40 pods. Each pod's connection pool was set to 20 connections:

  40 pods x 20 connections = 800 connections wanted
  PostgreSQL max_connections = 200
  -> new connections fail with "sorry, too many clients already"

How many connections does the work really need? Use Little's law from the slow-API scenario: busy connections = requests per second × time each request holds a connection. At the sale peak, 2,000 queries per second × 0.010 s = 20 busy connections on average. 800 was 40 times more than needed.

Fix: keep PgBouncer, now as a deliberate shared pool. Pods connect to PgBouncer (cheap), and PgBouncer keeps about 40 real connections to PostgreSQL in "transaction" mode, handing a connection to a pod only for the length of one transaction. The pod pool size was also lowered to 5.

12. Blameless Postmortem

A postmortem is a short write-up after an incident. "Blameless" means it looks for weak points in systems and processes, not for a person to blame. People make mistakes; good systems catch them.

Time (IST)Event
Tue 11:05Checkout deployed to the new cluster. All pods crash with "Connection timed out".
11:12Rollback not needed: old servers still serve all traffic. Investigation starts.
11:20DNS and database health confirmed fine. nc times out from pods.
11:35Comparison table: plain VM works, nodes fail. Focus moves to the nodes.
11:48ip route get shows traffic going into flannel.1. tcpdump confirms SYNs with no replies.
12:05Root cause found: pod range 10.0.0.0/16 overlaps Network A.
13:40PgBouncer on a plain VM in place. Checkout runs on the new cluster.
Following weekNew cluster with pod range 100.64.0.0/16. Old cluster removed.

Impact: none for customers (the old servers kept serving). About 2.5 hours of engineering time, and a one-week delay to the move.

What went well: the old servers were kept running during the move; the team tested one layer at a time; the comparison table found the right area in 15 minutes.

What went wrong: no central list of address ranges existed; the cluster config was copied without review of its address ranges; nothing in CI checked for overlaps.

Action items:

  1. Create an address registry (a shared file listing every range and its owner). Owner: platform team.
  2. Add a CI check that fails if any new range overlaps the registry (next section).
  3. Add the "can every node reach the database" test to the cluster's acceptance checklist.
  4. Set connection pool sizes from measured load, and keep PgBouncer as the shared pool.

13. Preventing It: An Address Registry and a CI Check

The registry can be as simple as a text file in a repository. A short script, run in CI on every change, catches overlaps before anything is built:

#!/usr/bin/env python3
"""Fail if any two address ranges in the registry overlap."""
import ipaddress
import itertools
import sys

REGISTRY = {
    "network-a (old prod)":    "10.0.0.0/16",
    "network-b (new prod)":    "10.1.0.0/16",
    "office vpn":              "172.20.0.0/16",
    "docker default bridge":   "172.17.0.0/16",
    "cluster-2 pods":          "100.64.0.0/16",
    "cluster-2 services":      "100.65.0.0/20",
    "cluster-1 pods (old)":    "10.0.0.0/16",     # the mistake from this incident
}

nets = {name: ipaddress.ip_network(cidr) for name, cidr in REGISTRY.items()}
problems = [
    (a, b) for a, b in itertools.combinations(nets, 2) if nets[a].overlaps(nets[b])
]
for a, b in problems:
    print(f"OVERLAP: {a} {nets[a]}  <->  {b} {nets[b]}")
sys.exit(1 if problems else 0)

Output with the old cluster still listed:

OVERLAP: network-a (old prod) 10.0.0.0/16  <->  cluster-1 pods (old) 10.0.0.0/16

The script exits with code 1, so the CI job fails and the change cannot be merged. Remove the old cluster's line and it passes.

14. Practice Problems

Try each one before reading the answer.

Problem 1: read the error

An app logs "Connection refused" to 10.0.12.34:5432. The database server is running. Name two likely causes and one command to check each.

Answer: A refusal means the packet reached the machine. (1) PostgreSQL listens only on 127.0.0.1: on the server, ss -ltnp | grep 5432 shows 127.0.0.1:5432 instead of 0.0.0.0:5432; fix listen_addresses. (2) Wrong port: check the server's real port with the same ss command and compare with the app's setting. (A firewall set to REJECT is a third possibility: check its rules.)

Problem 2: longest prefix match

A node has these routes: default via 10.1.0.1 dev eth0, 10.1.0.0/16 dev eth0, 100.64.0.0/16 via ... dev flannel.1, 100.64.7.0/24 dev cni0. Where do packets to 10.0.12.34, 100.64.7.9, 100.64.9.9, and 10.1.5.10 go?

Answer: 10.0.12.34: only the default matches → eth0 via 10.1.0.1 (correct for the database now). 100.64.7.9: matches /16 and /24 → cni0, a pod on this node. 100.64.9.9: matches the /16 → flannel.1, a pod on another node. 10.1.5.10: matches 10.1.0.0/16 → eth0 directly, same network.

Problem 3: which hosts break?

A cluster uses pod range 10.0.0.0/16 and gives each node a /24, in order from 10.0.0.0/24. It has 6 nodes. Which of these Network A addresses are unreachable from the nodes because of a pod route: 10.0.2.8, 10.0.5.200, 10.0.6.1, 10.0.12.34?

Answer: 6 nodes own 10.0.0.0/24 through 10.0.5.0/24. So 10.0.2.8 and 10.0.5.200 hit pod routes and break. 10.0.6.1 and 10.0.12.34 have no pod route yet, so packets leave via the default route. But pod traffic to them is still not masqueraded (they are inside the pod range), so replies go to the wrong place: they also fail from pods. And as more nodes join, more addresses hit pod routes.

Problem 4: pool sizing

A service handles 900 requests per second at peak. Each request runs two queries, each holding a connection for 4 ms. It runs on 30 pods. The database allows 300 connections, and you want to keep 50 free for admin tools and other services. What pool size per pod is safe, and how many connections are actually busy on average?

Answer: Busy connections = 900 × 2 × 0.004 = 7.2 on average. Budget = 300 − 50 = 250, so per pod at most 250 ÷ 30 ≈ 8. A pool of 3–5 per pod already gives 90–150 connections, far above the 7.2 needed, with room for bursts.

Problem 5: what does tcpdump tell you?

On the client you see Flags [S] going out on eth0, then Flags [R.] coming back from the server 0.4 ms later. What error does the app show, and what does it mean?

Answer: [R.] is a reset. The app shows "Connection refused". The path and routing are fine (the reply came back quickly), but nothing accepts connections on that port, or a firewall is set to REJECT.

15. Common Pitfalls

  • Debugging the app before the network. Run nc -vz first. If raw TCP fails, the app is not the problem.
  • Testing from your laptop instead of from where the app runs. Your laptop has different routes, DNS, and firewall rules. Use a debug pod on the same node.
  • Treating "timed out" and "refused" as the same thing. They point to completely different layers.
  • Copying cluster or network config without checking its address ranges. Defaults and copied values are the most common cause of overlaps.
  • Assuming the cloud will stop overlaps. It only checks the ranges it manages. Pod ranges, Docker bridges, and VPNs are your responsibility.
  • Stopping at the first fix. After the network works, expect TLS, login, and connection-limit errors next. Each one is progress.
  • Sizing connection pools by guesswork. Pods × pool size must stay below the database limit at maximum scale. Use Little's law and a shared pool.

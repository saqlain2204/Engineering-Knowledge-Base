Scenario: Debugging a Slow API End to End

A story that uses every CS Fundamentals page at once. An API that was fast yesterday is slow today. We follow the clues layer by layer: network, operating system, application, and database. Along the way you learn the small set of numbers and tools that find almost any slowdown.

1. The Situation

A shop runs an API behind a load balancer. The endpoint GET /api/orders?customer=... powers the "My orders" screen of the mobile app.

  • Normal day: about 200 requests per second, and 99% of requests finish within 120 ms.
  • Today a sale campaign starts at 18:00. Traffic doubles to 400 requests per second.
  • By 18:10, some requests take over 3 seconds. Some users get 504 Gateway Timeout. The app's error rate climbs to 8%.

Our job: find the cause, fix it, and make sure it does not happen again. The temptation is to guess ("the database is slow!", "add more servers!"). Guessing often works on small problems and fails on real ones. We will measure each layer instead.

Intuition: debugging a slow system is like finding where a traffic jam starts. You do not stand in one spot and guess. You check the road in sections. The first section where cars are crawling, but the one after it is clear, is where the jam begins.

2. Words for Speed: Latency, Percentiles, Throughput

  • Latency: how long one request takes, from start to finish.
  • Throughput: how many requests are finished per second.
  • Utilization: what fraction of time a resource (CPU, disk, a connection) is busy.
  • Saturation: work that is waiting because the resource is already busy. A queue.

Why averages lie: percentiles

Here are 20 real-looking request times in milliseconds, sorted:

45 48 50 52 52 55 58 60 61 63 65 70 72 75 80 90 110 150 900 2400

The average (mean) is 4,556 / 20 = 227.8 ms. But no request actually took about 228 ms. Most were around 60 ms, and two were terrible.

A percentile answers "how slow is the request that is slower than X% of all requests?" Using the simple nearest-rank rule: sort the values, and the p-th percentile is the value at position ceil(p/100 × n).

NamePosition (n = 20)ValuePlain meaning
p50 (median)ceil(0.50 × 20) = 10th63 msA typical request
p90ceil(0.90 × 20) = 18th150 ms1 in 10 is slower than this
p95ceil(0.95 × 20) = 19th900 ms1 in 20 is slower than this
p99ceil(0.99 × 20) = 20th2,400 msThe "tail": 1 in 100 is slower

Why care about the tail? A single screen often makes many API calls. If a page makes 10 calls and each one has a 1% chance of being slow, the chance that at least one is slow is 1 - 0.9910 ≈ 9.6%. Rare slowness per call becomes common slowness per user. That is why teams set goals on p95 or p99, not on the average.

A service level objective (SLO) is such a goal written down, for example: "99% of /api/orders requests finish within 300 ms, measured over 30 days."

3. Draw the Map First

Before touching any tool, draw every hop one request makes. Each arrow is a place where time can be spent or a queue can form.

  phone app
     |  DNS lookup, TCP + TLS handshake            (network)
     v
  load balancer  ----  timeout 3 s  ----+
     |                                  |
     v                                  v
  API server 1 ... API server 4         (OS: CPU, memory, threads)
     |  each server: 50 worker threads
     |  each server: DB connection pool of 10
     v
  PostgreSQL primary                    (database: queries, locks, disk)

Write the limits on the map too: the load balancer gives up after 3 seconds (that is where the 504s come from), each server has a pool of 10 database connections, so all four servers together can hold at most 40 connections.

4. Two Checklists: RED and USE

Two short checklists cover almost everything.

RED, for each service (Tom Wilkie)

  • Rate: requests per second.
  • Errors: failed requests per second.
  • Duration: latency percentiles.

USE, for each resource (Brendan Gregg)

  • Utilization: how busy is it?
  • Saturation: is work queuing up?
  • Errors: is it reporting failures?

RED tells you which service hurts. USE tells you which resource inside it is the bottleneck. Here is our first RED reading at 18:15:

ServiceRateErrorsp50p99
Load balancer400/s8% (504)1.9 s3.0 s (the timeout)
API servers400/s8%1.9 s3.0 s
PostgreSQL~380 queries/s0100 ms140 ms

Look closely at the last row. The API receives 400 requests per second, and each request needs one database query, but the database only completes about 380 per second. And each query takes about 100 ms, yet the API's requests take 1,900 ms. Where do the other 1,800 ms go? Hold on to that question.

5. Step 1: Network or Server?

First split the time into network parts and server parts. curl can print the time at the end of each phase (see TCP Deep Dive for the details of each phase):

curl -s -o /dev/null -w \
 'dns:     %{time_namelookup}s\nconnect: %{time_connect}s\ntls:     %{time_appconnect}s\nttfb:    %{time_starttransfer}s\ntotal:   %{time_total}s\n' \
 'https://api.shop.example/api/orders?customer=4242'

The times are cumulative (each one counts from the very start). Example output during the incident:

dns:     0.004s
connect: 0.031s
tls:     0.064s
ttfb:    2.212s
total:   2.215s

Subtract to get each phase:

PhaseMathTimeVerdict
DNS0.0044 msFine (cached)
TCP connect0.031 - 0.00427 msFine, one round trip
TLS0.064 - 0.03133 msFine, about one round trip
Waiting for first byte2.212 - 0.0642,148 msProblem is here
Download2.215 - 2.2123 msFine

Time to first byte (TTFB) minus the handshakes is "one round trip plus server time". The round trip is about 30 ms, so the server is spending over 2 seconds. The network is not the problem. DNS (see DNS & HTTP) and TLS are healthy. We move inside the servers.

6. Step 2: Is the Machine Struggling?

Log in to one API server and run three quick commands. Each takes seconds and rules out a whole class of causes.

uptime: load average

$ uptime
 18:16:02 up 41 days,  load average: 1.12, 0.98, 0.85

The load average is roughly the number of threads running or ready to run, averaged over 1, 5, and 15 minutes. (On Linux it also counts threads stuck waiting on disk.) Compare it to the number of CPU cores. This server has 4 cores, so 1.12 means the CPU is mostly idle. If it said 12, threads would be queuing for CPU time.

vmstat: CPU, memory, and waiting, every second

The surprising conclusion

The CPU is idle, memory is fine, and the disk is quiet. Yet requests take 2 seconds. When a system is slow but idle, the requests are not working. They are waiting for something: a lock, a pool, or another service. (This is the same clue as in the frozen payments service.)

7. Step 3: Where Does the Request Spend Its Time?

Distributed tracing records how long each step inside a request takes. Each timed step is called a span, and the spans together form a trace. OpenTelemetry is the common standard; tools like Jaeger, Grafana Tempo, or Honeycomb draw the result as a "waterfall".

One slow trace from 18:16:

GET /api/orders?customer=4242                        [==================================] 2,200 ms
  auth.check_token                                   [=]                                      4 ms
  db.pool.acquire  (waiting for a free connection)     [==============================]   2,089 ms
  db.query  SELECT ... FROM orders WHERE ...                                          [==]     104 ms
  json.serialize                                                                         []     3 ms

There is the missing time. The query itself takes 104 ms, close to what the database reported. But the request waited 2,089 ms just to get a database connection from the pool.

A connection pool is a fixed set of open database connections that request threads borrow and return. Opening a new connection for every request is slow (handshake, login, memory on the database), so apps reuse a few. If all connections are in use, the next thread waits in line. This is exactly the bounded buffer from semaphores: a pool of 10 is a counting semaphore that starts at 10.

The pool's own metrics confirm it:

db_pool_connections_active     10     (of max 10)
db_pool_connections_idle        0
db_pool_pending_threads        48     <- threads waiting in line
db_pool_acquire_seconds_p99    2.9

Utilization 100% and a growing queue: in USE terms, the pool is saturated. But why? On a normal day the same pool is fine. Time for a little math.

8. Step 4: Little's Law and the Connection Pool

Little's law is one of the most useful formulas in all of systems work. For any stable system:

  L  =  λ  ×  W

  L = average number of items inside the system (busy connections, people in a shop)
  λ = arrival rate (items per second)                         λ is the Greek letter "lambda"
  W = average time each item spends inside (seconds)
Intuition: a coffee shop gets 2 customers per minute, and each one stays 10 minutes. On average, 2 × 10 = 20 customers are inside. If they start staying 30 minutes, you need room for 60, even though no more people are arriving.

Worked example: one API server

Each of the 4 servers gets a quarter of the traffic. Each request holds a connection for the length of its query.

Normal daySale day
Arrival rate per server, λ200 / 4 = 50 per s400 / 4 = 100 per s
Time a connection is held, W0.020 s0.100 s
Busy connections needed, L = λ × W50 × 0.020 = 1100 × 0.100 = 10
Pool size1010

On a normal day, 1 of 10 connections is busy on average. There is lots of spare room. On sale day, the server needs 10 busy connections on average, which is every connection, all the time. Two things changed at once:

  1. The arrival rate doubled (50 to 100 per second per server).
  2. The query got five times slower (20 ms to 100 ms). The database was busier, and (step 5 shows) each query had to scan more and more data.

Little's law multiplies them: 2 × 5 = 10 times more busy connections. Neither change alone would have filled the pool.

Real traffic is also bursty. 100 per second on average can mean 180 in one second and 20 in the next. As a resource gets close to 100% busy, waiting time does not grow gently; it shoots up. In the simplest queue model, a single server that is 80% busy already has about 4 requests in line or being served on average; at 95% busy, about 19.

Capacity: the other way to use the law

Rearranged, Little's law gives the most a pool can handle: max rate = pool size / W.

  one server, normal day, W = 0.020 s:   10 / 0.020 = 500 requests per second
  one server, sale day,   W = 0.100 s:   10 / 0.100 = 100 requests per second
  four servers on sale day:              4 × 100   = 400 per second = exactly today's traffic
  add a few ms per borrow (W = 0.105 s): 4 × 10 / 0.105 ≈ 381 per second

That last line matches the ~380 queries per second the database was completing. And this is the trap. Once requests arrive faster than they can be served, the line does not stay a fixed length. It grows every second. With 400 arriving and about 380 served, the line grows by about 20 every second. After 100 seconds, about 2,000 are waiting, and a new arrival must wait about 2,000 / 380 ≈ 5 seconds. The load balancer gives up at 3 seconds, which produces the 504s we saw.

Why not just make the pool bigger? It may help a little, but the pool is protecting the database. 4 servers × 50 connections = 200 connections, each one a process on the database server, all fighting for the same CPU and disk. The queries get even slower, so W goes up and L goes up with it. A bigger pool often moves the queue from the app into the database, where it is harder to see. Fix the W first.

9. Step 5: Find and Fix the Slow Query

The query is "only" 100 ms, but it is the thing that holds each connection. Making it fast shrinks W, which shrinks L. On the database:

What is running right now?

SELECT state, wait_event_type, wait_event, count(*)
FROM pg_stat_activity
WHERE datname = 'shop'
GROUP BY 1, 2, 3 ORDER BY 4 DESC;

 state  | wait_event_type | wait_event   | count
--------+-----------------+--------------+------
 active | IO              | DataFileRead |    26
 active |                 |              |    12
 idle   | Client          | ClientRead   |     2

No sessions are waiting on Lock, so this is not a locking problem (if it were, see locks and deadlocks). Many sessions are reading data files. That is the sound of big scans.

Which query costs the most in total?

SELECT calls, round(mean_exec_time::numeric, 1) AS avg_ms,
       round(total_exec_time::numeric / 1000) AS total_s, query
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 3;

  calls  | avg_ms | total_s | query
---------+--------+---------+-----------------------------------------------------
 1180410 |   98.7 |  116507 | SELECT id, status, amount, created_at FROM orders
         |        |         |   WHERE customer_id = $1 ORDER BY created_at DESC LIMIT $2
   20211 |    3.2 |      65 | SELECT ... FROM customers WHERE id = $1
    ...

One query uses almost all the database time. Its plan:

EXPLAIN ANALYZE SELECT id, status, amount, created_at FROM orders
WHERE customer_id = 4242 ORDER BY created_at DESC LIMIT 20;

 Limit
   ->  Sort  (Sort Key: created_at DESC)
         ->  Gather  (Workers Planned: 2)
               ->  Parallel Seq Scan on orders
                     Filter: (customer_id = 4242)
                     Rows Removed by Filter: 1999993
 Execution Time: 97.8 ms

A full table scan for every request. The orders table grew fast during the year (6 million rows now), and the scan grew with it. Nobody noticed at 200 requests per second, because 1 connection was enough. The sale doubled the rate and the slow query turned that into a full pool. Two small problems multiplied into one big one.

The fix

Build an index that matches the query exactly. This is worked through in detail in Indexing, B+ Trees & Query Plans:

CREATE INDEX CONCURRENTLY orders_customer_recent_idx
  ON orders (customer_id, created_at DESC) INCLUDE (status, amount);

CONCURRENTLY matters here: a normal CREATE INDEX would block writes to orders while it builds, in the middle of a sale. After the build, the plan becomes Limit -> Index Only Scan and the query takes about 0.1 ms.

Run Little's law again: L = 100 × 0.0001 = 0.01 busy connections per server. The pool goes from full to almost empty.

10. Step 6: Why It Got Worse: Retry Storms

One more detail from the RED numbers: at 18:20 the API was receiving more than 400 requests per second, even though the number of users had stopped growing. The mobile app retried failed requests up to 3 times, right away.

Do the math. If most requests time out and each is tried up to 4 times in total (1 + 3 retries):

  real user demand:            400 requests/s
  worst case with retries:     400 × 4 = 1,600 requests/s

The system was already over capacity at 400. Retries pushed even more work onto the busiest part, which made more requests fail, which caused more retries. This loop is called a retry storm. It can keep a system down even after the original cause is gone.

Safe retries follow four rules:

  1. Exponential backoff: wait longer before each try (for example 100 ms, 200 ms, 400 ms).
  2. Jitter: add a random part to each wait, so thousands of clients do not retry at the same instant.
  3. A retry budget: for example, retries may add at most 10% extra traffic. Past that, fail fast.
  4. Only retry what is safe: timeouts and 503s, and only for idempotent requests.

11. Step 7: Make It Fail Gracefully Next Time

The index fixes today's cause. These changes make the next unknown problem smaller:

ChangeWhat it does
Pool acquire timeout of 500 msA thread that cannot get a connection fails fast with a clear error, instead of waiting until the load balancer gives up at 3 s
Database statement timeout (SET statement_timeout = '2s' for the app's user)One runaway query cannot hold a connection forever
Load sheddingWhen the queue is too long, reply 503 with Retry-After: 2 at once. Serving 90% of users well beats serving 100% badly
Timeouts that shrink inwardLoad balancer 3 s > app 2.5 s > database 2 s. Inner layers give up first, so outer layers get a real error instead of waiting for nothing
A short cache for "My orders"Even 5 seconds of caching per customer removes repeat queries when users pull to refresh again and again
Alerts on saturation, not just errorsAlert when pool wait p99 > 100 ms or query p99 doubles. This would have warned weeks earlier, as the table grew
Backpressure again: load shedding and bounded pools are the same idea as the bounded buffer in producer-consumer. A system with an unbounded queue does not fail fast; it fails slowly for everyone at once.

12. Step 8: Prove the Fix

"It looks better" is not proof. Compare the same numbers before and after, at the same traffic:

Metric18:15 (before)18:45 (after index)
Request rate400/s (plus retries)400/s
Error rate8%0.02%
p50 / p99 latency1.9 s / 3.0 s18 ms / 65 ms
Pool active / pending10 / 480 to 1 / 0
Database CPU92%14%

Then test the limit on purpose. Run a load test in a staging copy with tools like k6, Locust, or wrk, slowly raising traffic to 2 to 3 times the expected peak. Watch p99 and pool wait. The point where p99 bends sharply upward is your real capacity. Write it down, and plan the next sale against it.

13. Step 9: Write a Blameless Postmortem

A postmortem is a short write-up after an incident. "Blameless" means it looks for how the system allowed the problem, not for a person to blame. People share more honestly when they feel safe, and the system gets better faster. A simple template:

Title:      Slow "My orders" API during sale launch (17 Nov, 18:05-18:42)
Impact:     8% of order-list requests failed for 37 minutes; p99 3 s.
Timeline:   18:00 sale starts, traffic 2x
            18:05 p99 latency alert
            18:16 trace shows 2 s waiting for DB pool
            18:24 pg_stat_statements points to orders query (seq scan)
            18:31 index build started CONCURRENTLY
            18:42 index ready, latency normal
Root cause: The orders query had no matching index. It slowed as the
            table grew. Double traffic then filled the connection pool.
            Immediate client retries tripled load.
What went well:  Tracing showed the pool wait within minutes.
What to improve: No alert on pool wait time; retries had no backoff.
Actions:    [x] Add index                           (done)
            [ ] Alert on pool wait p99 > 100 ms     (owner, date)
            [ ] Retries with backoff + jitter       (owner, date)
            [ ] Load test before each big campaign  (owner, date)

14. Practice Problems

Work these out on paper. Answers follow each one.

Problem 1: percentiles

Ten request times (ms): 30, 31, 33, 35, 36, 40, 41, 44, 300, 1200. Find the mean, p50, and p90 (nearest-rank).

Answer: sum = 1,790, so the mean is 179 ms. p50 = position ceil(5) = 5th = 36 ms. p90 = position ceil(9) = 9th = 300 ms. The mean is five times the median because of two outliers.

Problem 2: pool size

A service gets 300 requests per second. Each holds a database connection for 15 ms. What is the average number of busy connections? If you want them to be at most 50% busy on average, how big should the pool be?

Answer: L = 300 × 0.015 = 4.5 busy connections. For 50% utilization, pool = 4.5 / 0.5 = 9, so about 9 or 10 connections.

Problem 3: where is the time?

curl prints dns 0.120, connect 0.150, tls 0.185, ttfb 0.230, total 0.240. Which phase is slowest, and what would you check?

Answer: DNS takes 120 ms, while the server only takes about 45 ms (0.230 - 0.185) including one round trip. Check DNS: is the resolver slow or far away, is the answer not cached (low TTL), or is a Kubernetes ndots search list causing several lookups?

Problem 4: retry math

Clients retry each failed request twice, with no backoff. During an outage, 50% of requests fail. Real demand is 1,000 requests per second. How many requests per second reach the server?

Answer: first tries: 1,000. Half fail, giving 500 second tries. Half of those fail, giving 250 third tries. Total = 1,000 + 500 + 250 = 1,750 per second, 75% more load during an outage.

15. Common Pitfalls

  • Watching averages. The mean hid the 2.4-second tail in section 2. Always look at p95 and p99.
  • Guessing instead of splitting. Cut the request into phases (network, queue, query) and measure each one.
  • Assuming "slow" means "busy". Idle CPU with slow requests means waiting: on a pool, a lock, or another service.
  • Scaling the wrong layer. Adding API servers here would add more connections to an already struggling database and make it worse.
  • Making the pool huge to hide a slow query. Fix W before L.
  • Timeouts that grow inward (database timeout longer than the load balancer's). Outer layers give up while inner layers keep burning resources on work nobody will receive.
  • Retries without backoff, jitter, or a budget.
  • Changing several things at once during an incident. If it gets better, you will not know which change helped. If it gets worse, you will not know which to undo.
  • Building an index without CONCURRENTLY on a busy table, and blocking all writes in the middle of the incident.

Scenario: Requests Stuck on Database Locks

The database is not slow. CPU is at 15%, disks are quiet, and every query is fast when you run it by hand. Yet requests hang for 10, 20, 30 seconds and then time out. This page follows three real kinds of lock trouble the way an on-call engineer meets them, shows the exact queries that find the cause in under a minute, and reproduces all three in a lab you can run against PostgreSQL 17, with measured results for each fix. It uses ideas from Transactions, Isolation & MVCC and Concurrency & Deadlocks. The company is made up; the code, the logs and the numbers are real.

1. The Situation

A shop's checkout API runs on 8 pods and talks to one PostgreSQL database. Over one week, on-call sees three strange problems:

  1. Monday 19:20 IST. Orders for one popular product hang for many seconds, then time out. Other products are fine.
  2. Wednesday 11:05 IST. A developer runs a migration that adds one column to the accounts table. It "should take a millisecond". For the next 8 seconds, every request that reads accounts hangs, including the login page. The error rate hits 40%.
  3. All week. The logs show a steady trickle of ERROR: deadlock detected from the wallet-transfer job, and some transfers fail.

Dashboards show the database server is calm: low CPU, low disk use, plenty of memory. That is the first clue. When requests are slow but the database is idle, they are usually waiting, not working. The most common thing to wait for is a lock.

2. Words You Need

WordPlain meaning
TransactionA group of statements that succeed or fail together, between BEGIN and COMMIT (or ROLLBACK).
LockA mark that says "I am using this; others must wait or share". Databases lock rows and tables.
Row lockTaken by UPDATE, DELETE and SELECT ... FOR UPDATE on the rows they touch. Held until the transaction ends, not until the statement ends.
Table lockA lock on a whole table. Every query takes a weak one (a plain SELECT takes ACCESS SHARE). Schema changes like ALTER TABLE take the strongest one (ACCESS EXCLUSIVE), which conflicts with everything.
BlockerThe session holding the lock others want.
WaiterA session that is stuck until the blocker lets go.
Idle in transactionA session that started a transaction, ran some statements, and is now doing nothing, while still holding all its locks. Usually the app is busy elsewhere (an HTTP call) or forgot to commit.
DeadlockTwo or more transactions each wait for a lock the other holds. None can ever move. The database must kill one.
TimeoutA limit on how long to wait. PostgreSQL has several: lock_timeout, statement_timeout, idle_in_transaction_session_timeout.

Intuition. A row lock is like taking a library book home. Nobody else can borrow it until you return it, even if you are not reading it right now. "Idle in transaction" is borrowing the book and then going on holiday.

3. How Lock Queues Work

Two facts explain almost every lock incident.

Fact 1: locks last until the transaction ends

BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;   -- row 1 locked from here...
-- app calls a payment API: 9 seconds
COMMIT;                                                     -- ...to here

The UPDATE took 0.1 ms. The lock lasted 9 seconds. Anyone else who wants to change row 1 waits those 9 seconds.

Fact 2: waiters form a line, and the line is fair

PostgreSQL serves lock requests roughly in arrival order. A new request will not jump ahead of an earlier waiter it conflicts with, even if the current holder would allow it. This stops strong locks from starving forever, but it has a nasty side effect:

time ──────────────────────────────────────────────────────►
long report:   holds ACCESS SHARE on accounts (a slow SELECT inside a transaction)
ALTER TABLE:        wants ACCESS EXCLUSIVE ── waits for the report
SELECT #1:               wants ACCESS SHARE ── would fit with the report,
                                               but must wait BEHIND the ALTER
SELECT #2:                   wants ACCESS SHARE ── also waits
login page:                       ...everything that touches accounts waits

The ALTER TABLE itself takes a millisecond once it gets the lock. The damage comes from waiting for the lock while holding a place in line. Plain reads, which never block each other, now queue behind it.

4. The Toolkit: Find the Blocker

When requests hang, run this first. It lists every session, what it is doing, and who is blocking it:

SELECT pid,
       state,
       wait_event_type,
       pg_blocking_pids(pid)          AS blocked_by,
       now() - xact_start             AS xact_age,
       now() - state_change           AS in_state_for,
       left(query, 60)                AS query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY xact_start;

How to read it:

  • wait_event_type = 'Lock': this session is waiting for a lock.
  • blocked_by: the process IDs it waits for. Follow the arrows until you reach a session whose blocked_by is empty. That is the root blocker.
  • state = 'idle in transaction' with a large in_state_for: the classic root blocker. The query column shows its last statement, not what it is doing now (it is doing nothing).

Ask the database to log waits

log_lock_waits = on          # log any lock wait longer than deadlock_timeout
deadlock_timeout = 1s        # the default; also how often deadlock checks run

Then the log shows lines like this (from our lab):

LOG:  process 512796 still waiting for ShareLock on transaction 740 after 1000.099 ms
DETAIL:  Process holding the lock: 512793. Wait queue: 512796.
CONTEXT:  while updating tuple (0,1) in relation "accounts"
STATEMENT:  UPDATE accounts SET balance = balance + 5 WHERE id = 1

"ShareLock on transaction 740" sounds strange. It is how PostgreSQL waits for a row: the row says "transaction 740 changed me", so the waiter waits for transaction 740 to finish. "Tuple (0,1)" means page 0, item 1: the physical spot of the row.

Stop the blocker (carefully)

SELECT pg_cancel_backend(12345);      -- cancel its current query (gentle)
SELECT pg_terminate_backend(12345);   -- end the whole session; its transaction rolls back

For an idle-in-transaction blocker, only pg_terminate_backend helps, because there is no running query to cancel. Its uncommitted work is lost, which is correct: it was never committed.

5. The Lab

This Python program reproduces all three incidents and times them. You need Python 3.10+, pip install "psycopg[binary]", and a PostgreSQL server. The quickest way to get one:

docker run --rm -d --name pglab -p 5432:5432 -e POSTGRES_HOST_AUTH_METHOD=trust \
  postgres:17 -c log_lock_waits=on -c deadlock_timeout=1s
python3 locklab.py                     # takes about 75 seconds
docker logs pglab 2>&1 | grep -A3 -E "still waiting|deadlock detected"
# locklab.py - reproduce three kinds of lock trouble in PostgreSQL and time them.
# Needs: pip install "psycopg[binary]", and a PostgreSQL server.
import os, random, threading, time
import psycopg

DSN = os.environ.get("DSN", "host=localhost port=5432 user=postgres dbname=postgres")

def conn():
    return psycopg.connect(DSN, autocommit=True)

def setup():
    with conn() as c:
        c.execute("DROP TABLE IF EXISTS accounts")
        c.execute("CREATE TABLE accounts (id int PRIMARY KEY, balance int NOT NULL)")
        c.execute("INSERT INTO accounts SELECT g, 1000 FROM generate_series(1, 100) g")

def timed(label, sql, results, setting=None):
    """Run one statement in its own connection; record how long it took."""
    with conn() as c:
        if setting:
            c.execute(setting)
        t0 = time.time()
        try:
            c.execute(sql)
            results.append((label, round(time.time() - t0, 2), "ok"))
        except psycopg.Error as e:
            results.append((label, round(time.time() - t0, 2), type(e).__name__))

def show_waits():
    with conn() as c:
        rows = c.execute("""
            SELECT pid, state, coalesce(wait_event_type, '-'), pg_blocking_pids(pid),
                   left(query, 45)
            FROM pg_stat_activity
            WHERE datname = current_database() AND pid <> pg_backend_pid()
              AND query NOT LIKE '%pg_stat_activity%'
            ORDER BY backend_start""").fetchall()
    for r in rows:
        print("   ", r)

def part1_idle_in_transaction(timeout=None):
    print(f"\n== Part 1: a transaction left open (idle_in_transaction_session_timeout={timeout}) ==")
    setup()
    holder = conn()
    if timeout:
        holder.execute(f"SET idle_in_transaction_session_timeout = '{timeout}'")
    holder.execute("BEGIN")
    holder.execute("UPDATE accounts SET balance = balance - 10 WHERE id = 1")
    # the app now "forgets" to commit: it waits on a slow HTTP call for 10 s
    results = []
    ts = [threading.Thread(target=timed, args=(f"update #{i}",
          "UPDATE accounts SET balance = balance + 5 WHERE id = 1", results)) for i in range(3)]
    for t in ts: t.start()
    time.sleep(1.5); show_waits()
    time.sleep(8.5)
    try:
        holder.execute("COMMIT"); print("    holder committed at t=10s")
    except psycopg.Error as e:
        print("    holder's COMMIT failed:", type(e).__name__)
    for t in ts: t.join()
    for r in results: print("   ", r)
    holder.close()

def part2_migration_queue(lock_timeout=None):
    print(f"\n== Part 2: ALTER TABLE behind a long read (lock_timeout={lock_timeout}) ==")
    setup()
    reader = conn()
    reader.execute("BEGIN")
    reader.execute("SELECT count(*) FROM accounts")        # holds ACCESS SHARE until commit
    results = []
    setting = f"SET lock_timeout = '{lock_timeout}'" if lock_timeout else None
    mig = threading.Thread(target=timed, args=("ALTER TABLE",
          "ALTER TABLE accounts ADD COLUMN note text", results, setting))
    mig.start(); time.sleep(0.5)
    reads = [threading.Thread(target=timed, args=(f"SELECT #{i}",
             "SELECT balance FROM accounts WHERE id = 7", results)) for i in range(3)]
    for t in reads: t.start()
    time.sleep(1); show_waits()
    time.sleep(6.5)
    reader.execute("COMMIT"); print("    long read committed at t=8s")
    for t in [mig] + reads: t.join()
    for r in results: print("   ", r)
    reader.close()

def transfer(a, b, ordered, stats):
    first, second = (min(a, b), max(a, b)) if ordered else (a, b)
    with conn() as c:
        try:
            with c.transaction():
                c.execute("UPDATE accounts SET balance = balance - 1 WHERE id = %s", (first,))
                time.sleep(0.05)                      # some app work between the two writes
                c.execute("UPDATE accounts SET balance = balance + 1 WHERE id = %s", (second,))
            stats["ok"] += 1
        except psycopg.errors.DeadlockDetected:
            stats["deadlock"] += 1

def part3_deadlocks(ordered):
    print(f"\n== Part 3: 200 transfers among 5 hot accounts, 20 at a time (ordered={ordered}) ==")
    setup()
    random.seed(42)
    pairs = [random.sample(range(1, 6), 2) for _ in range(200)]
    stats = {"ok": 0, "deadlock": 0}
    t0 = time.time()
    for i in range(0, 200, 20):
        ts = [threading.Thread(target=transfer, args=(a, b, ordered, stats)) for a, b in pairs[i:i+20]]
        for t in ts: t.start()
        for t in ts: t.join()
    print(f"    committed={stats['ok']} deadlocks={stats['deadlock']} time={time.time()-t0:.1f}s")

if __name__ == "__main__":
    part1_idle_in_transaction()
    part1_idle_in_transaction(timeout="3s")
    part2_migration_queue()
    part2_migration_queue(lock_timeout="2s")
    part3_deadlocks(ordered=False)
    part3_deadlocks(ordered=True)

We ran it on PostgreSQL 17.12 on Linux. The results are in the next three sections. Your process IDs and exact times will differ a little.

6. Incident 1: The Transaction That Never Ended

Back to Monday. The order code looked like this:

with db.transaction():
    db.execute("UPDATE products SET stock = stock - 1 WHERE id = %s", (pid,))
    payment = payment_api.charge(card, amount)     # HTTP call: usually 300 ms, sometimes 10 s
    db.execute("INSERT INTO orders ...")

The popular product's row stays locked during the whole payment call. When the payment provider got slow, every other order for that product queued behind it.

What the lab showed

Part 1 opens a transaction, updates row 1, then waits 10 s before committing (like the slow payment). Three other sessions try to update row 1. One and a half seconds in, the toolkit query shows:

(512793, 'idle in transaction', 'Client', [],               'UPDATE accounts SET balance = balance - 10 WH')
(512796, 'active',              'Lock',   [512793],         'UPDATE accounts SET balance = balance + 5 WHE')
(512798, 'active',              'Lock',   [512796],         'UPDATE accounts SET balance = balance + 5 WHE')
(512799, 'active',              'Lock',   [512796, 512798], 'UPDATE accounts SET balance = balance + 5 WHE')
holder committed at t=10s
('update #0', 10.01, 'ok')
('update #2', 10.01, 'ok')
('update #1', 10.01, 'ok')

Read it like a detective:

  • 512793 is idle in transaction and blocked by nobody: the root blocker.
  • 512796 waits directly for 512793.
  • 512798 and 512799 say they wait for 512796, not 512793. They are in line behind 512796 for the same row. Following the chain always leads back to 512793.
  • All three updates took 10.01 s, even though each needs under a millisecond of work.

Fix 1: never wait on the outside world inside a transaction

payment = payment_api.charge(card, amount, idempotency_key=order_id)  # outside any transaction
with db.transaction():                                                # short: a few ms
    db.execute("UPDATE products SET stock = stock - 1 WHERE id = %s AND stock > 0", (pid,))
    db.execute("INSERT INTO orders ...")

If the stock update fails after the charge, refund using the same idempotency key. (For a stronger design, look up the "outbox" and "saga" patterns.) The point is that a transaction should contain only database work.

Fix 2: a safety net timeout

Part 1 ran again with idle_in_transaction_session_timeout = '3s' on the holder:

holder's COMMIT failed: IdleInTransactionSessionTimeout
('update #0', 3.0, 'ok')
('update #2', 3.0, 'ok')
('update #1', 3.0, 'ok')

After 3 s idle, PostgreSQL ended the holder's session and rolled back its update. The waiters went through after 3.0 s instead of 10 s. The holder's work was lost, so the app must treat this like any failed transaction (retry or report). Set this timeout for app users, for example 10 to 60 s, as a net under bugs, not as a substitute for Fix 1.

7. Incident 2: The One-Second Migration That Froze Reads

Wednesday's migration was ALTER TABLE accounts ADD COLUMN note text. Adding a nullable column is instant in PostgreSQL: it only changes the table's description. But it needs an ACCESS EXCLUSIVE lock for that instant. At the same time, an analyst's reporting tool held a transaction open with a SELECT on accounts.

What the lab showed

Part 2 holds a read transaction open for 8 s, starts the ALTER TABLE, then 0.5 s later sends three simple SELECTs:

(512938, 'idle in transaction', 'Client', [],       'SELECT count(*) FROM accounts')
(512940, 'active',              'Lock',   [512938], 'ALTER TABLE accounts ADD COLUMN note text')
(512956, 'active',              'Lock',   [512940], 'SELECT balance FROM accounts WHERE id = 7')
(512958, 'active',              'Lock',   [512940], 'SELECT balance FROM accounts WHERE id = 7')
(512959, 'active',              'Lock',   [512940], 'SELECT balance FROM accounts WHERE id = 7')
long read committed at t=8s
('ALTER TABLE', 8.01, 'ok')
('SELECT #0', 7.51, 'ok')
...

The SELECTs are blocked by the ALTER (512940), not by the long read. A read that would normally take 0.1 ms took 7.51 s. In production, with hundreds of requests per second, that is hundreds of stuck requests, a full connection pool, and timeouts everywhere.

Fix: make the migration give up quickly, then retry

Part 2 again, with SET lock_timeout = '2s' before the ALTER:

('ALTER TABLE', 2.0, 'LockNotAvailable')
('SELECT #1', 1.5, 'ok')
('SELECT #2', 1.5, 'ok')
('SELECT #0', 1.5, 'ok')

The ALTER gave up after 2 s with ERROR: canceling statement due to lock timeout. The moment it left the line, the reads went through: 1.5 s instead of 7.5 s. In real migrations use a much shorter timeout and retry in a loop:

SET lock_timeout = '500ms';
-- run the ALTER; on "lock timeout", wait a few seconds and try again (up to N times)
ALTER TABLE accounts ADD COLUMN note text;

Each failed try blocks traffic for at most 0.5 s. Most migration tools can do this for you.

Safe-migration habits

  • Check for long transactions before you start: SELECT pid, now() - xact_start FROM pg_stat_activity WHERE xact_start < now() - interval '1 minute';
  • Build indexes with CREATE INDEX CONCURRENTLY (does not block writes; cannot run inside a transaction block).
  • Add foreign keys and check constraints as NOT VALID first, then VALIDATE CONSTRAINT later (validation takes a weaker lock).
  • Changing a column's type usually rewrites the whole table under ACCESS EXCLUSIVE. Instead: add a new column, backfill in small batches, switch the code, drop the old column.
  • Since PostgreSQL 11, ADD COLUMN ... DEFAULT 'x' with a constant default is instant too; on older versions it rewrote the table.
  • Set statement_timeout or idle_in_transaction_session_timeout for reporting users, so a forgotten notebook cannot hold locks for hours.

8. Incident 3: "deadlock detected"

The wallet job moves money between accounts:

with db.transaction():
    db.execute("UPDATE accounts SET balance = balance - %s WHERE id = %s", (amt, src))
    db.execute("UPDATE accounts SET balance = balance + %s WHERE id = %s", (amt, dst))

If transfer T1 moves money 1 → 2 while T2 moves money 2 → 1 at the same time:

TimeT1 (1 → 2)T2 (2 → 1)
0 mslocks row 1locks row 2
500 mswants row 2: waits for T2wants row 1: waits for T1
1,500 msdeadlock check runs (1 s after the wait began): cycle T1 → T2 → T1 found, T2 is cancelled

We ran exactly these two transactions:

T2 failed after 1.5 s: deadlock detected
T1 committed after 1.5 s

And the server log said:

ERROR:  deadlock detected
DETAIL:  Process 514415 waits for ShareLock on transaction 1181; blocked by process 514414.
         Process 514414 waits for ShareLock on transaction 1182; blocked by process 514415.
         Process 514415: UPDATE accounts SET balance = balance + 100 WHERE id = $1
         Process 514414: UPDATE accounts SET balance = balance + 100 WHERE id = $1

The DETAIL lines draw the cycle for you: 514415 waits for 514414, which waits for 514415. With more transactions the cycle gets longer. Our busy run logged a 4-process cycle, each waiting for the next.

How bad does it get? The lab

Part 3 runs 200 random transfers between 5 busy ("hot") accounts, 20 at a time, with 50 ms of app work between the two updates:

== 200 transfers among 5 hot accounts, 20 at a time (ordered=False) ==
    committed=95 deadlocks=105 time=32.2s
== 200 transfers among 5 hot accounts, 20 at a time (ordered=True) ==
    committed=200 deadlocks=0 time=6.4s

Without a fixed order, more than half of the transfers died, and the run took 5 times longer because each deadlock costs a 1 s wait before detection.

Fix: always lock in the same order

A deadlock needs a cycle. If every transaction locks rows in the same global order (for example, lower id first), a cycle is impossible: nobody holding a higher id ever waits for a lower one. This is the "break circular wait" rule from OS deadlock handling.

first, second = sorted([src, dst])
with db.transaction():
    # lock both rows up front, in id order
    db.execute("SELECT id FROM accounts WHERE id IN (%s, %s) ORDER BY id FOR UPDATE", (first, second))
    db.execute("UPDATE accounts SET balance = balance - %s WHERE id = %s", (amt, src))
    db.execute("UPDATE accounts SET balance = balance + %s WHERE id = %s", (amt, dst))

Other ways to reduce deadlocks:

  • Keep transactions short. Our lab's 50 ms gap made the window large. Less time holding locks means fewer collisions.
  • Batch updates in sorted order. An UPDATE ... WHERE id IN (...) touching many rows can deadlock with another batch. Lock them first with SELECT ... ORDER BY id FOR UPDATE.
  • Index foreign keys. Without an index, deleting a parent row scans the child table and can take more locks than you expect.
  • Job queues: use FOR UPDATE SKIP LOCKED so workers take different rows instead of waiting on each other.

9. Retrying Safely

Even with good habits, some deadlocks and serialization failures will happen. The database rolled back the whole transaction, so it is safe to run the whole transaction again (never just the last statement):

import random, time, psycopg

RETRYABLE = (psycopg.errors.DeadlockDetected,         # SQLSTATE 40P01
             psycopg.errors.SerializationFailure)     # SQLSTATE 40001

def run_with_retry(conn, work, tries=5):
    for attempt in range(1, tries + 1):
        try:
            with conn.transaction():
                return work(conn)
        except RETRYABLE:
            if attempt == tries:
                raise
            time.sleep(random.uniform(0, 0.05 * 2 ** attempt))   # backoff with jitter
  • The random delay (jitter) stops the same two transactions from colliding again at the same moment.
  • Do not retry lock timeouts blindly in request handlers. A lock timeout means "something is holding a lock for a long time"; retrying just adds more waiters. Fail fast and alert.
  • Make sure work has no outside side effects (emails, HTTP calls) that would happen twice.

10. The Same Problems in MySQL

MySQL's InnoDB engine has the same three problems with different tools:

One difference to remember: InnoDB at its default REPEATABLE READ level also locks gaps between index entries on locking reads and updates (to stop phantoms), so it can deadlock on rows that do not exist yet, such as two inserts into the same range. See isolation levels.

11. Prevention: Settings, Alerts, Reviews

Settings for the app's database user

ALTER ROLE app SET idle_in_transaction_session_timeout = '30s';
ALTER ROLE app SET statement_timeout = '15s';      -- longer than any normal query
ALTER ROLE app SET lock_timeout = '5s';            -- fail fast instead of piling up
ALTER ROLE migrator SET lock_timeout = '500ms';    -- migrations give up fast and retry
ALTER SYSTEM SET log_lock_waits = on;
SELECT pg_reload_conf();

Make sure the app's request timeout is a bit longer than statement_timeout, so the database cancels the query before the client gives up on it. Otherwise the database keeps working (and holding locks) for a request nobody is waiting for.

Alerts

  • Sessions waiting on locks for more than 5 s: count(*) FROM pg_stat_activity WHERE wait_event_type = 'Lock' AND now() - query_start > interval '5 s'.
  • Oldest open transaction older than 5 minutes (also blocks VACUUM cleanup, see MVCC).
  • Deadlocks per minute: the deadlocks column of pg_stat_database is a counter; alert on its rate.

Code review checklist

  • Is there any HTTP call, file upload, sleep, or user prompt inside a transaction?
  • Do multi-row updates lock rows in a fixed order?
  • Does this migration take ACCESS EXCLUSIVE? Is lock_timeout set? Does it rewrite the table?
  • Is retry on 40P01/40001 wrapped around the whole transaction?

12. Blameless Postmortem

A postmortem is a short write-up after an incident. "Blameless" means it looks at how the system allowed the mistake, not at who made it.

Title:    Reads on accounts blocked for 8 s during a migration (Wed 11:05 IST)
Impact:   ~40% of requests failed for 8 s; login unavailable.
Cause:    ALTER TABLE needed ACCESS EXCLUSIVE; a reporting session held a long
          transaction on accounts; the ALTER waited, and all reads queued behind it.
Why it was possible:
          - migrations ran with no lock_timeout
          - reporting user had no idle/statement timeout
          - no alert on lock waits
Actions:  - migration tool sets lock_timeout=500ms with retries        (done)
          - idle_in_transaction_session_timeout=5min for reporting role (done)
          - alert: any session waiting on a lock > 5 s                  (this week)
          - move the order flow's payment call out of the transaction   (Incident 1)
          - wallet transfers lock rows in id order + retry on 40P01     (Incident 3)

13. Practice Problems

Answers follow each one.

Problem 1: find the root blocker

 pid  | state               | wait_event_type | blocked_by
------+---------------------+-----------------+-----------
 201  | active              | Lock            | {203}
 202  | active              | Lock            | {201}
 203  | idle in transaction |                 | {}
 204  | active              | Lock            | {201,202}

Which session should you look at, and what is the gentlest fix?

Answer: Follow the arrows: 204 → 201/202 → 201 → 203. 203 waits for nobody and is idle in transaction: it is the root blocker. It has no running query, so pg_cancel_backend will not help; use pg_terminate_backend(203), then find the code path that left it open.

Problem 2: how long do they wait?

A job runs BEGIN; UPDATE settings SET v = v + 1 WHERE k = 'counter';, then calls an API that takes 4 s, then commits. Requests that update the same row arrive every 100 ms. Each update itself takes 1 ms. Roughly how many requests are waiting by the time the job commits, and how long did the first one wait?

Answer: Over 4 s, 4 / 0.1 = 40 requests pile up. The first one waited almost the full 4 s. After the commit they run one at a time, 1 ms each, so the line clears in about 40 ms. The fix is to move the API call out of the transaction.

Problem 3: will it deadlock?

T1 runs UPDATE items SET qty = qty - 1 WHERE id IN (5, 9). T2 runs UPDATE items SET qty = qty - 1 WHERE id IN (9, 5). Can they deadlock?

Answer: Yes, it is possible. The order of values in IN (...) does not decide the order rows are locked; that depends on the plan (an index scan visits 5 then 9; a sequential scan visits rows in physical order). If the two statements visit rows in different orders, they can deadlock. To be safe, lock first with SELECT ... WHERE id IN (5, 9) ORDER BY id FOR UPDATE.

Problem 4: pick the timeouts

Your API's request timeout is 10 s. Normal queries take under 200 ms; the slowest normal report query takes 3 s. Choose statement_timeout and lock_timeout for the API's role.

Answer: statement_timeout above 3 s and below 10 s, say 8 s, so the database cancels the query before the client gives up. lock_timeout lower, say 2 to 3 s, because a normal request should never wait seconds for a lock; failing fast keeps the connection pool from filling up.

Problem 5: is this migration safe?

ALTER TABLE orders ALTER COLUMN amount TYPE numeric(12,2); on a 200 GB table that was integer. What happens, and what would you do instead?

Answer: Changing integer to numeric rewrites the whole table while holding ACCESS EXCLUSIVE: no reads or writes on orders for the many minutes the rewrite takes. Instead: add a new nullable column amount_new numeric(12,2) (instant), backfill it in small batches, write to both columns from the app, switch reads, then drop the old column. Run each step with lock_timeout set.

14. Common Pitfalls

  • HTTP calls inside transactions. Locks live as long as the slowest outside service.
  • Thinking "the ALTER is instant, so it is safe". The danger is the wait for the lock, during which everything queues behind it.
  • No lock_timeout on migrations. PostgreSQL waits forever by default.
  • Killing the waiter instead of the blocker. The waiters are victims; find the root with pg_blocking_pids.
  • Retrying only the failed statement after a deadlock. The whole transaction was rolled back; retry all of it.
  • Unordered multi-row updates. Lock in a fixed order (by primary key).
  • Assuming idle means harmless. An "idle in transaction" session can hold locks and block VACUUM for hours.
  • App timeout shorter than the database's. The client gives up, but the query keeps running and holding locks.
  • Raising the connection pool size to "fix" lock waits. More waiters do not make the blocker finish sooner.

15. Cheat Sheet

-- who is waiting, and on whom?
SELECT pid, state, wait_event_type, pg_blocking_pids(pid) AS blocked_by,
       now() - xact_start AS xact_age, left(query, 60)
FROM pg_stat_activity WHERE datname = current_database() ORDER BY xact_start;

-- long open transactions
SELECT pid, usename, state, now() - xact_start AS age, left(query, 60)
FROM pg_stat_activity WHERE xact_start < now() - interval '1 minute' ORDER BY age DESC;

-- deadlocks so far (a counter)
SELECT datname, deadlocks FROM pg_stat_database WHERE datname = current_database();

SELECT pg_cancel_backend(pid);      -- stop the running query
SELECT pg_terminate_backend(pid);   -- end the session (needed for idle in transaction)

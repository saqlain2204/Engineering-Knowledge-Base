Scenario: A Pod Keeps Getting OOMKilled

An API's pods restart every 40 minutes or so. Each time, Kubernetes says OOMKilled, exit code 137. Someone suggests doubling the memory limit. This page follows the investigation the way an on-call engineer would, and ties together virtual memory, cgroups, and Kubernetes requests and limits. The service and numbers are made up, but every command, message, and lab output is real.

1. The Situation

The orders-api service runs as 6 pods. Last week a new feature shipped: a "download my report" button. Since then:

  • Every pod restarts roughly every 40 minutes. Users see a burst of errors each time.
  • At night, when traffic is low, pods live for many hours.
  • Each pod has requests.memory: 512Mi and limits.memory: 1Gi.

The quick idea is "give it 2Gi". That may buy time, but if the cause is a leak, the pods will just die every 80 minutes instead. We first find out why memory grows.

Two words, defined. A memory leak is memory a program keeps holding even though it will never use it again, so its memory use grows with time or traffic. OOM means "out of memory". An OOM kill is the kernel ending a process to free memory.

2. Step 1: Read the Evidence

$ kubectl get pods -l app=orders-api

  • CrashLoopBackOff is not a separate error. It means "this container keeps dying, so I wait before restarting it": 10 s, then 20 s, 40 s, and so on, up to 5 minutes. The wait resets after the container runs fine for 10 minutes.

What this tells us:

  1. Reason: OOMKilled means the kernel killed a process because the container went over its own memory limit (its cgroup's memory.max). The node itself was fine.
  2. Exit Code 137 = 128 + 9. A process killed by signal number N exits with 128 + N, and 9 is SIGKILL.
  3. Started 09:58:51, Finished 10:41:05: it lived 42 minutes. If every run lasts about the same time, memory is growing at a steady pace: a strong sign of a leak.

3. Which Kind of Kill Is It?

"My pod died because of memory" can mean four different things. They have different causes and different fixes, so tell them apart first:

What you seeWho killed itWhyLook at
Reason: OOMKilled, exit 137The kernel, inside the container's cgroupThe container went over its own limits.memoryThe app's memory use vs its limit
Pod Status: Failed, Reason: Evicted, "The node was low on resource: memory"The kubeletThe node ran low; the kubelet removed pods, starting with those using the most memory above their requestNode memory, other pods, requests that are too low
A container dies with OOMKilled even though it was under its limit; the node log shows a system-wide OOMThe kernel, for the whole nodeThe node ran out before the kubelet could evict; the kernel picked a victim by oom_score_adjNode overcommit: sum of limits far above node RAM
Exit 137 but Reason: Error, often exactly 30 s after a stopThe kubelet, after the grace periodThe app ignored SIGTERM, so it got SIGKILLSignal handling (see PID 1 and signals)

Ours is the first row: the container's own limit. To be sure, read the cgroup's own counter from inside the container (cgroup v2):

$ kubectl exec orders-api-7d9f8c6b5d-4xkzq -- cat /sys/fs/cgroup/memory.events
low 0
high 0
max 1843
oom 0
oom_kill 0

This counter belongs to the current container, which has not been killed yet (oom_kill 0). But max 1843 says it has already hit its limit 1843 times; each time the kernel had to free memory (mostly page cache) to make room. It is living on the edge. The kubelet and the node's kernel log (journalctl -k | grep -i oom on the node) record the actual kills.

4. What "Memory" Means: RSS, Working Set, Anon, Cache

Different tools report different numbers called "memory". Mixing them up is the most common mistake in this kind of incident.

          virtual size (VSZ): everything the process has reserved, touched or not
   +----------------------------------------------------------------------------+
   |   reserved but never touched (costs nothing)    |   resident in RAM (RSS)  |
   +----------------------------------------------------------------------------+

          the container's cgroup counts (memory.current):
   +-----------------------------------------+----------------------------------+
   |  anon: heap, stacks, tmpfs              |  file: page cache                |
   |  cannot be dropped (no swap)            |  active        |  inactive       |
   +-----------------------------------------+----------------+-----------------+
   |<------------ working set = memory.current - inactive file ------->|
  • VSZ (virtual size): all virtual memory the process has reserved. Linux hands out virtual memory freely and only uses real RAM when a page is first touched (see overcommit). A big VSZ is usually harmless.
  • RSS (resident set size): pages of this process that are in RAM right now.
  • anon ("anonymous" memory): memory not backed by a file: heap, stacks, and files in memory-backed tmpfs. With no swap (the Kubernetes default), the kernel cannot free it. This is what gets you killed.
  • file (page cache): copies of file data. Clean cache can be dropped at any time, so it rarely causes a kill.
  • Working set: what kubectl top and the metric container_memory_working_set_bytes show. It is memory.current minus inactive file cache. It is the best single number to compare against the limit.

Proof that VSZ is not RSS

# lazy.py
import mmap
m = mmap.mmap(-1, 1024*1024*1024)                # reserve 1 GiB, touch nothing
for off in range(0, 200*1024*1024, 4096):
    m[off] = 1                                    # touch 200 MiB, one byte per page
start                    VmSize:   14540 kB   VmRSS:   8532 kB
after reserving 1 GiB    VmSize: 1063116 kB   VmRSS:   8660 kB    <- 1 GiB more virtual, no RAM
after touching 200 MiB   VmSize: 1063116 kB   VmRSS: 213460 kB    <- RAM used only when touched

Proof that cache does not kill

In a cgroup limited to 100 MiB, writing a 300 MiB file finished fine. Afterwards memory.stat showed anon = 0.2 MiB and file = 95 MiB, and memory.current sat at 99 MiB, right at the limit, with no kill. (Full lab in How Containers Really Work.)

5. Requests, Limits, QoS, and Who Dies First

  • requests.memory is a promise used for placement. The scheduler puts the pod only on a node with that much unreserved memory. It is not enforced at runtime.
  • limits.memory is a hard cap. The kubelet writes it into the container's cgroup as memory.max. Going over means an OOM kill. (Memory cannot be "slowed down" like CPU, so there is no throttling, just death.)

The mix of requests and limits gives each pod a QoS class (quality of service), which decides who goes first when a node runs short:

QoS classRuleoom_score_adjKilled
GuaranteedEvery container has requests = limits for CPU and memory-997Last
BurstableSome request or limit set, but not Guaranteed2 to 999, from the formula belowMiddle
BestEffortNo requests or limits at all1000First

The kernel's OOM killer adds oom_score_adj (from -1000 to 1000) to each process's score; a higher score is killed first. For Burstable pods the kubelet uses:

oom_score_adj = min( max(2, 1000 - (1000 × memory request) / node memory), 999 )

Worked example: our pod requests 512 MiB on a 16 GiB node. 1000 × 0.5 / 16 = 31.25, so the value is 1000 - 31.25 ≈ 968. A pod requesting 8 GiB on the same node gets 1000 - 500 = 500. The smaller the request, the closer to the front of the kill line.

Our pod is Burstable: it may use up to 1Gi, but only 512Mi is reserved. If many pods on one node burst at once, the node runs short, and eviction or a node-level OOM picks the pods most above their requests. Setting requests = limits for memory removes that risk.

Newer clusters: on cgroup v2, recent Kubernetes versions mark each container's cgroup with memory.oom.group = 1. If one process in the container is OOM-killed, all its processes are killed together, so you do not get a half-dead container where a helper process died and the main one kept running.

6. Step 2: Read the Memory Graph

Plot container_memory_working_set_bytes for one pod over a few hours, with the limit as a line. The shape tells you the cause:

A. LEAK: steady climb, kill, repeat     B. LIMIT TOO SMALL: flat, but above   C. SPIKE: flat, then one huge jump
                                           the limit right after start
1Gi ----x--------x--------x-- limit     1Gi ------x-x-x-x-x-x-x-x--- limit     1Gi ---------------x------ limit
       /|       /|       /|                       | | | | | | | |                                  |
      / |      / |      / |                    __/ / / / / / / /                                 |
     /  |     /  |     /  |                   restarts every few seconds or         ____________/|_______
    /   |    /   |    /   |                   minutes, during startup               normal      one big request
   0   42m      84m     126m                                                                    (huge upload, a
                                                                                                query with no LIMIT)
  • A (leak): grows with time or traffic, never comes back down. The pod lives longer at night because there is less traffic. That is our case.
  • B (limit too small): the app simply needs more than the limit, for example a JVM whose heap is set larger than the container. Raising the limit or shrinking the heap is the right fix.
  • C (spike): one request loads too much at once. Fix the code path (stream instead of loading everything; paginate; cap upload size).

A healthy service looks like a flat line, or a sawtooth that goes up and down (garbage collection) around a stable level.

7. Step 3: Leak-Rate Math

From the graph: just after a restart the pod uses about 300 MiB. It hits the 1 GiB (1024 MiB) limit after about 42 minutes. Each pod serves about 50 requests per second.

  1. Growth = 1024 - 300 = 724 MiB in 42 minutes.
  2. Leak rate = 724 / 42 ≈ 17.2 MiB per minute.
  3. Requests per minute = 50 × 60 = 3000.
  4. Leak per request = 17.2 MiB / 3000 ≈ 17,600 KiB / 3000 ≈ 5.9 KiB per request.

That number is a clue. A few KiB per request smells like "something about each request is being saved and never removed": a cache, a list of past results, a log buffer, a map of sessions.

It also predicts what doubling the limit does: (2048 - 300) / 17.2 ≈ 102 minutes between kills. Better, but not fixed. And at night, at 5 requests per second, 1 GiB lasts about 420 minutes (7 hours), which matches the "pods live long at night" clue.

8. Step 4: Reproduce It Under a Real Limit

The report feature added this code. Here is a simplified, runnable copy:

# leaky_service.py
import time

_cache = {}                                   # BUG: never shrinks

def handle_request(user_id, request_id):
    report = f"report {user_id}/{request_id}: " + "x" * 2000
    _cache[(user_id, request_id)] = report    # request_id is unique, so every entry is new
    return len(report)

def rss_mib():
    for line in open("/proc/self/status"):
        if line.startswith("VmRSS"):
            return int(line.split()[1]) // 1024

request_id = 0
while True:
    for _ in range(10000):
        request_id += 1
        handle_request(request_id % 100, request_id)
    print(f"{request_id:7d} requests  RSS {rss_mib():4d} MiB", flush=True)
    time.sleep(0.05)

The author meant to cache reports so repeated downloads are fast. But the cache key includes request_id, which is different for every request. So no entry is ever reused, and none is ever removed.

Run it in a cgroup with a 150 MiB limit, exactly as a container would be:

$ echo 150M | sudo tee /sys/fs/cgroup/demo/memory.max
$ echo 0    | sudo tee /sys/fs/cgroup/demo/memory.swap.max
$ sudo bash -c 'echo $$ > /sys/fs/cgroup/demo/cgroup.procs; exec python3 leaky_service.py'
  10000 requests  RSS   29 MiB
  20000 requests  RSS   50 MiB
  30000 requests  RSS   72 MiB
  40000 requests  RSS   93 MiB
  50000 requests  RSS  115 MiB
  60000 requests  RSS  135 MiB

$ echo $?

$ sudo dmesg | grep "Killed process" | tail -1

anon-rss:153100kB, file-rss:6256kB, shmem-rss:0kB, UID:0 pgtables:372kB oom_score_adj:0

Same symptoms as production: steady growth of about 21.5 MiB per 10,000 requests (about 2.2 KiB per request in this small copy), then a kill with exit code 137, and the kernel log shows almost all of it is anon-rss, memory that cannot be dropped.

Tip: you do not need a cluster to reproduce an OOM kill. docker run --memory=150m does the same thing, and so does systemd-run --user --scope -p MemoryMax=150M python3 app.py on most Linux desktops.

9. Step 5: Find the Leaking Line

Growth tells you that it leaks. A heap profiler tells you where. Python ships one: tracemalloc. It records which line allocated each block of memory. Take a snapshot, run traffic, take another, and compare:

import tracemalloc
tracemalloc.start()
snap0 = tracemalloc.take_snapshot()
# ... handle 100,000 requests ...
snap1 = tracemalloc.take_snapshot()
for stat in snap1.compare_to(snap0, "lineno")[:3]:
    print(stat)

Output from a test copy of the same handler (saved as leak.py, so lines 6 and 7 are the same two lines as above), running 100,000 requests and printing RSS every 20,000:

after  20000 requests: RSS = 58 MiB, cache entries = 20000
after  40000 requests: RSS = 106 MiB, cache entries = 40000
after  60000 requests: RSS = 155 MiB, cache entries = 60000
after  80000 requests: RSS = 201 MiB, cache entries = 80000
after 100000 requests: RSS = 254 MiB, cache entries = 100000

Top growth by source line:
  leak.py:6: size=196 MiB (+196 MiB), count=100000 (+100000), average=2059 B
  leak.py:7: size=10.3 MiB (+10.3 MiB), count=99983 (+99983), average=108 B
  leak.py:19: size=3125 KiB (+3125 KiB), count=100000 (+100000), average=32 B
  • Line 6 builds the report string: 100,000 new strings of about 2 KB each, all still alive. Something is holding on to them.
  • Line 7 is the dictionary insert: the dictionary itself grows by about 100 bytes per entry. That is the "something".
  • The count (+100,000) equals the number of requests: one leaked object per request. That pattern almost always means a collection that only grows.

(RSS here is higher than in step 4 because tracemalloc itself uses memory to track every allocation. Use it in a test or staging copy, not on every production pod.)

10. Runtime Traps: JVM, Go, Node, Python

Not every OOMKilled is a leak. Many are a mismatch between what the language runtime thinks it may use and what the container allows. The runtime manages its own heap and only gives memory back to the OS lazily, so it must know the limit.

RuntimeTrapFix
JVM-Xmx set to the full limit. Total memory = heap + metaspace + thread stacks + direct buffers + JIT code, so it goes over.Let the JVM size from the container: -XX:MaxRAMPercentage=75 (Java 10+ reads cgroup limits). Leave 25% for non-heap.
GoThe garbage collector does not know the limit and lets the heap grow to twice the live data before collecting.Set GOMEMLIMIT (Go 1.19+) to about 90% of the limit, for example GOMEMLIMIT=900MiB for a 1Gi limit. The GC then works harder as memory gets close.
Node.jsThe V8 old-generation heap limit may not match the container.Set --max-old-space-size (in MiB) to about 75% of the limit.
PythonNo heap cap at all. Many threads can also cause glibc malloc to keep many memory "arenas" that are hard to give back.Fix the code; try MALLOC_ARENA_MAX=2 for heavily threaded servers; watch native memory from libraries like NumPy and PyTorch, which tracemalloc does not see.
AnyWriting to /dev/shm or an emptyDir with medium: Memory. These are tmpfs: RAM that counts as memory that cannot be dropped.Use disk-backed volumes for big temp files; set sizeLimit on memory-backed volumes.

11. The Fix and Right-Sizing the Limit

Fix the code

Two bugs: the key is wrong (it should identify the report, not the request) and the cache has no size bound. Fix both:

# fixed.py
from functools import lru_cache

@lru_cache(maxsize=5000)          # FIX: bounded; least recently used entries are evicted
def render_report(user_id, day):
    return f"report {user_id}/{day}: " + "x" * 2000

Same 100,000 requests (the load test passes distinct values for day, the worst case for any cache):

after  20000 requests: RSS = 20 MiB, cache size = 5000
after  40000 requests: RSS = 20 MiB, cache size = 5000
after  60000 requests: RSS = 20 MiB, cache size = 5000
after  80000 requests: RSS = 20 MiB, cache size = 5000
after 100000 requests: RSS = 20 MiB, cache size = 5000

Flat. Even with keys that never repeat, memory is capped at about 5000 × 2 KB ≈ 10 MB of reports. Other safe patterns: a time-to-live (TTL) on entries, or an external cache like Redis with its own memory limit and eviction policy.

Right-size the limit

After the fix, run a load test at peak traffic for at least an hour (a soak test, long enough to see slow leaks) and record the working set.

  1. Peak working set in the soak test: say 420 MiB.
  2. Add headroom for spikes and garbage collection, about 25%: 420 × 1.25 = 525, so limit = 576Mi (rounded up).
  3. Set requests.memory = limits.memory = 576Mi. Memory cannot be shared out like CPU time, so reserving what you may use avoids surprise node-level evictions (and with CPU requests equal to limits too, the pod becomes Guaranteed).

The fix let us lower the limit from 1Gi to 576Mi. Doubling it would have hidden the bug and wasted 6 × 1 GiB of reserved cluster memory.

12. Preventing the Next One: Alerts and Tests

Prometheus alerts using standard metrics from cAdvisor (built into the kubelet) and kube-state-metrics:

# Warn before the kill: working set above 90% of the limit for 15 minutes
- alert: ContainerMemoryNearLimit
  expr: |
    max by (namespace, pod, container) (container_memory_working_set_bytes{container!=""})
      / on (namespace, pod, container)
    max by (namespace, pod, container) (kube_pod_container_resource_limits{resource="memory"})
      > 0.9
  for: 15m

# Page when kills actually happen
- alert: ContainerOOMKilled
  expr: increase(container_oom_events_total{container!=""}[30m]) > 0

# Catch slow leaks: at the current growth rate, the limit is hit within 2 hours
- alert: ContainerMemoryLeakSuspected
  expr: |
    predict_linear(container_memory_working_set_bytes{container!=""}[1h], 2 * 3600)
      > on (namespace, pod, container) group_left
    max by (namespace, pod, container) (kube_pod_container_resource_limits{resource="memory"})
  for: 30m
  • Soak tests in CI or staging: run steady traffic for an hour and fail the build if memory keeps rising (for example, if the last 15 minutes average is more than 10% above the first 15 after warm-up).
  • Code review rule: every in-process cache, map, or list that grows with requests needs a bound (size or time) and a clear key. "Grows with traffic" should be a review comment.
  • Dashboards: show working set and the limit on the same graph, per container, plus restart counts.

13. Blameless Postmortem

A postmortem is a short write-up after an incident. "Blameless" means it looks at how the system allowed the problem, not at who made the mistake.

SummaryFor 5 days, orders-api pods were OOM-killed about every 42 minutes at peak, causing short bursts of 5xx errors during each restart.
ImpactAbout 0.4% of requests failed at peak. No data loss.
Root causeThe report cache used a key containing the request ID, so entries were never reused, and it had no size bound. Memory grew by about 6 KiB per request until the 1Gi limit.
DetectionUsers reported errors. No alert existed for memory near the limit or for OOM kills.
What went wellThe restart pattern and the leak-rate math pointed to a per-request leak within an hour; the bug was reproduced locally under a cgroup limit.
Action items(1) Bounded LRU cache with the correct key (done). (2) Alerts: near-limit, OOM events, linear-prediction leak (done). (3) One-hour soak test in staging for every release. (4) Review checklist item for unbounded collections. (5) Set memory requests = limits from soak-test data for all services.

14. Practice Problems

Try each one before reading the answer.

Problem 1: name the kill

For each case, say what happened: (a) Reason: OOMKilled, Exit Code: 137; (b) Status: Failed, Reason: Evicted, "The node was low on resource: memory"; (c) Reason: Error, Exit Code: 137, and the pod always takes 30 s to stop; (d) Exit Code: 143.

Answer: (a) The container went over its own memory limit; the kernel killed it in its cgroup. (b) The node ran low on memory and the kubelet evicted the pod; look at node usage and requests. (c) The grace period ran out and the kubelet sent SIGKILL; the app ignores SIGTERM. (d) 143 = 128 + 15: the app exited because of SIGTERM, a normal, graceful stop.

Problem 2: leak-rate math

A pod starts at 250 MiB, has a 2Gi limit, and serves 120 requests per second. It is killed every 2 hours and 10 minutes. How much does it leak per request? How long would it last with a 3Gi limit?

Answer: Growth = 2048 - 250 = 1798 MiB in 130 minutes = 13.8 MiB/min. Requests per minute = 7200. Per request = 13.8 × 1024 / 7200 ≈ 1.96 KiB. With 3Gi: (3072 - 250) / 13.8 ≈ 204 minutes (about 3 h 24 min). Still a leak.

Problem 3: oom_score_adj

Two Burstable pods run on a 32 GiB node: pod A requests 1 GiB, pod B requests 16 GiB. The node runs out of memory before the kubelet reacts. Compute each pod's oom_score_adj. Which is more likely to be killed if both use similar memory?

Answer: A: 1000 - 1000 × 1/32 = 1000 - 31.25 ≈ 969. B: 1000 - 1000 × 16/32 = 500. Higher means killed first, so pod A, the one that reserved less.

Problem 4: is this a problem?

A pod with a 1Gi limit shows memory.current at 990 MiB all day and has never restarted. memory.stat says anon = 310 MiB and file = 670 MiB. Should you raise the limit?

Answer: No. Most of it is page cache from files the app reads, and the kernel drops cache when it needs room. Only 310 MiB cannot be dropped. Watch anon or the working set (which leaves out inactive cache) instead of memory.current.

Problem 5: the JVM that dies at startup

A Java service has limits.memory: 2Gi and starts with -Xmx2g. It is OOM-killed within a minute of starting under load. Explain and fix.

Answer: The heap alone may grow to 2 GiB, but the JVM also needs memory for metaspace, thread stacks, the JIT compiler, and direct buffers. Heap + non-heap goes over 2Gi. This is graph B (limit too small for the settings), not a leak. Fix: drop -Xmx and use -XX:MaxRAMPercentage=75 (about 1.5 GiB heap), or raise the limit to fit the heap plus non-heap memory.

Problem 6: the shared-memory surprise

A PyTorch training pod with a 16Gi limit is OOM-killed, but the Python process's heap is only 9 GiB. Data-loading worker processes pass batches through /dev/shm, which is mounted from an emptyDir with medium: Memory. What is using the rest?

Answer: Files in /dev/shm live in tmpfs, which is RAM charged to the container and cannot be dropped like normal page cache. Batches waiting in shared memory, plus the memory of each worker process, push the total over 16Gi. Fix: fewer workers or a smaller prefetch, a sizeLimit on the volume, and count shared memory in the limit.

15. Common Pitfalls

  • Raising the limit first. For a leak, it only makes kills less frequent and wastes memory. Do the leak-rate math first.
  • Blaming every exit 137 on memory. 137 only means SIGKILL. Check the reason field and memory.events.
  • Watching VSZ or memory.current. Use the working set or anon. VSZ includes memory never touched; memory.current includes cache that can be dropped.
  • Memory requests far below limits. The node is overbooked, and when several pods burst together, eviction or node OOM hits pods that did nothing wrong.
  • Language heap set to the full container limit. Leave room for non-heap memory (JVM metaspace and stacks, Go runtime, native libraries).
  • Unbounded in-process caches. Every cache needs a size or time bound and a key that can actually repeat.
  • Profiling only in production, or never. Reproduce under a cgroup limit locally and compare two heap snapshots.

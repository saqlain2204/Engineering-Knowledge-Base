Scenario: The Disk Is Full

At 03:10 the pager goes off. The API returns errors, the database log says "No space left on device", and someone already deleted a big log file but the disk is still at 100%. This page walks through that night step by step, with two labs you can run yourself, the usual culprits on Linux servers, Docker hosts, Kubernetes nodes and PostgreSQL, and the alerts that would have woken you up two days earlier. It builds on File Systems & Disk I/O.

1. The Incident

03:10  alert: api error rate 34%
03:11  api logs:  OSError: [Errno 28] No space left on device: '/var/lib/app/uploads/tmp...'
03:12  postgres:  PANIC: could not write to file "pg_wal/xlogtemp.123": No space left on device
03:14  on-call runs df -h:   /dev/nvme0n1p1  100G  100G  0  100%  /
03:16  on-call deletes /var/log/app/app.log (41 GB)
03:17  df -h still says 100%.  Nothing changed.

Two facts look impossible at 03:17. A 41 GB file was deleted and no space came back. Later, after things are fixed, du will say the whole disk only holds 52 GB of files, but df says 100 GB is used. Both make sense once you know how files are stored. Errno 28 (ENOSPC) is the error code behind "No space left on device", and you will see it from every program that tries to write.

Why does a full disk break so much at once? Almost everything writes: databases write their log before every commit, apps write temp files and logs, package managers and containers unpack files. When the disk is full, all of them fail together, and often in confusing ways (a database may even shut itself down to protect your data).

2. Words You Need

  • File system. The structure on a disk that stores files and folders (ext4, XFS, tmpfs). Each one is mounted at a folder, like / or /var/lib/docker.
  • Block. The unit of disk space, usually 4 KB. A 1-byte file still uses one block.
  • Inode. A small record for each file that holds its size, owner, permissions and where its blocks are. The file's name is not in the inode; names live in directories and point to inodes. Many file systems create a fixed number of inodes when they are formatted.
  • Link count. How many names point to an inode. rm removes a name and lowers the count. The data is only freed when the count is 0 and no process has the file open.
  • File descriptor. A number a process uses to refer to a file it has open. While a descriptor is open, the file's data stays, even with no name.
  • df asks the file system "how many blocks are used in total?" du walks the folders, adds up the files it can find by name. They answer different questions.
  • Ephemeral storage. In Kubernetes, the node's local disk that pods use for logs, writable container layers and emptyDir volumes. It disappears with the pod.

3. The First Five Minutes

Do these in order. Each one takes seconds.

# 1. which file system is full? (bytes)
df -h

# 2. is it really inodes?
df -i

# 3. which top-level folder is big? (-x: do not cross into other file systems)
sudo du -xh --max-depth=1 / 2>/dev/null | sort -h | tail -15

# 4. does du add up to much less than df? look for deleted-but-open files
sudo lsof +L1 2>/dev/null | sort -k7 -n | tail

# 5. what is still writing right now?
sudo iotop -o -b -n 3      # or: pidstat -d 1 5

Step 1 tells you where. Step 2 tells you what kind of full. Step 3 finds normal big files. Step 4 finds the invisible ones. Step 5 tells you what will refill the disk two minutes after you clean it, which matters more than anything you delete.

Priority. First, stop the bleeding: free a few GB safely so the database and app can write again (section 11). Then find the root cause. Do not start by deleting things you do not understand under /var/lib.

4. Lab 1: Deleted, but Still Using Space

This is what happened at 03:16. We reproduced it on Linux with a small 64 MB file system (a tmpfs mounted at /mnt/lab), so it fills in seconds:

sudo mount -t tmpfs -o size=64M,nr_inodes=2048,uid=$(id -u) tmpfs /mnt/lab

# a "logger" that keeps the file open and writes 1 MB at a time until it fails
python3 - <<'EOF' &
f = open('/mnt/lab/app.log', 'wb')
try:
    while True: f.write(b'x' * 1048576); f.flush()
except OSError as e: print("writer error:", e)
import time; time.sleep(60)          # keep the file open, like a real server
EOF

The real output, step by step:

writer error: [Errno 28] No space left on device

$ df -h /mnt/lab
Filesystem      Size  Used Avail Use% Mounted on
tmpfs            64M   64M     0 100% /mnt/lab

$ echo hello > /mnt/lab/new.txt
echo: write error: No space left on device

$ rm /mnt/lab/app.log           # "delete the big log"

$ df -h /mnt/lab
tmpfs            64M   64M     0 100% /mnt/lab      <- still full!

$ du -sh /mnt/lab
0       /mnt/lab                                     <- du sees nothing

$ sudo lsof +L1 /mnt/lab
COMMAND   PID   USER  FD  TYPE DEVICE  SIZE/OFF NLINK NODE NAME
python3 67144   box   3w  REG  0,51    67108864     0    2 /mnt/lab/app.log (deleted)

Read the lsof line: process 67144 has the file open as descriptor 3, for writing (3w). Its size is 67,108,864 bytes (64 MB). NLINK 0 means no name points to it any more. That is why du, which finds files by name, sees 0, while df, which counts used blocks, sees 64 MB.

  before rm                         after rm
  directory /mnt/lab                directory /mnt/lab
    "app.log" --> inode 2             (no entry)       inode 2   <-- fd 3 of PID 67144
                    |                                    |
                 64 MB of blocks                      64 MB of blocks  (still used!)

Two ways to get the space back:

# A: truncate the file through the process's descriptor (no restart needed)
: > /proc/67144/fd/3
df -h /mnt/lab
tmpfs            64M     0   64M   0% /mnt/lab       <- space is back

# B: restart (or signal) the process so it closes the file
kill 67144              # or: systemctl restart app, or send SIGHUP if it reopens logs

Option A gave back all 64 MB instantly in our lab. Use it for log files, never for database files. Option B is the real fix: a process should not hold a deleted log open. That happens when a log is deleted (or rotated) by hand but the program is never told to reopen it.

The headline. Deleting a file that a process still has open frees nothing until the process closes it. To empty a live log, truncate it (: > app.log or truncate -s 0 app.log) instead of deleting it. If you already deleted it, find it with lsof +L1.

5. Lab 2: Full With Space Left (Inodes)

Same 64 MB file system, which has room for only 2,048 inodes. We created many tiny files, as a session store or a mail queue would:

mkdir /mnt/lab/sess
for i in $(seq 1 2100); do echo s > /mnt/lab/sess/s$i || { echo "failed at file $i"; break; }; done
bash: /mnt/lab/sess/s2046: No space left on device
failed at file 2046

$ df -h /mnt/lab
Filesystem      Size  Used Avail Use% Mounted on
tmpfs            64M  8.0M   57M  13% /mnt/lab        <- 57 MB free!

$ df -i /mnt/lab
Filesystem     Inodes IUsed IFree IUse% Mounted on
tmpfs            2048  2048     0  100% /mnt/lab       <- no inodes left

The same error message, "No space left on device", with 57 MB free. Every file needs one inode; the root folder and the sess folder used 2, so file number 2,046 was the first one with no inode left. The 8 MB used is 2,045 files × one 4 KB page each.

On real ext4 disks the inode count is set when the disk is formatted (by default about one inode per 16 KB of space), and you cannot add more later without reformatting. Fixes: delete the tiny files (old sessions, cache entries, a stuck mail queue), find which folder has millions of them, and change the app to store them in a database or a few big files. XFS and Btrfs allocate inodes on demand, so this is mostly an ext4 problem.

# which folders hold the most files (inodes)?
sudo du --inodes -x / 2>/dev/null | sort -n | tail -10

6. Other Reasons df and du Disagree

CauseWhat you seeHow to check
Deleted-but-open filesdf much higher than dulsof +L1
Reserved blocks (ext4 keeps 5% for root by default)Size minus Used is more than Avail. On a 1 TB disk, 50 GB is held back. Normal users get ENOSPC while root can still writesudo tune2fs -l /dev/sdX1 | grep -i reserved
Files hidden under a mount pointSomething wrote into /data before the disk was mounted there. The mount now covers those files, so du cannot see them, but they use space on the root disksudo mount --bind / /mnt/rootonly, then du -sh /mnt/rootonly/data
Sparse filesdu lower than ls -l says (a VM disk image of "100 GB" that only uses 3 GB)du -h --apparent-size vs du -h
Snapshots (Btrfs, ZFS, LVM)Deleted files still in an old snapshotThe file system's snapshot list

The reserved 5% is there on purpose: it lets root log in and clean up, and keeps system services alive when users fill the disk. On a big data-only disk you can lower it with sudo tune2fs -m 1 /dev/sdX1 (1%).

7. Finding What Is Big

# biggest folders, one level at a time (drill down by changing the path)
sudo du -xh --max-depth=1 /var 2>/dev/null | sort -h | tail

# biggest single files on this file system
sudo find / -xdev -type f -size +1G -printf '%s\t%p\n' 2>/dev/null | sort -n | tail | numfmt --field=1 --to=iec

# files changed in the last hour (what is growing right now?)
sudo find /var -xdev -type f -mmin -60 -size +100M -ls 2>/dev/null

# interactive browser, if installed
sudo ncdu -x /

The -x / -xdev flag is important. Without it, du / also walks other mounted disks, network shares and /proc, which is slow and confusing. You want only the full file system.

8. The Usual Culprits

8.1 Application logs and broken rotation

Log rotation means: every day (or every 100 MB), rename the current log, start a new one, compress old ones, and delete the oldest. On Linux, logrotate does this. There are two styles, and the wrong one causes Lab 1:

StyleHow it worksCatch
create (default)Rename app.log to app.log.1, create a new empty app.log, then run postrotate (usually a signal like SIGHUP) so the app reopens its logIf the app ignores the signal, it keeps writing to app.log.1, which is later deleted while still open
copytruncateCopy app.log to app.log.1, then truncate app.log to 0 in placeWorks with apps that never reopen. Lines written between the copy and the truncate are lost, and the copy briefly needs double the space
 
# /etc/logrotate.d/app
/var/log/app/*.log {
    daily
    rotate 7            # keep 7 old files
    maxsize 500M        # rotate early if a file passes 500 MB
    compress
    delaycompress
    missingok
    notifempty
    copytruncate        # the app cannot reopen its log on a signal
}

A debug log level left on after an incident is the classic source: 10 times more lines, and nobody notices until the disk fills.

8.2 The systemd journal

journalctl --disk-usage                     # how big is it?
sudo journalctl --vacuum-size=1G            # shrink it now
# keep it capped: in /etc/systemd/journald.conf
SystemMaxUse=1G

8.3 Docker hosts

docker system df                            # images, containers, volumes, build cache
docker image prune -a --filter "until=168h" # unused images older than 7 days
docker builder prune                        # build cache (often many GB on CI runners)
sudo du -sh /var/lib/docker/containers/*/*-json.log | sort -h | tail   # container logs

The default Docker log driver (json-file) does not rotate. A chatty container can write a 50 GB log under /var/lib/docker/containers/. Cap it for new containers in /etc/docker/daemon.json:

{ "log-driver": "json-file", "log-opts": { "max-size": "10m", "max-file": "3" } }

See Advanced Docker for smaller images, which also means less disk.

8.4 Kubernetes nodes

The kubelet watches the node's disk and acts before it is completely full. Default hard eviction thresholds on Linux:

SignalDefault thresholdMeaning
nodefs.available< 10%The node's main disk (logs, emptyDir, kubelet data)
imagefs.available< 15%Where container images and writable layers live
nodefs.inodesFree< 5%Inodes on the main disk

When a threshold is crossed:

  1. The node gets the condition DiskPressure=True and a taint, so no new pods are scheduled there.
  2. The kubelet deletes unused images. Separately, image cleanup also runs whenever image disk use passes 85% (imageGCHighThresholdPercent), until it is back to 80%.
  3. If that is not enough, it evicts pods, starting with those using the most disk compared to what they requested. The pod's status says The node was low on resource: ephemeral-storage.
resources:
  requests:
    ephemeral-storage: "1Gi"
  limits:
    ephemeral-storage: "4Gi"     # this pod is evicted if it uses more
volumes:
- name: scratch
  emptyDir:
    sizeLimit: 2Gi               # cap one emptyDir

Set these so one noisy pod (a model download, a runaway debug log, a big temp file) is evicted alone, instead of filling the node and getting everything evicted. The kubelet also rotates container logs (by default at 10 Mi, keeping 5 files), so kubectl logs output is bounded per container. See Scheduling for eviction order and taints.

9. The Database Case: WAL That Will Not Go Away

Back to our incident. After freeing space, du shows /var/lib/postgresql/17/main/pg_wal at 38 GB. Normally it is 1 to 2 GB.

PostgreSQL writes every change to its write-ahead log (WAL) before changing the data files (see Transactions). Old WAL files are deleted once they are no longer needed. Two things can make them "needed" forever:

  • A replication slot whose replica is gone. A slot promises "I will keep all WAL until this replica has read it" (see Replication). If the replica was deleted months ago but the slot was not, WAL piles up without limit.
  • A failing archive_command (the command that copies WAL to backup storage). WAL is kept until it has been archived successfully.
-- which slots hold WAL, and how much?
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;

--  slot_name        | active | retained
-- ------------------+--------+----------
--  replica_old_dc   | f      | 36 GB      <- inactive, holding 36 GB

-- is archiving failing?
SELECT archived_count, failed_count, last_failed_wal, last_failed_time
FROM pg_stat_archiver;

The fix for a dead slot is to drop it, after confirming no replica uses it: SELECT pg_drop_replication_slot('replica_old_dc');. PostgreSQL then removes the old WAL at the next checkpoint. To stop it from happening again, set max_slot_wal_keep_size (for example '20GB'): a slot that falls further behind is invalidated instead of filling the disk.

Never delete files in pg_wal by hand. Those files may be needed to recover after a crash. Deleting them can corrupt the database. The same goes for MySQL binary logs (use PURGE BINARY LOGS) and Kafka segments (use retention settings).

10. Time-to-Full Math

The night could have been a calm afternoon. Here is the simple math an alert can do.

disk size            100 GB
free right now        20 GB
growth (last 6 h)      2 GB per hour

time to full  =  free / growth  =  20 / 2  =  10 hours

A fixed threshold ("alert at 90%") is a poor fit for both slow and fast growth. On a disk that grows 1 GB a month, 90% might be a year away. On a disk filling at 10 GB an hour, 90% gives you one hour, at night. Alert on time to full instead. In Prometheus with node_exporter:

# fire if, at the trend of the last 6 hours, the disk is full within 24 hours
predict_linear(node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}[6h], 24 * 3600) < 0

# and the inode version
predict_linear(node_filesystem_files_free{fstype!~"tmpfs|overlay"}[6h], 24 * 3600) < 0

predict_linear draws a straight line through the last 6 hours of free space and asks where it will be in 24 hours. Pair it with a plain "free < 5%" alert as a safety net for sudden jumps.

11. The Fix, in Order

  1. Make a little room safely. Truncate (do not delete) the biggest live log: sudo truncate -s 0 /var/log/app/app.log. Vacuum the journal. Prune unused Docker images. A few GB is enough to let the database and app write again.
  2. Stop the source. Find what is writing (iotop, pidstat -d, files with recent -mmin). Turn the debug log level off, stop the runaway job, or cap it.
  3. Release deleted-but-open files. lsof +L1, then restart or signal those processes (or truncate through /proc/<pid>/fd/<n> for logs).
  4. Check the database. Did it shut down? Is WAL held by a slot or failed archiving? Fix with SQL, not rm.
  5. Grow the disk if needed. Cloud disks can usually be enlarged live: grow the volume, then the partition (growpart), then the file system (resize2fs for ext4, xfs_growfs for XFS).
  6. Write down the cause and add the alert that would have caught it (section 12).

In our incident: truncating the app log freed 41 GB (it had been deleted while open, so we truncated it through /proc), the debug flag was turned off, the old replication slot was dropped (36 GB back), and max_slot_wal_keep_size and a time-to-full alert were added the next morning.

12. Prevention and Alerts

  • Separate disks for separate jobs. Put database data, logs and Docker storage on their own file systems. A runaway log then fills the log disk, not the database disk.
  • Cap every log. logrotate with maxsize, journald SystemMaxUse, Docker max-size, and send app logs to a central system (stdout in containers) rather than local files.
  • Limits on pods. ephemeral-storage requests and limits, and emptyDir.sizeLimit.
  • Alerts on time to full, for bytes and inodes, plus a "slot inactive" and "archiver failing" alert for PostgreSQL.
  • Clean up by policy. Retention for backups, build caches and temp folders (systemd-tmpfiles, object-storage lifecycle rules), not by hand at 3 AM.
  • Practice. Fill a test disk on purpose (Lab 1 takes a minute) and see how each service fails. Some fail loudly, some silently drop data.

13. Common Pitfalls

  • Deleting a live log. It frees nothing while the process holds it open. Truncate instead.
  • Checking only df -h. "No space left" with free space means inodes. Run df -i.
  • Running du / without -x. It crosses into other disks and /proc, and lies about where the space is.
  • Deleting database files. Never rm WAL, binlogs or data files. Use the database's own commands.
  • Cleaning without stopping the source. The disk refills in minutes and you lose the evidence.
  • Forgetting reserved blocks and mounts. "Avail" is not "Size minus Used", and files can hide under a mount point.
  • docker system prune -a --volumes in a hurry. It also deletes unused volumes, which may hold data you wanted. Prune images and build cache first.
  • Thresholds instead of trends. "90% full" is too late on a fast disk and too noisy on a slow one.

14. Practice Problems

Problem 1

df -h / shows 200G size, 200G used, 0 available. sudo du -xsh / shows 120G. List three possible reasons for the 80 GB gap and the command to check each.

Solution

(1) Deleted-but-open files: sudo lsof +L1. (2) Files hidden under a mount point: bind-mount / to /mnt/rootonly and run du there. (3) Snapshots on Btrfs/ZFS/LVM: list them. (Reserved blocks do not explain it here, because they show up as "Avail" being lower than "Size minus Used", not as "Used" being higher than du.)

Problem 2

An app says "No space left on device". df -h shows 40% used. What do you run next, and what are you likely to find?

Solution

df -i. Likely 100% inode use from millions of tiny files: a session folder, a cache, a mail queue, or a temp folder nobody cleans. Find it with sudo du --inodes -x / | sort -n | tail.

Problem 3

A disk has 300 GB free and is filling at 25 GB per hour since a deploy 2 hours ago. When will it be full? Would an "85% full" alert on a 1 TB disk have fired yet?

Solution

300 / 25 = 12 hours. Used space is 1,000 - 300 = 700 GB = 70%, so the 85% alert has not fired. It will fire at 850 GB used, which is (850 - 700) / 25 = 6 hours from now, leaving only 6 hours. A predict_linear alert with a 24-hour look-ahead would already be firing.

Problem 4

A Kubernetes pod shows Status: Failed, Reason: Evicted, Message: The node was low on resource: ephemeral-storage. Container trainer was using 38Gi, request is 0. Explain and fix.

Solution

The container wrote 38 GiB to local disk (probably model checkpoints or a dataset in its writable layer or an emptyDir). The node crossed its disk eviction threshold, and this pod was evicted first because it used the most disk compared with its request (0). Fix: write big files to a PersistentVolume or object storage, set ephemeral-storage requests and limits, and set sizeLimit on any emptyDir.

Problem 5

A colleague suggests freeing space on the database server with rm /var/lib/postgresql/17/main/pg_wal/0000000100000A2*. What do you say, and what do you check instead?

Solution

Stop: deleting WAL by hand can make the database unrecoverable after a crash and break replicas. Check pg_replication_slots for inactive slots holding WAL and pg_stat_archiver for failing archiving. Drop the dead slot or fix the archive command, and PostgreSQL removes old WAL itself at the next checkpoint.

15. Cheat Sheet

# what is full?
df -h                  bytes per file system
df -i                  inodes per file system

# where?
sudo du -xh --max-depth=1 /path | sort -h | tail
sudo du --inodes -x / | sort -n | tail
sudo find / -xdev -type f -size +1G -ls
sudo lsof +L1          deleted but still open (NLINK 0)

# safe quick wins
sudo truncate -s 0 /var/log/app/app.log       (never rm a live log)
: > /proc/PID/fd/N                             (log already deleted, still open)
sudo journalctl --vacuum-size=1G
docker image prune -a; docker builder prune

# never
rm on pg_wal, binlogs, database data files

# PostgreSQL
SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn))
FROM pg_replication_slots;
SELECT pg_drop_replication_slot('dead_slot');
max_slot_wal_keep_size = '20GB'

# Kubernetes
kubectl describe node NODE | grep -i pressure
resources.limits.ephemeral-storage, emptyDir.sizeLimit
evictionHard defaults: nodefs.available<10% imagefs.available<15% nodefs.inodesFree<5%

# alert
predict_linear(node_filesystem_avail_bytes[6h], 24*3600) < 0

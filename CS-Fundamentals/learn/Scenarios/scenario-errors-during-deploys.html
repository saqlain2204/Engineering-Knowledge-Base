Scenario: Errors During Every Deploy

A team ships a new version of its orders API several times a day. Every single time, the error dashboard shows a short spike of 502 Bad Gateway errors, then it goes quiet until the next release. Nobody changed the code that handles requests. This page follows the investigation the way an on-call engineer would, then reproduces the problem in a small program you can run and measures how much each fix helps. It uses ideas from TCP, HTTP, processes and signals, and Kubernetes probes and rollouts. The company and names are made up; the error types, the code, and the measured numbers are real.

1. The Situation

The orders API runs on Kubernetes as a Deployment with 6 pods. Traffic comes in through a cloud load balancer, then an ingress controller (a proxy inside the cluster that routes HTTP requests to Services), then to the pods.

On Thursday at 15:10 IST, a release goes out. The dashboard shows:

15:09   0 errors / min       (normal)
15:10   release starts
15:10   41 x 502 / min
15:11   37 x 502 / min
15:12   0 errors / min        (release finished)

(These dashboard numbers are part of the story. The numbers measured by real code are in section 7.)

The same pattern shows up on every release, and also whenever the autoscaler removes pods at night. Customers sometimes see "Something went wrong" when they place an order. A few retried and were charged twice.

2. Read the Status Code: 502, 503, 504

Status codes in the 5xx range mean "the server side failed". But which server? When there is a proxy in front (and there almost always is), these three codes usually come from the proxy, describing what happened when it tried to talk to your app (the upstream):

CodeNameWhat the proxy is sayingUsual causes
502Bad Gateway"I reached for the upstream, and the connection failed or the answer was broken."Connection refused (nothing listening), connection reset mid-request (the process died), upstream closed a keep-alive connection at the wrong moment
503Service Unavailable"I have no healthy upstream to send this to," or the app itself says "I am overloaded."No ready pods in the Service, load shedding, maintenance
504Gateway Timeout"I sent the request, and the upstream did not answer in time."Slow app, slow database, a firewall silently dropping packets (see the database scenario)

Intuition. A 502 means the connection to the app went wrong, not that the app's logic returned an error. If your app had a bug, you would see 500s written by the app. A burst of 502s that matches the deploy time points at pods starting or stopping.

3. Draw the Path a Request Takes

  user
   │ HTTPS
   ▼
  cloud load balancer ──► ingress controller pods (nginx)
                                 │  picks a pod IP from the Service's
                                 │  endpoint list (keeps its own copy)
                 ┌───────────────┼───────────────┐
                 ▼               ▼               ▼
              orders-1        orders-2  ...   orders-6
               (pod)           (pod)           (pod)

The important detail: the ingress controller does not ask Kubernetes "which pods are ready?" on every request. It keeps its own copy of the list of pod IPs and updates it when Kubernetes tells it something changed. So does kube-proxy on every node, and so does the cloud load balancer if it sends traffic straight to pods. Each copy is updated a little later than the change.

4. Collect Clues: When, Where, How Many

The on-call engineer checks four things, changing one question at a time:

  1. Which component wrote the 502? The ingress controller's access log has the line, with the upstream address and an upstream status of - (no answer). The app's own logs have nothing for those requests. So the proxy could not get an answer from a pod.
  2. Which pods? Every failing request went to a pod IP that was being shut down, or to one that had just been created.
  3. The error text. The ingress error log shows two kinds of message: connect() failed (111: Connection refused) while connecting to upstream and upstream prematurely closed connection while reading response header from upstream. Error 111 is "connection refused" (the port is closed). "Prematurely closed" means the process went away in the middle of a request.
  4. The pod spec. There is no readiness probe, no preStop hook, and the app is started by a small shell script.

That last point hides another clue. When a container's main process is a shell script (sh start.sh), the shell is process number 1 in the container. The shell does not pass SIGTERM on to the real app. So the app never hears it, and after 30 seconds it is killed with SIGKILL, cutting every request in flight. (The fix is exec python app.py in the script, so the app replaces the shell, or a small init like tini.)

5. The Root Cause: Two Things Happen at Once

When Kubernetes deletes a pod, it starts two things in parallel (see How a Pod Shuts Down):

t = 0 s    pod marked "terminating"
           ├── kubelet sends SIGTERM to the app         ─► app exits at once
           └── pod removed from the endpoint list ─► ...
t ≈ 0-2 s       ingress, kube-proxy, LB each get the news at different times

           Between "app exited" and "everyone has the news",
           traffic still goes to a closed port:  502 Connection refused

And at the start of the rollout, a similar gap happens the other way:

new pod created, container starts, app still loading (no readiness probe)
           ├── Kubernetes: "container running, so it is ready"
           └── pod added to the endpoint list at once
           traffic goes to a port that is not listening yet: 502

And requests that were already running in the old pod are cut when it exits: 502 "prematurely closed".

So there are three separate holes: too early in, too early out, and cut mid-request. Each needs its own fix.

6. Reproduce It: a Lab You Can Run

A theory is good. A measurement is better. This single Python file (standard library only) builds a tiny version of the system: a round-robin load balancer, two "pods" (separate processes), 16 clients sending requests non-stop, and a rolling update that replaces both pods one at a time. It copies the real timing problems:

  • a new pod needs 2 s to load before it listens;
  • each request takes 100 ms;
  • the load balancer hears "pod removed" 1 s after SIGTERM is sent (the propagation delay).

It runs four cases:

CaseReadiness checkOn SIGTERM
ANo: new pod gets traffic at onceExit immediately
BYes: traffic only after /ready says 200Exit immediately
CYesStop accepting, finish requests in flight, exit
DYesKeep serving 3 s (like a preStop sleep), then finish in-flight requests and exit
 
"""Rolling-deploy lab: why pods return errors while a new version rolls out.

One file, standard library only. It starts a tiny load balancer and two
"pods" (backend processes), sends steady traffic, then replaces both pods one
by one, the way a Kubernetes rolling update does. It counts every response.

Usage: python3 deploy_lab.py A|B|C|D
  A = no readiness check, pod exits at once on SIGTERM
  B = readiness check,    pod exits at once on SIGTERM
  C = readiness check,    pod finishes in-flight requests, then exits
  D = readiness check,    pod keeps serving for a few seconds (preStop sleep),
      then finishes in-flight requests and exits
"""
import http.client, http.server, os, signal, subprocess, sys, threading, time
from collections import Counter

WORK = 0.1          # each request takes 100 ms of "work"
STARTUP = 2.0       # a new pod needs 2 s before it can serve (loading)
PROPAGATION = 1.0   # the load balancer hears "pod removed" 1 s after SIGTERM
PRESTOP = 3.0       # case D: keep serving this long after SIGTERM

def backend(port, mode):
    time.sleep(STARTUP)                      # loading config, warming caches
    state = {"draining": False}
    class H(http.server.BaseHTTPRequestHandler):
        def log_message(self, *a): pass
        def do_GET(self):
            if self.path == "/ready":
                code = 503 if state["draining"] else 200
            else:
                time.sleep(WORK); code = 200
            self.send_response(code); self.send_header("Content-Length", "2")
            self.end_headers(); self.wfile.write(b"ok")
    class Server(http.server.ThreadingHTTPServer):
        def handle_error(self, *a): pass      # a client gave up; ignore
    srv = Server(("127.0.0.1", port), H)
    srv.daemon_threads = False                # so we can wait for in-flight work
    def on_term(*_):
        if mode in "AB":
            os._exit(0)                       # die now, drop in-flight requests
        def drain():
            state["draining"] = True
            if mode == "D":
                time.sleep(PRESTOP)           # still serving while LB catches up
            srv.shutdown()                    # stop accepting new connections
            srv.server_close()                # wait for in-flight requests
            os._exit(0)
        threading.Thread(target=drain).start()
    signal.signal(signal.SIGTERM, on_term)
    srv.serve_forever()

class LB:
    def __init__(self):
        self.pool, self.lock, self.i = [], threading.Lock(), 0
    def pick(self):
        with self.lock:
            if not self.pool: return None
            self.i += 1; return self.pool[self.i % len(self.pool)]
    def add(self, p):
        with self.lock: self.pool.append(p)
    def remove(self, p):
        with self.lock:
            if p in self.pool: self.pool.remove(p)

def send(port, path="/"):
    c = http.client.HTTPConnection("127.0.0.1", port, timeout=5)
    try:
        c.request("GET", path); r = c.getresponse(); r.read(); return r.status
    finally:
        c.close()

def main(mode):
    lb, results, stop = LB(), Counter(), threading.Event()
    count_lock = threading.Lock()
    procs = {}
    def start(port):
        procs[port] = subprocess.Popen([sys.executable, __file__, "serve", str(port), mode])
        if mode == "A":
            lb.add(port)                      # no readiness check: add at once
            return
        while True:                           # readiness check every 100 ms
            try:
                if send(port, "/ready") == 200: break
            except OSError: pass
            time.sleep(0.1)
        lb.add(port)
    def terminate(port):
        procs[port].send_signal(signal.SIGTERM)          # kubelet sends SIGTERM...
        threading.Timer(PROPAGATION, lb.remove, [port]).start()  # ...LB learns later
    def client():
        while not stop.is_set():
            port = lb.pick()
            try:
                outcome = send(port) if port else "no backend"
            except ConnectionRefusedError:
                outcome = "refused"               # nothing listening on that port
            except (ConnectionResetError, http.client.HTTPException):
                outcome = "reset"                 # connection cut mid-request
            except OSError as e:
                outcome = type(e).__name__
            with count_lock:
                results[outcome] += 1
    start(9101); start(9102)
    if mode == "A": time.sleep(STARTUP + 0.5)      # let the first pods load
    threads = [threading.Thread(target=client) for _ in range(16)]
    t0 = time.time()
    for t in threads: t.start()
    time.sleep(2)
    for old, new in [(9101, 9103), (9102, 9104)]:  # rolling update, one at a time
        start(new); terminate(old); time.sleep(PRESTOP + 2)
    time.sleep(2); stop.set()
    for t in threads: t.join()
    for p in procs.values():
        p.kill(); p.wait()                    # clean up before the next run
    total = sum(results.values()); bad = total - results[200]
    print(f"case {mode}: {total} requests in {time.time()-t0:.1f} s, "
          f"{results[200]} ok, {bad} failed ({100*bad/total:.2f}%)  {dict(results)}")

if __name__ == "__main__":
    if sys.argv[1] == "serve": backend(int(sys.argv[2]), sys.argv[3])
    else: main(sys.argv[1])

Run it with for m in A B C D; do python3 deploy_lab.py $m; done.

How the lab maps to the real thing. A real proxy turns "connection refused" and "connection reset" into a 502 for the user. Our clients talk to the pods directly through the load balancer's choice, so they see the raw errors instead. The lab's "LB" is a list of ports inside the client; removing a port from that list after 1 s plays the role of the endpoint update reaching the ingress controller.

7. The Results, Case by Case

We ran all four cases three times on an 8-core Linux machine. Real output from one round:

case A: 3184 requests in 14.1 s, 2210 ok, 974 failed (30.59%)  {200: 2210, 'reset': 16, 'refused': 958}
case B: 3049 requests in 18.3 s, 2876 ok, 173 failed (5.67%)  {200: 2876, 'reset': 16, 'refused': 157}
case C: 3032 requests in 18.3 s, 2880 ok, 152 failed (5.01%)  {200: 2880, 'reset': 2, 'refused': 150}
case D: 2880 requests in 18.3 s, 2880 ok, 0 failed (0.00%)  {200: 2880}

All three rounds:

CaseFailed (3 runs)RefusedReset
A: no readiness, exit at once30.59%, 30.66%, 30.71%958, 957, 95816, 16, 16
B: readiness, exit at once5.67%, 5.62%, 5.75%157, 156, 16016, 16, 16
C: readiness, finish in-flight5.01%, 5.26%, 5.26%150, 158, 1582, 2, 2
D: readiness, keep serving 3 s, finish in-flight0.00%, 0.00%, 0.00%0, 0, 00, 0, 0

(Case A runs for less time because it does not wait for new pods to become ready.)

What each number tells us

  • A → B: the readiness check removed about 800 refusals per run. In case A, each new pod was in the list for 2 s before it listened. With round robin, a share of all requests went there and were refused.
  • The 16 resets in A and B are requests in flight being cut. 16 clients spread over 2 pods means about 8 requests are running on each pod at any moment. Two pods were killed: 2 × 8 = 16. That matches exactly.
  • B → C: graceful shutdown removed the cut requests (16 → 2). But the refusals stayed, because the pod stopped listening right away while the load balancer still had it in the list for 1 s.
  • The 2 resets left in C are connections that had already reached the pod's waiting queue (the TCP accept backlog) when it closed its listening socket. They were accepted by the kernel but never handled.
  • C → D: keeping on serving for 3 s, longer than the 1 s delay, removed everything. By the time the pod stopped listening, nobody was sending to it any more.

Why the percentages look so large. A refused connection fails in well under a millisecond, while a good request takes 100 ms. So during an error window, the clients fire many fast failures. Do not read "30%" as "30% of users". The better summary is: case A had error windows of a few seconds per pod; case D had none.

9. Graceful Shutdown in the App

The order of steps on SIGTERM matters:

  1. Make /ready return 503 (so any remaining health checks stop sending traffic).
  2. Keep serving normally for a few seconds (if you do not use a preStop hook).
  3. Stop accepting new connections.
  4. Wait for requests in flight to finish, with a time limit below the grace period.
  5. Close database pools and flush logs. Exit with code 0.

Most servers already know how to do steps 3 and 4:

ServerOn SIGTERM
Gunicorn (Python)Graceful: workers finish current requests, up to --graceful-timeout (30 s by default)
Uvicorn (Python)Graceful; use --timeout-graceful-shutdown to cap the wait
Go net/httpNothing by itself: you catch the signal and call server.Shutdown(ctx)
Node.js httpNothing by itself: catch SIGTERM and call server.close()
nginxSIGTERM is a fast stop; SIGQUIT is the graceful one (so nginx images set STOPSIGNAL SIGQUIT)

And the container must actually deliver the signal: in the Dockerfile, use the exec form CMD ["python", "app.py"], not the shell form CMD python app.py, which wraps the app in a shell (see Docker Fundamentals).

10. The Second Cause: Keep-Alive Timeout Races

After the fix, the deploy spikes are gone. But a few 502s a day remain, at random times. The ingress log says upstream prematurely closed connection, always on a connection that had been idle for a while.

The proxy keeps connections to pods open and reuses them (keep-alive, see TCP) to skip new handshakes. The app's server closes idle connections after its own timeout. If the app's timeout is shorter than the proxy's, this can happen:

proxy idle timeout: 60 s       app idle timeout: 5 s

t = 0      last request on connection #7 finishes; both sides keep it open
t = 5.000  app: "idle 5 s, closing #7"  ─► sends FIN
t = 5.000  proxy, at the same moment: sends a new request on #7
           (the FIN has not arrived yet)
           app's kernel: connection is closed  ─► RST
           proxy: "upstream prematurely closed"  ─► 502 to the user

Rule: the side that sends the request must time out idle connections first. Set the app's keep-alive timeout longer than the proxy's (and the proxy's longer than the cloud load balancer's, if that one reuses connections to the proxy). For example, Gunicorn's --keep-alive defaults to 2 seconds, which is shorter than most load balancers' idle timeouts.

11. Should the Load Balancer Retry?

Proxies can retry a failed request on another pod. It hides many 502s. But remember the customers who were charged twice.

  • Safe to retry: requests that failed with "connection refused" (the request never reached the app), and idempotent methods like GET, PUT, DELETE (see Methods and Idempotency).
  • Not safe by default: a POST /orders that was cut mid-request. The app might have created the order before dying. A retry creates a second one.
  • The fix for POST: an idempotency key. The client sends a unique ID with the request (Idempotency-Key: 6f1c...). The server stores the result under that key; a repeat with the same key returns the stored result instead of acting twice.

nginx, for example, does not retry non-idempotent requests on another upstream unless you allow it with proxy_next_upstream ... non_idempotent. Keep it that way unless the app uses idempotency keys. Also cap retries, or a struggling service gets a retry storm (see Debugging a Slow API).

12. Blameless Postmortem

A postmortem is a short written review after an incident. "Blameless" means it looks for the weak points in the system, not a person to blame.

SummaryEvery release, and every night-time scale-down, caused about 1-2 minutes of 502 errors on the orders API. Some customers who retried were charged twice.
ImpactFailed requests during each release; duplicate orders when a user retried after a cut POST.
Root causes(1) No readiness probe: new pods got traffic before listening. (2) The app started from a shell script, so SIGTERM never reached it; it was SIGKILLed after 30 s, cutting requests. (3) No preStop delay: pods stopped listening before every proxy had removed them. (4) App keep-alive timeout (2 s) shorter than the proxy's.
What went wellThe ingress log recorded the upstream address and error text, which pointed straight at pods starting and stopping.
ActionsAdd startup and readiness probes; exec the app; handle SIGTERM gracefully; preStop sleep 10 s; grace period 45 s; app keep-alive 75 s (above the proxy's 60 s); idempotency keys on POST /orders; the CI check below.

13. Preventing It: a Deploy Check in CI

The lab above is also a test. The same idea works against a real staging cluster: send steady traffic, do a rollout, and fail the pipeline if any request failed.

# sketch of a CI step (staging cluster)
hey -z 120s -c 20 https://orders.staging.example.com/healthz-deep > load.txt &
kubectl -n staging set image deployment/orders app=registry.example.com/orders:$GIT_SHA
kubectl -n staging rollout status deployment/orders --timeout=300s
wait
grep -E "^\s+\[(5[0-9]{2})\]" load.txt && { echo "errors during rollout"; exit 1; } || echo "clean rollout"

hey is a small load-testing tool; its report lists each status code with a count, like [200] 23081 responses. The script fails if any 5xx line appears. Run it on every change to the Deployment, the Dockerfile, or the app's server settings, since those are what break shutdown behavior. (See CI/CD and MLOps for wiring steps like this into a pipeline.)

14. Practice Problems

Answers follow each one.

Problem 1: which code?

For each, say whether a proxy would most likely return 502, 503 or 504: (a) every pod of the Service is failing readiness; (b) the app takes 90 s and the proxy timeout is 60 s; (c) the pod's process crashed while handling the request.

Answer: (a) 503, no healthy upstream. (b) 504, upstream too slow. (c) 502, the connection broke.

Problem 2: predict the resets

In the lab, change the number of clients from 16 to 32 and keep 2 pods. In case B, about how many "reset" errors do you expect? Why?

Answer: About 32. 32 clients over 2 pods is about 16 requests in flight per pod; two pods are killed: 2 × 16 = 32. (Each request takes 100 ms and clients send without pause, so nearly every client is always in the middle of a request.) We ran exactly this change: case B with 32 clients gave 'reset': 32.

Problem 3: how long a preStop?

You measured that the slowest part of your system (a cloud load balancer) takes up to 8 s to stop sending to a removed pod. The slowest normal request is 12 s. Choose the preStop sleep and the grace period.

Answer: preStop a bit more than 8 s, say 10 s. The grace period must cover preStop + the slowest request + margin: 10 + 12 = 22, so 30 s or more (the default 30 s just fits; 40 s is safer).

Problem 4: the keep-alive rule

A cloud load balancer has an idle timeout of 350 s and reuses connections to your nginx ingress. nginx keeps upstream connections to pods for 60 s. The app's server times out idle connections after 5 s. Which settings are wrong, and what would you change?

Answer: Each side that receives requests must keep idle connections longer than the side that sends them. nginx's client-side keep-alive must be over 350 s, and the app's must be over 60 s. Set the app to, say, 75 s and nginx's client keep-alive to, say, 360 s (or lower the load balancer's idle timeout below nginx's).

Problem 5: is it safe to retry?

The proxy got "connection refused" for a POST /payments. Is it safe to retry on another pod? What if it got "upstream prematurely closed connection while reading response header"?

Answer: Connection refused means no TCP connection was made, so the app never saw the request: safe to retry. "Prematurely closed while reading the response" means the request was sent and the app may have acted on it: not safe unless the request carries an idempotency key.

15. Common Pitfalls

  • Blaming the code change. If errors appear on every deploy regardless of what changed, look at how pods start and stop, not at the diff.
  • Shell as PID 1. CMD python app.py (shell form) or a start script without exec: the app never sees SIGTERM.
  • Readiness that always says yes. A /ready that returns 200 before the app has loaded is the same as no probe.
  • preStop longer than the grace period. The pod is SIGKILLed during the sleep.
  • Only testing with no traffic. A rollout on an idle staging cluster always looks perfect.
  • Retrying non-idempotent requests at the proxy to hide errors. It turns 502s into duplicate orders.
  • App keep-alive shorter than the proxy's. Rare, random 502s that are very hard to find.

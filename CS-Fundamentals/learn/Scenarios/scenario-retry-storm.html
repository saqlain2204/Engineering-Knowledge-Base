Scenario: A Retry Storm Takes the Service Down

A checkout API is fine at 9:00. At 9:12 the payment dependency gets slow. By 9:14 your error rate is near 100%, the dependency's CPU is on the floor, and adding more replicas of your own service makes things worse. This page walks through that incident, with a lab you can run in your head and in Python. It builds on timeouts and safe retries and on debugging a slow API.

1. The Incident

You run an API with 50 workers. Each request needs 50 ms of work from a payment service, so the chain can handle about 1,000 requests per second. Normal traffic is 400 requests per second. At 9:12 the payment service starts taking 150 ms instead of 50 ms. Its capacity drops to about 333 requests per second, a little under the 400 you are still sending.

That should be a mild overflow, not an outage. Instead you see:

  • Client timeouts (200 ms) start firing.
  • Each timed-out request is retried three times, immediately.
  • The payment service is now offered far more than 400 requests per second, most of them repeats of work it has already started or already finished too late.
  • Your own queue grows. Requests spend so long in the queue that they time out after a worker has picked them up. The worker still finishes the work (abandoned work). The client has already retried, so the work is done twice, or four times, and nobody is happy.

By 9:14, success looks like a floor, not a dip. This is a retry storm. The original slowdown was real. The collapse is something you helped build, in the retry policy.

2. Words You Need

  • Timeout. How long the caller will wait for a response before giving up. If this is shorter than the work plus the queue delay, every request fails, even if the server would have gotten there eventually.
  • Retry. Sending the same logical request again after a failure or a timeout.
  • Amplification. How many attempts the server sees for each user request. Three retries plus the original is up to 4× if every attempt is sent.
  • Abandoned work. The server keeps working on a request after the client has given up. The result, when it arrives, has no one waiting, and the worker was not free for a request that still had a chance.
  • Exponential backoff. Wait 50 ms, then 100 ms, then 200 ms, and so on, between retries, instead of retrying at once.
  • Jitter. Randomness in that wait, so that a thousand clients do not retry on the same millisecond.
  • Retry budget. A cap on how many retries the system will start (per second, or as a fraction of live traffic).
  • Circuit breaker. After enough recent failures, stop sending (or stop retrying) for a short time, so the dependency can recover.
  • Load shedding. Refuse some work on purpose, early, so the work you do accept can finish inside the timeout.
  • Idempotent. Doing the request twice has the same effect as doing it once. Safe to retry. A "charge this card" call is not idempotent unless you give it an idempotency key.
  • Thundering herd. Many clients wake up and retry at the same time, often after a shared outage ends.

3. How Retries Amplify Load

Write the amplification out before you look at a graph.

Each user request may become:
  1 original attempt
  + up to R retries

If every attempt times out, offered load is (1 + R) × user traffic.

User traffic        400 req/s
R = 3 immediate retries
Offered load        up to 1,600 req/s

Dependency capacity after the slowdown
  50 workers × (1000 ms / 150 ms)  =  333 req/s

1,600 into a 333-capacity service cannot recover. Even 400 into 333 was only a mild overflow. The retries are what turn a queue into a stampede.

There is a second multiplier: layers. If the mobile app retries, and your API retries, and the service mesh retries, a single user action can become 4 × 4 × 4 = 64 attempts. The rule is: retry in one place, with a budget, and make the other layers fail fast or not retry at all.

Intuition. A busy shop has one counter and a line. If every person who has waited two minutes leaves, walks back in, and goes to the front, the line is no shorter, and the people who would have been served are now behind a crowd of repeat visits. A retry storm is that crowd. Load shedding is a sign on the door that says "we are full, please come back later," before anyone stands in a line that cannot finish in time.

4. Why It Cascades

The deadly loop is:

dependency slows
    -> queue delay grows
        -> more callers hit their timeout
            -> more retries arrive
                -> workers are busy with abandoned work and retries
                    -> queue delay grows again

Once queue delay plus service time is larger than the client timeout, almost every started request is abandoned. The workers are busy, the success rate is near zero, and from the outside it looks like "we need more capacity." Adding clients or replicas that all retry with the same policy feeds the loop.

This is why the lab below can show a capacity of 333 requests per second and a success rate far below 333 / 400. The missing requests are not "unlucky." They are work that could not finish inside the timeout, plus work that was done for a caller who had already left.

5. The Lab: A Slowdown at t = 2 s

We simulated 10 seconds of traffic on a Linux machine. Arrivals are a Poisson process at 400 requests per second (3,875 users in 10 seconds). There are 50 workers. Service time is 50 ms, then at t = 2 s it steps to 150 ms and stays there. The client timeout is 200 ms. The first two seconds are healthy; the last eight seconds are the incident.

Expected, if nothing else goes wrong after the slowdown: about 800 successful requests in the first two seconds, then about 333 per second, so around 3,460 successes (about 89%). That is the ceiling the best policy can hope for, because 400 does not fit into 333. The rest must be shed or they will fail anyway.

What retries did do is stretch the queue from 96 to about 360, and send on the order of nine thousand extra attempts. Backoff and jitter, by themselves, could not fix a queue that had already grown past the timeout.

The fix that actually moved the number: cap the queue

If a request will not finish inside the 200 ms timeout, it is kinder (and cheaper) to refuse it at the door. The door is a maximum queue length. A rough budget:

timeout 200 ms, service 150 ms
so a request can wait at most about 50 ms in the queue
50 workers, 150 ms each: a queue of 10 is about

30 + 150 = 180 ms, which still fits in 200 ms

A cap of 10, with no retries, reached 87.8% success (3,404 of 3,875). That is essentially the ceiling we computed above. Timeouts dropped to zero: every request we accepted finished in time, and the rest were refused quickly. A cap of 20 looked conservative and still let the timeout catch running work, so success fell back to 55.5% and abandoned work came back (1,270 timed-out attempts that a worker still had to finish).

Retries can make a weak cap worse

With the too-loose cap of 20, we added a single retry with exponential backoff and jitter.

PolicySuccessRetriesAbandoned
Cap 20, no retries55.5%01,270
Cap 20, 1 retry, exp. backoff + jitter35.6%1,4852,092

Success dropped from 55.5% to 35.6%. The retries filled the small remaining queue with repeat attempts, crowded out new users, and created more abandoned work. Retries are not "safe as long as you have a cap." The cap has to be tight enough that accepted work finishes, and the retry policy has to respect that cap (a retry budget helps; a retry that goes back into an already-full queue does not).

With the tight cap of 5, adding retries changed nothing: every accepted request already succeeded, so no retry was ever started, and success stayed at 87.0%. That is the boring, healthy outcome you want.

The headline. When the dependency slowed, unbounded queues plus retries left us at about 24% success. Capping the queue so that wait plus service stayed under the timeout lifted success to about 88%. Immediate retries without that cap used 8,805 extra attempts and did not help. Retries on a sloppy cap made success worse (55.5% down to 35.6%).

6. When the Timeout Is Shorter Than the Work

We ran the same incident with a harsher slowdown: service time 300 ms, timeout still 200 ms. Now even a request that gets a worker immediately cannot finish in time.

PolicySuccessRetriesMax queue
No retries19.4% (753, almost all in the first 2 s)099
3 immediate retries19.4%9,366358
3 exp. backoffs + jitter19.4%9,366364

9,366 retries, and not one extra user succeeded. The timeout was impossible. Raising the timeout to 1 second, without shedding, only moved success to 25.9% (1,003), because capacity is then 50 × 1000/300 ≈ 167 requests per second, and the queue still grew past the new timeout. The same 1-second timeout plus a cap of 10 reached 54.5% (2,113), with zero timeouts and zero abandoned work: 1762 requests were shed on purpose, and every accepted request finished.

If you remember only one check from this page, remember this: if timeout < service time + honest queue delay, retries cannot work. You must change the timeout, shed load, or make the work faster. Retrying a 300 ms call with a 200 ms timeout is a guaranteed failure with extra traffic.

7. The Thundering Herd

A related pattern: a dependency is down for a few seconds, then comes back, and every waiting client retries at once. We sent 2,000 retries at 50 workers that each need 50 ms (so 20 requests per worker per second, and 2,000 requests need 2 seconds of full capacity no matter what).

Spread over 200 ms1,8001,755 ms2,004 ms

Jitter did not shrink the total work: the last request still finished at about 2 seconds, as the capacity math requires. It cut the peak queue and the worst waits roughly in half when the retries were spread over one second. Jitter is how you avoid a second, self-inflicted spike. A retry budget is how you avoid 2,000 retries you cannot take. You usually want both.

8. The Fixes, in Order

  1. Make sure the timeout can succeed. Timeout must be larger than typical service time plus a small queue. If the dependency needs 150 ms, a 200 ms timeout only has 50 ms of slack.
  2. Shed load when the queue would blow that budget. A short queue and a fast failure (HTTP 503, with a Retry-After header if you can) is better than a long queue of doomed requests. In the lab, this is what moved success from 24% to 88%.
  3. Retry only when it can help: transient errors (connection reset, 503, 429), not 4xx validation errors, and not when the timeout is already shorter than the work. Prefer retrying on a safe, idempotent operation, with an idempotency key for anything that charges, writes, or sends a message.
  4. Cap retries. One retry is often enough. Three immediate retries is a common default and a common outage cause.
  5. Backoff with jitter so retries do not synchronize. Full jitter (wait a random time between 0 and the current cap) is a simple, good default.
  6. Give the system a retry budget (for example, retries may be at most 10% of current traffic, or at most N per second). When the budget is spent, fail fast.
  7. Use a circuit breaker on a clearly sick dependency, so you stop calling it for a short interval and give it room to recover.
  8. Retry in one layer of the stack, not in the app and the mesh and the client SDK at once.
  9. Cancel abandoned work when you can (a cancellation token, a context, a server that notices the client hung up) so a worker is not stuck finishing a reply nobody will read.

More replicas help only if they add real capacity on the bottleneck. If the payment service is the slow thing, doubling your own API pods doubles the number of clients that can retry into that same bottleneck.

9. What to Look at During the Incident

  • Compare offered load to user load. If the server sees 1,600 requests per second and you only have 400 users per second, the extra 1,200 are retries (or a bug). A label or header such as X-Retry-Attempt: 2 makes this visible.
  • Timeout rate vs error rate vs latency. A jump in timeouts together with a jump in latency is this scenario. A jump in 500s with low latency is a different bug.
  • Queue length and worker utilization. Workers at 100% plus a growing queue plus timeouts means you are doing abandoned work. Workers idle plus timeouts means you are stuck on something else (locks, DNS, a connection pool). The slow API scenario and the lock-wait scenario cover those paths.
  • The dependency's view. If its incoming rate is several times yours, you (or a layer in front of you) are amplifying.

A short-term mitigation during the fire: turn retries down or off, shed at the edge, and give the dependency a quieter minute. Then fix the policy so the next slowdown does not light the same fire. After the incident, write down the amplification math with the real numbers from your metrics, the way this page does with the lab.

10. Common Pitfalls

  • Defaulting to three immediate retries on every HTTP client, including the ones that already sit behind a mesh that retries.
  • A timeout shorter than the work you just rolled out (a new endpoint takes 300 ms, the client still waits 200 ms).
  • Retrying non-idempotent POSTs without an idempotency key. You may fix the error rate and double-charge a card. See also 0-RTT replay on the QUIC page.
  • Unbounded queues, which turn a small overflow into a timeout collapse.
  • A queue cap that still lets wait + service exceed the timeout (cap 20 in the lab looked safe and was not).
  • Adding replicas of the caller when the bottleneck is the callee.
  • No retry marking in metrics, so a storm looks like "real demand went up 4×."
  • Jitter without a budget. Jitter spreads a spike. It does not reduce work.

11. Practice Problems

Problem 1: the amplification

User traffic is 200 requests per second. Each request may be tried once, then retried three more times, all of them sent. What offered load can the dependency see? If the dependency's capacity is 250 requests per second, can retries get you out of an overflow on their own?

Answer: Up to 200 × 4 = 800 req/s. No. 800 is farther over 250 than 200 was. Retries make an overflow worse unless most attempts succeed the first time (in which case you barely retry).

Problem 2: pick a cap

You have 50 workers, service time 150 ms, client timeout 200 ms. What is a safe maximum queue length, roughly, and what happened in the lab at 10 vs 20?

Answer: Slack is 50 ms. A queue of about 50 workers × 50 ms / 150 ms ≈ 16 is already the theoretical ceiling; staying clearly under it is safer. In the lab, a cap of 10 (about 30 ms of wait) reached 87.8% success and zero timeouts. A cap of 20 (about 60 ms of wait) fell to 55.5% because wait plus service crossed the timeout.

Problem 3: is a retry legal?

A handler creates a paid order. The client timed out at 200 ms; the server finished at 250 ms and charged the card. The client retries the same POST with no extra headers. What happens, and what should have been true instead?

Answer: A second paid order may be created (or a second charge). The request should carry an idempotency key so the server returns the original order instead of charging again. It is also a timeout budget bug: the client gave up before the honest work was done, which is how abandoned work begins.

Problem 4: read these two rates

Edge traffic is 400 requests per second. The payment service is receiving 1,500 requests per second from your API, and 70% of those are labeled as retries. Success at the edge is 22%. Name the two most useful switches to flip first, based on this page's lab.

Answer: Shed load so accepted work can finish inside the timeout, and cut retries (or enforce a tight retry budget) so the payment service sees something close to the 400 real users, not 1,500 attempts. Adding API replicas would likely raise 1,500 even further.

12. Cheat Sheet

# questions
#   is timeout > service + a small queue?
#   is offered load several times user load?
#   are retries happening in more than one layer?
#   can this POST be retried safely (idempotency key)?

# a safe client starting point
#   timeout set from measured p99 plus slack
#   at most 1 retry, only on transient errors
#   exponential backoff with full jitter
#   a retry budget (for example 10% of traffic)
#   a circuit breaker on a sick dependency

# a safe server starting point
#   cap the queue so wait + service < client timeout
#   fail fast with 503 (and Retry-After if you can)
#   cancel work when the caller hangs up
#   label attempts so metrics can show amplification

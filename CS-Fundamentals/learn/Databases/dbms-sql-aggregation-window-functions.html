SQL Aggregation, GROUP BY & Window Functions

Most questions people ask of data are summaries. "How much did each city sell?" "Who is our top customer?" "What was the running total by day?" "What was each customer's biggest order?" This page answers all of them on one tiny table you can check by hand, then shows how the database computes them and why one way of writing the same question can be 2,000 times slower than another. It builds on SQL Joins and Indexing & Query Plans.

1. The Idea: Many Rows In, Fewer Rows Out

A table of orders may have millions of rows. A manager does not want to read them. They want a few numbers. SQL has two tools for that:

GROUP BY (aggregation)                     window function
many rows  ->  one row per group           many rows  ->  the SAME rows,
                                                         each with an extra
 Pune  300 \                                             column computed
 Pune  200  \                                            from its group
 Pune  700   >  Pune  2300
 Pune  400  /                               Pune 300 | Pune total 2300
 Pune  700 /                                Pune 200 | Pune total 2300
                                            Pune 700 | Pune total 2300
 Delhi 500 \                                ...
 Delhi 100  >  Delhi  600
 Delhi NULL/

GROUP BY squashes each group into one row. A window function keeps every row and adds a value computed over related rows. Most real reports need one or the other, and many need both.

2. Words You Need

  • Aggregate function. A function that takes many values and returns one: COUNT, SUM, AVG, MIN, MAX.
  • Group. A set of rows that share the same value in the GROUP BY columns.
  • NULL. SQL's "unknown" or "missing" value. It is not zero and not an empty string.
  • Window. The set of rows a window function looks at for the current row.
  • Partition. A window function's version of a group: PARTITION BY city means "look only at rows with the same city". Unlike GROUP BY, rows are not squashed.
  • Frame. A sliding part of the partition, like "from the first row up to this one" (for running totals) or "the 2 rows before this one and this one" (for moving averages).
  • Correlated subquery. A query inside a query that uses a value from the outer row, so it runs again for every outer row.

4. Aggregate Functions and NULL

SELECT COUNT(*), COUNT(amount), COUNT(coupon), SUM(amount), AVG(amount)
FROM orders;
COUNT(*)  COUNT(amount)  COUNT(coupon)  SUM(amount)  AVG(amount)
       8              7              3         2900     414.2857

Read it slowly:

  • COUNT(*) counts rows: 8.
  • COUNT(amount) counts non-NULL values in that column: 7, because order 6 is NULL.
  • COUNT(coupon): only 3 orders used a coupon.
  • SUM skips NULLs: 300 + 500 + 200 + 700 + 100 + 400 + 700 = 2,900.
  • AVG also skips NULLs: 2,900 / 7 = 414.29, not 2,900 / 8 = 362.5.

Rule. Every aggregate except COUNT(*) ignores NULLs. If a missing amount should count as 0, say so: AVG(COALESCE(amount, 0)) gives 362.5. Neither answer is "right"; they answer different questions. Decide which one the report needs.

One more edge case: SUM over zero rows (or only NULLs) returns NULL, not 0. COUNT over zero rows returns 0. Wrap sums in COALESCE(SUM(x), 0) when a report must show 0.

5. GROUP BY, Drawn as Buckets

SELECT city, COUNT(*) AS orders, SUM(amount) AS total
FROM orders
GROUP BY city;

Picture the database dropping each row into a bucket labeled with its city, then running the aggregates once per bucket:

bucket "Delhi"           bucket "Pune"
  id 2   500               id 1   300
  id 5   100               id 3   200
  id 6   NULL              id 4   700
                           id 7   400
                           id 8   700
COUNT(*)  = 3            COUNT(*)  = 5
SUM       = 600          SUM       = 2300
city   orders  total
Delhi       3    600
Pune        5   2300

The one rule of GROUP BY

After grouping, each output row stands for a whole bucket. So every column in SELECT must be either in the GROUP BY (the same for the whole bucket) or inside an aggregate (one value computed from the bucket).

-- Wrong: which customer should the "Pune" row show? asha or chen?
SELECT city, customer, SUM(amount) FROM orders GROUP BY city;

PostgreSQL rejects this with "column orders.customer must appear in the GROUP BY clause or be used in an aggregate function". SQLite and old MySQL settings quietly pick some row's value, which is worse: you get a random-looking answer with no error.

NULL is a group too

SELECT coupon, COUNT(*) FROM orders GROUP BY coupon;
coupon  COUNT(*)
NULL           5
BIG50          1
NEW10          2

In GROUP BY, all NULLs go into one bucket. (This is different from joins, where NULL never equals NULL; see NULL keys do not match.)

6. WHERE vs HAVING, and the Real Order of a Query

"Which customers spent more than 600 in total?"

SELECT customer, SUM(amount) AS total
FROM orders
GROUP BY customer
HAVING SUM(amount) > 600
ORDER BY total DESC;
customer  total
chen       1400
asha        900

Why HAVING and not WHERE? Because SQL does not run in the order you write it. It runs in this order:

1. FROM / JOIN      which rows exist
2. WHERE            keep or drop single ROWS       (no totals exist yet)
3. GROUP BY         drop rows into buckets
4. HAVING           keep or drop whole GROUPS      (totals exist now)
5. SELECT           compute output columns, including window functions
6. DISTINCT
7. ORDER BY         sort (can use SELECT aliases like "total")
8. LIMIT / OFFSET

WHERE SUM(amount) > 600 fails because at step 2 there are no sums yet. Use this order to answer most "why does this not work?" questions:

  • You cannot use a SELECT alias in WHERE (aliases are made at step 5).
  • You can use it in ORDER BY (step 7).
  • You cannot filter on a window function in WHERE (windows are computed at step 5). Wrap the query and filter outside; section 10 shows how.

Speed tip: filter rows in WHERE whenever you can. WHERE city = 'Pune' throws rows away before grouping. HAVING city = 'Pune' gives the same answer but groups everything first.

7. Window Functions: Keep Every Row

"For each order, show the customer's total, and what percent of it this order is." With GROUP BY you would lose the individual orders. A window function keeps them:

SELECT id, customer, amount,
       SUM(amount) OVER (PARTITION BY customer) AS cust_total,
       ROUND(100.0 * amount / SUM(amount) OVER (PARTITION BY customer), 1) AS pct
FROM orders
WHERE amount IS NOT NULL
ORDER BY customer, id;
id  customer  amount  cust_total   pct
 1  asha         300         900  33.3
 3  asha         200         900  22.2
 7  asha         400         900  44.4
 2  ben          500         600  83.3
 5  ben          100         600  16.7
 4  chen         700        1400  50.0
 8  chen         700        1400  50.0

How to read SUM(amount) OVER (PARTITION BY customer): "for this row, sum amount over all rows with the same customer". Seven rows went in, seven rows came out. Asha's three orders each see her total of 900, and 300 / 900 = 33.3%.

The parts of OVER (...):

func(...) OVER ( PARTITION BY ...   which rows are "related" (like a group)
                 ORDER BY ...       order inside the partition
                 ROWS BETWEEN ... ) which slice of the partition (the frame)

All three parts are optional. OVER () with nothing inside means "all rows": SUM(amount) OVER () puts the grand total 2,900 on every row.

8. Ranking: ROW_NUMBER, RANK, DENSE_RANK

"Rank orders by size within each city." Pune has a tie: two orders of 700.

SELECT id, city, amount,
       ROW_NUMBER() OVER w AS rn,
       RANK()       OVER w AS rnk,
       DENSE_RANK() OVER w AS drnk
FROM orders
WHERE amount IS NOT NULL
WINDOW w AS (PARTITION BY city ORDER BY amount DESC)
ORDER BY city, rn;
id  city   amount  rn  rnk  drnk
 2  Delhi     500   1    1     1
 5  Delhi     100   2    2     2
 4  Pune      700   1    1     1
 8  Pune      700   2    1     1     <- tie
 7  Pune      400   3    3     2
 1  Pune      300   4    4     3
 3  Pune      200   5    5     4
FunctionOn a tieNext number after a 2-way tie at 1Use it for
ROW_NUMBERBreaks it (which one wins is arbitrary unless you add a tiebreaker column)2"Exactly one row per group", de-duplication
RANKSame rank, then skips3 (like a sports table: 1, 1, 3)Competitions, "position"
DENSE_RANKSame rank, no gaps2"Top 3 distinct amounts"

The WINDOW w AS (...) clause just names a window so you do not repeat it. It works in PostgreSQL, MySQL 8 and SQLite.

9. Running Totals, LAG, and Frames

"Daily sales, a running total, and yesterday's number next to today's":

SELECT day,
       SUM(amount)                            AS daily,
       SUM(SUM(amount)) OVER (ORDER BY day)   AS running,
       LAG(SUM(amount)) OVER (ORDER BY day)   AS prev_day
FROM orders
GROUP BY day
ORDER BY day;
day         daily  running  prev_day
2026-11-01    800      800      NULL
2026-11-02    900     1700       800
2026-11-03    100     1800       900
2026-11-04   1100     2900       100

Three ideas in one query:

  • SUM(SUM(amount)) looks odd but follows the query order. The inner SUM is the GROUP BY aggregate (one value per day). The outer SUM ... OVER is a window over those daily rows. Grouping happens first, then windows run over the grouped rows.
  • ORDER BY day inside OVER turns a total into a running total: each row sums from the first day up to itself.
  • LAG(x) reads x from the previous row in the window. LEAD(x) reads the next row. The first row has no previous row, so LAG gives NULL. Day-over-day change is daily - LAG(daily).

Note 2026-11-03: the daily sum is 100, because order 6's NULL is skipped.

9.1 Moving averages with ROWS

SELECT id, amount,
       AVG(amount) OVER (ORDER BY id ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS avg3
FROM orders WHERE amount IS NOT NULL;
id  amount   avg3
 1     300  300.0        only 1 row so far
 2     500  400.0        (300+500)/2
 3     200  333.3        (300+500+200)/3
 4     700  466.7        (500+200+700)/3
 5     100  333.3        (200+700+100)/3
 7     400  400.0        (700+100+400)/3
 8     700  400.0        (100+400+700)/3

ROWS BETWEEN 2 PRECEDING AND CURRENT ROW means "this row and the 2 before it". The window slides one row at a time. Near the start there are fewer rows, so the first two averages use 1 and 2 rows.

9.2 The ROWS vs RANGE trap

When you write ORDER BY in a window and no frame, SQL uses a default frame: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. RANGE means "all rows whose ORDER BY value is up to mine, including ties". On raw orders (not grouped by day), two orders share each day:

SELECT id, day, amount,
       SUM(amount) OVER (ORDER BY day)                      AS range_default,
       SUM(amount) OVER (ORDER BY day ROWS UNBOUNDED PRECEDING) AS rows_frame
FROM orders WHERE amount IS NOT NULL ORDER BY id;
id  day         amount  range_default  rows_frame
 1  2026-11-01     300            800         300
 2  2026-11-01     500            800         800
 3  2026-11-02     200           1700        1000
 4  2026-11-02     700           1700        1700
 5  2026-11-03     100           1800        1800
 7  2026-11-04     400           2900        2200
 8  2026-11-04     700           2900        2900

With the default, both orders on 11-01 show 800, because ties are included together. With ROWS, the total grows one row at a time. Neither is a bug, but many "my running total is wrong" questions are this. If you want a strict row-by-row running total, write ROWS UNBOUNDED PRECEDING and give a unique tiebreaker: ORDER BY day, id.

10. Top-N per Group

"Each customer's single biggest order." This is one of the most common real queries (latest status per order, newest version per document, best score per player). Rank inside each group, then keep rank 1:

SELECT *
FROM (
  SELECT customer, id, amount,
         ROW_NUMBER() OVER (PARTITION BY customer
                            ORDER BY amount DESC, id) AS rn
  FROM orders
  WHERE amount IS NOT NULL
) ranked
WHERE rn = 1;
customer  id  amount  rn
asha       7     400   1
ben        2     500   1
chen       4     700   1

Step by step:

  1. The inner query numbers each customer's orders from biggest to smallest.
  2. Chen has a tie (orders 4 and 8, both 700). The extra id in ORDER BY breaks it the same way every time, so order 4 always wins. Without a tiebreaker, the winner could change between runs.
  3. The outer query keeps rn = 1. The filter must be outside, because window functions do not exist yet at the WHERE step (section 6).

For "top 3 per group" change it to rn <= 3. Use RANK instead if ties should all be kept. PostgreSQL also has a shortcut for "one row per group": SELECT DISTINCT ON (customer) ... ORDER BY customer, amount DESC.

11. How the Engine Computes It

A database has two main ways to do GROUP BY. They are the same two ideas you saw for joins.

Hash aggregation

read each row once:
  key = city
  look up key in a hash table; if missing, add {count:0, sum:0}
  update count and sum

rows:  (Pune,300) (Delhi,500) (Pune,200) (Pune,700) ...
table: Pune  -> {count 1, sum 300}
       Delhi -> {count 1, sum 500}
       Pune  -> {count 2, sum 500}  ...

One pass over the data, memory proportional to the number of groups (not rows). Great when there are few groups. If there are too many groups to fit in memory, the engine spills to disk, which is slower. In PostgreSQL the plan node is called HashAggregate, and its memory budget is work_mem.

Sort (group) aggregation

sort rows by city:  Delhi 500, Delhi 100, Delhi NULL, Pune 300, Pune 200, ...
walk the sorted list; when the city changes, output the finished group

Sorting costs more (about n log n), but if the rows already come out of an index in order, there is no sort at all, and the engine can stream groups out one by one. PostgreSQL calls this GroupAggregate. In our SQLite lab, adding an index on (customer, amount) changed the plan from USE TEMP B-TREE FOR GROUP BY (sort into a temporary structure) to SCAN big USING COVERING INDEX big_cust (read the index in order, no sort).

Window functions

A window function needs rows grouped by the PARTITION BY columns and ordered by the window's ORDER BY. So the engine sorts by (partition columns, order columns), then walks the sorted rows once, keeping a small running state (a counter for ROW_NUMBER, a running sum, the previous row for LAG). PostgreSQL shows this as a Sort under a WindowAgg node. An index that already matches that order removes the sort.

12. Lab: 77 Seconds vs 34 Milliseconds

We made a table with 50,000 random orders for 2,000 customers and asked one question three ways: "how many orders are their customer's biggest order?" (that is, top-1 per group, counting ties).

-- A: correlated subquery
SELECT COUNT(*) FROM big b
WHERE amount = (SELECT MAX(amount) FROM big b2 WHERE b2.customer = b.customer);

-- B: window function
SELECT COUNT(*) FROM (
  SELECT amount, MAX(amount) OVER (PARTITION BY customer) AS m FROM big
) WHERE amount = m;

-- C: GROUP BY, then join back
SELECT COUNT(*) FROM big b
JOIN (SELECT customer, MAX(amount) AS m FROM big GROUP BY customer) g
  ON g.customer = b.customer AND b.amount = g.m;
QueryNo indexWith index on (customer, amount)Rows
A: correlated subquery77,484 ms17.6 ms2,023
B: window function34 ms15.2 ms2,023
C: GROUP BY + join32 ms3.6 ms2,023

All three return the same 2,023 rows (a little more than 2,000 customers' worth, because of ties). The times are wildly different:

  • A without an index runs the inner query once for each of the 50,000 outer rows, and each run scans all 50,000 rows: 50,000 × 50,000 = 2.5 billion row visits. That is 77 seconds, about 2,300 times slower than B.
  • B and C read the table a small, fixed number of times (one sort or one hash pass), so they finish in tens of milliseconds even with no index.
  • With the index, A becomes 50,000 quick index lookups, and everything is fast. C wins because the index already holds rows sorted by customer and amount, so the MAX per customer is just "read the last entry".

The headline. A correlated subquery hides a loop. With a supporting index it can be fine. Without one, it is a nested loop over the whole table, and it gets 4 times slower every time the table doubles. Window functions and GROUP BY read the data once. When a report query suddenly takes minutes, look for a subquery that mentions the outer table.

13. Real-World Walkthroughs

13.1 Daily active users

Table events(user_id, ts). "How many different users were active each day?"

SELECT DATE(ts) AS day, COUNT(DISTINCT user_id) AS dau
FROM events
GROUP BY DATE(ts)
ORDER BY day;

COUNT(DISTINCT x) counts unique values. COUNT(user_id) would count events, so one busy user with 500 clicks would count as 500 "users".

13.2 Remove duplicate rows, keep the newest

A sync job inserted some customers twice. Keep the newest row per email:

DELETE FROM customers
WHERE id IN (
  SELECT id FROM (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY updated_at DESC, id DESC) AS rn
    FROM customers
  ) t
  WHERE rn > 1
);

Run the inner SELECT first and look at the rows it would delete. Then run the DELETE inside a transaction, check the count, and commit. Then add a unique index on email so it cannot happen again (see schema design).

13.3 Percent change week over week

WITH weekly AS (
  SELECT DATE_TRUNC('week', ts) AS week, SUM(amount) AS revenue   -- PostgreSQL
  FROM payments GROUP BY 1
)
SELECT week, revenue,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY week))
             / NULLIF(LAG(revenue) OVER (ORDER BY week), 0), 1) AS pct_change
FROM weekly ORDER BY week;

WITH ... AS (a CTE, common table expression) names a sub-result so the main query reads cleanly. NULLIF(x, 0) turns 0 into NULL, so a week with zero revenue gives NULL instead of a divide-by-zero error.

13.4 The fan-out trap in a dashboard

A dashboard showed revenue per customer twice as high as finance's number. The query was:

SELECT c.name, SUM(o.amount)
FROM customers c
JOIN orders o   ON o.customer_id = c.id
JOIN tickets t  ON t.customer_id = c.id     -- added later for a "tickets" column
GROUP BY c.name;

A customer with 3 orders and 2 support tickets produces 3 × 2 = 6 joined rows, so each order is summed twice. The fix is to aggregate each table before joining:

SELECT c.name, o.revenue, t.tickets
FROM customers c
LEFT JOIN (SELECT customer_id, SUM(amount) AS revenue FROM orders  GROUP BY customer_id) o ON o.customer_id = c.id
LEFT JOIN (SELECT customer_id, COUNT(*)    AS tickets FROM tickets GROUP BY customer_id) t ON t.customer_id = c.id;

The joins page explains why many-to-many joins multiply rows.

14. Common Pitfalls

  • Forgetting that AVG skips NULLs. Decide whether missing means "unknown" (skip) or "zero" (COALESCE).
  • Integer division. In PostgreSQL, SUM(int_col) / COUNT(*) is integer division: 7 / 2 = 3. Multiply by 100.0 or cast to numeric first.
  • Selecting a column that is not grouped. Some databases allow it and return an arbitrary value.
  • Filtering a window function in WHERE. It does not exist yet at that step. Wrap the query.
  • ROW_NUMBER without a tiebreaker. Results can change between runs. Add a unique column to the window's ORDER BY.
  • The default RANGE frame. Ties are included together in running totals. Use ROWS for row-by-row.
  • Joining before aggregating. Two one-to-many joins multiply rows and inflate sums.
  • COUNT(col) when you meant COUNT(*). They differ whenever the column has NULLs.
  • A correlated subquery with no index. It is a hidden nested loop: 77 seconds in our lab.

15. Practice Problems

Use the 8-row orders table from section 3 for problems 1 to 4.

Problem 1

What does SELECT city, AVG(amount), AVG(COALESCE(amount,0)) FROM orders GROUP BY city return for Delhi?

Solution

Delhi has 500, 100 and NULL. AVG(amount) = (500 + 100) / 2 = 300. AVG(COALESCE(amount,0)) = (500 + 100 + 0) / 3 = 200.

Problem 2

Write a query for "cities with at least 4 orders that have a known amount".

Solution 
SELECT city, COUNT(amount) AS n
FROM orders
GROUP BY city
HAVING COUNT(amount) >= 4;

Only Pune (5). Delhi has 2 known amounts. COUNT(amount) skips order 6; COUNT(*) would have counted it.

Problem 3

For each order with a known amount, show amount - AVG(amount) over the same city. What is the value for order 1?

Solution 
SELECT id, amount - AVG(amount) OVER (PARTITION BY city) AS diff
FROM orders WHERE amount IS NOT NULL;

Pune's average is 2,300 / 5 = 460. Order 1: 300 - 460 = -160.

Problem 4

Give ROW_NUMBER, RANK and DENSE_RANK for the amounts 900, 700, 700, 700, 500 sorted from high to low.

Solution 
amount  ROW_NUMBER  RANK  DENSE_RANK
   900           1     1           1
   700           2     2           2
   700           3     2           2
   700           4     2           2
   500           5     5           3

Problem 5

Table logins(user_id, ts). Find users whose time between two logins in a row was ever more than 30 days. Use LAG.

Solution 
SELECT DISTINCT user_id
FROM (
  SELECT user_id, ts,
         LAG(ts) OVER (PARTITION BY user_id ORDER BY ts) AS prev_ts
  FROM logins
) t
WHERE ts - prev_ts > INTERVAL '30 days';   -- PostgreSQL

Partition by user so LAG never reads another user's login. The first login of each user has prev_ts NULL, and the comparison with NULL is not true, so it is dropped.

Problem 6

A report runs WHERE price > (SELECT AVG(price) FROM products p2 WHERE p2.category = p.category) on 200,000 products and takes minutes. Rewrite it.

Solution 
SELECT * FROM (
  SELECT p.*, AVG(price) OVER (PARTITION BY category) AS cat_avg
  FROM products p
) t
WHERE price > cat_avg;

One sort by category and one pass, instead of re-running an average for every product. An index on (category, price) would also make the original fast, but the window version is fast with or without it.

16. Cheat Sheet

# query order
FROM -> WHERE -> GROUP BY -> HAVING -> SELECT (windows) -> DISTINCT -> ORDER BY -> LIMIT

# NULL rules
COUNT(*) counts rows; every other aggregate skips NULL
SUM of no rows = NULL  ->  COALESCE(SUM(x), 0)
GROUP BY puts all NULLs in one group

# GROUP BY rule
every SELECT column is grouped or aggregated

# window shapes
SUM(x) OVER (PARTITION BY g)                       group total on every row
SUM(x) OVER (ORDER BY t ROWS UNBOUNDED PRECEDING)  running total, row by row
AVG(x) OVER (ORDER BY t ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)  7-row moving avg
LAG(x) / LEAD(x) OVER (PARTITION BY g ORDER BY t)  previous / next row

# ranking with ties 700,700,500
ROW_NUMBER 1,2,3   RANK 1,1,3   DENSE_RANK 1,1,2

# top-N per group
SELECT * FROM (SELECT ..., ROW_NUMBER() OVER (PARTITION BY g ORDER BY x DESC, id) rn
               FROM t) s WHERE rn <= N

# engine
HashAggregate   one pass, memory per group (work_mem)
GroupAggregate  needs sorted input (or a matching index)
WindowAgg       sort by (partition, order), then one pass

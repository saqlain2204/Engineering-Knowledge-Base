Transactions, Isolation Levels & MVCC

Why two people withdrawing money at the same time can break a bank, and the exact tools databases use to stop it. Every anomaly is shown as a step-by-step timeline you can reproduce in two terminals.

1. Why Transactions Exist

Moving 100 from Alice to Bob takes two writes:

UPDATE accounts SET balance = balance - 100 WHERE owner = 'alice';
UPDATE accounts SET balance = balance + 100 WHERE owner = 'bob';

Two things can go wrong:

  1. Failure in the middle. The server crashes after the first line. Alice lost 100, Bob got nothing. Money vanished.
  2. Interference. While this runs, another request reads both balances and sees the "in between" state, or changes Alice's balance at the same moment.

A transaction groups several operations into one logical unit. Either all of them happen or none do, and concurrent transactions are kept from stepping on each other.

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE owner = 'alice';
UPDATE accounts SET balance = balance + 100 WHERE owner = 'bob';
COMMIT;      -- make it permanent
-- or ROLLBACK;  to undo everything since BEGIN

Note: the "C" is partly your job. The database cannot know that "total money must stay constant" unless you encode it. A CHECK (balance >= 0) constraint is something it can enforce for you.

3. Atomicity and Durability: the Write-Ahead Log

Data files are big and written in pages (8 KiB in PostgreSQL, 16 KiB in InnoDB). Writing every changed page to disk at every commit would be slow and random. Instead, databases use a write-ahead log (WAL), also called a redo log or journal.

The one rule

Before a changed data page is written to disk, the log record describing that change must already be on disk.

Commit, step by step

  1. The transaction changes pages in memory (the buffer pool). They are now "dirty".
  2. Each change also appends a small record to the WAL buffer: "in page 42, slot 3, balance 500 became 400".
  3. On COMMIT, the database appends a commit record and flushes the WAL up to that point with fsync. The log is sequential, so this is fast.
  4. Only now does COMMIT return success to the client.
  5. Dirty data pages are written later, in the background, at a checkpoint.

Crash recovery

After a crash, the database reads the WAL from the last checkpoint and redoes every logged change. Transactions with a commit record are restored (durability). Transactions without one never become visible (atomicity): in PostgreSQL their row versions are simply ignored as "aborted"; in InnoDB they are rolled back using the undo log.

Intuition: the WAL is a chef's order slip. Before cooking anything, the order is written down. If the kitchen catches fire, you rebuild from the slips. Writing a slip is much faster than finishing the dish, so you can promise the customer "your order is safe" early.

The same log also feeds replication (replicas replay the WAL) and change data capture (tools like Debezium read it to stream changes to Kafka).

4. Concurrency Anomalies, One Timeline Each

Start state for all examples: Alice has 500, Bob has 300. T1 and T2 are two transactions running at the same time. Time goes down.

4.1 Dirty read: reading uncommitted data

StepT1T2
1UPDATE ... alice = 400
2SELECT alice sees 400
3ROLLBACK
4Acts on 400, a value that never officially existed

4.2 Non-repeatable read: same row, two different answers

StepT1T2
1SELECT alice = 500
2UPDATE alice = 400; COMMIT
3SELECT alice = 400

Inside one transaction, the same question gave two answers. A report that sums rows while they change will be wrong.

4.3 Phantom read: new rows appear

StepT1T2
1SELECT count(*) WHERE balance > 100 = 2
2INSERT carol, 900; COMMIT
3Same query = 3

No existing row changed. A new row matching the condition appeared, a "phantom".

4.4 Lost update: one write silently overwrites another

Two withdrawals of 100 and 50 from Alice. The application reads, computes in code, then writes the result.

StepT1 (withdraw 100)T2 (withdraw 50)
1SELECT = 500
2SELECT = 500
3UPDATE SET balance = 400
4UPDATE SET balance = 450 (waits for T1's row lock)
5COMMIT
6update proceeds; COMMIT

Final balance 450. It should be 350. T1's withdrawal was lost. This is one of the most common real bugs in web apps, and the default isolation level of PostgreSQL does not prevent it when you compute values in application code.

4.5 Write skew: two valid decisions, one invalid result

Rule: at least one doctor must be on call. Alice and Bob are both on call. Both feel sick at the same time.

StepT1 (Alice)T2 (Bob)
1SELECT count(*) WHERE on_call = 2
2SELECT count(*) WHERE on_call = 2
32 > 1, OK. UPDATE alice SET on_call = false
42 > 1, OK. UPDATE bob SET on_call = false
5COMMITCOMMIT

Nobody is on call. The two transactions wrote different rows, so there was no write conflict and no lock to wait for. Each decision was correct given what it read, but the reads became stale. Only true serializable isolation (or explicit locking) catches this.

5. Isolation Levels

Full isolation costs performance, so SQL lets you choose. The SQL standard defines four levels by which anomalies they allow:

LevelDirty readNon-repeatable readPhantom
Read Uncommittedpossiblepossiblepossible
Read Committedpreventedpossiblepossible
Repeatable Readpreventedpreventedpossible
Serializablepreventedpreventedprevented

Serializable means the result equals some one-at-a-time order of the transactions. It prevents every anomaly above, including lost update and write skew.

What real databases actually do

The standard table is a minimum. Real engines differ, and these details matter in production:

LevelPostgreSQLMySQL InnoDB
DefaultRead CommittedRepeatable Read
Read UncommittedBehaves exactly like Read Committed (no dirty reads ever)Allows dirty reads
Read CommittedEach statement sees a fresh snapshot of committed dataEach consistent read sees a fresh snapshot
Repeatable ReadSnapshot isolation: one snapshot for the whole transaction, so no phantoms either. If you try to update a row someone else changed and committed after your snapshot, you get a serialization error. Write skew is still possible.Plain SELECTs read one snapshot. But UPDATE, DELETE, and locking reads act on the latest committed rows and take next-key locks. Lost updates in read-then-write code are not detected.
SerializableSerializable Snapshot Isolation (SSI): tracks read/write dependencies and aborts a transaction if a cycle could form. No extra blocking.Like Repeatable Read, but plain SELECTs become locking reads (FOR SHARE) when autocommit is off, so conflicts block instead of abort.
Rule for app code: at Repeatable Read or Serializable in PostgreSQL, a transaction can fail with SQLSTATE 40001 (serialization_failure). This is expected, not a bug. Your code must retry the whole transaction. 
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ...
COMMIT;

-- or for the session
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SHOW transaction_isolation;

6. MVCC: How Readers and Writers Stop Blocking Each Other

Old databases used only locks: a writer locks a row, and readers wait. Reports would freeze the checkout page. Multi-Version Concurrency Control (MVCC) keeps several versions of each row. Writers create new versions; readers look at the version that was current for them. Readers never block writers, and writers never block readers. Writers still block other writers of the same row.

How PostgreSQL does it

Every transaction gets a transaction ID (XID). Every row version (a "tuple") carries two hidden fields:

  • xmin: the XID that created this version.
  • xmax: the XID that deleted or replaced it (0 if still live).

An UPDATE does not overwrite. It marks the old version's xmax and inserts a new version with a new xmin.

Alice's row after: XID 100 inserts it, XID 205 updates 500 -> 400

  version   xmin   xmax   balance
  v1        100    205    500       (old, replaced by 205)
  v2        205    0      400       (current)

A snapshot records which transactions had committed when it was taken. The visibility rule, simplified: a version is visible if its creator (xmin) had committed as of my snapshot, and its deleter (xmax) had not.

  • A snapshot taken before XID 205 committed sees v1 (500): v2's creator is not visible yet, and v1's deleter is not visible yet.
  • A snapshot taken after sees v2 (400).

You can see these fields yourself:

SELECT xmin, xmax, * FROM accounts;
SELECT txid_current();     -- or pg_current_xact_id() on PostgreSQL 13+

The cost: dead versions and VACUUM

Old versions that no running transaction can see anymore are "dead tuples". They waste space and slow scans. PostgreSQL's VACUUM (run automatically by autovacuum) reclaims them. A transaction left open for hours keeps an old snapshot alive, so VACUUM cannot clean anything newer than it, and tables bloat.

How InnoDB does it

InnoDB (MySQL) updates rows in place and writes the old values to an undo log. A reader that needs an older version follows the undo chain backwards to rebuild it. A background "purge" thread removes undo records no one needs. Oracle uses a similar undo-based design.

Intuition: MVCC is like a shared document with full version history. Each reader is handed a frozen copy as of the moment they started. Writers keep editing the live copy. The cleanup crew deletes old versions once nobody is looking at them.

7. Locks, Two-Phase Locking, and Deadlocks

Lock modes

  • Shared (S) lock: "I am reading this; do not change it." Many transactions can hold S on the same row.
  • Exclusive (X) lock: "I am changing this." Conflicts with everything else.

In MVCC databases, plain reads take no row locks. Writes take X locks on the rows they change, held until commit. You can ask for locks explicitly:

SELECT * FROM accounts WHERE owner = 'alice' FOR UPDATE;  -- X-style row lock
SELECT * FROM accounts WHERE owner = 'alice' FOR SHARE;   -- S-style row lock
SELECT * FROM jobs WHERE status = 'new'
  ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED;            -- job-queue pattern

Two-Phase Locking (2PL)

Classic serializability via locks: a transaction has a growing phase (it may acquire locks, never release) followed by a shrinking phase (it may release, never acquire). Strict 2PL, used in practice, holds all write locks until commit or abort, so nobody reads uncommitted data. 2PL guarantees serializable schedules, but readers and writers block each other and deadlocks are possible.

Deadlock, step by step

StepT1 (Alice pays Bob)T2 (Bob pays Alice)
1lock Alice's row (update)
2lock Bob's row (update)
3wants Bob's row: waits for T2
4wants Alice's row: waits for T1

A cycle in the "waits-for" graph: T1 → T2 → T1. Neither can ever proceed. PostgreSQL checks for cycles after a lock wait exceeds deadlock_timeout (default 1 second) and aborts one transaction with ERROR: deadlock detected (SQLSTATE 40P01). InnoDB detects deadlocks immediately by default.

Prevention: always lock rows in a consistent order, for example by ascending account ID. Then T2 would also lock Alice first, wait at step 2, and no cycle can form.

-- transfer(from, to): lock both rows in id order first
SELECT id FROM accounts WHERE id IN (:from, :to) ORDER BY id FOR UPDATE;

8. Hands-On Lab: Reproduce It in PostgreSQL

You only need Docker and two terminals. Doing this once teaches more than reading about it ten times. (Every result below was reproduced on PostgreSQL 17.5 while writing this page.)

docker run -d --name pglab -e POSTGRES_PASSWORD=pw postgres:17
docker exec -it pglab psql -U postgres     # run this in TWO terminals: A and B
-- in A, once
CREATE TABLE accounts (id int PRIMARY KEY, owner text, balance int CHECK (balance >= 0));
INSERT INTO accounts VALUES (1, 'alice', 500), (2, 'bob', 300);
CREATE TABLE doctors (name text PRIMARY KEY, on_call boolean);
INSERT INTO doctors VALUES ('alice', true), ('bob', true);

Experiment 1: lost update at Read Committed

Terminal ATerminal B
BEGIN;
SELECT balance FROM accounts WHERE id=1; (500)
BEGIN;
SELECT balance FROM accounts WHERE id=1; (500)
UPDATE accounts SET balance=400 WHERE id=1;
UPDATE accounts SET balance=450 WHERE id=1; (hangs)
COMMIT;(unblocks) COMMIT;

Check: SELECT balance FROM accounts WHERE id=1; gives 450. Lost update reproduced. Reset with UPDATE accounts SET balance=500 WHERE id=1;

Experiment 2: the same thing, fixed by an atomic update

Repeat, but write UPDATE accounts SET balance = balance - 100 WHERE id=1; in A and ... balance - 50 ... in B. When B unblocks, PostgreSQL re-reads the newly committed row (400) and applies - 50 to it. Final: 350. Correct.

Experiment 3: Repeatable Read catches the conflict

Repeat Experiment 1 but start both with BEGIN ISOLATION LEVEL REPEATABLE READ;. When A commits, B's update fails:

ERROR:  could not serialize access due to concurrent update

B must ROLLBACK and retry from the beginning, now reading 400.

Experiment 4: write skew passes Repeatable Read, fails Serializable

  1. Both terminals: BEGIN ISOLATION LEVEL REPEATABLE READ; and SELECT count(*) FROM doctors WHERE on_call; (2).
  2. A: UPDATE doctors SET on_call=false WHERE name='alice'; B: same for 'bob'.
  3. Both COMMIT;. Both succeed. Zero doctors on call.
  4. Reset both to true and repeat with ISOLATION LEVEL SERIALIZABLE. Now the second COMMIT fails with ERROR: could not serialize access due to read/write dependencies among transactions. Retry it, and it will see only 1 doctor on call and refuse.

9. Scenario: The Double-Booked Seat

Situation. A ticketing site sells concert seats. The booking code does:

seat = db.query("SELECT status FROM seats WHERE id = 42")
if seat.status == "free":
    db.execute("UPDATE seats SET status='sold', buyer=%s WHERE id = 42", user)
    charge_card(user)

On a busy launch, support tickets arrive: two people paid for seat 42. The logs show both requests within the same 20 ms.

Diagnosis

This is check-then-act across two statements, the lost-update pattern. Both requests read "free" before either wrote "sold". At Read Committed, nothing stops it.

Four fixes, from simplest

  1. Make the check part of the write (conditional update). Then check how many rows changed. 
    UPDATE seats SET status='sold', buyer=$1
WHERE id = 42 AND status = 'free';
-- 1 row updated: you got it. 0 rows: someone else did.
    The second request waits on the row lock, then re-checks status = 'free' on the new version, finds it false, and updates 0 rows.
  2. Lock the row while deciding: SELECT ... FOR UPDATE inside a transaction. The second request blocks until the first commits, then sees "sold".
  3. Let a constraint enforce it. A table bookings(seat_id PRIMARY KEY, ...): a second INSERT for the same seat fails with a unique violation. Constraints are the most robust guard, because they hold no matter which code path writes.
  4. Run at SERIALIZABLE and retry on 40001. The most general fix, and it also covers write-skew cases that span many rows.

Also: charge the card after the booking commits (or use a payment hold), never inside a transaction that might roll back.

10. Common Pitfalls

  • Assuming the default level is serializable. PostgreSQL, SQL Server, and Oracle default to Read Committed; MySQL to Repeatable Read. None defaults to Serializable.
  • No retry logic. Using Repeatable Read or Serializable without retrying on serialization failures turns safe aborts into user-facing errors.
  • Long or idle transactions. They hold locks and old snapshots, block VACUUM, and cause bloat. Watch for idle in transaction in pg_stat_activity and set idle_in_transaction_session_timeout.
  • Slow external calls inside a transaction. An HTTP call to a payment API while holding row locks makes every other request wait.
  • Inconsistent lock order. The main cause of deadlocks.
  • Trusting ORMs blindly. "Load object, change field, save" is read-then-write. Use atomic updates, select_for_update, or optimistic locking with a version column (UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?).

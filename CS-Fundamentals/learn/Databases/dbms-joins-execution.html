SQL Joins & How the Database Executes Them

Real data is almost never in one table. Customers live in one place, orders in another, items in a third. A join is how the database stitches those tables back together, row by row, using a shared key. This page starts with four people and three teams, then shows the three algorithms a database actually uses, with times we measured. It builds on Normalization & Schema Design (why the data is split) and Indexing, B+ Trees & Query Plans (how a single table is searched).

1. Why Data Lives in More Than One Table

Suppose you store every order like this:

order_id  customer_name  customer_city  product  amount
1         Ada            Pune           mug      400
2         Ada            Pune           book     250
3         Dev            Delhi          mug      400

Ada's city is stored twice. If she moves, you must update every row. Miss one, and the same person lives in two cities. That is the update anomaly that normalization is designed to stop.

The usual fix is to split the data and point at it:

customers                     orders
id  name  city                id  customer_id  product  amount
1   Ada   Pune                1   1            mug      400
2   Dev   Delhi               2   1            book     250
                              3   2            mug      400

Ada's city now lives in one place. To print "who bought what, and from which city?" the database must join the two tables on orders.customer_id = customers.id.

Intuition. A join is the reverse of a careful split. You split so each fact is stored once. You join so a question that needs two facts can still be answered in one result.

2. Words You Need

  • Join key. The column (or columns) that say "these two rows belong together." Here, customer_id and id.
  • Inner join. Keep a result row only when both sides have a match.
  • Left (outer) join. Keep every row from the left table. If the right side has no match, fill those columns with NULL (a marker that means "unknown / not present").
  • Right join. The mirror of a left join. Most people write a left join and swap the table order instead.
  • Full (outer) join. Keep rows from either side, with NULLs where the other side is missing.
  • Cross join. Every row of A paired with every row of B. Row count is |A| × |B|.
  • Cardinality. How many rows a step produces. A join can shrink a result, or blow it up.
  • Selectivity. How picky a condition is. "customer_id = 42" is selective. "amount > 0" often is not.
  • Nested loop, hash, and merge join. The three algorithms the engine uses to actually find matching pairs. The SQL you write does not name them. The planner picks one. You read the choice in EXPLAIN.
  • Build side and probe side. In a hash join, the engine builds a hash table from one input (usually the smaller one) and probes it with the other.

3. Four Join Shapes, Worked by Hand

Here is a tiny company. We will use it for the rest of this section.

employees                     teams
id  name    team_id           id  name
1   Ada     10                10  Design
2   Bilal   10                20  Ops
3   Chen    20                30  Research
4   Diya    NULL

Diya has no team. Research has no people.

Inner join

SELECT e.name, t.name AS team
FROM employees e
JOIN teams t ON e.team_id = t.id;

Walk each employee, look up the team, keep the row only if a team exists:

Ada   + 10 -> Design     keep  (Ada, Design)
Bilal + 10 -> Design     keep  (Bilal, Design)
Chen  + 20 -> Ops        keep  (Chen, Ops)
Diya  + NULL -> no match drop

Result: three rows. Diya is gone. Research is gone.

JOIN with no extra word means INNER JOIN. The two spellings are the same.

Left join

SELECT e.name, t.name AS team
FROM employees e
LEFT JOIN teams t ON e.team_id = t.id;
Ada   + Design
Bilal + Design
Chen  + Ops
Diya  + NULL          <- kept, with no team name

Four rows. Every employee is there. This is the usual way to ask "list people, and their team if they have one."

Right join

SELECT e.name, t.name AS team
FROM employees e
RIGHT JOIN teams t ON e.team_id = t.id;
Ada   + Design
Bilal + Design
Chen  + Ops
NULL  + Research      <- the team with no people

Diya is gone, because she is on the left and this join is driven by the right table. The same result is usually written as a left join with the tables swapped:

SELECT e.name, t.name AS team
FROM teams t
LEFT JOIN employees e ON e.team_id = t.id;

Full join

SELECT e.name, t.name AS team
FROM employees e
FULL JOIN teams t ON e.team_id = t.id;
Ada   + Design
Bilal + Design
Chen  + Ops
Diya  + NULL
NULL  + Research

Five rows. Nobody and no team is missing. SQLite did not have FULL JOIN until recently; PostgreSQL and most other engines have it. If you need to be portable, you can build it from a left join, a right join, and UNION.

Counting check. After an inner join, every result row has a real key on both sides. After a left join, the number of rows is at least the size of the left table, and is larger when a left row matches more than one right row. If you expected one row per employee and got more, a left row matched several teams. That is usually a sign that the join key is not unique on the right side.

4. Cross Joins: When the Row Count Explodes

A cross join pairs every row with every row. There is no ON condition.

SELECT * FROM employees CROSS JOIN teams;
-- same accidental form:
SELECT * FROM employees, teams;          -- comma join, no WHERE
SELECT * FROM employees JOIN teams;      -- missing ON (error in most engines)

With 4 employees and 3 teams you get 12 rows. That is easy to spot. With real tables it is not:

100 rows  × 100 rows            =      10,000
100       × 100       × 100     =   1,000,000
1,000     × 1,000     × 1,000   = 1,000,000,000

We ran the 100 × 100 × 100 case in SQLite. It produced 1,000,000 rows in 8.9 ms on this machine. The time is not the scary part. The scary part is the next size up: a billion rows, a lot of memory, and a query that looks "almost right" because you only forgot the ON clause or wrote the wrong key.

Cross joins are legal and sometimes useful (for example, a calendar of every store and every date). They should be written as CROSS JOIN on purpose, never reached by accident.

5. Algorithm 1: Nested Loop Join

The simplest algorithm has a loop inside a loop:

for each row L in the left table:          # the "outer" input
    for each row R in the right table:     # the "inner" input
        if L.key == R.key:
            emit (L, R)

For 2,000 outer rows and 10,000 inner rows, this can compare up to 20 million pairs. If the inner key is unique and we stop at the first match, the average number of comparisons is smaller, but it is still proportional to |left| × |right| when matches are spread out.

That sounds hopeless, and without an index it is. With an index on the inner key, the inner "loop" becomes a lookup:

for each row L in the left table:
    R = index_lookup(right, L.key)     # a B+ tree or hash lookup, not a full scan
    if R found:
        emit (L, R)

This is an index nested loop join. The plan reads as "scan (or search) the outer table, then search the inner table with an index." It is the usual choice when one input is small, or when you want only the first few matching rows (LIMIT), or when the inner table has a useful index and the outer side is already well filtered.

Worked on the tiny tables, inner join, no index, Ada first:

outer Ada  (team_id=10)
    compare with Design 10  -> match, emit (Ada, Design)
    compare with Ops 20     -> no
    compare with Research 30 -> no
outer Bilal (team_id=10)
    ... same three comparisons, one match
outer Chen  (team_id=20)
    ... match on Ops
outer Diya  (team_id=NULL)
    NULL equals nothing, not even NULL. no match.

Twelve comparisons, three results. Add an index on teams.id and each employee does one lookup instead of three scans. On a 200,000-row table the difference is not "three vs one." It is "scan everything vs jump to the right leaf."

6. Algorithm 2: Hash Join

A hash join builds a hash table from one input, then probes it with the other. Equality joins love this, because a hash table answers "do you have this key?" in about one step.

build:
    for each row B in the smaller table:
        put B in hash_table[B.key]

probe:
    for each row P in the other table:
        for each B in hash_table[P.key]:   # usually 0 or 1 row
            emit (P, B)

Worked with our teams as the build side:

build hash on teams.id:
    10 -> Design
    20 -> Ops
    30 -> Research

probe with employees:
    Ada  10 -> Design      emit
    Bilal 10 -> Design     emit
    Chen  20 -> Ops        emit
    Diya  NULL -> nothing  skip

Cost is roughly |build| + |probe|, plus the memory to hold the hash table. That is why the planner wants the smaller input on the build side. If the build side does not fit in memory, the engine spills partitions to disk and the join still works, just more slowly. In PostgreSQL you will see this as a "Hash" node under a "Hash Join," and in EXPLAIN (ANALYZE, BUFFERS) you may see temp writes if it spilled.

Hash joins need an equality key (= or a conjunction of equalities). They cannot do <, BETWEEN, or LIKE 'ab%'. For those, the planner uses a nested loop or a merge join, or it filters after a hash join on the equality part of the condition.

Intuition. A nested loop is looking up a word in a book by flipping every page, or by using the index at the back. A hash join is pouring the smaller list into labeled buckets, then walking the larger list and going straight to the right bucket.

7. Algorithm 3: Merge Join

If both inputs are sorted on the join key, you can zip them together like merging two sorted lists:

sort employees by team_id (if not already)
sort teams by id          (if not already)
i = 0, j = 0
while both lists have rows:
    if employees[i].team_id == teams[j].id:
        emit the pair (and handle extra matches on either side)
    else if employees[i].team_id < teams[j].id:
        i += 1
    else:
        j += 1

Worked, after putting Diya's NULL at the start (NULLs sort first in this picture):

employees by team_id:  Diya NULL, Ada 10, Bilal 10, Chen 20
teams by id:           Design 10, Ops 20, Research 30

Diya  NULL vs 10  -> NULL is not 10, advance Diya
Ada   10   vs 10  -> match, emit Ada+Design
Bilal 10   vs 10  -> match, emit Bilal+Design, then advance both
Chen  20   vs 20  -> match, emit Chen+Ops
                   teams still have Research 30: no employee left, done

If an index already returns rows in key order, the sort can be skipped. That is why a merge join often appears after an index scan. If both sides are large, already sorted (or cheap to sort), and you are joining on equality or a range, merge join is a strong choice. The extra cost is the sort when the inputs are not ordered: you pay for the sort once, then the merge itself is a single pass.

8. The Lab: Measured Times

All numbers in this section were measured on a Linux machine with 8 logical CPUs, using Python 3.13 and SQLite 3.46. The data is 10,000 customers and 200,000 orders. Each order points at a random customer. The join is "give me every order and the customer's name."

The three algorithms in Python

First, a smaller slice so a nested loop can finish: 2,000 orders against all 10,000 customers, stopping at the first match (the customer id is unique).

                break
    return out

A nested loop over all 200,000 orders at the same rate would take about 30 seconds. We did not wait for it. The 2,000-row sample already tells the story: without an index, nested loop is the wrong tool for two large tables.

The same join inside SQLite

SQLite has a primary key on customers.id, so it can do an index nested loop: scan every order, look up each customer by id.

EXPLAIN QUERY PLAN
SELECT o.id, c.name, o.amount
FROM orders o
JOIN customers c ON o.customer_id = c.id;

-- SCAN o
-- SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

That query returned 200,000 rows in 191 ms. Adding an index on orders.customer_id did not change this plan. That is correct: we already want every order, so scanning orders and looking up each customer is the natural path. The extra index would help a different question.

When the extra index matters

Ask for one customer's orders instead:

SELECT o.id, o.amount
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.id = 42;
Index on orders.customer_id?PlanTime (24 rows)
NoSEARCH c by primary key, then SCAN all 200,000 orders6.8 to 8.8 ms
YesSEARCH c by primary key, then SEARCH o using the index0.018 ms

The index made this query about 380 times faster (6.79 ms down to 0.018 ms). The plan change is the thing to look for: SCAN o became SEARCH o USING INDEX.

Takeaway. "I added an index" is not a magic spell. An index helps when the plan can use it to avoid a scan. For a join that already walks the whole table, the useful index is usually on the other table's join key, so each lookup is a search. That is the same idea as the index nested loop above, and the same idea as the B+ tree page.

9. Reading the Plan

SQLite prints a short text plan, as above. PostgreSQL prints a tree. The join algorithms show up as node names.

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, c.name, o.amount
FROM orders o
JOIN customers c ON o.customer_id = c.id
WHERE c.id = 42;

A healthy plan for that query often looks like this (times will differ on your machine):

Nested Loop
  ->  Index Scan on customers c
        Index Cond: (id = 42)
  ->  Index Scan on orders o
        Index Cond: (customer_id = 42)

Read it from the inside out. First find the one customer. Then, for that customer, find their orders with the index. That is an index nested loop.

If you drop the WHERE and join every order to its customer, PostgreSQL will often pick a hash join:

Hash Join
  Hash Cond: (o.customer_id = c.id)
  ->  Seq Scan on orders o
  ->  Hash
        ->  Seq Scan on customers c

The inner Hash node is the build side (customers, the smaller table). The outer scan of orders is the probe side. If you see a Seq Scan on a large table and you thought you had a useful index, ask why the planner thought a full read was cheaper. Common reasons: it needs most of the rows anyway, the statistics are stale (ANALYZE the table), or the query is written so the index cannot be used (see the leftmost-prefix rule on the indexing page).

A merge join looks like this:

Merge Join
  Merge Cond: (o.customer_id = c.id)
  ->  Index Scan on orders o          -- already in customer_id order
  ->  Index Scan on customers c       -- already in id order

If a Sort node sits above an input, you are paying to create that order.

Plan nodeWhat it is doingUsually good when
Nested LoopFor each outer row, find inner matchesOuter side is small, or inner side has a selective index
Hash JoinBuild a hash table, probe with the other sideEquality join, both sides large, enough memory
Merge JoinWalk two ordered inputs togetherBoth sides sorted (or indexed) on the join key

10. Join Order and Many Tables

With two tables there are two orders (A then B, or B then A). With five tables there are many more. The planner searches this space and picks an order it thinks is cheap. You usually want the most selective table first, so later lookups have less work.

-- "orders in Pune for product X in the last day"
orders
  JOIN customers  ON customer_id = customers.id
  JOIN products   ON product_id  = products.id
WHERE customers.city = 'Pune'
  AND products.sku   = 'MUG-1'
  AND orders.created_at >= now() - interval '1 day'

If "MUG-1 yesterday" is 80 rows, and "people in Pune" is 200,000 rows, starting from the product (or from yesterday's orders) is much cheaper than starting from every customer in Pune.

Help the planner with fresh statistics (ANALYZE) and with the indexes those filters and join keys need. Forcing an order by hand (join_collapse_limit, optimizer hints, or rewriting the query) is a last resort. If you do it, leave a comment about why, and re-check the plan when the data grows.

One more rule: filter early. A condition like orders.created_at >= ... belongs in WHERE (or in the ON clause of an inner join). If you put a filter on the right table into the WHERE of a left join, you can accidentally turn it into an inner join, because the rows that had a NULL right side fail the filter and disappear. For "keep all orders, and the product if it is a mug," the product filter belongs in the ON clause.

-- keeps every order; non-mugs show NULL product columns
FROM orders o
LEFT JOIN products p ON p.id = o.product_id AND p.sku = 'MUG-1'

-- accidentally drops orders that are not mugs
FROM orders o
LEFT JOIN products p ON p.id = o.product_id
WHERE p.sku = 'MUG-1'

11. Exists, In, and Anti-Joins

Sometimes you do not want the joined columns at all. You only want to know whether a match exists.

-- customers who have at least one order
SELECT * FROM customers c
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.id
);

-- customers with no orders (an anti-join)
SELECT * FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.id
);

-- same anti-join, written with a left join
SELECT c.*
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

EXISTS can stop at the first match. A join that then uses SELECT DISTINCT to undo row multiplication does extra work. Prefer EXISTS (or IN on a unique column) when you only need a yes or no.

IN and EXISTS are often planned the same way for a subquery that returns keys. One trap: NOT IN (SELECT team_id FROM ...) is not the same as NOT EXISTS if the subquery can return NULL. If one value is NULL, NOT IN becomes unknown for every row, and the result can be empty. Prefer NOT EXISTS for anti-joins.

12. NULL Keys Do Not Match

In SQL, NULL = NULL is not true. It is unknown. Join conditions use that same rule, so two NULL keys do not pair up. We checked it: 1,000 orders, 50 of them with customer_id set to NULL.

QueryRow count
Inner join to customers950 (the NULL keys vanished)
Left join to customers1,000 (50 rows with a NULL customer)

That is why Diya disappeared from the inner join in section 3. If you need "unassigned" to be a real group, store a real key (for example team 0, "No team") or use an outer join and treat NULL as its own bucket in the application.

13. Common Pitfalls

  • Missing or wrong ON clause. You get a cross join. Row counts in the millions are the clue. Check COUNT(*) against the sizes you expect.
  • Joining on a non-unique key. Two orders with the same amount are not related. We joined 2,000 orders to themselves on amount and got 9,888 rows, a 4.9× blow-up. Join on keys, not on "columns that happen to be equal."
  • Filter in WHERE after a left join. Turns the left join into an inner join. Put filters on the right table in the ON clause.
  • NULL join keys. They never match. Inner joins drop them.
  • NOT IN with NULLs. Use NOT EXISTS.
  • Selecting * from a join. You get two id columns and a wide row. Name the columns you need. That is also cheaper.
  • Using DISTINCT to hide a bad join. Fix the key or use EXISTS.
  • Stale statistics. The planner picked a nested loop when a hash join would be faster, or the other way around. Run ANALYZE.
  • Index on the wrong table. For "one customer and their orders," you need an index on orders.customer_id, not another index on customers.id (that one already exists as the primary key).

14. Practice Problems

Problem 1: predict the row count

Table a has 100 rows, table b has 200 rows. Every a.id appears exactly twice in b.a_id. How many rows do SELECT * FROM a JOIN b ON b.a_id = a.id and SELECT * FROM a LEFT JOIN b ON b.a_id = a.id return?

Answer: Both return 200 rows. Every row of a has matches, so the left join does not add extra NULL rows. The inner join already has two result rows per a row.

Problem 2: why is this left join dropping rows?

SELECT e.name, t.name
FROM employees e
LEFT JOIN teams t ON t.id = e.team_id
WHERE t.name <> 'Ops';

Diya (no team) is missing from the result. Why? How do you keep her, and still hide Ops people?

Answer: t.name is NULL for Diya, and NULL <> 'Ops' is not true, so the WHERE clause drops her. The left join has been turned into an inner join. Move the filter into the ON clause: LEFT JOIN teams t ON t.id = e.team_id AND t.name <> 'Ops'. Then Diya stays, with a NULL team, and Ops employees also stay but with a NULL team name. If you instead want Ops employees to disappear and Diya to stay, use WHERE t.name <> 'Ops' OR t.name IS NULL.

Problem 3: pick the algorithm

You join 5 million fact rows to a 200-row dimension table on an equality key. There is no useful order on either input. Which join algorithm should you expect, and which side is the build side?

Answer: A hash join, with the 200-row table as the build side and the 5 million fact rows as the probe side.

Problem 4: read this plan

Nested Loop
  ->  Seq Scan on orders
  ->  Seq Scan on customers
        Filter: (customers.id = orders.customer_id)

The query is the lab join (200,000 orders, 10,000 customers) without a WHERE clause. What is wrong, and what two changes might fix it?

Answer: This is a nested loop with a full scan of customers for every order: about 200,000 × 10,000 comparisons. Fix 1: make sure customers.id is a primary key (or has an index) so the inner side becomes an index lookup. Fix 2: let the planner use a hash join, which we measured at 50 ms in Python for this size. Running ANALYZE and checking that work_mem is reasonable helps the planner pick it.

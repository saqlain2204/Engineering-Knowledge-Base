Replication, Sharding & the CAP Theorem

One database server can hold a lot. But one day it is too slow, too full, or it breaks at 3 AM. This page shows the two big ideas that fix this: replication (keep copies of the same data on several machines) and sharding (split the data so each machine holds only part of it). Then it explains the hard trade-off that every system with copies must make, known as the CAP theorem. You only need the ideas from Transactions & MVCC (what a commit is, and what the write-ahead log is). Every term is explained when it first appears.

1. Why One Server Is Not Enough

Picture a small online shop. It has one PostgreSQL server. Everything works. Then the shop grows, and three different problems show up:

  • It breaks. The disk fails, or the cloud restarts the machine. While it is down, nobody can buy anything. One machine is a single point of failure: one broken part stops everything.
  • Too many reads. Thousands of people browse products. Most queries only read. The one server's CPU is at 100%.
  • Too much data or too many writes. The orders table no longer fits on one disk, or one machine cannot write fast enough.

Each problem has a different fix:

ProblemFixIdea
Server breaksReplicationKeep a full copy on another machine, ready to take over
Too many readsReplicationSend reads to the copies
Too much data, too many writesShardingSplit the data across machines; each holds a part

Intuition. Replication is photocopying a book so several people can read it, and so you still have it if one copy is lost. Sharding is splitting an encyclopedia into volumes A-F, G-M, and so on, because no single shelf can hold it all. Big systems do both: they split the data into shards, and keep copies of each shard.

Before you reach for either, remember the cheaper steps: add an index, fix slow queries, add a cache, or buy a bigger machine (called scaling up or vertical scaling). Adding more machines is called scaling out or horizontal scaling. Scaling out is powerful, but it makes everything harder, as this page will show.

2. The Words, in Plain English

WordMeaning
NodeOne machine (or one database process) in the group.
ReplicaA copy of the data on one node.
Leader (also primary, master)The one node that accepts writes.
Follower (also replica, standby, secondary)A node that copies changes from the leader. It can serve reads.
Replication lagHow far behind the leader a follower is, in time or in bytes of log.

Network partitionThe network breaks so that some nodes cannot talk to others, while each side is still running.

Consistency (in CAP)Every read sees the latest write, as if there were only one copy.
Availability (in CAP)Every request to a working node gets an answer (not an error).

Note: "consistency" in CAP is not the C in ACID. ACID's C means "the data follows its rules" (for example, a balance is never negative). CAP's C means "all copies look like one copy". Same word, two meanings.

3. Leader and Followers: How Copies Are Made

The most common setup is single-leader replication. One node is the leader. All writes go to it. The leader sends every change to the followers, and they apply the changes in the same order.

                 writes                      reads
   app  ───────────────────►  LEADER  ◄──────────── app
                                │
              change log (WAL)  │  sent in order
                ┌───────────────┼────────────────┐
                ▼               ▼                ▼
           FOLLOWER 1      FOLLOWER 2       FOLLOWER 3
               ▲               ▲                ▲
               └──── reads ────┴──── reads ─────┘

What exactly is sent?

In PostgreSQL, the leader already writes every change to its write-ahead log (WAL) before changing the data files (see Transactions). The WAL is a list of low-level changes, like "in page 812 of the orders table, put these bytes at this spot". Streaming replication simply sends this WAL to followers over a network connection. Each follower replays it, so its files become byte-for-byte the same as the leader's.

MySQL usually sends a different log, the binlog, which can hold the changed rows ("row 42 of orders now has status = 'shipped'"). This is called logical replication: it describes rows, not bytes on disk. PostgreSQL also has logical replication for special cases, like copying one table into another kind of system.

MethodWhat is sentGood forLimits
Physical (WAL streaming)Byte-level page changesExact copies, failoverSame major version on both sides; copies the whole server
Logical (row changes)"Insert / update / delete this row"Copying some tables, upgrades, feeding other systemsSchema changes need care; more work per change
Statement-basedThe SQL text itselfSmall logsNOW() or RANDOM() give different results on each copy. Mostly avoided today.

Adding a new follower

  1. Take a copy (a snapshot) of the leader's data while it keeps running. Remember the log position at that moment, for example WAL position 0/3A000060.
  2. Load the snapshot on the new machine.
  3. Ask the leader for every change after that position, and replay them.
  4. When the follower has caught up, it keeps streaming new changes as they happen.

In PostgreSQL, the tool pg_basebackup does steps 1 and 2. A log position is called an LSN (log sequence number). It just counts bytes in the WAL, so a bigger LSN means "later".

4. Synchronous vs Asynchronous: When Is a Write "Done"?

When the app sends COMMIT, when should the leader say "OK"? There are two choices.

ASYNCHRONOUS                              SYNCHRONOUS
app      leader      follower             app      leader      follower
 │ COMMIT  │            │                  │ COMMIT  │            │
 │────────►│ write WAL  │                  │────────►│ write WAL  │
 │◄────────│ "OK"       │                  │         │──── WAL ──►│ write WAL
 │         │──── WAL ──►│ (later)          │         │◄─── ack ───│
 │         │            │                  │◄────────│ "OK"       │
  • Asynchronous: the leader says OK as soon as its own disk has the change. It sends the change to followers afterwards. Fast. But if the leader dies right after saying OK, and before the change left the machine, that committed write is lost when a follower takes over.
  • Synchronous: the leader waits until at least one follower confirms it has the change. No committed write is lost if the leader dies. But every commit now waits one network round trip, and if that follower is down or slow, writes stop or slow down.

Worked example: what does waiting cost?

The leader is in one data center. The synchronous follower is in another data center, and a round trip between them (the RTT, see TCP) is 2 ms. A local disk flush takes 1 ms.

  • Async commit: about 1 ms (just the local flush).
  • Sync commit: about 1 ms + 2 ms (send and get the ack) + the follower's own flush, so at least 3 ms.

If the follower were in another country with an RTT of 120 ms, every commit would take more than 120 ms. That is why the usual setup is: one synchronous follower nearby (no data loss if the leader dies), plus asynchronous followers further away (for reads and disaster recovery). PostgreSQL lets you say this with synchronous_standby_names = 'ANY 1 (replica_a, replica_b)': wait for any one of those two.

Note. In PostgreSQL, the setting synchronous_commit picks how much to wait for: remote_write (the follower received it), on (the follower flushed it to disk), or remote_apply (the follower has also applied it, so a read there will see it). More waiting means more safety and more delay.

5. Replication Lag and Stale Reads

With async followers, a follower is always a little behind. Usually it is milliseconds. Under heavy load, or while a follower runs a long query, it can be seconds or minutes. Reading old data from a follower is called a stale read.

The classic bug: "my comment disappeared"

time  user                          leader           follower (lag 2 s)
 0.0  posts a comment  ──write──►   comment saved
 0.3  page reloads     ──read───────────────────────► no comment yet!
 2.0                                                  comment arrives
 2.5  reloads again    ──read───────────────────────► comment shows

The user thinks the site lost their comment. The data was fine; the read just went to a copy that had not caught up. Different users need different promises:

PromiseWhat it meansA common way to get it
Read-your-writesYou always see your own changes.For a short time after a user writes (say, 10 s), send that user's reads to the leader. Or remember the LSN of their write, and only read from a follower that has replayed past it.
Monotonic readsYou never see time go backwards (new data, then old data on the next refresh).Send each user to the same follower every time (for example, pick the follower by hashing the user ID).
Consistent prefixYou see changes in the order they happened (never an answer before its question).Keep related data in the same shard, so one log orders it.

Measuring lag

On the PostgreSQL leader, the view pg_stat_replication has one row per follower. Its columns write_lag, flush_lag and replay_lag show how long recent changes took to reach each step on that follower. On a follower you can ask:

SELECT now() - pg_last_xact_replay_timestamp() AS replay_delay;

This shows how old the last replayed transaction is. (Careful: if the leader has had no writes for a minute, this number grows even though the follower is fully caught up.)

Worked example: lag that keeps growing

During a sale, the leader produces 60 MB of WAL per second. One follower, on a slow disk, can only replay 50 MB per second. Every second it falls 10 MB further behind. After 10 minutes (600 s), it is 600 × 10 = 6,000 MB = about 6 GB behind. At normal load it catches up, but during the sale its reads get older and older. Lesson: followers need the same disk speed as the leader, and you need an alert on lag.

6. Failover and Split Brain

When the leader dies, something must pick a follower and make it the new leader. Doing it by hand is slow (someone must wake up). Doing it automatically is fast but tricky. The steps are:

  1. Notice the leader is dead. Usually: "no heartbeat for 30 seconds". A heartbeat is a small "I am alive" message sent every few seconds.
  2. Choose the new leader. Pick the follower that is most up to date (the highest replayed LSN), so the least data is lost.
  3. Promote it (it starts accepting writes) and point the apps at it, usually by moving a DNS name or a virtual IP address, or by updating a proxy.
  4. Make sure the old leader cannot come back as a leader.

Why step 4 matters: split brain

"No heartbeat" does not always mean "dead". Maybe the old leader is fine, and only the network between it and the others broke. If a new leader is promoted while the old one still accepts writes, you now have two leaders. Some apps write to one, some to the other. Their data goes in two directions and cannot be simply merged. This is called split brain.

   network partition
          ┊
 app A ──►┊   OLD LEADER  (still thinks it leads, takes order #9001)
          ┊
 app B ───┊──►NEW LEADER  (promoted, also takes an order #9001)
          ┊
 Two different orders with the same ID. Which one is real?

The fixes:

  • Majority vote. A node may only be leader if a majority of nodes agree. With 3 nodes, a majority is 2. In a split, only one side can have 2 of the 3, so only one side can have a leader. This is the idea behind consensus protocols like Raft, used by etcd (the Kubernetes database, see Kubernetes Architecture). PostgreSQL tools such as Patroni use etcd to hold the "who is leader" lock.
  • Fencing. Before the new leader starts, cut the old one off for sure: power it off, revoke its disk, or block it at the firewall. (The old joke name is STONITH: "shoot the other node in the head".)
  • Leases. The leader holds a lock that expires, for example after 10 seconds. If it cannot renew the lock, it must stop taking writes by itself.

Why odd numbers? With 3 nodes, a majority is 2, so you survive 1 failure. With 4 nodes, a majority is 3, so you still survive only 1 failure. The 4th node adds cost but no safety. With 5 nodes you survive 2. In general, with n nodes the majority is floor(n/2) + 1, and you survive n minus that.

The data-loss window

With async replication, writes the old leader committed but did not send yet are lost after failover. If the chosen follower was 300 ms behind, the last 300 ms of commits are gone. Systems state this as the RPO (recovery point objective: how much data you can lose) and the RTO (recovery time objective: how long you can be down). A synchronous follower gives an RPO of zero.

7. Leaderless Replication and Quorums

Some databases, inspired by Amazon's Dynamo paper (for example Cassandra and ScyllaDB), have no leader. The client (or a coordinator node) sends each write to several replicas at once, and reads from several replicas at once.

Three numbers control this:

  • N = how many replicas hold each piece of data.
  • W = how many replicas must confirm a write before it counts as done.
  • R = how many replicas you ask when you read. You take the newest value among the answers.

The key rule: if W + R > N, every read overlaps at least one replica that has the latest write.

Worked example: N = 3, W = 2, R = 2

write x = 7 (version 5):    A ✓   B ✓   C ✗ (was down, still has version 4)
                            2 confirmations = W, so the write is done

read x, ask any 2:
   ask A, B  → 7 (v5), 7 (v5)          → answer 7
   ask A, C  → 7 (v5), 3 (v4)          → newest is v5 → answer 7
   ask B, C  → 7 (v5), 3 (v4)          → newest is v5 → answer 7

W + R = 2 + 2 = 4 > 3, so any 2 readers include at least 1 writer.

Now try W = 1, R = 1. W + R = 2, which is not more than 3. A write might land only on A, and a read might ask only C, and get the old value. Fast, but stale reads are possible.

N, W, RW + R > N?SurvivesFeels like
3, 2, 2Yes (4 > 3)1 node down for both reads and writesBalanced, the usual choice
3, 3, 1Yes (4 > 3)Reads survive 2 down; writes fail if any node is downFast reads, fragile writes
3, 1, 3Yes (4 > 3)Writes survive 2 down; reads fail if any node is downFast writes, fragile reads
3, 1, 1No (2)Up to 2 downVery available, stale reads likely

How stale copies get fixed

  • Read repair: when a read sees that C has an old version, it writes the new value back to C.
  • Anti-entropy: a background job compares replicas and copies over what is missing. To compare quickly it uses a Merkle tree: a tree of hashes where each parent is a hash of its children. If the top hashes match, everything below matches, so you only dig into parts that differ.
  • Hinted handoff: if C is down during a write, another node keeps a note ("this belongs to C") and hands it over when C comes back.

Two writes at the same time

Without a leader, two clients can write the same key at once on different replicas. Which one wins? The simple rule is last write wins (LWW): keep the one with the later timestamp. But clocks on different machines are never exactly equal, so LWW can silently throw away a write. When that matters, systems keep both versions and let the app merge them (for example, a shopping cart keeps the union of both carts), or use special data types called CRDTs (conflict-free replicated data types), such as counters that can always be merged.

8. Sharding: Splitting the Data

Replication copies all the data to every node. That does not help when the data is too big for one node, or when writes are too many for one leader. Then you shard: each shard holds some of the rows, and each shard has its own leader (and usually its own followers).

                    router (knows which shard has which keys)
                     ┌──────────────┼──────────────┐
                     ▼              ▼              ▼
                 SHARD 1         SHARD 2        SHARD 3
              customers 1..    customers ..    customers ..
              leader + 2       leader + 2      leader + 2
              followers        followers       followers

The big question: which shard does a row go to? That is decided by the shard key. There are three common methods.

Range sharding

Each shard gets a range of key values: customers A-H on shard 1, I-P on shard 2, Q-Z on shard 3. Range queries ("all orders from 1 to 7 November") are easy, because neighbours are stored together. The danger: if the key is a time or an increasing ID, all new rows go to the last shard, and that one shard does all the work. Systems like CockroachDB and HBase use ranges and split a range in two when it gets too big.

Hash sharding

Compute a hash of the key. A hash function turns any input into a number that looks random but is always the same for the same input. Then use the hash to pick a shard. Keys spread evenly, even if they arrive in order. The price: range queries must ask every shard, because neighbours are now scattered.

The simplest version is shard = hash(key) mod N, where N is the number of shards and "mod" means "the remainder after dividing". It has one big problem, shown next.

Directory (lookup table) sharding

Keep a small table that says "tenant 42 lives on shard 3". Very flexible: you can move one big customer to its own shard. But the directory must be fast, and always available, or nothing works.

9. Consistent Hashing (Real Experiment)

The problem with hash mod N

Say you have 4 shards and use hash(key) mod 4. A key with hash 10 goes to shard 10 mod 4 = 2. Now you add a 5th shard. The same key goes to 10 mod 5 = 0. It must move. In fact, most keys move. Moving data is slow and risky, so this is bad.

The hash ring

Consistent hashing fixes this. Imagine the hash values as a clock face (a ring). Put each shard at one or more points on the ring by hashing its name. To find a key's shard, hash the key, find that point on the ring, and walk clockwise to the first shard you meet.

                 0
            S1 ●   ● key "user:7" → walks clockwise → S2
          ●              ● S2
   S4 ●                      
          ●              ●
            ●   ● S3
                 
 Add S5 between S1 and S2: only keys in that one arc (S1 → S5)
 move, from S2 to S5. Every other key stays where it was.

One point per shard makes the arcs uneven: one shard can get a huge arc and most of the keys. The fix is virtual nodes: put each shard at many points (for example, hash "s1#0", "s1#1", ... "s1#99"). Many small arcs average out, so each shard gets about the same share.

The experiment

We ran this Python program (standard library only) on 100,000 keys, growing from 4 shards to 5. A perfect result would move exactly 1/5 = 20% of the keys (just enough to fill the new shard), and give each of the 5 shards 20,000 keys.

import bisect, hashlib

def h(s):  # stable 64-bit hash (Python's built-in hash() changes every run)
    return int.from_bytes(hashlib.sha256(s.encode()).digest()[:8], "big")

KEYS = [f"user:{i}" for i in range(100_000)]

class Ring:
    def __init__(self, shards, vnodes):
        self.points = sorted((h(f"{s}#{v}"), s) for s in shards for v in range(vnodes))
        self.hashes = [p for p, _ in self.points]
    def owner(self, key):  # first point clockwise from the key's hash
        i = bisect.bisect(self.hashes, h(key)) % len(self.points)
        return self.points[i][1]

def moved(before, after):
    return sum(1 for k in KEYS if before(k) != after(k))

print(moved(lambda k: h(k) % 4, lambda k: h(k) % 5))
for v in (1, 10, 100, 200):
    r4 = Ring([f"s{i}" for i in range(4)], v)
    r5 = Ring([f"s{i}" for i in range(5)], v)
    print(v, moved(r4.owner, r5.owner))

Real output, with the keys-per-shard spread added:

100000 keys, growing from 4 shards to 5
hash mod N:              79888 keys moved (79.9%)
ring,   1 vnodes/shard: 53016 keys moved (53.0%), keys per shard after: min 5374, max 53016
ring,  10 vnodes/shard: 23797 keys moved (23.8%), keys per shard after: min 14112, max 28442
ring, 100 vnodes/shard: 22372 keys moved (22.4%), keys per shard after: min 16500, max 22398
ring, 200 vnodes/shard: 20803 keys moved (20.8%), keys per shard after: min 19098, max 20803
hash mod 5 spread: min 19853, max 20320

How to read it:

  • hash mod N moved 79.9% of all keys. That matches the math: a key stays only if hash mod 4 equals hash mod 5, which happens for about 1 in 5 keys. So about 4 in 5 move.
  • A ring with 1 point per shard moved 53%, and was badly unbalanced: the new shard landed on a huge arc and took 53,016 keys, while one shard kept only 5,374. Fewer moves, but a terrible spread.
  • With 200 virtual nodes, only 20.8% moved, very close to the perfect 20%, and every shard holds between 19,098 and 20,803 keys.

In real systems. Cassandra and DynamoDB use rings with many tokens per node. Redis Cluster uses a fixed set of 16,384 hash slots (slot = CRC16(key) mod 16384) and moves whole slots between nodes. That is the same trick in another form: the number of slots never changes, so adding a node only moves the slots you choose to give it.

10. Hot Keys and Cross-Shard Queries

Hot keys

Even spreading of keys is not the same as even spreading of work. If one celebrity's account gets a million reads per minute, the one shard that holds that account melts, no matter how good the hash is. This is a hot key (or hot spot).

  • For hot reads: put a cache in front, or keep extra read copies of that key.
  • For hot writes (like a "likes" counter): split the key into pieces, such as likes:post42:0 to likes:post42:9. Each write picks a random piece. A read adds up all 10. The work now spreads over up to 10 shards.

Choosing a shard key

A good shard key:

  • Has many different values (country is bad: only a few values, and one country may be huge).
  • Spreads the work evenly (not a timestamp with range sharding).
  • Matches the most common query, so that query touches one shard. For a shop, most queries are "this customer's orders", so customer_id is a good key. For a business app with many company customers, tenant_id (the company) is the usual key.

Cross-shard queries

A query that includes the shard key goes to one shard: fast. A query that does not must ask every shard and combine the answers. This is called scatter-gather.

SELECT * FROM orders WHERE customer_id = 42;        -- one shard (good)
SELECT * FROM orders WHERE product_id = 'P9';       -- every shard, then merge
SELECT COUNT(*) FROM orders WHERE day = '2026-11-21';  -- every shard, add the counts

Scatter-gather is only as fast as the slowest shard. If each shard is slow 1% of the time, a query that asks 50 shards hits at least one slow shard 1 - 0.9950 = about 39.5% of the time.

Writes that touch two shards (move money from a customer on shard 1 to one on shard 3) cannot use one normal transaction. They need two-phase commit (2PC): a coordinator first asks every shard "can you commit?" and only if all say yes, tells them all "commit". It works, but it is slow and blocks if the coordinator dies at the wrong moment. Good designs avoid most cross-shard writes by picking the shard key well.

A global unique ID is also harder: one auto-increment counter would be a bottleneck. Common choices are random UUIDs, or IDs built from "time + shard number + a counter" (Twitter's Snowflake design), which stay roughly sorted by time.

11. The CAP Theorem and PACELC

Now the big trade-off. Take two replicas, A and B, of the same data. The network between them breaks (a partition). A client sends a write to A. Another client then reads from B. What should B do?

  client 1                         client 2
     │ write x = 7                     │ read x
     ▼                                 ▼
     A  ────────── ✂ network cut ✂ ──── B   (B still has x = 3)

  Option 1: B answers "x = 3"          → available, but not consistent
  Option 2: B answers "error, try later" → consistent, but not available

There is no third option. B cannot know about the write, because the message cannot get through. This is the CAP theorem: when a network Partition happens, a replicated system must choose between Consistency and Availability.

  • CP systems refuse some requests during a partition, so they never return stale data. Example: etcd and ZooKeeper (the minority side of a split stops accepting writes), a PostgreSQL cluster with a synchronous follower (writes stop if the follower is unreachable).
  • AP systems keep answering on both sides, and fix up the differences later. Example: Cassandra with W = 1 and R = 1, DNS (see DNS: caches answer with old records until the TTL runs out).

Common misreading. People say "pick 2 of 3". That is misleading. You cannot "choose" to have no partitions: networks break whether you like it or not. The real statement is: when there is a partition, pick C or A. When the network is fine, you can have both.

PACELC: the trade-off that happens every day

Partitions are rare. A more useful rule for normal days is PACELC: if there is a Partition, choose A or C; Else (normal times), choose low Latency or Consistency. Waiting for other replicas before answering (synchronous replication, W = 3, reading from the leader) gives consistency but adds round trips. Answering right away from the nearest copy is fast but may be stale.

System (typical setup)During a partitionNormal times
Single PostgreSQL leader, async followers, reads from followersWrites only where the leader isLow latency reads, may be stale
etcd / ZooKeeperC: minority side refuses writesC: reads go through the leader
Cassandra, W = R = QUORUMRequests that cannot reach a quorum failPays latency for consistency
Cassandra, W = R = ONEA: always answersL: fastest, may be stale

Most real systems let you choose per request. A bank balance check uses a strong read; a "people also viewed" list uses a fast, maybe-stale read.

12. Worked Design: Growing a Shop's Database

Let us put it all together. The shop from section 1 grows in stages.

Stage 1: one server goes down once a month

Add two followers: one in the same region as a synchronous standby (no lost orders on failover), one in another region as an async copy for disasters. Use a tool like Patroni with a 3-node etcd for automatic failover (majority vote, no split brain). Apps connect through one DNS name or proxy that always points at the current leader.

Stage 2: product pages are slow

Send product browsing (reads that may be a second old) to followers. Keep checkout, the cart, and "my orders" on the leader for read-your-writes. Add an alert when replay_lag is over 5 seconds.

Stage 3: the orders table is 4 TB and growing 300 GB a month

Shard orders and order_items by customer_id, using hash slots so shards can be added later without moving most data. A customer's orders and their items live on the same shard, so "show my orders" is one shard, and placing an order is one normal transaction. The products table is small and read-heavy: copy it fully to every shard (a reference table) instead of sharding it.

Stage 4: the finance team needs "revenue per day"

That query crosses every shard. Do not run it on the live shards. Stream changes (logical replication, or a change-data-capture tool) into a separate analytics store and run reports there.

Notice the order: indexes and caching first, then replication, then sharding. Each step adds machines and new ways to fail, so take it only when the earlier step is not enough.

13. Common Pitfalls

  • Reading your own write from a follower. Users see their change vanish. Route those reads to the leader, or wait for the write's LSN.
  • Calling a follower a backup. A follower copies mistakes too: DROP TABLE on the leader drops it on every follower within milliseconds. You still need real backups with point-in-time recovery.
  • Automatic failover without fencing. Leads to split brain and two diverging copies of the truth.
  • Two-node clusters. With 2 nodes, neither side of a split has a majority, so either both stop or you risk split brain. Use 3 (or add a small "witness" node).
  • A shard key nobody queries by. Every common query becomes scatter-gather.
  • Range sharding on time or a growing ID. All new writes hit the last shard.
  • hash mod N. Adding a shard moves almost all data (79.9% in our run). Use a ring with virtual nodes or fixed hash slots.
  • Trusting clocks for "last write wins". Machine clocks drift, so the "later" write may really be the earlier one, and data is lost without any error.
  • Forgetting lag on failover. With async replication, promoting a lagging follower loses recent commits. Know your RPO.

14. Practice Problems

Work these out on paper. Answers follow each one.

Problem 1: quorums

N = 5. You want reads to always see the latest write, and you want writes to keep working when 2 nodes are down. What W and R do you choose?

Answer: Writes must work with 3 nodes up, so W ≤ 3. Reads must overlap writes, so W + R > 5. With W = 3, R must be at least 3. Choose W = 3, R = 3. Reads also survive 2 nodes down.

Problem 2: how many failures?

An etcd cluster has 5 members. How many can fail before writes stop? What about 6 members?

Answer: 5 members: majority is floor(5/2) + 1 = 3, so 2 can fail. 6 members: majority is 4, so still only 2 can fail. The 6th member adds nothing.

Problem 3: lag math

A follower is 900 MB behind. The leader now writes 20 MB/s of WAL, and the follower can replay 50 MB/s. How long until it has caught up?

Answer: It gains 50 - 20 = 30 MB each second. 900 / 30 = 30 seconds.

Problem 4: sync or async?

A payments service must never lose a confirmed payment. Its database leader is in Mumbai. Option A: a synchronous follower in Hyderabad (RTT 20 ms). Option B: a synchronous follower in another zone of the Mumbai region (RTT 1 ms) plus an async one in Hyderabad. Which is better and why?

Answer: Option B. Both give zero data loss if the leader's machine dies, but B adds about 1 ms per commit instead of about 20 ms. The async Hyderabad copy still protects against losing the whole Mumbai region (with a small RPO). If you must survive a full region loss with zero data loss, you need A and must pay the 20 ms.

Problem 5: keys that move

You use hash(key) mod N and go from 10 shards to 11. About what fraction of keys move? With a good consistent-hashing ring, about what fraction?

Answer: With mod, a key stays only when h mod 10 = h mod 11, about 1 in 11 keys, so about 10/11 = 91% move. With a ring, only enough to fill the new shard: about 1/11 = 9%.

Problem 6: pick a shard key

A chat app stores messages. The main screen shows "the last 50 messages in this chat room". Candidates: message_id (random), sent_at (time), room_id. Which one, and what could still go wrong?

Answer: room_id (hashed): the main query touches one shard, and a room's messages are stored together in order. message_id would scatter one room over all shards; sent_at with ranges would send all new messages to one shard. What can still go wrong: one giant room (a hot key). For very large rooms, split by (room_id, month) or give them their own shard.

Problem 7: CAP in practice

During a partition, a shopping cart service can either show "error, try again" or let the user add items to a cart copy that may be stale. A seat booking system for a concert can do the same. Which should choose which?

Answer: The cart should choose availability: merging two carts later (union of items) is easy and users hate errors. Seat booking should choose consistency: selling one seat to two people cannot be fixed later, so refuse bookings on the minority side.

15. Cheat Sheet

IdeaOne-line rule
ReplicationSame data on many nodes: for failover and more reads
ShardingDifferent data on each node: for more data and more writes
Async replicationFast commits; may lose the last few writes on failover
Sync replicationNo lost commits; each commit waits at least one RTT
Read-your-writesRead from the leader just after a write, or wait for the write's LSN
Majorityfloor(n/2) + 1; use odd n (3 or 5)
Split brainPrevent with majority votes, fencing, and leases
QuorumW + R > N means reads see the latest write
hash mod NAdding a shard moves about N/(N+1) of keys (79.9% for 4 to 5 in our run)
Consistent hashingAdding a shard moves about 1/(N+1) of keys; use many virtual nodes
Shard keyMany values, even load, matches the main query
CAPDuring a partition, pick consistency (refuse) or availability (maybe stale)
PACELCOtherwise, pick latency or consistency

Normalization & Schema Design

How to decide which tables a database should have and which columns go where. We start from one messy spreadsheet, watch it break, and fix it step by step. By the end you can find keys by hand, name the normal form of any table, split it correctly, and know when breaking the rules on purpose is the right call.

1. The Big Picture: One Big Table

A small shop starts by keeping orders in one spreadsheet. Every row is "one product in one order":

order_idorder_datecustomer_idcustomer_namecustomer_cityproduct_idproduct_nameunit_priceqty
1012026-11-017AshaPuneP1Pen203
1012026-11-017AshaPuneP2Notebook602
1022026-11-029RaviMysuruP1Pen201
1022026-11-029RaviMysuruP3Bag9001
1032026-11-057AshaPuneP2Notebook605

It is easy to read. It is also full of repetition: "Asha, Pune" appears 3 times, and "Notebook, 60" appears twice. With 10,000 orders, Asha's city might be stored hundreds of times.

Repetition by itself only wastes space. The real problem is that every copy is a chance for the copies to disagree. Once two rows say different things about the same fact, the database no longer knows the truth.

Normalization is a step-by-step method for splitting a table so that each fact is stored in exactly one place. The steps are called normal forms: 1NF, 2NF, 3NF, BCNF, and so on. Each one removes one kind of repetition.

Intuition: a well-designed table is about one thing. A customers table is about customers. A products table is about products. The big table above is about four things at once, which is why it breaks.

2. Three Ways the Big Table Breaks

An anomaly is a case where a normal change to the data causes a wrong or impossible result. The big table has all three kinds.

Update anomaly

Asha moves to Bengaluru. You must change three rows. If the app updates only the rows for her latest order, the table now says she lives in two cities at once. Which one is true? Nobody knows.

Insert anomaly

The shop adds a new product, P4 "Stapler", price 150. Nobody has ordered it yet. To add a row you need an order_id, but there is no order. You cannot store the product without inventing a fake order.

Delete anomaly

Ravi cancels order 102, so you delete its two rows. Order 102 was the only order with the Bag. Now the fact "P3 is a Bag that costs 900" is gone too. Deleting one fact destroyed a different fact.

All three come from the same cause: facts about customers and products are stored inside rows about order lines. Normalization fixes the cause, and the anomalies disappear with it.

3. Keys, in Plain Words

A relation is the textbook word for a table. An attribute is a column. A tuple is a row. This page mostly uses the everyday words.

TermPlain meaningIn the big table
SuperkeyAny set of columns whose values are never the same in two rows. It picks out exactly one row.{order_id, product_id}, and also {order_id, product_id, qty}
Candidate keyA superkey with nothing extra: remove any column and it stops being unique.{order_id, product_id}
Primary keyThe one candidate key you choose to identify rows.(order_id, product_id)
Composite keyA key made of more than one column.(order_id, product_id) is composite
Prime attributeA column that is part of some candidate key.order_id, product_id
Foreign keyA column that points to the primary key of another table. The database checks the target exists.(appears after we split: orders.customer_id → customers)
Surrogate keyA made-up ID with no meaning, such as an auto-increment number or a UUID.customer_id = 7
Natural keyA key that has real-world meaning, such as an email address or a vehicle number.none here

Why is {order_id} alone not a key of the big table? Because order 101 has two rows (Pen and Notebook). Why is {order_id, product_id} a key? Because one order lists each product at most once. That is a business rule, and keys always come from business rules, not from looking at a few rows of sample data.

4. Functional Dependencies

A functional dependency (FD) is a rule of the form X → Y. Read it as "X decides Y": whenever two rows have the same X, they must have the same Y.

Example: customer_id → customer_name. Any two rows with customer_id 7 must both say "Asha". If one said "Asha" and another said "Asha K", the rule would be broken.

The FDs in the shop are:

  F1:  order_id               ->  order_date, customer_id
  F2:  customer_id            ->  customer_name, customer_city
  F3:  product_id             ->  product_name, unit_price
  F4:  order_id, product_id   ->  qty

Three facts about FDs that you will use all the time:

  • They chain. If order_id → customer_id and customer_id → customer_city, then order_id → customer_city. This kind of chained FD is called transitive.
  • Adding columns on the left keeps it true. If product_id → unit_price, then product_id, qty → unit_price too.
  • A key decides every column. That is really the definition of a key: key → all columns.

Two special kinds

  • A partial dependency is when a column depends on only part of a composite key. product_id → product_name is partial, because product_id is only half of the key (order_id, product_id).
  • A transitive dependency is when a non-key column depends on another non-key column. In the orders data, customer_id → customer_city is transitive, because customer_id is not the key; it is itself decided by order_id.

Most of normalization is: find the partial and transitive dependencies, and move them into their own tables.

5. Attribute Closure and Finding Keys by Hand

The closure of a set of columns X, written X+, is every column that X decides, directly or through chains. If X+ contains every column, X is a superkey.

The algorithm

  1. Start with result = X.
  2. Look for any FD A → B where all of A is already in the result. Add B to the result.
  3. Repeat step 2 until nothing new can be added.

Worked example 1

Table R(A, B, C, D, E) with FDs: A → B, B → C, C, D → E. Find {A, D}+.

  start:                       {A, D}
  A -> B   (A is in)     add B  {A, B, D}
  B -> C   (B is in)     add C  {A, B, C, D}
  C,D -> E (C, D are in) add E  {A, B, C, D, E}   <- every column
  nothing more to add.  So {A, D} is a superkey.

Is it a candidate key? Check each smaller set: {A}+ = {A, B, C} (no D, no E). {D}+ = {D}. Neither is a superkey, so {A, D} is minimal: it is a candidate key.

A shortcut for finding all candidate keys

Sort the columns into groups by where they appear in the FDs:

  • Never on any right side: nothing can decide these, so they must be in every key.
  • Only on right sides: they are always decided by something else, so they are never in a minimal key.
  • On both sides: try them.

In example 1: A and D never appear on a right side, so every key must contain both. {A, D}+ is already everything, so {A, D} is the only candidate key.

Worked example 2: the shop

Columns that never appear on a right side of F1–F4: order_id and product_id. So both must be in every key. Their closure:

  {order_id, product_id}
  F1 adds order_date, customer_id
  F2 adds customer_name, customer_city   (customer_id is now in)
  F3 adds product_name, unit_price
  F4 adds qty
  = every column  ->  {order_id, product_id} is the only candidate key

6. First Normal Form (1NF)

Rule: every cell holds one single value, and there are no repeating groups of columns. Each row can be identified by a key.

Before the shop's table above, an even earlier version looked like this:

order_idcustomerproducts
101AshaP1 x3, P2 x2
102RaviP1 x1, P3 x1

The products cell holds a list. Questions like "how many pens did we sell?" now need text parsing. You cannot add an index on "the second product". You cannot use a foreign key to check that P3 exists.

Another version had columns product1, qty1, product2, qty2, product3, qty3. That is a repeating group. An order with 4 products does not fit, and most cells are empty.

Fix: one row per order line. That gives the big table from section 1, which is in 1NF. It still has every anomaly, which shows that 1NF alone is not enough.

Modern note: PostgreSQL has array and JSON columns. Storing a list of tags in a JSON column is sometimes fine, as long as you never need to join on, constrain, or update single items inside it. If you do, it should be its own table.

7. Second Normal Form (2NF)

Rule: be in 1NF, and have no partial dependencies. Every non-key column must depend on the whole key, not just part of it.

Only tables with a composite key can break 2NF. If the key is one column, there is no "part" of it.

The shop's key is (order_id, product_id). Check each non-key column:

ColumnDepends onWhole key?
qtyorder_id + product_idYes
order_date, customer_idorder_id onlyNo, partial
customer_name, customer_cityorder_id only (through customer_id)No, partial
product_name, unit_priceproduct_id onlyNo, partial

Fix: move each group into a table keyed by the part it depends on.

  order_items(order_id, product_id, qty)                         key: (order_id, product_id)
  orders(order_id, order_date, customer_id, customer_name, customer_city)   key: order_id
  products(product_id, product_name, unit_price)                key: product_id

The product anomalies are gone: a new product can be added to products without an order, and deleting order 102 no longer deletes the Bag. But orders still repeats Asha's name and city for each of her orders.

8. Third Normal Form (3NF)

Rule: be in 2NF, and have no transitive dependencies. A non-key column must not depend on another non-key column.

A classic way to remember 2NF and 3NF together: every non-key column must depend on "the key, the whole key, and nothing but the key".

In orders(order_id, order_date, customer_id, customer_name, customer_city):

  order_id  ->  customer_id  ->  customer_name, customer_city
   (key)        (not a key)       depend on a non-key column  =  transitive

Fix: move the customer facts to their own table, and keep only the customer_id in orders as a foreign key.

  customers(customer_id, customer_name, customer_city)      key: customer_id
  orders(order_id, order_date, customer_id -> customers)     key: order_id
  products(product_id, product_name, unit_price)            key: product_id
  order_items(order_id -> orders, product_id -> products, qty)   key: (order_id, product_id)

Now check the anomalies again:

  • Asha moves: change one row in customers.
  • New product: insert into products. No order needed.
  • Cancel an order: delete from order_items and orders. Products and customers stay.

The full formal definition is a little wider. A table is in 3NF if, for every non-trivial FD X → A, either X is a superkey, or A is a prime attribute (part of some candidate key). That "or" matters in the next section.

9. Boyce-Codd Normal Form (BCNF)

Rule: for every non-trivial FD X → Y, X must be a superkey. No exceptions. (A trivial FD is one like A, B → A, where the right side is already part of the left. It is always true and tells you nothing.)

BCNF is 3NF without the "or A is prime" escape. The two only differ when a table has several overlapping candidate keys. That is rare, but it does happen.

Worked example: tutoring sessions

A college runs tutoring. The rules:

  • Each tutor teaches exactly one subject: tutor → subject.
  • For each subject, a student has exactly one tutor: student, subject → tutor.
studentsubjecttutor
AshaDBMSMeera
RaviDBMSMeera
AshaOSKiran
ZoyaDBMSArjun

Candidate keys: student never appears on a right side, so it is in every key. {student, subject}+ = all (through the second rule). {student, tutor}+ = all (tutor gives subject). So there are two keys: {student, subject} and {student, tutor}. Prime attributes: all three columns.

3NF? The FD tutor → subject has a left side that is not a superkey, but subject is prime. So 3NF allows it. Yes, 3NF.

BCNF? tutor is not a superkey. No. And you can see the repetition: "Meera teaches DBMS" is stored twice. If Meera switches to teaching OS and only one row is updated, the data contradicts itself.

Fix: split on the bad FD. Put tutor → subject in its own table, and keep the rest:

  tutors(tutor, subject)          key: tutor
  sessions(student, tutor)        key: (student, tutor)

Both tables are in BCNF. But there is a price: the rule "a student has one tutor per subject" now spans two tables. No single table can enforce it with a key. Asha could be booked with both Meera and Arjun, who both teach DBMS, and no key would stop it. You would need a trigger or app logic.

The trade-off: 3NF can always be reached while keeping every rule enforceable inside single tables. BCNF removes all FD-based repetition, but sometimes at the cost of a rule. Most real designs aim for BCNF and fall back to 3NF when a rule like this matters more.

10. Splitting Safely: Lossless Joins and Kept Rules

Splitting a table is only correct if you can join the pieces back and get exactly the original rows: no rows lost and no fake rows added. This is called a lossless join.

A bad split, with numbers

Table grades(student, course, grade):

  student | course | grade
  Asha    | DBMS   | A
  Ravi    | OS     | A

Split it into (student, grade) and (course, grade). Then join them back on grade:

  (student, grade): (Asha, A), (Ravi, A)
  (course, grade):  (DBMS, A), (OS, A)

  join on grade = A gives 2 x 2 = 4 rows:
  Asha | DBMS | A      real
  Asha | OS   | A      FAKE
  Ravi | DBMS | A      FAKE
  Ravi | OS   | A      real

We got more rows, but we lost information: we can no longer tell who took which course. ("Lossy" means information is lost, even though rows were added.)

The test for a split into two tables

Split R into R1 and R2. The split is lossless if the shared columns (R1 ∩ R2) form a key of R1 or a key of R2.

  • Bad split above: shared column is grade. Grade is not a key of either piece. Lossy.
  • Our 3NF step: orders and customers share customer_id, which is the key of customers. Lossless.
  • Tutoring BCNF step: shared column tutor is the key of tutors. Lossless.

The safe habit: when you split on a bad FD X → Y, make a new table (X, Y) with key X, and remove Y from the old table. X stays in both, and it is a key of the new table, so the split is always lossless.

Keeping rules (dependency preservation)

A split preserves dependencies if each original FD can still be checked inside one table. The shop split keeps all four FDs (each lives in one table). The tutoring split loses student, subject → tutor, as we saw.

11. Beyond BCNF: 4NF in One Example

Some repetition is not caused by FDs at all. A teacher can teach several subjects and speak several languages, and the two lists have nothing to do with each other:

  teacher | subject | language
  Meera   | DBMS    | English
  Meera   | DBMS    | Kannada
  Meera   | OS      | English
  Meera   | OS      | Kannada

The only key is all three columns, and there are no FDs, so this table is in BCNF. Yet adding a third language means adding two rows (one per subject). This is a multi-valued dependency: a teacher has a set of subjects and, separately, a set of languages.

4NF says: put independent lists in separate tables. teacher_subjects(teacher, subject) and teacher_languages(teacher, language). Adding a language is now one row.

Higher forms (5NF and beyond) exist, but tables that are in BCNF and avoid independent lists like this are well designed for nearly all real work.

12. From an ER Diagram to Tables

In practice, people often design a schema from an ER diagram (Entity-Relationship diagram) first. An entity is a thing you store facts about (customer, product). A relationship is how two entities are linked (a customer places orders). The cardinality says how many of each side can be linked.

  CUSTOMER 1 ----< places >---- N ORDER N ----< contains >---- M PRODUCT
                                                  |
                                                 qty

Three rules turn any diagram into tables:

RelationshipExampleTables
1 to N (one-to-many)One customer, many ordersPut a foreign key on the "many" side: orders.customer_id
N to M (many-to-many)An order has many products; a product is in many ordersA new junction table with both foreign keys as its key: order_items(order_id, product_id, qty). Facts about the link itself (qty) live here.
1 to 1A user and their profile settingsForeign key on either side with a UNIQUE constraint, or simply merge into one table

If you draw the ER diagram well, the tables you get are usually already in 3NF. Normalization is then a check that you did not miss anything.

13. When to Denormalize on Purpose

Denormalization means adding repetition back on purpose, usually to make reads faster. A normalized design needs joins. Joins are fast with good indexes (see Indexing & Query Plans), but at very large scale, or for a screen that is read millions of times, a pre-joined copy can be worth it.

First: some "copies" are not repetition at all

Look at unit_price. If it lives only in products, then raising the pen's price to 25 would silently change the total of every old order. That is wrong. The price paid on that day is a different fact from the current price. So order_items should have its own unit_price column. The same goes for a shipping address on an order: it is "where this order was sent", not "where the customer lives now". Ask "is this the same fact, or a snapshot of it at a moment in time?"

Common, reasonable denormalizations

  • Stored totals and counters: keep orders.total or posts.comment_count instead of summing every time. You must update it in the same transaction as the rows it summarises (see Transactions), or it will drift.
  • Materialized views: the database stores the result of a join or summary and you refresh it on a schedule. Good for dashboards that may be a few minutes old.
  • Read models and caches: a search index or a cache that holds a ready-made "order page" built from the normalized tables. The normalized tables stay the source of truth.
  • Analytics tables: data warehouses often use a star schema: one big "fact" table (one row per sale) surrounded by "dimension" tables (date, product, store). It repeats on purpose because analysts scan huge amounts of data and rarely update it.
Rule of thumb: normalize first (to BCNF or 3NF). Denormalize only for a measured, specific slow read, and write down which table is the source of truth and how the copy is kept in sync.

14. Lab: Build the Shop Schema

Save this as shop.sql and run it with sqlite3 shop.db < shop.sql, or paste it into any SQLite tool. For PostgreSQL, remove the PRAGMA line (PostgreSQL always checks foreign keys).

PRAGMA foreign_keys = ON;   -- SQLite only: turn on foreign key checks

CREATE TABLE customers (
  customer_id   INTEGER PRIMARY KEY,
  name          TEXT NOT NULL,
  city          TEXT NOT NULL
);

CREATE TABLE products (
  product_id    TEXT PRIMARY KEY,
  name          TEXT NOT NULL,
  price         INTEGER NOT NULL CHECK (price >= 0)   -- current price, in rupees
);

CREATE TABLE orders (
  order_id      INTEGER PRIMARY KEY,
  order_date    TEXT NOT NULL,
  customer_id   INTEGER NOT NULL REFERENCES customers(customer_id)
);

CREATE TABLE order_items (
  order_id      INTEGER NOT NULL REFERENCES orders(order_id),
  product_id    TEXT    NOT NULL REFERENCES products(product_id),
  qty           INTEGER NOT NULL CHECK (qty > 0),
  unit_price    INTEGER NOT NULL,          -- price paid on that day (a separate fact)
  PRIMARY KEY (order_id, product_id)
);

INSERT INTO customers VALUES (7, 'Asha', 'Pune'), (9, 'Ravi', 'Mysuru');
INSERT INTO products  VALUES ('P1', 'Pen', 20), ('P2', 'Notebook', 60), ('P3', 'Bag', 900);
INSERT INTO orders    VALUES (101, '2026-11-01', 7), (102, '2026-11-02', 9), (103, '2026-11-05', 7);
INSERT INTO order_items VALUES
  (101, 'P1', 3, 20), (101, 'P2', 2, 60),
  (102, 'P1', 1, 20), (102, 'P3', 1, 900),
  (103, 'P2', 5, 60);

-- Asha moves: ONE row changes, no matter how many orders she has.
UPDATE customers SET city = 'Bengaluru' WHERE customer_id = 7;

-- Rebuild the original wide view with joins.
SELECT o.order_id, c.name, c.city, p.name AS product, i.qty, i.unit_price,
       i.qty * i.unit_price AS line_total
FROM order_items i
JOIN orders    o ON o.order_id    = i.order_id
JOIN customers c ON c.customer_id = o.customer_id
JOIN products  p ON p.product_id  = i.product_id
ORDER BY o.order_id, p.product_id;

-- The database now refuses bad data:
INSERT INTO orders VALUES (104, '2026-11-06', 42);   -- no customer 42

Output (checked with SQLite 3.46):

order_id | name | city      | product  | qty | unit_price | line_total
101      | Asha | Bengaluru | Pen      | 3   | 20         | 60
101      | Asha | Bengaluru | Notebook | 2   | 60         | 120
102      | Ravi | Mysuru    | Pen      | 1   | 20         | 20
102      | Ravi | Mysuru    | Bag      | 1   | 900        | 900
103      | Asha | Bengaluru | Notebook | 5   | 60         | 300
Error: FOREIGN KEY constraint failed

Three things to notice:

  1. One UPDATE moved Asha in every order. The update anomaly is gone.
  2. A view can give people the old wide table back without storing it twice: CREATE VIEW order_lines AS SELECT ... (the query above).
  3. The foreign key stopped an order for a customer who does not exist. The big table could never do that.

15. Practice Problems

Work these out on paper. Answers follow each one.

Problem 1: closure

R(A, B, C, D, E, F) with FDs A → B C, C D → E, B → D, E → A. Find {A}+ and {E}+. Is A a key?

Answer: {A}+: A gives B, C → {A, B, C}; B gives D → {A, B, C, D}; C, D give E → {A, B, C, D, E}. F is never added. So A is not a key (F is missing). {E}+: E gives A, and then the same chain: {A, B, C, D, E}. Also not a key.

Problem 2: all candidate keys

Same table and FDs as Problem 1. Find every candidate key.

Answer: F appears on no right side, so F is in every key. {F}+ = {F}. Try adding one column: {A, F}+ = all, {E, F}+ = all (E gives A). {B, F}+ = {B, D, F}, no. {C, F}+ = {C, F}, no. {D, F}+ = {D, F}, no. Now try three columns without A or E: {C, D, F}+: C, D give E, E gives A, A gives B → all. {B, C, F}+: B gives D, then C, D give E → all. Each is minimal (no smaller part works). Candidate keys: {A, F}, {E, F}, {B, C, F}, {C, D, F}.

Problem 3: name the normal form

R(A, B, C, D) with FDs A B → C, C → D, D → A. Find the candidate keys and the highest normal form (up to BCNF).

Answer: B is on no right side, so it is in every key. {B}+ = {B}. {A, B}+ = {A, B, C, D}. {B, C}+ = {B, C, D, A}. {B, D}+ = {B, D, A, C}. Keys: {A, B}, {B, C}, {B, D}. Every column is prime. 3NF: every FD's right side (C, D, A) is prime, so 3NF holds. BCNF: C → D has C, which is not a superkey, so not BCNF. Highest form: 3NF.

Problem 4: normalize a library

loans(member_id, member_name, book_id, title, author, loan_date, due_date). One member can borrow the same book on different days. Rules: member_id decides member_name; book_id decides title and author; (member_id, book_id, loan_date) decides due_date. Give a BCNF design.

Answer: The key is (member_id, book_id, loan_date). member_name depends on only member_id and title, author on only book_id: partial dependencies, so it is not even 2NF. Split:

  members(member_id, member_name)                         key: member_id
  books(book_id, title, author)                           key: book_id
  loans(member_id, book_id, loan_date, due_date)          key: (member_id, book_id, loan_date)

Every FD now has a key on its left side, so all three tables are in BCNF. (In real life, book_id would be a physical copy, and title and author would move to a separate "titles" table, because a library has many copies of one book.)

Problem 5: lossless or not?

R(A, B, C) with FD B → C. Is the split R1(A, B), R2(B, C) lossless? What about R1(A, C), R2(B, C)?

Answer: First split: shared column B is a key of R2(B, C) because B → C. Lossless. Second split: shared column C. C does not decide A or B, so it is not a key of either piece. Lossy.

Problem 6: denormalize or not?

A social app shows "1,204 likes" under every post. Counting rows in a likes table for every post on every screen is slow. What would you do, and what must you be careful about?

Answer: Add a like_count column to posts. Keep the likes table as the source of truth (it stops double likes with a key on (user_id, post_id)). Update the counter in the same transaction as the insert or delete into likes, using UPDATE posts SET like_count = like_count + 1 so two likes at the same moment do not overwrite each other (a lost update; see Transactions). Run a nightly job that recounts and fixes any drift.

16. Common Pitfalls

  • Guessing FDs from sample data. Five rows where every city has one pin code does not mean city decides pin code. Ask what the business rules are.
  • Lists in a text column ("P1,P3,P7"). You lose indexes, foreign keys, and simple queries. Use a junction table.
  • Pointing old orders at the current price. Store the price paid on the order line. The same applies to addresses, tax rates, and exchange rates.
  • Over-splitting. Splitting a table into pieces that have no repeated facts (for example, moving first_name and last_name into separate tables) adds joins and gains nothing.
  • Lossy splits. Always split so the shared columns are a key of one piece.
  • Forgetting constraints. A normalized design only protects you if you declare PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, and CHECK. Without them, the app has to get it right every time.
  • Missing indexes on foreign keys. PostgreSQL does not index foreign key columns for you. Joins and deletes on the parent table can become slow. Add an index on orders(customer_id) and similar columns.
  • Denormalizing without a sync plan. Copies drift. Decide who updates them and how drift is found and fixed.

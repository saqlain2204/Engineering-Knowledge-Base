1. Why Pipelines Exist

Imagine releasing software by hand: someone runs the tests (if they remember), builds the app on their own laptop, copies it to a server, and restarts it. Every step can go wrong, and every release is a little different. People then release rarely, so each release is big and scary.

Intuition: A pipeline is a factory assembly line for code. Every change goes through the same stations in the same order: check, test, package, ship. A broken part is stopped at the station that finds it, not discovered by a customer.

With a pipeline, releasing becomes boring and safe, so teams release small changes often. Small changes are easier to test and easier to undo.

3. CI Step by Step: a GitHub Actions Workflow

GitHub Actions runs pipelines defined in YAML files inside your repository, in the folder .github/workflows/. The parts:

  • on: which events start it (a pull request, a push to main, a schedule).
  • jobs: groups of steps. Jobs run in parallel unless one needs another.
  • runs-on: the kind of machine (runner) the job uses.
  • steps: either uses: (a ready-made action, like checking out the code) or run: (a shell command).

Here is a complete workflow for a Python API that also ships a model. It runs tests on every pull request, runs a model quality gate (section 8), and on a push to main builds an image and pushes it to the GitHub container registry:

name: ci

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write

env:
  IMAGE: ghcr.io/${{ github.repository }}/api

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
      - run: pip install -r requirements.txt
      - run: ruff check .
      - run: pytest -q

  model-gate:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - run: python gate.py   # exits 1 if the new model is worse

  build-and-push:
    needs: [test, model-gate]
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ${{ env.IMAGE }}:${{ github.sha }}

We checked this file with actionlint 1.7.7, a linter for GitHub Actions workflows. Result: no problems found.

Read it line by line

  • permissions: gives the job's built-in token only what it needs: read the code, write packages. The default can be broader; always narrow it.
  • cache: pip reuses downloaded Python packages between runs, so CI is faster.
  • needs: [test, model-gate] means the image is only built if tests and the gate pass.
  • if: github.event_name == 'push' means pull requests are tested but never pushed to the registry.
  • The image tag is the commit SHA (${{ github.sha }}), the unique ID of the commit. Never deploy a tag like latest: it changes over time, so you cannot tell what is running or go back to it. A SHA tag always points to exactly one build.
Golden rule: build once, promote the same artifact. The exact image tested in staging is the one that goes to production. Never rebuild for production. See also Docker in CI/CD for scanning and signing images.

4. CD: Getting the Image onto Kubernetes

Push style vs pull style

  • Push: the CI job runs kubectl apply or helm upgrade against the cluster. Simple, but CI now holds powerful cluster credentials, and nobody notices if someone changes the cluster by hand.
  • Pull (GitOps): the desired Kubernetes YAML lives in a Git repository. A controller inside the cluster (Argo CD or Flux) watches that repository and applies changes. CI only needs permission to commit to Git. Every change is a reviewed commit, and rollback is git revert.

The Kubernetes side

A Deployment and Service for the API. CD changes only one line: the image tag.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  labels:
    app: api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: ghcr.io/acme/shop/api:3f2c1d9   # CD changes only this line
          ports:
            - containerPort: 8000
          readinessProbe:
            httpGet:
              path: /healthz
              port: 8000
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              memory: 512Mi
---
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api
  ports:
    - port: 80
      targetPort: 8000

maxUnavailable: 0 and maxSurge: 1 mean: start one new pod, wait until its readiness probe passes, then remove one old pod, and repeat. Capacity never drops. (Deployments and probes are explained in Workloads.)

The GitOps side: an Argo CD Application

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/acme/shop-deploy
    targetRevision: main
    path: k8s
  destination:
    server: https://kubernetes.default.svc
    namespace: shop
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
  • automated: apply changes as soon as they land in Git.
  • selfHeal: true: if someone edits the cluster by hand, Argo CD puts it back to match Git. This is called fixing drift (here meaning config drift, not data drift).
  • prune: true: delete resources that were removed from Git.

The last CI step then becomes: "change the image tag in the deploy repo and commit". Tools like Argo CD Image Updater or a small script can do this.

5. Release Strategies and Rollbacks

Every strategy below replaces pods, so each one depends on pods starting and stopping cleanly. How maxSurge and maxUnavailable pace a rolling update is worked step by step in Rolling Updates, Step by Step, and a measured walkthrough of why releases cause 502 errors is in Scenario: Errors During Every Deploy.

StrategyHow it worksGoodWatch out
RollingReplace pods a few at a time (the Deployment above)Built in, no extra capacityOld and new versions run side by side for a while, so both must work with the same database and APIs
Blue-greenRun the full new version ("green") next to the old ("blue"), then switch all traffic at onceInstant switch and instant rollbackNeeds double capacity during the switch
CanarySend a small share of traffic (say 10%) to the new version, watch metrics, then increaseA bad release hurts only a few usersNeeds good metrics to judge the canary
Feature flagsShip the code turned off, switch it on in configSeparates deploying from releasingOld flags pile up; clean them

A canary with Argo Rollouts

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: api
spec:
  replicas: 10
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: ghcr.io/acme/shop/api:3f2c1d9
  strategy:
    canary:
      steps:
        - setWeight: 10
        - pause: {duration: 10m}
        - setWeight: 50
        - pause: {duration: 10m}

This sends 10% of traffic to the new version, waits 10 minutes, goes to 50%, waits again, then finishes. Argo Rollouts can also run automatic analysis (for example, query Prometheus for the error rate) and abort if the canary looks worse.

Rolling back

# plain Deployment: go back to the previous revision
kubectl rollout undo deployment/api
kubectl rollout status deployment/api

# GitOps: revert the commit that changed the tag; Argo CD syncs the old tag back
git revert <commit-sha> && git push

With GitOps, prefer the git revert route. If you only run kubectl rollout undo, Git still says "new version", and self-heal will put the bad version right back.

6. Secrets and Permissions in Pipelines

  • Never put passwords or keys in the workflow file or the repo. Use the CI system's secret store (in GitHub: repository or environment secrets).
  • Prefer short-lived credentials. GitHub Actions can prove its identity to AWS, Google Cloud, or Azure with OIDC (a standard way to issue short-lived identity tokens). The cloud gives the job a token valid for minutes, so there is no long-lived key to leak.
  • Least privilege: set permissions: in every workflow, and give deploy jobs access only to their own environment.
  • Protect production: GitHub environments can require a reviewer's approval before a job that deploys to production runs.
  • Pin third-party actions to a version tag or, safer, a full commit SHA, so a hijacked action cannot change under you.
  • Pull request code from forks does not get your secrets by default. Keep it that way.

7. What Changes for Machine Learning (MLOps)

A normal app's behaviour is set by its code. An ML system's behaviour is set by code + data + trained model. Any of the three can change and break things. MLOps is CI/CD extended to cover data and models.

                  |
  data (version) -+--> training pipeline --> model + metrics --> quality gate
                  |        (tracked run)                          |  pass
  config/params --+                                               v
                                                           model registry
                                                    (v12: "staging" -> "production")
                                                                  |
                                                                  v
                                                   serving on Kubernetes -> monitoring
                                                                  |
                                    drift or new data -> retrain (continuous training)

Data versioningKnow exactly which data trained which model; be able to get it backDVC, lakeFS, versioned tables (Delta Lake, Iceberg)

For LLM apps (prompts, RAG, agents), the "model" step is often a new prompt, a new retrieval setup, or a new base model version. The same rules apply: version it, evaluate it in CI, release gradually. See Evaluation and LLMOps and Monitoring.

8. A Model Quality Gate (Real Run)

Unit tests check code. A quality gate checks the model: it scores the new ("candidate") model on a fixed, versioned test set and blocks the release if it is worse than the model in production.

Here is a small gate using the breast cancer classifier from Classical ML from Zero. Two candidates are trained with different regularisation strength C (smaller C means a simpler, more constrained model). The rule: accuracy must be at least 0.95, and recall (the share of cancers caught) must not drop by more than 0.01.

"""Model quality gate: exit 1 if the candidate model is worse than production."""
import sys, warnings; warnings.filterwarnings("ignore")
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression
from sklearn.preprocessing import StandardScaler
from sklearn.pipeline import make_pipeline
from sklearn.metrics import accuracy_score, recall_score

d = load_breast_cancer(); X, y = d.data, 1 - d.target      # 1 = malignant
Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.25, random_state=42, stratify=y)

def train(n_rows, C):
    return make_pipeline(StandardScaler(), LogisticRegression(C=C, max_iter=1000)).fit(Xtr[:n_rows], ytr[:n_rows])

def score(m):
    p = m.predict(Xte); return accuracy_score(yte, p), recall_score(yte, p)

prod_acc, prod_rec = score(train(n_rows=426, C=1.0))      # model in production today
for name, cand in [("candidate A", train(426, C=0.01)), ("candidate B", train(426, C=10.0))]:
    acc, rec = score(cand)
    ok = acc >= 0.95 and rec >= prod_rec - 0.01
    print(f"{name}: acc={acc:.4f} recall={rec:.4f} | prod acc={prod_acc:.4f} recall={prod_rec:.4f} -> {'PASS' if ok else 'FAIL'}")

Real output (scikit-learn 1.9.1):

candidate A: acc=0.9510 recall=0.8679 | prod acc=0.9650 recall=0.9245 -> FAIL
candidate B: acc=0.9650 recall=0.9245 | prod acc=0.9650 recall=0.9245 -> PASS

Candidate A would have missed about 6 more cancers in every 100 (recall 0.8679 versus 0.9245). Its accuracy alone (0.951) still looks fine, which is exactly why the gate checks recall, the metric that matches the real cost. In a real pipeline the script ends with sys.exit(1) on FAIL, so the CI job turns red and the build-and-push job never runs.

Gate design tips: keep the test set fixed and versioned (otherwise scores move for reasons other than the model); compare against the current production model, not a fixed old number; check slices (for example each customer region), not only the average; and leave a small tolerance for noise.

9. Serving Models on Kubernetes

Where does the model file live?

  • Baked into the image: one artifact, simple rollbacks. But images get huge (LLM weights are many GB) and every model update needs a new image.
  • Downloaded at start-up from a model registry or object storage (an init container or the server itself fetches it). Small images, models change independently. Pin the exact model version in config, never "latest".
  • On a shared volume that many pods mount. Avoids downloading the same big file on every pod start.

Model-serving platforms

KServe adds an InferenceService resource: you say "serve this model from this storage path with this runtime", and it creates the Deployment, Service, autoscaling, and canary routing for you:

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: cancer-screen
spec:
  predictor:
    model:
      modelFormat:
        name: sklearn
      storageUri: s3://models/cancer-screen/v12

For LLMs, the model server is usually vLLM or a similar engine on GPU nodes. See Serving an LLM on Kubernetes. Always give model servers a startupProbe with enough time to load the model, or Kubernetes will kill them mid-load.

10. Monitoring Models: Drift and PSI

Normal app monitoring asks "is it up, is it fast, is it erroring?" A model can be up, fast, and error-free while giving wrong answers. So model monitoring adds more layers:

LayerExamples
SystemCPU, memory, GPU use, pod restarts
ServiceRequests per second, latency, error rate
DataMissing values, value ranges, input distributions
ModelPrediction distribution, confidence, and (when labels arrive later) accuracy and recall

Kinds of drift

  • Data drift (covariate shift): the inputs change. New customers are younger; a sensor is replaced.
  • Label drift (prior shift): how common each answer is changes. Fraud rises during a holiday sale.
  • Concept drift: the relationship itself changes. The same behaviour that meant "safe" last year now means "fraud".
  • Pipeline bugs: not real-world change at all, but broken data: a unit change, a renamed column, nulls filled with zero. In practice these are very common.

PSI: one number for "has this distribution moved?"

The Population Stability Index compares a feature's distribution now with a reference (usually the training data):

  1. Split the reference values into bins (often 10 bins with equal counts).
  2. For each bin, find the share of reference values \(r_i\) and the share of current values \(c_i\) that fall in it.
  3. Add up:

\[ \text{PSI} = \sum_i (c_i - r_i)\,\ln\frac{c_i}{r_i} \]

Worked example with 2 bins. Reference shares 0.5 and 0.5; current shares 0.8 and 0.2.

\[ (0.8-0.5)\ln\frac{0.8}{0.5} + (0.2-0.5)\ln\frac{0.2}{0.5} = 0.3 \times 0.470 + (-0.3)\times(-0.916) = 0.141 + 0.275 = 0.416 \]

A common rule of thumb: below 0.1 means little change, 0.1 to 0.25 moderate, above 0.25 a big shift worth investigating. Treat these as starting points: with small samples, PSI is noisy (you will see this below).

Other tools: the KS test (Kolmogorov-Smirnov, a statistical test for "are these two samples from the same distribution?") and simple checks like "share of nulls" or "value outside the training range".

11. Scenario: the Model That Quietly Got Worse

This walkthrough uses real runs. The model is the logistic regression cancer classifier from Classical ML from Zero (an educational dataset, not a medical tool). The "production traffic" is its 143-row test set, with a bug injected exactly as described.

The situation

The model has served well for months: accuracy 0.9650, recall 0.9245, and it flags 34.97% of cases as malignant. An upstream team changes how the imaging system exports area measurements. All three area features ("mean area", "area error", "worst area") now arrive 100 times smaller. No error is raised. Every request still returns HTTP 200 in normal time.

Step 1: what the model now does (measured)

MetricBeforeAfter the upstream change
Accuracy0.96500.9021
Recall (cancers caught)0.9245 (49 of 53)0.7358 (39 of 53)
Missed cancers (FN)414
Share flagged malignant34.97%27.27%

The model misses 10 more cancers out of 53. But true labels (biopsy results) arrive weeks later, so on day one nobody can see the accuracy and recall columns. Service dashboards look perfect.

Step 2: label-free signals that would have caught it

  • Prediction distribution: the share flagged malignant fell from 34.97% to 27.27%. An alert on "positive rate moved more than X" fires the same day.
  • PSI of the model's output probability: 0.370 against the training data, versus 0.048 for the healthy test set. Well above the 0.25 rule of thumb.
  • Per-feature PSI:
PSI mean area:            8.265
PSI area error:           8.265
PSI worst area:           8.265
PSI worst texture:        0.129   <- largest of the 27 untouched features
PSI concave points error: 0.118

Three features score 8.265, far above anything else: every value fell into the lowest bin. Notice that untouched features reached 0.129 just from sampling noise with only 143 rows, which is above the 0.1 rule of thumb. That is why alert thresholds should be set from what normal days look like, not copied blindly.

Step 3: find the root cause

The three drifted features have the same unit (area). The mean of "mean area" fell from 660.1 in training to 6.39 in production: exactly a factor of 100. Checking the upstream change log reveals the export change.

Step 4: fix and prevent

  1. Fix now: convert the units back at the input boundary (we re-ran it: accuracy returns to 0.9650), or roll back the upstream change.
  2. Data contract: validate every request against expected types and ranges (for example "mean area between 100 and 3000"). Reject or flag out-of-range inputs instead of predicting on them.
  3. Alerts: per-feature PSI and prediction-rate alerts, with thresholds tuned on normal days.
  4. Add a test to CI that sends a known input and checks the prediction, so a schema change upstream fails a pipeline rather than patients.

A subtler lesson from the same data

We first tried breaking only "mean area". Accuracy stayed at 0.9650 (recall dipped from 0.9245 to 0.9057), because other features carry similar information. Yet that feature's PSI was already 8.265. The model was running on broken input and looked fine. Silent bugs like this become loud the moment another feature drifts. Monitor inputs, not only outputs.

Show the code used for this scenario 
import numpy as np
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression
from sklearn.preprocessing import StandardScaler
from sklearn.pipeline import make_pipeline
from sklearn.metrics import accuracy_score, recall_score

d = load_breast_cancer(); X, y, names = d.data, 1 - d.target, d.feature_names
Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.25, random_state=42, stratify=y)
m = make_pipeline(StandardScaler(), LogisticRegression(max_iter=1000)).fit(Xtr, ytr)

def psi(ref, cur, bins=10):
    edges = np.quantile(ref, np.linspace(0, 1, bins + 1)); edges[0], edges[-1] = -np.inf, np.inf
    r = np.histogram(ref, edges)[0] / len(ref); c = np.histogram(cur, edges)[0] / len(cur)
    r, c = np.clip(r, 1e-4, None), np.clip(c, 1e-4, None)   # avoid log(0)
    return float(((c - r) * np.log(c / r)).sum())

area = [j for j, n in enumerate(names) if "area" in n]
Xprod = Xte.copy(); Xprod[:, area] /= 100        # the upstream unit change
pred = m.predict(Xprod)
print(accuracy_score(yte, pred), recall_score(yte, pred), pred.mean())
for j in range(X.shape[1]):
    print(names[j], round(psi(Xtr[:, j], Xprod[:, j]), 3))
print(psi(m.predict_proba(Xtr)[:, 1], m.predict_proba(Xprod)[:, 1]))

12. A Real Pipeline: This Site's Own Checks

This knowledge base runs a small CI workflow of its own, in .github/workflows/site-checks.yml. On every pull request it:

  1. Rebuilds the search index and fails if the committed index is out of date (someone added a page but forgot to run the index script).
  2. Runs the link checker, which fails on any internal link or #anchor that does not exist.

It follows the rules on this page: read-only permissions, pinned action versions, and a clear error message that tells you the fix. See CONTRIBUTING.md.

13. Common Pitfalls

  • Deploying latest. You cannot tell what runs or roll back. Tag by commit SHA or digest.
  • Rebuilding per environment. Staging tested a different artifact than production runs.
  • Manual hotfixes in a GitOps cluster. Self-heal reverts them, or worse, they silently drift from Git.
  • Long-lived cloud keys in CI secrets. Use OIDC short-lived credentials.
  • Gates that only check average accuracy. Check the metric that matches the real cost, and important slices.
  • Monitoring only latency and errors for models. Wrong answers return HTTP 200. Watch input and prediction distributions.
  • Copying drift thresholds blindly. Tune them on normal days for your traffic volume.
  • No owner for alerts. An alert nobody reads is the same as no alert.

14. Practice Problems (with Solutions)

Problem 1: delivery or deployment?

Every merge to main builds and tests an image and deploys it to staging automatically. Production needs a manager to click "approve". Is this continuous delivery or continuous deployment?

Solution

Continuous delivery. Every change is ready to release, but a human decides when it goes to production. In continuous deployment, production would update automatically.

Problem 2: compute PSI

A feature has 3 bins. Training shares: 0.2, 0.5, 0.3. Today's shares: 0.1, 0.5, 0.4. Compute PSI and say whether to worry.

Solution

Bin 1: (0.1 - 0.2) × ln(0.1/0.2) = (-0.1) × (-0.693) = 0.0693. Bin 2: 0 (no change). Bin 3: (0.4 - 0.3) × ln(0.4/0.3) = 0.1 × 0.2877 = 0.0288. Total = 0.098. Under the 0.1 rule of thumb: a small change. Keep watching, especially if it keeps growing day after day.

Problem 3: the bad rollback

Your cluster uses Argo CD with self-heal. A release breaks production, so an engineer runs kubectl rollout undo deployment/api. Two minutes later the broken version is back. Why, and what should they do?

Solution

Git still holds the new (broken) image tag. Argo CD sees the cluster differs from Git and "heals" it back to the broken version. Revert the commit in the deploy repo (git revert), so Git itself points at the old tag.

Problem 4: design the gate

You ship a spam filter. Losing a real email (false positive) is much worse than letting some spam through. Write a simple gate rule for a new model.

Solution

Example: on the fixed test set, the candidate's precision must be at least the production model's precision minus a small tolerance (say 0.005), and its recall must be at least a floor (say 0.90). Also check precision on important slices, such as emails from known contacts.

Problem 5: what to monitor first

A loan-approval model's true outcomes (did the borrower repay?) are known only after 12 months. What can you monitor from day one?

Solution

Input data quality (nulls, ranges, schema), per-feature drift (PSI or KS against training data), the prediction distribution (approval rate, score distribution, PSI of scores), and service health. Use early proxy labels if any exist (for example, first missed payment) before the full outcome arrives.

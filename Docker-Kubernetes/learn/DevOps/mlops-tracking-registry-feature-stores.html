Experiment Tracking, Model Registry & Feature Stores

Three questions come up in every ML team. "Which settings and data made this model?" "Which model is running in production right now, and how do we roll it back?" "Why does the model score well offline but badly for real users?" This page explains the three tools that answer them: experiment tracking, a model registry, and a feature store. It goes deeper than the overview in CI/CD and MLOps, and every number comes from a run you can repeat.

1. Why These Tools Exist

Normal software has one moving part: code. Git tracks it. An ML system has three moving parts: code, data, and the model (the file that training produces). Git alone tracks only the first.

   code (git)  ─┐
   data         ─┼─► training run ─► model file ─► registry ─► serving
   settings     ─┘        │                           │            │
                          ▼                           ▼            ▼
                 experiment tracking:        "version 7 is      features at request
                 params, metrics, files      champion"          time must match the
                                                                features used in training
                                                                (feature store)

Intuition. A lab scientist keeps a notebook: what they mixed, how much, at what temperature, and what happened. Without it, a great result cannot be repeated. Experiment tracking is that notebook. The model registry is the shelf of labelled, approved samples. The feature store makes sure the kitchen uses the same recipe as the lab.

2. The Words, in Plain English

WordMeaning
RunOne training attempt, with its settings, results and output files.
ExperimentA named group of runs that try to solve the same problem.
Parameter (param)A setting you chose for a run, like learning rate or tree depth.
MetricA number that measures the result, like validation AUC.
ArtifactA file a run produced: the model, a plot, a list of features.
LineageThe chain that says where something came from: model version 7 came from run X, which used commit Y and data snapshot Z.
Registered model / versionA named model in the registry ("fraud-detector"), with numbered versions 1, 2, 3...
AliasA movable name tag pointing at one version, like champion or challenger.
FeatureAn input number for the model, like "average spend in the last 30 days".
EntityThe thing a feature describes: a user, a card, a product.
Training-serving skewA feature has a different value (or meaning) in production than it had in training.
Point-in-time joinAttaching to each training example the feature values as they were at that moment, not as they are today.

3. What Makes a Run Reproducible

To train the same model again, you need five things. Missing any one is a common reason a "great model from last month" cannot be rebuilt.

IngredientHow to pin itExample
CodeGit commit hash3f2a9c1
DataA snapshot path plus a content hash, or a data versioning tool (DVC, lakeFS, table snapshots)s3://ml/fraud/2026-11-01/, sha256 9b1e...
SettingsAll params logged, config file saved as an artifactC=1.0, max_iter=1000
EnvironmentA lock file of exact library versions, or a container image digestscikit-learn==1.9.1, image @sha256:...
RandomnessFixed seeds for splits, initialisation and samplingrandom_state=0

Even then, GPU training can differ in the last digits from run to run (the order of floating-point additions changes). Aim for "same metrics within noise", not "same bytes".

A content hash is one line of Python:

import hashlib
digest = hashlib.sha256(open("train.parquet", "rb").read()).hexdigest()
# log it with the run, e.g. mlflow.set_tag("data_sha256", digest)

If anyone changes one byte of the file, the hash changes, so you can prove two runs used the same data.

4. Experiment Tracking (Real MLflow Run)

MLflow is a popular open-source tracker (Weights & Biases and cloud ML platforms do the same job). Your training code calls a few functions, and the tracker stores everything in a database plus file storage, with a web page to compare runs.

This script trains three logistic regression models on the breast cancer data (same data as in Classical ML from Zero) with different regularisation strengths C, logs each run, registers the best, and loads it back by alias:

import mlflow
from mlflow import MlflowClient
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.metrics import roc_auc_score

mlflow.set_tracking_uri("sqlite:///mlflow.db")      # a real team uses a shared server
mlflow.set_experiment("cancer-demo")

X, y = load_breast_cancer(return_X_y=True)
X_tr, X_val, y_tr, y_val = train_test_split(X, y, test_size=0.25, random_state=0, stratify=y)

best = None
for C in [0.01, 0.1, 1.0]:
    with mlflow.start_run(run_name=f"C={C}") as run:
        model = make_pipeline(StandardScaler(), LogisticRegression(C=C, max_iter=1000))
        model.fit(X_tr, y_tr)
        auc = roc_auc_score(y_val, model.predict_proba(X_val)[:, 1])
        mlflow.log_params({"C": C, "model": "logistic"})
        mlflow.log_metric("val_auc", auc)
        mlflow.set_tag("git_commit", "3f2a9c1")
        info = mlflow.sklearn.log_model(model, name="model")
        print(f"run {run.info.run_id[:8]}  C={C}  val_auc={auc:.4f}")
        if best is None or auc > best[0]:
            best = (auc, info.model_uri, C)

mv = mlflow.register_model(best[1], "cancer-classifier")
print("registered version", mv.version, "from C =", best[2])
MlflowClient().set_registered_model_alias("cancer-classifier", "champion", mv.version)

served = mlflow.sklearn.load_model("models:/cancer-classifier@champion")
print("loaded by alias; first 5 predictions:", served.predict(X_val[:5]))

Real output (MLflow 3.18, scikit-learn 1.9.1):

run 062ea0a0  C=0.01  val_auc=0.9849
run 2285bec3  C=0.1  val_auc=0.9929
run 5fc0b346  C=1.0  val_auc=0.9952
Successfully registered model 'cancer-classifier'.
Created version '1' of model 'cancer-classifier'.
registered version 1 from C = 1.0
loaded by alias; first 5 predictions: [1 0 0 1 0]

What you gain: six months later, anyone can open the tracker, sort runs by val_auc, and see that version 1 came from run 5fc0b346, with C=1.0, commit 3f2a9c1, and the exact model file.

Choose on validation, report on test. We picked the best of three runs by validation AUC. That number is now slightly optimistic, because we chose the winner by looking at it. With 3 runs the effect is tiny; with 300 runs it is not. Keep a separate test set, score the chosen model on it once, and report that number.

A small real-world catch we hit while writing this page: newer MLflow versions save scikit-learn models in a safer format (skops) and refuse, by default, to save some tree models, asking you to list the types you trust. That is a security feature: loading a model file can run code, so only load models from sources you trust.

5. The Model Registry: Versions and Aliases

The tracker records every run, including failures. The registry holds only the models you might ship, with a clear history:

registered model: fraud-detector
  version 5   from run a81c...   (retired)
  version 6   from run 3d07...   <── @champion    (production serves this)
  version 7   from run 5fc0...   <── @challenger  (shadow / canary)

Serving code never asks for "the latest version". It asks for an alias: models:/fraud-detector@champion. To ship version 7, you move the alias. To roll back, you move it back. No code change and no new image.

Older MLflow versions used fixed "stages" (Staging, Production, Archived). These are deprecated in favour of aliases, which are more flexible (you can have champion, challenger, eu-champion...). You will still see stages in older tutorials.

Each version should carry, as tags or a description: the run it came from (lineage), the data snapshot, evaluation results on the fixed test set, who approved it, and any known limits ("not tested on users under 18").

6. Promotion and Rollback, Step by Step

  1. Train (a scheduled job or a pipeline). Log the run.
  2. Register the candidate as a new version, for example version 7.
  3. Gate: an automatic check scores it on the fixed test set and compares it with the champion (see A Model Quality Gate). Fail = stop here.
  4. Set @challenger = 7. Run it in shadow mode (it sees real traffic, but its answers are only logged) or as a small canary.
  5. Compare live metrics for a few days.
  6. Promote: set @champion = 7. Serving pods load the new version on their next restart or reload.
  7. Rollback, if needed: set @champion = 6 and restart the serving pods.
client = MlflowClient()
client.set_registered_model_alias("fraud-detector", "champion", "7")   # promote
client.set_registered_model_alias("fraud-detector", "champion", "6")   # roll back
client.get_model_version_by_alias("fraud-detector", "champion").version

One caution: if pods resolve the alias only at start-up, different pods can serve different versions during a change. Log the model version with every prediction, so you always know which model made which decision.

7. Training-Serving Skew

A model learns the link between features as computed in training and the label. If production computes a feature even slightly differently, the model receives numbers that mean something else, and it has no way to know.

The usual cause is two pipelines: a data scientist computes features in SQL or pandas over history for training, and an engineer rewrites the same features in the serving service (Java, Go, or a different Python code path) for live requests.

  TRAINING (batch, over history)                SERVING (live, one request)
  SQL: AVG(amount) over last 30 days            service code: avg(last N days from cache)
  missing value -> filled with median           missing value -> filled with 0
  amounts in rupees                             amounts in paise (from the payments API)
  timezone: UTC                                 timezone: server local time
              └──────────── any difference = skew ────────────┘

Common kinds:

  • Logic skew: different windows, filters, rounding, units, default values, or time zones.
  • Data freshness skew: training used values computed a day later (with complete data), while serving sees values that are minutes old or still arriving.
  • Leakage skew: training features accidentally used information from after the prediction moment (next section), so they look better than anything serving can provide.

Skew is different from drift. Drift means the world changed (users behave differently). Skew means your two code paths disagree. Drift needs retraining; skew needs a bug fix.

8. Point-in-Time Joins, by Hand

To build a training set, you take labelled events ("this transaction turned out to be fraud") and attach feature values. The trap: you must attach the values as they were at the time of the event, not today's values.

Labelled events (what we want to learn from):

user_idevent timelabel (fraud?)
72026-03-02 09:000
72026-03-10 14:001

Feature history for user 7, "avg_amount_30d", recomputed every night at 00:00:

Feature timestampavg_amount_30d (rupees)
2026-03-02 00:00840
2026-03-10 00:00845
2026-03-11 00:002,950 (includes the fraud spree of 10 March)

Wrong (naive) join: take the latest value. Both rows get 2,950. The model learns "fraud rows have a high average", but that high value only exists because of the fraud. At prediction time, before the spree, the value is 845. This is data leakage: offline scores look great, production scores are poor.

Right: point-in-time join. For each event, take the latest feature value whose timestamp is at or before the event time:

EventLatest feature value at or before itValue used
2026-03-02 09:002026-03-02 00:00840
2026-03-10 14:002026-03-10 00:00845

Now the training row looks exactly like what the live model would have seen at 14:00 on 10 March. You can do this yourself with pandas:

import pandas as pd
events = pd.DataFrame({"user_id": [7, 7],
                       "ts": pd.to_datetime(["2026-03-02 09:00", "2026-03-10 14:00"]),
                       "label": [0, 1]})
feats = pd.DataFrame({"user_id": [7, 7, 7],
                      "ts": pd.to_datetime(["2026-03-02", "2026-03-10", "2026-03-11"]),
                      "avg_amount_30d": [840, 845, 2950]})
train = pd.merge_asof(events.sort_values("ts"), feats.sort_values("ts"),
                      on="ts", by="user_id", direction="backward")
print(train)   # avg_amount_30d: 840 and 845, never 2950

Two more details. A feature value can be too old to trust (a user inactive for a year); feature stores let you set a TTL (time to live) after which the value counts as missing. And if your nightly job finishes at 02:00, the value stamped 00:00 was not really available until 02:00; stamp features with the time they became available, or events between 00:00 and 02:00 will leak a little.

9. Feature Stores: Offline and Online

A feature store is a system that lets you define a feature once and then get it in two ways: as history for training, and as the latest value for serving.

                    feature definitions (code, in git)
                                 │
               ┌─────────────────┴──────────────────┐
               ▼                                    ▼
     OFFLINE STORE                         ONLINE STORE
     (data warehouse / files)              (Redis, DynamoDB, ...)
     full history with timestamps          only the latest value per entity
     point-in-time joins for training      millisecond lookups for serving
               │        "materialize": copy latest     ▲
               └────────── values offline ─► online ────┘
               ▼                                    ▼
        training job                         model server: get features
                                             for user_id=7 in ~5 ms

The key promise: both stores are filled from the same definition, so training and serving cannot drift apart through two hand-written versions of the logic. Popular options include Feast (open source), Tecton, Hopsworks, and the feature stores built into cloud ML platforms.

What it looks like in Feast

A sketch of a definition and the two ways to read it (Feast's Python API):

from datetime import timedelta
from feast import Entity, FeatureStore, FeatureView, Field, FileSource
from feast.types import Float32, Int64

user = Entity(name="user", join_keys=["user_id"])

user_stats = FeatureView(
    name="user_stats",
    entities=[user],
    ttl=timedelta(days=2),                       # older values count as missing
    schema=[Field(name="avg_amount_30d", dtype=Float32),
            Field(name="txn_count_7d", dtype=Int64)],
    source=FileSource(path="data/user_stats.parquet", timestamp_field="event_timestamp"),
)

store = FeatureStore(repo_path=".")           # after `feast apply` registered the definitions

# training: point-in-time join for every (user_id, event_timestamp) row in events_df
train_df = store.get_historical_features(
    entity_df=events_df, features=["user_stats:avg_amount_30d", "user_stats:txn_count_7d"]
).to_df()

# serving: latest values from the online store
online = store.get_online_features(
    features=["user_stats:avg_amount_30d", "user_stats:txn_count_7d"],
    entity_rows=[{"user_id": 7}],
).to_dict()

A scheduled job (on Kubernetes, a CronJob) runs feast materialize-incremental <now> to copy new values into the online store.

Do you need one?

SituationAdvice
One model, batch predictions (score everyone nightly)No. The same batch code makes training and scoring features. Use point-in-time joins in SQL or pandas.
Real-time predictions from features that are simple to compute from the requestProbably not. Share one feature function (one library) between training and serving.
Real-time predictions that need history (aggregates over days), several models sharing features, several teamsYes, this is where a feature store pays off.

10. Scenario: the Fraud Model That Missed Half the Fraud

This is a simulation you can run (code at the end of this section). The data is synthetic, but the failure is one of the most common in real ML systems.

The setup

A card-fraud model uses three features per user:

  • spike_ratio = log(average daily spend over the last 3 days ÷ average daily spend over the window). Fraudsters often spend much more than usual in a short burst, so this goes up.
  • txn_count_7d: number of transactions in the last 7 days.
  • log_account_age: log of account age in days.

In training, the "window" is 30 days (a SQL query over the warehouse). The model is a logistic regression trained on 40,000 users (about 5% fraud), flagging a user when its score is at least 0.5. Offline results on 20,000 new users are excellent.

For serving, an engineer re-implemented the feature in the payments service. The service's cache only kept 7 days of history, so the code used a 7-day window. Same feature name, same type, different meaning.

What happened in production

Metric (same 20,000 users)Offline (30-day window, as trained)Online (7-day window, the bug)
AUC0.9920.984
Precision at 0.50.9540.992
Recall at 0.50.8440.460
Share of users flagged4.54%2.38%
Mean spike_ratio0.0210.010

The model now catches 46% of fraud instead of 84%. Why so much? A 7-day average already contains the 3 spike days as a big share (3 of 7 days, instead of 3 of 30), so the average is pulled up and the ratio comes out smaller. Every fraudster looks "less spiky". Their scores fall, and many drop below the 0.5 threshold.

Why the dashboards stayed green

  • AUC barely moved (0.992 to 0.984). AUC measures ranking: are frauds scored above non-frauds? They still mostly are, just all lower. But decisions use a fixed threshold, and the scores slid under it.
  • Precision went up (0.954 to 0.992). Fewer flags, and the ones left are the most obvious frauds. On a dashboard that looks like an improvement.
  • Feature drift (PSI) on spike_ratio was 0.072, under the usual 0.1 alert line (see PSI). Most users are not fraudsters, and for them the 7-day and 30-day averages are similar, so the overall distribution hardly moves.
  • Recall needs labels, and fraud labels (chargebacks) arrive weeks later. So the drop showed up a month late, as a finance report about rising fraud losses.

The check that catches it on day one

Log the feature values the service actually used for each request. Every night, recompute the same features for the same users and times with the training code, and compare row by row:

rows where served value differs from recomputed value by more than 0.01: 92.7%

A row-level skew check like this fires immediately, even when distribution checks (PSI) and ranking metrics (AUC) look fine. A healthy pipeline is near 0% (small differences from timing are normal; set the alert at, say, 1%).

The fix and the follow-ups

  1. Hotfix: the service computes the 30-day window (the cache was extended to 30 days of daily totals, which is small).
  2. Root fix: the feature is defined once, in the feature store, and both training and serving read it from there.
  3. Guardrails: the nightly row-level skew check with an alert; logging of served features plus model version for every prediction; and a monitor on the share of users flagged (it fell from 4.5% to 2.4% on day one, a signal that does not need labels).

The code

import numpy as np
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.metrics import roc_auc_score, precision_score, recall_score

rng = np.random.default_rng(7)

def make(n):                                   # 30 days of daily spend per user
    age = rng.integers(1, 1500, n)
    fraud = rng.random(n) < 0.05
    base = rng.lognormal(6.5, 0.6, n)
    days = np.tile(base[:, None], (1, 30)) * rng.lognormal(0, 0.3, (n, 30))
    days[:, -3:] *= np.where(fraud, rng.uniform(1.3, 3.5, n), 1.0)[:, None]  # fraud burst
    count7 = rng.poisson(np.where(fraud, 6, 4))
    age = np.where(fraud, rng.integers(1, 600, n), age)
    return days, count7, age, fraud.astype(int)

def feats(days, count7, age, window):
    spike_ratio = np.log(days[:, -3:].mean(1) / days[:, -window:].mean(1))
    return np.c_[spike_ratio, count7, np.log(age)]

d, c, a, y = make(40000)
model = make_pipeline(StandardScaler(), LogisticRegression(max_iter=1000)).fit(feats(d, c, a, 30), y)

d2, c2, a2, y2 = make(20000)
for name, X in [("offline, 30-day", feats(d2, c2, a2, 30)), ("online, 7-day", feats(d2, c2, a2, 7))]:
    p = model.predict_proba(X)[:, 1]; flag = p >= 0.5
    print(f"{name}: AUC {roc_auc_score(y2, p):.3f} precision {precision_score(y2, flag):.3f} "
          f"recall {recall_score(y2, flag):.3f} flagged {flag.mean():.2%}")

off, on = feats(d2, c2, a2, 30)[:, 0], feats(d2, c2, a2, 7)[:, 0]
print(f"row-level skew: {np.mean(np.abs(on - off) > 0.01):.1%} of rows differ")

11. How It Fits on Kubernetes

  ┌───────────── Kubernetes cluster ─────────────────────────────────────────┐
  │                                                                          │
  │  CronJob: build-features ─► offline store (warehouse / object storage)   │
  │  CronJob: materialize    ─► online store (Redis StatefulSet or managed)  │
  │                                                                          │
  │  Job: train (GPU or CPU) ─► MLflow tracking server (Deployment)          │
  │                               ├─ metadata: PostgreSQL                    │
  │                               └─ artifacts: object storage (S3, GCS)     │
  │                                                                          │
  │  CI gate ─► set alias @champion = N                                      │
  │                                                                          │
  │  Deployment: model-server  (loads models:/fraud-detector@champion        │
  │                             at start; reads features from online store;  │
  │                             logs features + model version per request)   │
  │                                                                          │
  │  CronJob: skew-check (recompute features offline, compare, alert)        │
  └──────────────────────────────────────────────────────────────────────────┘
  • Run the tracking server as a normal Deployment with a database and object storage behind it; never keep its data on a pod's local disk.
  • Give training Jobs credentials to write to the tracker, and serving pods only to read the registry (see Config, Secrets & Security).
  • To roll out a new champion, change the alias and run kubectl rollout restart deployment/model-server. The rolling update (see Rolling Updates) swaps pods without downtime, and the readiness probe should only pass once the model is loaded.
  • For GPU models, see Serving an LLM on the GPU Scheduling page.

12. Common Pitfalls

  • Tracking only metrics. Without the data hash, code commit and environment, you know a run was good but not how to rebuild it.
  • Serving "latest". A new version appears in the registry and production picks it up without any gate. Always serve an alias that a person or a gate moves on purpose.
  • Two implementations of one feature. The classic source of skew. One definition, two readers.
  • Joining today's feature values onto old labels. Leakage. Use point-in-time joins.
  • Feature timestamps = computation start, not availability. A small, steady leak for events that happened while the job was still running.
  • Watching only AUC and PSI. As the scenario showed, both can stay calm while recall halves. Add row-level skew checks and a "share flagged" monitor.
  • Not logging served features. Then you cannot check skew, debug a single bad decision, or build the next training set from real serving data.
  • Loading model files from unknown sources. Pickle-based model files can run code when loaded. Only load what your own pipeline produced.
  • A feature store for one batch model. Extra systems to run, for no gain. Start with shared feature code and point-in-time SQL.

13. Practice Problems (with Solutions)

Problem 1: what is missing?

A run logged the code commit, all parameters and the metrics. A month later, retraining with the same commit and parameters gives AUC 0.91 instead of 0.95. Name two likely missing ingredients.

Solution

The data version (the table changed since then: new rows, fixed labels) and the environment (a library upgrade changed defaults). Seeds are a third candidate, though they usually cause smaller differences.

Problem 2: point-in-time join

Feature "orders_7d" for user 42: 3 at 2026-05-01 00:00, 5 at 2026-05-02 00:00, 9 at 2026-05-03 00:00. Labelled events: 2026-05-02 18:30 and 2026-05-03 00:00. Which value does each event get?

Solution

Take the latest value at or before the event. 2026-05-02 18:30 gets 5. 2026-05-03 00:00 gets 9 (timestamps equal, and "at or before" includes equal). If the 9 was only available at 02:00, its timestamp should say 02:00, and the second event would get 5.

Problem 3: rollback

Version 9 is @champion. Errors rise after the switch from version 8. Write the steps to roll back without building anything.

Solution

Set the alias back: set_registered_model_alias("fraud-detector", "champion", "8"). Restart the serving pods so they load it: kubectl rollout restart deployment/model-server. Check the model version in the prediction logs to confirm all pods serve version 8.

Problem 4: skew or drift?

(a) After a festival sale, average order value doubles for two weeks. (b) After a service rewrite, the "account_age_days" feature is in hours. Which one is skew and which is drift, and what is the fix for each?

Solution

(a) is drift: the world changed. Monitor, and retrain if the change lasts and hurts quality. (b) is skew: your serving code disagrees with training. Fix the code (or move the feature into the shared feature store); retraining would only teach the model the bug.

Problem 5: the threshold effect

Why can AUC stay nearly the same while recall at a fixed threshold drops by half?

Solution

AUC only checks the order of scores (are positives above negatives?). If skew lowers all fraud scores but keeps them mostly above the non-fraud scores, the order, and so AUC, hardly changes. Recall at 0.5 depends on the actual values: lowered scores fall under 0.5 and stop being flagged.

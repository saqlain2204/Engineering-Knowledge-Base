Infrastructure as Code

Servers, networks, and databases can be described in files, stored in git, reviewed like application code, and applied by a tool. That idea is infrastructure as code (IaC). This page starts with a leaky firewall rule made by a console click, then shows a small reconciler you can run, and only then walks through Terraform's plan, apply, and state file. It sits next to CI/CD and MLOps: CI is how the files get applied safely.

1. The Problem with Clicking in a Console

A team has a database that should only accept connections from the web subnet, 10.0.1.0/24, on port 5432. On Monday someone debugs a laptop connection and, in the cloud console, adds a rule: allow 0.0.0.0/0 on 5432. The bug is fixed. The rule stays. Nobody reviews it, because there is no diff. Three months later a scan finds a database on the public internet.

The same story happens in quieter ways:

  • Two environments, "staging" and "production," started the same and slowly stopped matching, because each change was clicked only in one of them.
  • A machine was created by hand, never recorded, and was missed by a backup policy.
  • After an incident, nobody can answer "what did we change last Thursday?"

Infrastructure as code treats the desired shape of the system as a set of files. A tool compares that shape to what really exists, shows a plan (create, update, delete), and only then applies it. The files go through the same review as application code.

Intuition. A console is a conversation you cannot replay. A file is a recipe. If the cake comes out wrong, you can read the recipe, see the last change, and bake it again the same way in another kitchen.

2. Words You Need

  • Desired state. What you said you want: three web servers on image app:1.4, a database, a tight firewall.
  • Actual state. What exists right now in the cloud or in the cluster.
  • Drift. The two states do not match. Someone clicked, a process failed halfway, or an auto-scaler changed a count.
  • Reconcile. Compute the difference and take the actions that make actual state match desired state.
  • Plan. A preview of those actions, without doing them yet.
  • Apply. Carry out the plan.
  • State file. The tool's own record of what it created and which real objects map to which resources in the files. Terraform's terraform.tfstate is the usual example.
  • Idempotent apply. Running apply twice with no changes the second time. The second plan is empty.
  • Provider. The plugin that talks to a particular API (one cloud, DNS, Kubernetes, and so on).

3. Imperative vs Declarative

An imperative script says how to do the work, step by step:

create_vpc()
create_subnet()
create_vm(count=3)
# if you run this again, it may try to create a second VPC
# and fail, or worse, create a duplicate

A declarative file says what you want, and leaves the how to the tool:

web: { count: 3, image: "app:1.4" }

If three servers already exist with that image, the tool does nothing. If two exist, it creates one. If the image is old, it updates them. Kubernetes manifests, Terraform configurations, and the lab below are declarative. Ansible can be used either way; many playbooks are a mix (declarative modules called in an imperative order).

Declarative does not mean "no danger." A file that says count: 0 will delete everything that used to be there. The plan is how you see that before it happens.

4. The Lab: A Tiny Reconciler

You do not need a cloud account to see the idea. We wrote a small Python program that treats dictionaries as "the infrastructure." Desired state is the file you would keep in git. Actual state is what we found after a week of console clicks.

desired = {
    "vpc":             {"cidr": "10.0.0.0/16"},
    "subnet-public":   {"cidr": "10.0.1.0/24", "in": "vpc"},
    "subnet-private":  {"cidr": "10.0.2.0/24", "in": "vpc"},
    "web":             {"count": 3, "image": "app:1.4",
                        "subnet": "subnet-public", "cpu_milli": 200},
    "db":              {"count": 1, "image": "postgres:16",
                        "subnet": "subnet-private", "cpu_milli": 500,
                        "disk_gb": 50},
    "firewall":        {"allow": ["10.0.1.0/24:5432"],
                        "deny":  ["0.0.0.0/0:5432"]},
}

# after a week of clicks:
#   - only 2 web servers, still on the old image
#   - the database port is open to the world
#   - a forgotten "old-worker" machine is still running
actual = {
    "vpc":             {"cidr": "10.0.0.0/16"},
    "subnet-public":   {"cidr": "10.0.1.0/24", "in": "vpc"},
    "subnet-private":  {"cidr": "10.0.2.0/24", "in": "vpc"},
    "web":             {"count": 2, "image": "app:1.3",
                        "subnet": "subnet-public", "cpu_milli": 200},
    "db":              {"count": 1, "image": "postgres:16",
                        "subnet": "subnet-private", "cpu_milli": 500,
                        "disk_gb": 50},
    "firewall":        {"allow": ["0.0.0.0/0:5432"], "deny": []},
    "old-worker":      {"count": 1, "image": "app:0.9",
                        "subnet": "subnet-public", "cpu_milli": 100},
}

def plan(desired, actual):
    creates, updates, deletes, same = [], [], [], []
    for name, spec in desired.items():
        if name not in actual:
            creates.append((name, spec))
        elif actual[name] != spec:
            updates.append((name, actual[name], spec))
        else:
            same.append(name)
    for name, spec in actual.items():
        if name not in desired:
            deletes.append((name, spec))
    return creates, updates, deletes, same

We ran plan(desired, actual). This is what it printed:

create:   (none)
update:   web       count 2 -> 3, image app:1.3 -> app:1.4
          firewall  allow 0.0.0.0/0:5432  ->  only 10.0.1.0/24:5432
                    deny  []              ->  0.0.0.0/0:5432
delete:   old-worker
unchanged: vpc, subnet-public, subnet-private, db

Three facts, all in one reviewable plan:

  1. The web tier has drifted (wrong count, old image).
  2. The firewall rule that was meant to be private is open to the world. This is the Monday debug rule from section 1, still sitting there.
  3. A machine that is not in the desired file still exists. The tool will delete it, which is what you want if the file is the source of truth, and dangerous if someone created it on purpose and never added it to the file.

We then applied the plan (copy desired values into actual, drop the extra resource). A second plan was empty: no creates, no updates, no deletes. That empty second plan is the test you want in real life too. If apply is not idempotent, the tool is not safe to run from CI.

What the lab is not. A real provider also has to deal with APIs that fail halfway, with delays ("the VM is still booting"), and with objects that other tools own. The comparison itself, though, is the same comparison Terraform makes when you run terraform plan.

5. Terraform: Plan, Apply, State

Terraform is the most common language for this kind of file when the resources live in a cloud API. A configuration looks like this (a sketch, not a full project):

resource "aws_security_group" "db" {
  name   = "db"
  vpc_id = aws_vpc.main.id

  ingress {
    description = "Postgres from the web subnet only"
    from_port   = 5432
    to_port     = 5432
    protocol    = "tcp"
    cidr_blocks = [aws_subnet.public.cidr_block]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

The usual commands:

terraform init     # download providers, set up the backend
terraform fmt      # rewrite the files in the standard style
terraform validate # catch syntax and some type errors
terraform plan     # show the diff, write a plan file if you ask
terraform apply    # carry out the plan (prefer: apply the saved plan)
terraform destroy  # tear down the resources in this configuration

A careful apply in a shared environment is two steps, not one:

terraform plan  -out=tfplan
# review the plan in the pull request
terraform apply tfplan

That way the apply cannot pick up a new change that landed between the review and the click. The plan file is the reviewed artifact, the same way a container image digest is the reviewed artifact in CI/CD.

Read a plan the way you read a code review: creates are usually easy, updates need a check for downtime (will this replace a database?), and deletes need a slow look. Terraform marks some updates as force new: it will destroy the object and create a replacement, because the cloud API cannot change that field in place. A force-new on a database is a migration, not a tidy metadata edit.

6. The State File Is Precious

Terraform maps each resource block to a real ID (a volume, a group, a DNS record) in a state file. Without state, the next plan cannot tell a resource it already created from a resource it still needs to create. That is how you get duplicates, or a plan that wants to build the world again from scratch.

Rules that prevent a bad day:

  • Store state remotely, with locking (for example an object store plus a lock table, or Terraform Cloud, or another backend that supports locks). Two applies at once on local state will corrupt it or double-create resources.
  • Do not commit state to git if it can contain secrets (and it often can: database passwords, private keys, attributes a provider wrote back). Remote state still needs tight access control.
  • Never hand-edit the state file to "fix" a plan, except with terraform state commands, and even then only when you understand the mapping you are changing.
  • If someone created an object in the console and you now want the file to own it, terraform import attaches the existing object to a resource block. If you skip import and just write the block, the next apply may create a second object, or fail, or (in a worse setup) replace the original.
  • If you delete a block from the file, the next apply will destroy the real object, unless you first remove it from state with terraform state rm (when you want to keep the object and stop managing it).

Drift can also be found with terraform plan when nobody has changed the files: the plan shows updates that bring the world back to the file. Some teams run that plan on a schedule and open a review if it is not empty. That is how the leaked firewall rule in the lab would have been caught, even if no one remembered the Monday click.

7. Modules, Workspaces, and Blast Radius

A module is a reusable folder of Terraform files with input variables and outputs. "A private database in this network" can be a module used by staging and by production, with different sizes. Modules are good when they hide repetition. They are bad when a single apply walks a module that can touch every environment at once.

Blast radius is the question: if this apply is wrong, how much can it break? Smaller states (one per environment, or even one per service) shrink the radius. One giant state for the whole company means a typo in a test resource can show up next to a production database in the same plan, and a lock on that state blocks everyone else.

Workspaces (named states for the same files) can separate environments, but they make it easy to run apply in the wrong one. Many teams prefer a separate directory or a separate pipeline for production, with a required review, rather than a workspace switch on a laptop.

8. Secrets Do Not Belong in the File

A password in a .tf file will end up in git, in the plan output, and often in state. Prefer:

  • A secret manager, and a data source that reads the secret at apply time.
  • Environment variables or a short-lived token for the provider itself.
  • Writing secrets into a store that the application reads, not into the repo.

Plans are also logs. A CI system that prints the full plan can leak a secret that a provider marked as sensitive, if you have not marked it yourself. Treat plan output as carefully as you treat build logs.

9. Terraform, Pulumi, Ansible, and Kubernetes

ToolYou writeGood forWatch out for
Terraform / OpenTofuDeclarative HCL (or JSON)Cloud resources, DNS, many providersState files, force-new replacements
PulumiTypeScript, Python, Go, and othersThe same kind of work, with general-purpose language toolsThe same state problem, plus the temptation to hide side effects in ordinary code
AnsibleYAML playbooks, often step by stepConfiguring servers, one-off operations, mixed fleetsScripts that are not idempotent; less native "plan" than Terraform
Kubernetes manifests / Helm / KustomizeDeclarative YAMLWorkloads already inside a clusterDoes not, by itself, create the cluster and the cloud around it
Crossplane and similarKubernetes resources that represent cloud objectsTeams that already live in the cluster APIYet another control loop to understand and secure

These tools combine. A common shape: Terraform (or similar) creates the cluster, the networks, and the databases. Helm or Kustomize describes the workloads. The CI pipeline in the CI/CD page glues the two together. Kubernetes itself is already a reconciler: you write a Deployment, the control plane keeps that many Pods running. The idea in section 3 is the same idea.

10. Plan on the Pull Request, Apply on Merge

A safe pipeline looks like this:

on pull request:
  terraform fmt -check
  terraform validate
  terraform plan -out=tfplan
  attach the plan to the review (or a bot comment)

on merge to the main branch (protected, required review):
  terraform apply tfplan     # the same plan, or a freshly made
                             # plan that is compared to the review

Production applies should need a human approval, and should use credentials that are not a developer's laptop. A laptop apply with admin rights is how "I only changed a tag" becomes "I destroyed a bucket," because the local files were on the wrong branch, or the wrong workspace was selected.

After a production incident, a temporary console change is sometimes the fastest mitigation. The follow-up, before the incident is closed, is to put that change in the file, review it, and apply it, so the next plan does not revert the fix. The lab's leaked firewall rule is what happens when that follow-up never comes.

11. Common Pitfalls

  • Applying without reading the plan. Especially deletes and force-new replacements.
  • Local state, no lock. Two people apply, state goes wrong, resources are duplicated or orphaned.
  • Secrets in git or in unsanitized plan logs.
  • One enormous state file. Huge blast radius, constant lock fights.
  • Changing the console and never importing or updating the file. The next apply may undo the fix, or the leak stays forever.
  • Using terraform destroy in production as a reflex. It means what it says.
  • A module default that is fine in staging and fatal in production (public IP, tiny backup window, open CIDR).
  • Ignoring a failed apply. Actual state and the state file may now disagree. The next plan is the start of the repair, not a second wild apply.

12. Practice Problems

Problem 1: read this plan

A plan says: update firewall (allow list changes from 10.0.1.0/24:5432 to 0.0.0.0/0:5432), no other changes. The pull request title is "open Postgres for a debug session." Do you approve? What would you ask for instead?

Answer: Do not approve a permanent public allow-list for a database. If a temporary opening is truly needed, prefer a short-lived, IP-specific rule, a jump host, or a tunnel, and put a time limit or a follow-up task in the same review so the next apply is guaranteed to close it. The lab in section 4 is this change, left to rot.

Problem 2: empty second plan

You apply a configuration. You immediately run plan again, with no file changes. The second plan still wants to update a tag on a resource, every time. What is going on?

Answer: The apply is not idempotent. Common causes: a tag or attribute the provider recomputes (a timestamp, a computed fingerprint), a default you did not set in the file, or a bug in the provider. Until the second plan is empty, CI will always look "dirty," and you cannot trust drift detection.

Problem 3: an object the file does not mention

In the lab, old-worker is in actual state but not in desired state, so the plan deletes it. When is that correct, and when is it a disaster? What command would you use if you want Terraform to forget the object but leave it running?

Answer: It is correct if the file is the source of truth and the machine is leftover waste. It is a disaster if the machine holds data and was never added to the file. If you want to keep it and stop managing it, remove it from state (terraform state rm in Terraform) and do not leave a resource block for it. If you want to keep it and start managing it, add a block and terraform import it.

Problem 4: which tool?

You need to create a Kubernetes cluster, a managed database, and DNS records, then deploy a stateless web app that already has a Helm chart. Which tool would you use for which part, and why not one tool for all of it?

Answer: A cloud IaC tool (Terraform or similar) for the cluster, the database, and DNS. Helm (or raw manifests) for the app, because that is already the native description of in-cluster workloads. You can do everything in one tool, but you then fight either "Helm trying to own the database" or "Terraform trying to own every Deployment," and the blast radius of a single apply gets large. A clean split, glued by CI, is the usual design.

13. Cheat Sheet

terraform init
terraform fmt -check
terraform validate
terraform plan  -out=tfplan
terraform apply tfplan
terraform state list
terraform import <resource.address> <real-id>

# questions to ask of every plan
#   any deletes?
#   any force-new (destroy + create) on a stateful resource?
#   any 0.0.0.0/0 on a private port?
#   is the second plan, right after apply, empty?

Debugging Pods: Pending, CrashLoopBackOff, ImagePullBackOff

Sooner or later, kubectl get pods shows something other than Running. The good news: there are only a handful of failure states, each one tells you which step of a pod's life failed, and the same five commands solve almost all of them. This page is a playbook. Find your STATUS, follow the steps, fix the cause. It ends with a full walkthrough of a real-style incident.

1. A Pod's Life, and Where It Can Break

A pod goes through the same steps every time. Each failure state belongs to one step:

  kubectl apply
       │
  1. SCHEDULE   scheduler picks a node     ─► fails as: Pending
       │
  2. PREPARE    network + volumes set up   ─► fails as: ContainerCreating (stuck)
       │
  3. PULL       image downloaded           ─► fails as: ErrImagePull / ImagePullBackOff
       │
  4. CONFIGURE  env from ConfigMap/Secret  ─► fails as: CreateContainerConfigError
       │
  5. RUN        your process runs          ─► fails as: Error, CrashLoopBackOff, OOMKilled
       │
  6. READY      readiness probe passes     ─► fails as: Running but READY 0/1
       │
  serving traffic ... later, 7. STOP       ─► fails as: Terminating (stuck)

Intuition. Debugging a pod is like finding where a parcel got stuck. "Not yet shipped" (Pending), "at the depot" (ContainerCreating), "wrong address" (image not found), "opened and returned" (crash). The status tells you the step, so you only need to look at that step.

Steps 1 to 4 fail before your code runs, so your app's logs are empty. The answer is in events. Step 5 onward fails in your code, so the answer is usually in the logs.

2. The Words, in Plain English

WordMeaning
PhaseThe pod's overall stage: Pending, Running, Succeeded, Failed, or Unknown.
Container stateEach container is Waiting, Running, or Terminated. The reason (like CrashLoopBackOff) is what kubectl get pods shows in STATUS.
EventA short message Kubernetes records about an object ("pulled image", "back-off restarting"). Kept for about one hour by default.
Restart countHow many times the kubelet restarted a container in this pod.
Exit codeThe number a process returns when it ends. 0 means success; anything else is a failure.
Back-offWaiting longer and longer between retries, so a broken thing is not retried thousands of times a minute.
SignalA message the operating system sends to a process. SIGTERM means "please stop"; SIGKILL means "stop now" and cannot be ignored.
FinalizerA "do not delete yet" note on an object. A controller must remove it before the object really goes away.

3. The Five Commands

# 1. What state is it in? (-o wide also shows the node and pod IP)
kubectl get pods -o wide

# 2. Why? Events at the bottom, container state and last state in the middle
kubectl describe pod <pod>

# 3. What did the app print? --previous = the container that just crashed
kubectl logs <pod> --previous
kubectl logs <pod> -c <container>          # pick a container if there are several

# 4. What happened around it, in time order?
kubectl get events --sort-by=.lastTimestamp

# 5. Let me look inside
kubectl debug -it <pod> --image=busybox:1.36 --target=<container>

The single most useful habit: when a container keeps restarting, kubectl logs shows the new, maybe empty, container. Add --previous to see the one that crashed.

5. Pending

No node was chosen yet. kubectl describe pod shows a FailedScheduling event that lists why each node was rejected, like 0/5 nodes are available: 3 Insufficient cpu, 2 node(s) had untolerated taint. Every phrase in that message is decoded in Scheduling: Reading a FailedScheduling Message.

One more common cause: the pod uses a PersistentVolumeClaim that is not bound yet. Check with kubectl get pvc; a claim stuck in Pending usually means a wrong storageClassName or no provisioner (see Storage).

6. Stuck in ContainerCreating

The pod has a node, but the kubelet cannot finish setting it up. A short ContainerCreating (seconds) is normal; minutes is not. Look at the events:

Event message (shortened)MeaningFix
MountVolume.SetUp failed ... secret "db-creds" not foundA volume refers to a Secret or ConfigMap that does not exist in this namespaceCreate it, or fix the name/namespace
Multi-Attach error for volume ... already used by pod(s)A ReadWriteOnce disk is still attached to another node (often the old pod during a rollout)Use the Recreate strategy for single-disk apps, or a StatefulSet
FailedCreatePodSandBox ... failed to set up networkThe network plugin (CNI) could not give the pod an IPCheck CNI pods in kube-system; check the node or subnet has free IPs
Unable to attach or mount volumes: timed out waitingCloud disk attach is slow or failingCheck the CSI driver pods and the disk's zone (it must match the node's zone)

7. ErrImagePull and ImagePullBackOff

ErrImagePull is one failed pull. ImagePullBackOff means "it failed, and I am waiting before I try again". The wait grows (about 10 s, 20 s, 40 s... up to 5 minutes), so after fixing the cause you may wait a while unless you delete the pod to retry at once.

The event message tells you which problem you have:

Message containsCauseCheck
not found / manifest unknownThe tag does not exist (typo, or CI never pushed it)List tags in the registry; compare with the image line in the pod
unauthorized / pull access denied / 403Private registry, no or wrong credentialsimagePullSecrets on the pod or its ServiceAccount; secret in the same namespace
toomanyrequestsRegistry rate limit (common with anonymous Docker Hub pulls)Authenticate, or use a mirror or your own registry
no match for platform in manifestImage built for another CPU type (arm64 vs amd64)Build multi-arch images (see Advanced Docker)
i/o timeout / no such hostThe node cannot reach the registry (DNS, firewall, proxy)Test from a debug pod on that node

Tip: pin images by digest (image: repo/app@sha256:...) or by a unique tag per build. The tag latest makes it hard to know what is running and why two pods differ.

8. CreateContainerConfigError

The image is there, but the kubelet cannot build the container's settings. Almost always: an environment variable points to a ConfigMap or Secret (or a key inside one) that does not exist.

Warning  Failed  kubelet  Error: couldn't find key DB_PASSWORD in Secret payments/db-creds

Fix the name or add the key. The pod starts on its own at the next retry; no restart needed.

Two ways to load config, two different failures. With valueFrom: configMapKeyRef (one named key), a missing key stops the container from being created: CreateContainerConfigError, and your code never runs. With envFrom: configMapRef (load every key), Kubernetes loads whatever keys exist and does not complain about missing ones; your app starts without the variable and crashes, which you see as CrashLoopBackOff. The walkthrough in section 14 is exactly this case.

9. CrashLoopBackOff and the Back-off Math

CrashLoopBackOff is not an error by itself. It means: "the container keeps exiting, so I am waiting before I start it again". The real error is in the logs of the crashed container and in its exit code.

How long the waits are

With the default restartPolicy: Always, the kubelet restarts a container that exits. After each crash it waits: 10 s, then 20 s, 40 s, 80 s, 160 s, and then 300 s (5 minutes, the cap) for every later crash. If a container then runs fine for 10 minutes, the wait resets to 10 s. (Newer Kubernetes versions have optional settings to shorten these waits; check your cluster version.)

wait before restart n  =  min(10 s × 2^(n-1), 300 s)

Worked example. An app crashes 2 seconds after it starts. Times since the first start:

EventTimeRESTARTS shown
Start, crash at 2 s, wait 10 s0 to 12 s0
Restart 1, crash, wait 20 s12 to 34 s1
Restart 2, crash, wait 40 s34 to 76 s2
Restart 3, crash, wait 80 s76 to 158 s3
Restart 4, crash, wait 160 s158 to 320 s4
Restart 5, crash, wait 300 s320 to 622 s5
Then every 302 s or so...about 12 per hour

So right after you fix the cause (say, you add a missing Secret), the pod may sit in back-off for up to 5 more minutes. Deleting the pod (its Deployment makes a fresh one) or kubectl rollout restart skips the wait.

The diagnosis steps

  1. kubectl describe pod <pod>: read Last State (reason and exit code) and Restart Count.
  2. kubectl logs <pod> --previous: read the last lines the crashed process printed.
  3. Match the exit code to the table in section 10.
  4. Ask: what changed? A new image, new config, a new dependency, or new limits? Compare with kubectl rollout history deployment/<name>.

Common causes: missing or wrong config, cannot reach a database at start-up and exits instead of retrying, wrong command or arguments, missing file, permission denied (the image expects root but the pod runs as non-root), the liveness probe killing a slow-starting app (exit code 137 or 143, with "Liveness probe failed" in events; fix with a startup probe, see Probes), and running out of memory (OOMKilled).

10. Exit Codes, Decoded

Codes from 0 to 127 come from the program itself. Codes above 128 mean "killed by a signal": subtract 128 to get the signal number.

Exit codeMeaningUsual cause in Kubernetes
0SuccessNormal for Jobs. For a server, it means the process ended when it should keep running (for example, the main command ran in the background and the shell exited).
1General errorThe app threw an error: read the logs
2Misuse of a shell commandBad arguments or a shell script syntax error
126Found but not executableFile lacks execute permission, or permission denied
127Command not foundTypo in command, or a tool missing from a slim image. (If the very first program cannot be started, the runtime may report StartError with "executable file not found in $PATH" instead.)
137128 + 9 = SIGKILLOOMKilled (check the reason), or killed after the grace period, or by a failing liveness probe
139128 + 11 = SIGSEGVThe program touched memory it should not (a crash in native code)
143128 + 15 = SIGTERMAsked to stop: normal during shutdown; during start-up it often means a liveness probe restart

Read the exit code from describe, or directly:

kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[0].lastState.terminated}'
# {"exitCode":1,"reason":"Error","startedAt":"...","finishedAt":"..."}

11. Running but Not Ready

The process is running, but the readiness probe fails, so the Service sends it no traffic. Users may see 503 errors if no pod is ready.

kubectl describe pod <pod>
#  Warning  Unhealthy  kubelet  Readiness probe failed: HTTP probe failed with statuscode: 500

kubectl get endpointslices -l kubernetes.io/service-name=<service>   # empty = no ready pods

Check, in order: is the probe's path and port right (a common slip is probing 8080 when the app listens on 3000)? Does the app bind to 0.0.0.0 and not only to 127.0.0.1? Does the readiness endpoint depend on something that is down (a database), so that every pod drops out at once? The design of good probe endpoints is covered in Autoscaling, Probes & Rollouts.

12. Stuck in Terminating

A pod being deleted gets SIGTERM, then up to terminationGracePeriodSeconds (default 30 s), then SIGKILL. If it shows Terminating for much longer:

  • The node is down or unreachable. The kubelet on it cannot confirm the pod stopped. The API keeps the pod until the node returns or the node object is deleted.
  • A finalizer is waiting. Check kubectl get pod <pod> -o jsonpath='{.metadata.finalizers}'. The controller that owns the finalizer must finish its cleanup.
  • A long grace period on purpose (some databases set minutes).

kubectl delete pod <pod> --grace-period=0 --force removes the pod from the API without waiting for the node to confirm. If the node is actually still running it, two copies may run at once. For a StatefulSet pod writing to a disk, that can corrupt data. Force delete only when you are sure the node or process is really gone.

13. Getting Inside: kubectl debug

Many production images are "distroless": no shell, no curl, nothing to debug with. kubectl debug solves this.

# A temporary debug container inside the running pod; --target shares the app's process view
kubectl debug -it api-7d9c6b5f4-x2k8p --image=busybox:1.36 --target=api
/ # ps aux                      # see the app's processes
/ # wget -qO- localhost:8080/ready
/ # cat /proc/1/environ | tr '\0' '\n'   # the app's environment variables

# Crash-looping pod? Make a copy whose app container runs a shell instead of the app
# (needs a shell in the image), then start the app by hand and watch it fail
kubectl debug api-7d9c6b5f4-x2k8p -it --copy-to=api-debug --container=api -- sh

# Debug the node itself (its files are mounted at /host)
kubectl debug node/worker-1 -it --image=busybox:1.36

Ephemeral debug containers cannot be removed from a pod once added; they simply stop when you exit. Delete --copy-to pods when you are done.

14. Walkthrough: a Release Stuck in a Crash Loop

The setup. The checkout service runs 4 replicas. Its Deployment uses maxSurge: 1, maxUnavailable: 0 and loads config with envFrom from the ConfigMap checkout-config. At 14:00 the team ships version 2.3. At 14:12 someone notices the deploy job is still "waiting for rollout".

Step 1: what state is it in?

$ kubectl get pods -l app=checkout
NAME                        READY   STATUS             RESTARTS      AGE
checkout-6f8b7c9d5-4lq2m    1/1     Running            0             2d
checkout-6f8b7c9d5-9xk7w    1/1     Running            0             2d
checkout-6f8b7c9d5-c2v8n    1/1     Running            0             2d
checkout-6f8b7c9d5-t5r1z    1/1     Running            0             2d
checkout-7d9c6b5f4-x2k8p    0/1     CrashLoopBackOff   4 (32s ago)   3m10s

Reading it: 4 old pods (hash 6f8b7c9d5) are fine. One new pod (hash 7d9c6b5f4) is crash-looping. Because maxUnavailable: 0, the rollout will not remove an old pod until a new one is ready, so users are not affected. That setting just turned a possible outage into a stuck deploy. (RESTARTS 4 at age 3m10s matches the back-off table in section 9: restarts at 12, 34, 76 and 158 seconds, the last one 32 seconds ago.)

Step 2: why is it crashing?

$ kubectl describe pod checkout-7d9c6b5f4-x2k8p
...
    State:          Waiting
      Reason:       CrashLoopBackOff
    Last State:     Terminated
      Reason:       Error
      Exit Code:    1
    Restart Count:  4
...
Events:
  Warning  BackOff  kubelet  Back-off restarting failed container checkout in pod checkout-7d9c6b5f4-x2k8p

$ kubectl logs checkout-7d9c6b5f4-x2k8p --previous
INFO  starting checkout v2.3
ERROR config: required setting PAYMENTS_URL is not set
Traceback (most recent call last):
  ...
KeyError: 'PAYMENTS_URL'

Exit code 1, an application error. The log says exactly what is missing: PAYMENTS_URL.

Step 3: what changed?

$ kubectl get configmap checkout-config -o jsonpath='{.data}' | tr ',' '\n'
{"DB_HOST":"pg.internal"
"LOG_LEVEL":"info"
"PAYMENTS_HOST":"payments.internal"}

Version 2.3 replaced the old setting PAYMENTS_HOST with a full PAYMENTS_URL. The developer added the new key to the staging ConfigMap only. Because the Deployment uses envFrom, Kubernetes did not complain about a missing key (section 8); the app started without it and crashed.

Step 4: stop the bleeding, then fix

Two safe options:

  • Roll back: kubectl rollout undo deployment/checkout. The crashing pod is removed and you are back to 4 healthy pods. Best when the fix is not obvious.
  • Roll forward: add the key, then restart the rollout. Environment variables are read only when a container starts, so the new value reaches pods only through new pods.
$ kubectl patch configmap checkout-config --type merge \
    -p '{"data":{"PAYMENTS_URL":"https://payments.internal:8443"}}'
$ kubectl rollout restart deployment/checkout      # new pods, no 5-minute back-off wait
$ kubectl rollout status deployment/checkout
deployment "checkout" successfully rolled out

In a GitOps setup (see CD with Argo CD), make the same change in Git instead of with kubectl patch, or the next sync will undo it.

Step 5: what if nobody had noticed?

A Deployment has progressDeadlineSeconds (default 600). After 10 minutes without progress, its status gets the condition Progressing=False, reason ProgressDeadlineExceeded, and kubectl rollout status exits with an error. It does not roll back by itself. Make your deploy job wait on rollout status and fail loudly, or let a tool like Argo Rollouts roll back automatically.

Step 6: make it not happen again

  • Fail fast with a clear message. The app checked its config at start-up and printed the missing name. That made the fix take minutes. Keep it.
  • Check config in CI. A small test can list the environment variables the code requires and compare them with each environment's ConfigMap.
  • Prefer explicit keys for required settings. With valueFrom.configMapKeyRef, a missing key blocks the pod before it starts (CreateContainerConfigError), which is clearer than a crash.
  • Keep maxUnavailable: 0 for user-facing services. It is why this was a stuck deploy and not an outage.
  • Alert on restarts, for example when kube_pod_container_status_restarts_total rises by more than 3 in 10 minutes (see Prometheus).

15. Common Pitfalls

  • Reading kubectl logs without --previous on a restarting pod, and seeing nothing useful.
  • Looking for logs when the pod never started. For Pending, ContainerCreating, ImagePullBackOff and CreateContainerConfigError, the answer is in events, not logs.
  • Waiting for events that expired. Events are kept for about an hour. Ship them to your logging system if you need history.
  • Thinking CrashLoopBackOff is the error. It is only the waiting. Find the exit code and the last log lines.
  • Changing a ConfigMap and expecting env vars to update. They do not change in running containers. Restart the pods. (Files mounted from a ConfigMap do update after a short delay, unless mounted with subPath.)
  • Liveness probe checks a dependency. The database blips and every pod restarts in a loop.
  • Force-deleting StatefulSet pods on a node that might still be alive.
  • Using the latest tag. Two pods of the "same" version can run different code.
  • Debugging the wrong namespace. Add -n <namespace>, or check your context with kubectl config get-contexts.

16. Practice Problems (with Solutions)

Problem 1: logs or events?

A pod shows ImagePullBackOff. A teammate runs kubectl logs and gets an error. Where should they look, and why?

Solution

In kubectl describe pod (the Events section). The image was never pulled, so no container ever ran, and there are no logs. The event message (not found, unauthorized, rate limit, platform) names the cause.

Problem 2: back-off timing

A container crashes 1 second after it starts, over and over. About how many restarts will the RESTARTS column show after 10 minutes?

Solution

Restart times (each run 1 s plus the wait): 11, 32, 73, 154, 315, then 616 s. 616 s is just after 10 minutes (600 s), so about 5 restarts. After that, roughly one every 5 minutes.

Problem 3: decode the exit code

Last State shows Reason: Error, Exit Code: 143, and events show Liveness probe failed: Get "http://10.0.3.7:8080/healthz": context deadline exceeded about 30 seconds after each start. What is going on?

Solution

143 = 128 + 15 = SIGTERM. The kubelet stopped the container because the liveness probe failed: the app is not answering /healthz in time, likely because it is still starting. Add a startup probe with enough budget (or fix slow start-up). Do not just raise the liveness timeouts for the whole life of the pod.

Problem 4: which error will you see?

A Secret api-keys has the key STRIPE. Pod A uses valueFrom.secretKeyRef with key STRIPE_KEY. Pod B uses envFrom.secretRef: api-keys and its code reads STRIPE_KEY. What STATUS does each show?

Solution

Pod A: CreateContainerConfigError ("couldn't find key STRIPE_KEY in Secret"). Pod B: it starts with an env var named STRIPE, not STRIPE_KEY; if the code requires STRIPE_KEY it exits, and you see Error then CrashLoopBackOff.

Problem 5: the silent Completed

A web server pod goes Completed, then CrashLoopBackOff, with exit code 0. The Dockerfile ends with CMD ./start.sh, and start.sh runs ./server &. What is wrong?

Solution

The & runs the server in the background, so the script reaches its end and exits with 0. The container's main process ended, so the container ended. Run the server in the foreground, ideally with exec ./server so it becomes PID 1 and also receives SIGTERM correctly (see How Containers Really Work).

Problem 6: stuck rollout, no alerts

In the walkthrough, which two settings decided that users saw no errors, and which setting would have reported the failure after 10 minutes?

Solution

maxUnavailable: 0 (no old pod removed before a new one is ready) together with the readiness gate (a crashing pod is never ready, so it never gets traffic). progressDeadlineSeconds: 600 marks the rollout as failed (ProgressDeadlineExceeded) after 10 minutes without progress.

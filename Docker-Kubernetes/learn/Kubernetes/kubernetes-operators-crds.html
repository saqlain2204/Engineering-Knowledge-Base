Operators & Custom Resources

Kubernetes knows how to run a Deployment. It does not know how to run a PostgreSQL cluster with backups and failover, or a Ray cluster for training a model. An operator teaches it. You add a new kind of object (a custom resource), and a program (a controller) that keeps the real world matching it. This page builds that idea from zero, runs a toy operator you can read in one sitting, and then shows the real tools. It builds on the reconciliation loop and Workloads.

1. The Idea: a Robot That Keeps Things True

Think of a thermostat. You set the desired temperature: 22°C. The thermostat keeps reading the actual temperature. If it is too cold, it turns on the heater. If it is too warm, it turns it off. It never stops checking. You never tell it "heat for 10 minutes"; you only say what you want.

Kubernetes is built from many small thermostats called controllers. You write "I want 3 copies of this pod" in YAML. The ReplicaSet controller keeps counting pods and creating or deleting them until there are 3.

An operator is the same idea for something Kubernetes does not know about. You write:

apiVersion: db.example.com/v1
kind: Database
metadata:
  name: orders-db
spec:
  replicas: 3
  version: "17"
  backupSchedule: "0 2 * * *"

and a program you install in the cluster turns that into pods, services, volumes, a backup CronJob, and a failover plan, and keeps them right forever. It encodes what a human database admin would do, which is where the name comes from: it replaces a human operator.

  you write:                     the operator does, again and again:
  +-----------------+            +-----------------------------------+
  | kind: Database  |  watch     | read desired state (spec)         |
  | replicas: 3     | ---------> | read actual state (pods, PVCs...) |
  +-----------------+            | make one step toward desired      |
          ^                      | write what it saw into status     |
          |   status: ready 3/3  +-----------------------------------+
          +-------------------------------------|

2. Words You Need

  • Resource. A kind of object the API server stores, like Pod or Service. Each object has spec (what you want) and usually status (what is true now).
  • Controller. A program that watches some resources and acts to make actual state match desired state.
  • Reconcile. One pass of "compare desired with actual, then fix the difference". The function that does it is the reconciler.
  • CRD (CustomResourceDefinition). An object that tells the API server about a brand new resource kind, like Database. After it is created, you can kubectl get databases.
  • Custom resource (CR). One object of that new kind, like orders-db.
  • Operator. CRDs plus a controller that manages them. Usually it carries expert knowledge about one piece of software.
  • Watch. A long-lived request to the API server that streams every change to a set of objects.
  • Idempotent. Doing it twice has the same effect as doing it once. A reconciler must be idempotent.
  • Owner reference. A note on an object that says "I belong to that other object". Used for automatic cleanup.
  • Finalizer. A label-like string on an object that blocks its deletion until a controller has done its cleanup and removed the string.

3. How Built-In Controllers Work

When you scale a Deployment from 3 to 5, nobody sends "create 2 pods" anywhere. Here is the chain:

kubectl scale deploy web --replicas=5
   |
   v
API server stores Deployment web: spec.replicas = 5      (in etcd)
   |  watch event
   v
Deployment controller: "web wants 5; its ReplicaSet says 3"
   -> updates ReplicaSet web-7d9f: spec.replicas = 5
   |  watch event
   v
ReplicaSet controller: "web-7d9f wants 5; I see 3 pods with its labels"
   -> creates 2 Pod objects (no node yet)
   |  watch event
   v
Scheduler: picks a node for each new pod
   |  watch event
   v
kubelet on that node: starts the containers, reports status

Every arrow is the same pattern: a component watches objects, notices a gap between spec and reality, and writes a small change to the API server. Nobody calls anybody directly. The API server is the shared notice board.

Inside a controller

Real controllers (built with the Go library client-go or controller-runtime) have three parts:

  API server
      |  watch stream (list once, then changes)
      v
 +-----------+      +-------------------+      +-------------------+
 | informer  | ---> | work queue        | ---> | reconcile(name)   |
 | + local   | key  | "default/orders-db"|     | reads from cache, |
 |   cache   |      | de-duplicated,    |      | writes to API     |
 +-----------+      | rate-limited      |      +-------------------+
                    +-------------------+         |  error? requeue
                            ^---------------------+  with back-off
  • The informer lists all objects once, then watches for changes, and keeps a local copy (the cache). Reads come from the cache, so the controller does not hammer the API server.
  • Every change puts the object's key (namespace/name) in the work queue, not the change itself. If the same object changes 10 times in a second, the key is in the queue once.
  • The reconcile function gets just the name. It reads the current desired and actual state and fixes the difference. If it fails, the key goes back in the queue with a growing delay (back-off).

4. Level-Triggered, Not Edge-Triggered

This is the most important idea on the page.

  • Edge-triggered: act on each change. "Replicas went from 3 to 5, so create 2 pods."
  • Level-triggered: act on the current state. "Desired is 5, I see 3, so create 2."

They look the same until something goes wrong. Say the controller crashes, and while it is down someone scales to 5, then to 4. An edge-triggered controller that missed those two events, or replays them in a strange order, ends up wrong. A level-triggered controller does not care what happened while it was away. It looks: desired 4, actual 3, create 1. Done.

The same is true when a human deletes a pod by hand, a node dies, or a network call half-fails. There is no event that says "please fix this"; there is only a world that does not match the spec. Level-triggered reconcilers fix it on the next pass. That is why Kubernetes controllers also resync every so often, even with no events, and why a reconciler must never assume it saw every event.

Intuition. An edge-triggered thermostat would say "someone opened the window, so heat for 5 minutes". If it misses the "window closed" event, it heats forever. A level-triggered one just reads the thermometer. It cannot get confused by events, because it does not use them for anything except "time to look again".

5. Adding a New Kind: the CRD

Here is a complete CRD for our Database kind. Read the comments; every line matters.

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.db.example.com        # must be <plural>.<group>
spec:
  group: db.example.com                 # your API group (use a domain you own)
  scope: Namespaced                     # or Cluster
  names:
    kind: Database                      # used in YAML "kind:"
    plural: databases                   # used in URLs and kubectl get
    singular: database
    shortNames: [db]                    # kubectl get db
  versions:
  - name: v1
    served: true                        # the API answers for this version
    storage: true                       # exactly one version is stored in etcd
    subresources:
      status: {}                        # status is updated separately from spec
    additionalPrinterColumns:           # extra columns in kubectl get
    - name: Replicas
      type: integer
      jsonPath: .spec.replicas
    - name: Ready
      type: integer
      jsonPath: .status.readyReplicas
    - name: Age
      type: date
      jsonPath: .metadata.creationTimestamp
    schema:
      openAPIV3Schema:                  # the API server rejects objects that break this
        type: object
        properties:
          spec:
            type: object
            required: [replicas, version]
            properties:
              replicas:
                type: integer
                minimum: 1
                maximum: 9
              version:
                type: string
                enum: ["15", "16", "17"]
              backupSchedule:
                type: string
          status:
            type: object
            properties:
              readyReplicas: {type: integer}
              observedGeneration: {type: integer}
              conditions:
                type: array
                items:
                  type: object
                  x-kubernetes-preserve-unknown-fields: true

After kubectl apply -f crd.yaml, the API server has a new endpoint, /apis/db.example.com/v1/namespaces/<ns>/databases, stored in etcd like any built-in kind. You can now apply the orders-db YAML from section 1 and see:

$ kubectl get db
NAME        REPLICAS   READY   AGE
orders-db   3                  5s

READY is empty. Nothing happens yet. A CRD is only storage plus validation. No pods appear until a controller watches databases and acts. Also try replicas: 20: the API server refuses it, because the schema says at most 9. Validation in the schema catches mistakes before your controller ever sees them.

Why subresources: status? It splits the object into two parts with separate write paths. Users (and GitOps tools) write spec; the controller writes status through /status. A user's kubectl apply cannot overwrite status by accident, and RBAC can allow the controller to touch only status.

6. Lab: A Toy Operator

To see the reconcile loop without a cluster, we wrote a toy in plain Python. The "API server" is a dictionary. The reconciler is the real logic, in about 30 lines:

api = {"crs": {}, "pods": {}, "backups": {}}    # pods: name -> owner

def reconcile(name):
    cr = api["crs"].get(name)
    mine = sorted(p for p, owner in api["pods"].items() if owner == name)
    if cr is None:
        return "gone"                            # nothing to do
    if cr.get("deleting"):                       # deletionTimestamp is set
        if "backup" in cr["finalizers"]:
            api["backups"][name] = f"backup-of-{name}"   # cleanup work
            cr["finalizers"].remove("backup")
        for p in mine:
            del api["pods"][p]
        if not cr["finalizers"]:
            del api["crs"][name]                 # now it can really go
            return "deleted"
        return "waiting"
    if "backup" not in cr["finalizers"]:
        cr["finalizers"].append("backup")        # add our finalizer first
    want, have = cr["spec"]["replicas"], len(mine)
    for _ in range(want - have):                 # too few: create
        create_pod(owner=name)
    for p in mine[want:]:                        # too many: delete extras
        del api["pods"][p]
    cr["status"] = {"readyReplicas": count_pods(name)}
    return f"ok, ready={cr['status']['readyReplicas']}/{want}"

Notice what it does not do: it never looks at what changed. It only compares "want" with "have". We then played six events at it. This is the real output:

1. user applies Database orders-db with replicas: 3
  create orders-db-pod-1
  create orders-db-pod-2
  create orders-db-pod-3
  reconcile #1: ok, ready=3/3
2. reconcile again with no change (idempotent?)
  reconcile #1: ok, ready=3/3
3. user scales to 2
  delete orders-db-pod-3
  reconcile #1: ok, ready=2/2
4. someone deletes a pod by hand (drift)
  create orders-db-pod-4
  reconcile #1: ok, ready=2/2
5. controller was down; two edits (5 then 4) happened while it was away
  create orders-db-pod-5
  create orders-db-pod-6
  reconcile #1: ok, ready=4/4
6. user deletes the CR (kubectl delete)
  finalizer: saved backup, removed finalizer
  reconcile #1: deleted
  reconcile #2: gone
final state: {'backups': {'orders-db': 'backup-of-orders-db'}, 'pods': {}, 'crs': {}}

What each step proves:

StepWhat it shows
2Idempotent. Running it again with nothing to do did nothing. Controllers run reconcile many times for the same object, so this is required.
4Heals drift. No event said "pod-1 was deleted by a human". The count was simply 1 instead of 2, so it made pod-4.
5Level-triggered. It never saw "5". It only saw "want 4, have 2" and created 2. An edge-triggered version that replayed "+3 then -1" from a stale count would be wrong.
6Finalizer. Delete did not remove the object at once. The controller first saved a backup, then removed its finalizer, and only then did the object disappear. One more reconcile found nothing to do.

7. Owner References and Cascading Delete

In the toy, the controller deletes its own pods. In real Kubernetes you rarely need to. When the operator creates a child object, it sets an owner reference:

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: orders-db
  ownerReferences:
  - apiVersion: db.example.com/v1
    kind: Database
    name: orders-db
    uid: 3f6c1a2e-0b7d-4c55-9a51-8d1f2e7c9b10   # the owner's exact uid
    controller: true             # this owner is THE managing controller
    blockOwnerDeletion: true

Now the built-in garbage collector controller knows the StatefulSet belongs to the Database. Delete the Database, and the StatefulSet is deleted too, and then its pods (which are owned by the StatefulSet). This is how deleting a Deployment removes its ReplicaSets and pods.

Database orders-db
   └── StatefulSet orders-db         (owner: Database)
         └── Pod orders-db-0, -1, -2 (owner: StatefulSet)
   └── Service orders-db             (owner: Database)
   └── CronJob orders-db-backup      (owner: Database)

kubectl delete has three cascade modes: --cascade=background (the default: delete the owner now, children shortly after), foreground (children first, then the owner), and orphan (delete only the owner and leave children running). Owner references only work inside one namespace, or from a cluster-scoped owner; a namespaced object cannot own a cluster-scoped one.

Owner references also help the controller: with controller-runtime you write Owns(&appsv1.StatefulSet{}), and a change to any owned StatefulSet puts the owner's key in the work queue. That is how the operator notices "someone scaled my StatefulSet by hand" and puts it back.

8. Finalizers, and Objects Stuck in Terminating

Owner references clean up things inside the cluster. But some cleanup is outside: a cloud load balancer, a DNS record, a final backup to S3. For that, use a finalizer:

  1. When the controller first sees the object, it adds a string to metadata.finalizers, for example db.example.com/backup.
  2. When a user deletes the object, the API server does not delete it. It sets metadata.deletionTimestamp and leaves it there. kubectl get shows it as Terminating.
  3. The controller sees the deletion timestamp, does the cleanup, and removes its string from the list.
  4. When the list is empty, the API server really deletes the object.

The trap: if the controller is gone (uninstalled, crashing, missing permissions), nobody removes the finalizer and the object is stuck in Terminating forever. This is very common with namespaces that will not delete because some custom resource inside them has a finalizer from an operator that was already removed.

# find what is holding it
kubectl get database orders-db -o jsonpath='{.metadata.finalizers}'
kubectl get database orders-db -o jsonpath='{.metadata.deletionTimestamp}'

# best fix: bring the controller back (reinstall, fix RBAC) and let it finish

# last resort: remove the finalizer by hand. The cleanup it guarded
# (backup, cloud resource) will NOT happen; do it yourself first.
kubectl patch database orders-db --type=merge -p '{"metadata":{"finalizers":null}}'

Rule of thumb: uninstall operators last. Delete their custom resources first, while the controller is still running to process the finalizers. See also stuck Terminating pods.

9. Status, Conditions and observedGeneration

A good operator tells you what it sees. The common shape is a list of conditions:

status:
  observedGeneration: 7
  readyReplicas: 2
  conditions:
  - type: Ready
    status: "False"
    reason: ReplicaNotReady
    message: "orders-db-2 is failing its readiness probe"
    lastTransitionTime: "2026-11-28T08:41:10Z"
  - type: BackupSucceeded
    status: "True"
    reason: Completed
    lastTransitionTime: "2026-11-28T02:00:41Z"

Each condition has a type, a status of "True", "False" or "Unknown", a short CamelCase reason for machines, and a message for humans. Tools can wait on them: kubectl wait --for=condition=Ready database/orders-db --timeout=5m.

observedGeneration answers "has the controller seen my latest change yet?" Every time the spec changes, the API server adds 1 to metadata.generation. The controller copies the generation it just processed into status.observedGeneration.

metadata.generation = 8, status.observedGeneration = 7
  -> your latest edit has NOT been processed yet; status describes the old spec
metadata.generation = 8, status.observedGeneration = 8
  -> status is about your current spec

Without this, a CI pipeline might apply a change, read Ready=True left over from the old version, and announce success too early. Deployments use the same trick, which is how kubectl rollout status knows when to stop waiting.

10. A Real Operator in Python (kopf)

Most production operators are written in Go with kubebuilder or the Operator SDK (both on top of controller-runtime). For learning, the Python framework kopf is much shorter. This is a small but real operator that turns a Database into a StatefulSet:

import kopf, kubernetes

def statefulset_for(name, spec):
    return {
        "apiVersion": "apps/v1", "kind": "StatefulSet",
        "metadata": {"name": name},
        "spec": {
            "replicas": spec["replicas"],
            "serviceName": name,
            "selector": {"matchLabels": {"app": name}},
            "template": {
                "metadata": {"labels": {"app": name}},
                "spec": {"containers": [{
                    "name": "postgres",
                    "image": f"postgres:{spec['version']}",
                }]},
            },
        },
    }

@kopf.on.create("db.example.com", "v1", "databases")
@kopf.on.update("db.example.com", "v1", "databases")
@kopf.on.resume("db.example.com", "v1", "databases")   # also on operator restart
def reconcile(spec, name, namespace, body, **_):
    sts = statefulset_for(name, spec)
    kopf.adopt(sts, owner=body)          # sets ownerReferences for cascading delete
    apps = kubernetes.client.AppsV1Api()
    try:
        apps.create_namespaced_stateful_set(namespace, sts)
    except kubernetes.client.ApiException as e:
        if e.status != 409:              # 409 = already exists
            raise                        # kopf retries with back-off
        apps.patch_namespaced_stateful_set(name, namespace, sts)

@kopf.on.delete("db.example.com", "v1", "databases")
def take_final_backup(name, **_):
    # kopf adds and removes its own finalizer around this handler
    print(f"saving a final backup of {name}")

Run it on your laptop against any cluster (kind or minikube is fine) with kopf run operator.py; in production, package it in an image and run it as a Deployment. Points to notice:

  • The handler is create-or-update, so running it twice is safe (idempotent).
  • @kopf.on.resume runs for every existing object when the operator starts, which covers anything that changed while it was down.
  • kopf.adopt writes the owner reference, so deleting the Database deletes the StatefulSet.
  • An exception means "try again later". The framework requeues with back-off.

In Go, the same reconcile function has this famous shape:

func (r *DatabaseReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var db dbv1.Database
    if err := r.Get(ctx, req.NamespacedName, &db); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)   // deleted: nothing to do
    }
    sts := buildStatefulSet(&db)
    ctrl.SetControllerReference(&db, sts, r.Scheme)        // owner reference
    _, err := controllerutil.CreateOrUpdate(ctx, r.Client, sts, func() error { ... })
    if err != nil {
        return ctrl.Result{}, err                          // requeue with back-off
    }
    db.Status.ObservedGeneration = db.Generation
    return ctrl.Result{}, r.Status().Update(ctx, &db)
}

11. Running an Operator Safely

11.1 RBAC: only what it needs

An operator is a program with API permissions. Give it exactly what it uses (see Config, Secrets & Security):

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: database-operator
rules:
- apiGroups: ["db.example.com"]
  resources: ["databases"]
  verbs: ["get", "list", "watch", "patch", "update"]
- apiGroups: ["db.example.com"]
  resources: ["databases/status", "databases/finalizers"]
  verbs: ["get", "patch", "update"]
- apiGroups: ["apps"]
  resources: ["statefulsets"]
  verbs: ["get", "list", "watch", "create", "patch", "update", "delete"]
- apiGroups: [""]
  resources: ["events"]
  verbs: ["create", "patch"]

Missing list or watch is the classic first bug: the informer cannot start, and the operator logs "forbidden" and does nothing.

11.2 Conflicts: 409 is normal

Every object has a metadata.resourceVersion. An update must send the version it read. If someone else changed the object in between, the API server answers 409 Conflict. This is optimistic concurrency: no locks, just "your copy is old, read again". The right response is to return an error and let the work queue retry; the next reconcile reads fresh state. Do not loop and retry inside the reconciler.

11.3 One active copy: leader election

For high availability you run 2 replicas of the operator, but only one should act. They compete for a Lease object; the holder is the leader and renews it every few seconds. If it dies, the other takes over after the lease expires (about 15 seconds by default in controller-runtime).

11.4 Do not fight other controllers

If your operator sets replicas: 3 on a StatefulSet and an HPA (autoscaler) also sets replicas, they will flip it back and forth forever. Decide who owns each field. Server-side apply (kubectl apply --server-side, and the same in client libraries) records a field manager for every field and reports a conflict when two managers try to own one field.

13. When Not to Write One

An operator is code you must test, upgrade and keep secure for years. Before writing one, ask:

  • Is it just "install these YAML files with some settings"? Use a Helm chart or Kustomize. Templates do not need a running program.
  • Does a well-known operator already exist? For databases, queues, certificates and ML platforms, almost always yes. Use it.
  • Does it need ongoing decisions? Failover, backups on a schedule, ordered upgrades, resizing, reacting to the app's own health: these are what operators are for.

A useful test: if the job description for a human doing this by hand includes "watch it and react when something happens", it might be an operator. If it says "run these commands once", it is a chart or a script.

14. Common Pitfalls

  • Edge-triggered logic. "On update, add the difference" breaks after missed events. Always compare desired with actual.
  • Not idempotent. "Create" that fails with 409 on the second run, or a backup taken on every reconcile. Use create-or-update, and record what was done in status.
  • Hot loops. Writing status on every pass (with a new timestamp each time) creates a watch event, which triggers another reconcile, forever. Only write when something really changed.
  • Writing the user's spec. The controller should own status and child objects, not rewrite the user's spec; GitOps tools will fight it.
  • No owner references. Children are left behind (orphans) when the custom resource is deleted.
  • Finalizer with no way out. If cleanup can fail forever (a cloud API that is gone), the object is stuck forever. Add a timeout or an escape hatch, and log loudly.
  • Uninstalling the operator before its resources. Finalizers can then never be removed; namespaces hang in Terminating.
  • Breaking CRD versions. Removing a field from a served version breaks every user. Add a new version (v1beta1 to v1) with a conversion webhook, and migrate slowly.

15. Practice Problems

Problem 1: edge vs level

A controller keeps a counter in memory. On each "scale" event it adds or removes the difference between the old and new value. It restarts (losing its counter) while the user changes replicas 3 to 6 to 2. After restart, it sees only the final object with replicas 2, and 3 pods exist. What does a level-triggered controller do? What can go wrong with the edge-triggered one?

Solution

Level-triggered: desired 2, actual 3, delete 1. Correct. Edge-triggered: its counter is gone, and it saw no events while down. It may do nothing (still 3 pods), or, if it replays events from a stale starting point, create and delete the wrong numbers. It has no reliable way to know the truth except by looking, which is what level-triggered means.

Problem 2: the stuck namespace

kubectl delete namespace team-a has said Terminating for an hour. kubectl get databases -n team-a shows one object with a deletion timestamp and finalizer db.example.com/backup. The database operator was uninstalled yesterday. What happened and what do you do?

Solution

The namespace waits for every object inside it to be deleted. The Database object waits for its finalizer, and the only program that would remove it is gone. Best: reinstall the operator so it can take the backup and remove the finalizer itself. If that is not possible, take the backup by hand, then patch metadata.finalizers to null on the Database. The namespace then finishes deleting.

Problem 3: observedGeneration

A CI job applies a Database with version: "17", then immediately reads Ready=True and reports success. The rollout later fails. The object shows generation: 12 and observedGeneration: 11 at the time CI read it. Explain and fix.

Solution

The status was still about generation 11 (the old version). The controller had not processed the new spec yet. CI must wait until observedGeneration == generation and Ready=True. For example: loop until both hold, or use kubectl wait --for=jsonpath='{.status.observedGeneration}'=12 and then wait on the condition.

Problem 4: hot loop

An operator's CPU is at 100% and the API server shows thousands of status updates per minute for one object. The reconciler ends with status.lastChecked = now() and an update. Why is this a loop, and what is the fix?

Solution

Each status update changes the object, which sends a watch event, which queues the key, which runs reconcile, which writes a new lastChecked, and so on. Fix: compare the new status with the old one and only write if something meaningful changed. Drop lastChecked or update it on a timer (for example by returning "requeue after 5 minutes").

Problem 5: who deletes what

A Database owns a StatefulSet and a Service (owner references set). The StatefulSet owns 3 pods. A PersistentVolumeClaim was created by the StatefulSet's volume template and has no owner reference. What remains after kubectl delete database orders-db with the default cascade?

Solution

The StatefulSet, the Service and the 3 pods are garbage-collected. The PVCs remain, because nothing owns them. This is on purpose: StatefulSets keep PVCs by default so data is not lost by accident. If the operator should delete data too, it must do so explicitly (for example in a finalizer, after a backup), or set the StatefulSet's persistentVolumeClaimRetentionPolicy.

reconcile(name): read desired (spec) + actual (children) -> fix the gap -> write status
must be: level-triggered, idempotent, quick; errors -> requeue with back-off

kubectl explain database.spec
kubectl get db -A
kubectl get database orders-db -o yaml          # spec, status, finalizers, generation

# conditions and readiness
kubectl wait --for=condition=Ready database/orders-db --timeout=5m

# stuck in Terminating
kubectl get <kind> <name> -o jsonpath='{.metadata.finalizers}'
# fix the controller first; last resort (cleanup is skipped):
kubectl patch <kind> <name> --type=merge -p '{"metadata":{"finalizers":null}}'

# delete modes
kubectl delete database orders-db --cascade=background   # default
kubectl delete database orders-db --cascade=foreground   # children first
kubectl delete database orders-db --cascade=orphan       # keep children

# CRD must-haves
schema (openAPIV3Schema) with required fields and limits
subresources.status, additionalPrinterColumns
one storage version; new version + conversion for breaking changes

# operator must-haves
owner references on children   finalizer only for outside cleanup
status.conditions + observedGeneration
least-privilege RBAC (list + watch!)   leader election for 2+ replicas
uninstall order: custom resources first, operator last

GPU Scheduling on Kubernetes

How a cluster finds, hands out, shares, and monitors GPUs for training and LLM inference. From "what is a device plugin" to MIG slices, DRA claims, and gang-scheduled training jobs.

1. Why GPUs Are Different from CPU and Memory

Kubernetes was built around CPU and memory. Those are easy: the kubelet reads them from the operating system, and the Linux kernel can divide them finely (CPU shares, memory limits). GPUs break those assumptions:

  • Kubernetes does not know they exist. The kubelet cannot discover GPUs by itself. A vendor plugin must tell it.
  • They are whole devices. You cannot ask for "0.3 of a GPU" the way you ask for 300m CPU. GPU counts are integers.
  • No overcommit. A GPU given to one container is not handed to another (unless you explicitly set up sharing, section 6).
  • Extra software is needed on the node: a kernel driver, a container runtime hook that mounts the device files and driver libraries into containers, and the CUDA libraries in the image.
  • They are expensive. An idle H100 costs real money every hour. Good scheduling is about cost as much as correctness.
Intuition: CPU and memory are like water from a tap: you can take any amount. GPUs are like rental cars: you take a whole car, someone has to register the cars with the rental office first (device plugin), and you might want a specific model (node labels).

2. Device Plugins: How Kubernetes Learns About GPUs

The device plugin framework is how hardware vendors teach the kubelet about special devices without changing Kubernetes code.

Step by step

  1. The vendor's device plugin runs on each GPU node, usually as a DaemonSet.
  2. It finds the GPUs (for NVIDIA, through the driver's management library) and registers with the kubelet over a gRPC Unix socket in /var/lib/kubelet/device-plugins/.
  3. It advertises an extended resource name and count, for example nvidia.com/gpu: 8, and reports device health.
  4. The kubelet adds this to the node's status.capacity and status.allocatable. Now the scheduler can see it.
  5. When a Pod requesting nvidia.com/gpu: 1 is scheduled to the node, the kubelet asks the plugin to allocate a specific device. The plugin returns what the container needs: device files, environment variables (which GPU IDs are visible), and mounts.
  6. The container runtime (with the NVIDIA Container Toolkit) starts the container with only that GPU visible.
$ kubectl get nodes -o custom-columns=NAME:.metadata.name,GPUS:.status.allocatable.nvidia\.com/gpu
NAME            GPUS
cpu-node-1      <none>
gpu-node-1      8
gpu-node-2      8

3. The NVIDIA GPU Operator

Installing and upgrading drivers, toolkit, and plugin by hand on every node is error-prone. The NVIDIA GPU Operator (installed with Helm) manages all of it as containers:

ComponentJob
Driver containerInstalls the kernel driver on the node (can be skipped if the node image already has it, as on many managed clouds)
Container ToolkitConfigures containerd/CRI-O so containers can access GPUs
Device pluginAdvertises nvidia.com/gpu (section 2)
GPU Feature Discovery (GFD)Adds node labels such as GPU product, memory, count, and MIG capability
DCGM exporterExposes GPU metrics to Prometheus
MIG managerApplies MIG partition layouts from a node label
 
helm repo add nvidia https://helm.ngc.nvidia.com/nvidia && helm repo update
helm install gpu-operator nvidia/gpu-operator -n gpu-operator --create-namespace

# a few minutes later
kubectl get pods -n gpu-operator
kubectl get node gpu-node-1 --show-labels | tr ',' '\n' | grep nvidia.com/gpu

Typical GFD labels: nvidia.com/gpu.product=NVIDIA-H100-80GB-HBM3, nvidia.com/gpu.memory=81559 (MiB), nvidia.com/gpu.count=8.

4. Requesting a GPU in a Pod

apiVersion: v1
kind: Pod
metadata:
  name: cuda-smoke-test
spec:
  restartPolicy: Never
  containers:
    - name: cuda
      image: nvidia/cuda:12.4.1-base-ubuntu22.04
      command: ["nvidia-smi"]
      resources:
        limits:
          nvidia.com/gpu: 1

Rules for extended resources like GPUs:

  • Specify them in limits. If you also set requests, it must equal the limit. If you set only the limit, the request defaults to the same value.
  • Only whole numbers. 0.5 is rejected.
  • GPUs are given per container, and are not shared between containers in a Pod.
$ kubectl apply -f cuda-smoke-test.yaml
$ kubectl logs cuda-smoke-test       # nvidia-smi table showing exactly ONE GPU

If the log shows one GPU, the whole chain (driver, toolkit, plugin, scheduler) works.

5. Putting GPU Pods on the Right Nodes

Keep non-GPU pods off GPU nodes: taints

If ordinary pods land on a GPU node, they can use up its CPU or memory and block GPU pods from fitting. So GPU nodes are usually tainted, and only GPU workloads tolerate the taint. Several managed clouds add a taint like nvidia.com/gpu=present:NoSchedule automatically, and the ExtendedResourceToleration admission plugin can add the matching toleration to any pod that requests GPUs. (Taints, tolerations and affinity in general, with worked examples, are on the Scheduling page.)

kubectl taint nodes gpu-node-1 nvidia.com/gpu=present:NoSchedule

Pick the GPU model: node affinity on GFD labels

apiVersion: v1
kind: Pod
metadata:
  name: trainer
spec:
  tolerations:
    - key: nvidia.com/gpu
      operator: Exists
      effect: NoSchedule
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: nvidia.com/gpu.product
                operator: In
                values: ["NVIDIA-H100-80GB-HBM3", "NVIDIA-A100-SXM4-80GB"]
  containers:
    - name: train
      image: ghcr.io/example/trainer:1.0
      resources:
        limits:
          nvidia.com/gpu: 4
          cpu: "32"
          memory: 256Gi
Remember: a toleration only allows a pod on a tainted node; it does not attract it. You need both a toleration (permission) and affinity or a GPU request (attraction).

6. Sharing GPUs: Time-Slicing, MPS, and MIG

Many workloads (notebooks, small models, dev environments) use a fraction of a big GPU. Giving each a whole H100 wastes money. Three NVIDIA sharing options, from weakest to strongest isolation:

Time-slicingMPSMIG
HowProcesses take turns on the whole GPUA server merges work from several processes so they run concurrentlyHardware splits the GPU into isolated instances
Memory isolationNone: one pod can use all memory and crash others (OOM)Limits can be set per client; no full fault isolationYes, each slice has its own memory
Performance isolationNonePartialYes, dedicated compute and memory bandwidth
HardwareAny NVIDIA GPUMost NVIDIA GPUsA100, A30, H100, H200, B200 and other data-center GPUs
Good forDev, notebooks, bursty light jobsMany small inference processesMulti-tenant production, guaranteed QoS

Time-slicing config

Each physical GPU is advertised as several "replicas". Pods still request nvidia.com/gpu: 1, but now get a shared slot.

apiVersion: v1
kind: ConfigMap
metadata:
  name: time-slicing-config
  namespace: gpu-operator
data:
  any: |-
    version: v1
    sharing:
      timeSlicing:
        resources:
          - name: nvidia.com/gpu
            replicas: 4

A node with 8 GPUs now advertises nvidia.com/gpu: 32. Point the operator at it (devicePlugin.config.name=time-slicing-config). Remember: nothing stops one pod from using all 80 GB.

MIG: real hardware partitions

Multi-Instance GPU splits one GPU into up to 7 instances, each with its own compute units, cache, and memory. Profiles are named <compute slices>g.<memory>gb. For an H100 80 GB, examples are 1g.10gb, 2g.20gb, 3g.40gb, and 7g.80gb (the whole GPU).

With the operator's "mixed" strategy, each profile becomes its own resource:

resources:
  limits:
    nvidia.com/mig-1g.10gb: 1

Worked example: a team runs 14 small embedding services, each needing under 8 GB. On 2 H100s split into 7 x 1g.10gb each, all 14 fit on 2 GPUs, with hard isolation, instead of 14 whole GPUs.

7. Dynamic Resource Allocation (DRA)

The device plugin model has limits: a device is just a count. You cannot say "a GPU with at least 40 GB of memory", "two GPUs connected by NVLink", or "share this GPU between these two pods". Dynamic Resource Allocation fixes this. Its core API reached general availability with the resource.k8s.io/v1 API in Kubernetes v1.34, and the Kubernetes docs list it as stable and always on from v1.35.

The new objects

ObjectWho creates itMeaning
DeviceClassAdmin / driver installA kind of device, for example "NVIDIA GPU"
ResourceSliceThe DRA driver on each nodeThe devices on the node, with attributes (model, memory, driver version) and capacity
ResourceClaimUser"I need devices matching these rules"
ResourceClaimTemplateUserStamps out a new claim per pod (like a PVC template)

The scheduler reads the ResourceSlices, finds devices matching the claim (rules are written in CEL, a small expression language), allocates them, and the driver prepares them on the node. It is the same idea as PersistentVolumeClaims, but for devices.

apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: one-gpu
spec:
  spec:
    devices:
      requests:
        - name: gpu
          exactly:
            deviceClassName: gpu.nvidia.com
---
apiVersion: v1
kind: Pod
metadata:
  name: dra-demo
spec:
  resourceClaims:
    - name: gpu
      resourceClaimTemplateName: one-gpu
  containers:
    - name: app
      image: nvidia/cuda:12.4.1-base-ubuntu22.04
      command: ["nvidia-smi", "-L"]
      resources:
        claims:
          - name: gpu

The device class name and the attributes you can filter on come from the installed DRA driver (here NVIDIA's). Use kubectl get deviceclasses and kubectl get resourceslices -o yaml to see what your cluster offers. Device plugins still work and remain common; DRA is where new GPU features (fine-grained sharing, topology-aware multi-GPU, network devices) are heading.

8. Distributed Training and Gang Scheduling

A training job across 4 nodes x 8 GPUs needs all 32 GPUs at once. The default scheduler places pods one by one. Imagine two such jobs and only 32 free GPUs:

Job A gets 16 GPUs (2 of its 4 pods) ... waits for the rest
Job B gets 16 GPUs (2 of its 4 pods) ... waits for the rest
=> 32 GPUs allocated, 0 jobs running. Deadlock, and expensive.

Gang scheduling means all-or-nothing: either every pod of a job starts, or none do. Common tools:

  • Kueue (a Kubernetes SIG project): a job-queueing layer. It admits a whole job only when quota for all its resources is available, manages team quotas with borrowing (ClusterQueues and cohorts), and supports fair sharing and preemption. Works with Jobs, JobSets, Kubeflow training jobs, RayJobs, and more.
  • Volcano: a batch scheduler with PodGroups (minMember) for gang scheduling, popular for AI and HPC.

Also think about topology: GPUs in the same node talk over NVLink, nodes talk over InfiniBand or RoCE. Placing a job's pods close together (same rack, same network block) can change training speed a lot. Kueue's topology-aware scheduling and cloud placement policies address this. For the training side, see Distributed Training.

9. Serving an LLM: a Complete Deployment

A vLLM server for an 8B model on one GPU, with the details that usually trip people up:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-8b
spec:
  replicas: 2
  selector:
    matchLabels: { app: llm-8b }
  template:
    metadata:
      labels: { app: llm-8b }
    spec:
      tolerations:
        - { key: nvidia.com/gpu, operator: Exists, effect: NoSchedule }
      containers:
        - name: vllm
          image: vllm/vllm-openai:latest   # pin a specific version in production
          args:
            - --model=meta-llama/Llama-3.1-8B-Instruct
            - --max-model-len=8192
            - --gpu-memory-utilization=0.90
            - --enable-prefix-caching
          env:
            - name: HF_TOKEN
              valueFrom: { secretKeyRef: { name: hf-token, key: token } }
          ports:
            - containerPort: 8000
          resources:
            limits:
              nvidia.com/gpu: 1
              memory: 48Gi
            requests:
              cpu: "4"
              memory: 48Gi
          readinessProbe:
            httpGet: { path: /health, port: 8000 }
            periodSeconds: 10
          startupProbe:                    # model download + load can take minutes
            httpGet: { path: /health, port: 8000 }
            periodSeconds: 10
            failureThreshold: 60
          volumeMounts:
            - { name: cache, mountPath: /root/.cache/huggingface }
            - { name: dshm, mountPath: /dev/shm }
      volumes:
        - name: cache
          persistentVolumeClaim: { claimName: hf-cache }
        - name: dshm                       # shared memory for NCCL / multi-process
          emptyDir: { medium: Memory, sizeLimit: 8Gi }
  • startupProbe: without it, the liveness/readiness checks may kill or hide the pod while it downloads 16 GB of weights.
  • Model cache on a PVC: avoids re-downloading weights on every restart.
  • /dev/shm: the container default is only 64 MB; multi-GPU (tensor parallel) serving needs more.

Why the memory settings matter, and how many users one GPU can hold: see Inference Optimization: capacity planning.

10. Autoscaling and Cost

  • Node autoscaling: Cluster Autoscaler or Karpenter adds GPU nodes when GPU pods are Pending and removes idle ones. Keep GPU node pools able to scale to zero for dev and batch.
  • Pod autoscaling for inference: scale on queue depth, requests in flight, or KV cache usage (via custom or external metrics, or KEDA), not on CPU. GPU utilization is a weak signal for LLM servers.
  • Cold starts: a new GPU node plus image pull plus weight loading can take 5 to 15 minutes. Keep warm capacity, pre-pull images, and use fast model storage.
  • Spot/preemptible GPUs: much cheaper for fault-tolerant training with checkpointing, risky for latency-critical serving.

11. Monitoring GPUs

The DCGM exporter publishes per-GPU metrics with pod and namespace labels:

MetricMeaning
DCGM_FI_DEV_GPU_UTILPercent of time any kernel was running. Coarse: 100% does not mean the GPU is fully used.
DCGM_FI_PROF_GR_ENGINE_ACTIVE, DCGM_FI_PROF_SM_ACTIVEBetter measures of how busy the compute engines really are
DCGM_FI_DEV_FB_USEDGPU memory used (MiB)
DCGM_FI_DEV_POWER_USAGE, DCGM_FI_DEV_GPU_TEMPPower and temperature; throttling shows up here
DCGM_FI_DEV_XID_ERRORSDriver-reported GPU errors; certain XIDs mean the node needs draining

A useful cost dashboard: GPUs allocated per namespace (from kube_pod_container_resource_limits) next to how busy those GPUs actually are. Big gaps mean wasted money and candidates for MIG or time-slicing.

12. Scenario: My GPU Pod Is Stuck in Pending

Situation. You deploy a training pod requesting 2 GPUs. It stays Pending for 20 minutes.

Step 1: read the scheduler's reason

$ kubectl describe pod trainer | sed -n '/Events/,$p'
  Warning  FailedScheduling  0/6 nodes are available: 3 Insufficient nvidia.com/gpu,
           3 node(s) had untolerated taint {nvidia.com/gpu: present}. ...

Step 2: decode the message, piece by piece

Message partMeaningFix
Insufficient nvidia.com/gpuThose nodes do not have 2 free GPUsWait, free GPUs, request fewer, or add nodes
untolerated taintPod lacks the toleration for GPU nodesAdd the toleration
didn't match Pod's node affinity/selectorLabel mismatch, for example a typo in the GPU product nameCompare with real node labels
No GPU node mentioned at all, and none have the resourceDevice plugin not running, or driver brokenCheck the operator pods and node allocatable

Step 3: check what is really free

kubectl get nodes -o custom-columns=NAME:.metadata.name,ALLOC:.status.allocatable.nvidia\.com/gpu
kubectl describe node gpu-node-1 | sed -n '/Allocated resources/,/Events/p'
kubectl get pods -A -o wide --field-selector spec.nodeName=gpu-node-1

Often you find GPUs held by a forgotten notebook or a finished Job whose pod was never cleaned up. (Pods in Completed state do not hold GPUs; pods stuck Running with nothing to do do.)

Step 4: check the plugin if allocatable is missing or 0

kubectl get pods -n gpu-operator
kubectl logs -n gpu-operator -l app=nvidia-device-plugin-daemonset

Common causes: driver install failed after a kernel upgrade, a GPU fell off the bus (XID errors), or the node is missing the label the operator uses to select GPU nodes.

13. Common Pitfalls

  • Setting NVIDIA_VISIBLE_DEVICES=all in an image or pod spec without requesting the resource. Depending on runtime configuration this can expose GPUs the scheduler thinks are free, leading to two jobs on one GPU. Always go through resource requests.
  • Treating time-slicing as isolation. One pod's memory leak crashes its neighbours.
  • Forgetting CPU and RAM for GPU pods. Data loaders starve the GPU when the pod gets 1 CPU. Request enough CPU and memory, and set /dev/shm.
  • Image and driver mismatch. The CUDA version in the image must be supported by the node's driver (newer drivers run older CUDA, not the other way around).
  • No startupProbe for model servers. Pods get killed during multi-minute model loads.
  • Scheduling distributed jobs without gang semantics. Partial allocations can deadlock the cluster's GPUs.

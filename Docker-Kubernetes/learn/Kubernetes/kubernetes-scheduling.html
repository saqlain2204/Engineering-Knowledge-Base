Scheduling: Taints, Affinity, Spreading & Priority

Every pod you create must end up on one node. The scheduler makes that choice. Most of the time you never think about it, until a pod is stuck in Pending, all three replicas land on the same machine and die together, or a batch job pushes your API off its node. This page explains how the choice is made and every knob that changes it, with numbers you can check by hand. It builds on the scheduler's place in the control plane and on requests and limits.

1. The Big Picture

The scheduler is a program in the control plane. It watches for pods that have no node yet. For each one it does three things:

  new pod (spec.nodeName is empty)
        │
        ▼
  1. FILTER   drop every node that CANNOT run the pod
              (not enough free CPU/memory, taint not tolerated,
               affinity rule not met, spread rule broken, ...)
        │     0 nodes left? ─► pod stays Pending (+ maybe preemption, section 9)
        ▼
  2. SCORE    give each remaining node 0-100 per scoring rule,
              add the weighted scores, pick the highest
        │
        ▼
  3. BIND     write spec.nodeName = chosen node
        │
        ▼
  the kubelet on that node sees the pod and starts its containers

The scheduler only chooses. It does not start containers, and it never moves a running pod. If conditions change later (a node fills up, a label changes), running pods stay where they are.

Intuition. Think of a hotel front desk. First it removes rooms that cannot work (too small, wrong floor, under repair). Then it ranks the rest (quiet side, near the lift) and gives you the best. Once you are in the room, the desk does not move you, even if a better room frees up.

2. The Words, in Plain English

WordMeaning
RequestHow much CPU and memory a container says it needs. The scheduler reserves this much on the node.
CapacityThe total CPU and memory of the machine.
AllocatableThe part of capacity that pods may reserve, after the system takes its share.
LabelA key=value tag on an object, like disktype=ssd or topology.kubernetes.io/zone=zone-a.
TaintA "keep out" mark on a node. Pods are repelled unless they tolerate it.
TolerationA pass on a pod that lets it ignore a matching taint.
AffinityA rule that attracts a pod to certain nodes, or to (or away from) other pods.
Topology domainA group of nodes that share a label value: one zone, one rack, or one node (by hostname).
SkewHow uneven a spread is: pods in the fullest domain minus pods in the emptiest one.
PriorityA number on a pod. Higher-priority pods are scheduled first and may push out lower ones.
PreemptionRemoving lower-priority pods from a node to make room for a higher-priority pod.
EvictionThe kubelet (or an API call) stopping a pod and removing it from its node.

3. How Much Room Does a Node Have? Allocatable

A node with 4 CPUs and 16 GiB of memory does not offer all of it to pods. The operating system, the kubelet and the container runtime need some, and the kubelet keeps a small safety margin for evictions:

allocatable = capacity - system-reserved - kube-reserved - eviction threshold

Worked example. Capacity 4 CPU (4000m) and 16 GiB (16384 Mi). Reserved: system 100m CPU and 1 GiB, kube 100m CPU and 1 GiB. Hard eviction threshold: 100 Mi of memory (the default memory.available<100Mi).

  • CPU: 4000m - 100m - 100m = 3800m.
  • Memory: 16384 - 1024 - 1024 - 100 = 14236 Mi (about 13.9 GiB).

See the real values with:

kubectl describe node worker-1     # look at "Capacity", "Allocatable", and "Allocated resources"

The scheduler checks requests, not real use. A pod fits if:

sum of requests of pods already on the node + this pod's request <= allocatable

So a node can be "full" while its CPUs sit at 10% use, because pods requested far more than they use. And a pod with no requests always "fits", even on a busy node. Managed clouds set the reserved amounts for you, and often reserve more on bigger machines.

4. Filter, Then Score: a Worked Example

A new pod requests cpu: 1 and memory: 2Gi. Three nodes:

NodeAllocatableAlready requestedFree
A4 CPU, 16 Gi2 CPU, 4 Gi2 CPU, 12 Gi
B8 CPU, 32 Gi6 CPU, 8 Gi2 CPU, 24 Gi
C4 CPU, 8 Gi3.5 CPU, 2 Gi0.5 CPU, 6 Gi

Filter. Node C has only 0.5 CPU free and the pod needs 1. C is removed. A and B pass.

Score. Many scoring plugins run, each giving 0 to 100. The main resource one, by default, is LeastAllocated: prefer the node that will have the most room left, as a share of its size. For each resource, after adding the pod:

score = (allocatable - requested after placing the pod) / allocatable × 100
NodeCPU scoreMemory scoreAverage
A(4 - 3) / 4 = 25(16 - 6) / 16 = 62.543.75
B(8 - 7) / 8 = 12.5(32 - 10) / 32 = 68.7540.6

Node A wins on this rule. The other scorers (balanced CPU-to-memory use, image already on the node, preferred affinities, spreading) add their own scores with weights, and the total decides. If two nodes tie, one is picked at random.

Spreading vs packing. LeastAllocated spreads pods out, which is kind to noisy neighbours. The opposite strategy, MostAllocated, packs pods tight, so the autoscaler can remove empty nodes and save money. With MostAllocated: A = (75 + 37.5) / 2 = 56.25, B = (87.5 + 31.25) / 2 = 59.4, so B wins. You choose the strategy in the scheduler configuration (managed clouds often expose it as an "optimize utilization" profile).

In large clusters the scheduler does not score every node. Once it has found enough feasible nodes (a percentage that shrinks as the cluster grows), it stops looking and scores only those. This keeps scheduling fast.

5. Choosing Nodes: nodeSelector and Node Affinity

nodeSelector: the simple way

Run only on nodes that have all these labels:

spec:
  nodeSelector:
    disktype: ssd

Node affinity: the flexible way

Node affinity has two kinds of rules. The long names tell you exactly what they do:

  • requiredDuringSchedulingIgnoredDuringExecution: a hard rule. Nodes that fail it are filtered out. "IgnoredDuringExecution" means: if the node's labels change later, the running pod is not removed.
  • preferredDuringSchedulingIgnoredDuringExecution: a soft rule with a weight from 1 to 100. Matching nodes get extra score; others are still allowed.
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64"]
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 80
      preference:
        matchExpressions:
        - key: topology.kubernetes.io/zone
          operator: In
          values: ["zone-a"]
    - weight: 20
      preference:
        matchExpressions:
        - key: node.kubernetes.io/instance-type
          operator: In
          values: ["m6i.xlarge"]

Operators: In, NotIn, Exists, DoesNotExist, Gt, Lt. Logic: several nodeSelectorTerms are ORed (any one may match); several matchExpressions inside one term are ANDed (all must match).

Worked example. Under the rule above, an amd64 node in zone-a of type m6i.xlarge gets 80 + 20 = 100 preference points. One in zone-a of another type gets 80. One in zone-b of type m6i.xlarge gets 20. An arm64 node is filtered out completely. (The preference points are scaled and added to the other scores, so a strongly preferred node can still lose to one with much more free room.)

6. Keeping Pods Away: Taints and Tolerations

Affinity pulls a pod toward nodes. A taint pushes pods away from a node. Only pods with a matching toleration may stay.

kubectl taint nodes gpu-1 dedicated=ml:NoSchedule        # add
kubectl taint nodes gpu-1 dedicated=ml:NoSchedule-       # remove (note the minus at the end)

A taint has a key, an optional value, and an effect:

EffectNew pods without a tolerationPods already running without a toleration
NoScheduleNot placed hereStay
PreferNoScheduleAvoided if possible (soft)Stay
NoExecuteNot placed hereEvicted (right away, or after tolerationSeconds)

The matching toleration on the pod:

tolerations:
- key: dedicated
  operator: Equal      # key and value must match; "Exists" matches any value
  value: ml
  effect: NoSchedule   # leave effect empty to match every effect

A toleration is permission, not attraction. The pod above may run on gpu-1, but nothing sends it there; it can still land on any normal node. To reserve nodes for a team, use both: a taint (keep others out) and node affinity or a nodeSelector (bring this team in). The GPU Scheduling page uses exactly this pattern.

Taints Kubernetes adds by itself

  • node-role.kubernetes.io/control-plane:NoSchedule keeps normal pods off control-plane nodes.
  • node.kubernetes.io/not-ready and node.kubernetes.io/unreachable with effect NoExecute are added when a node stops being healthy.
  • node.kubernetes.io/memory-pressure, disk-pressure, pid-pressure (NoSchedule) are added when the node is short on that resource.
  • node.kubernetes.io/unschedulable is added by kubectl cordon or drain.

Worked timeline: a node dies

Every pod gets two tolerations by default: not-ready and unreachable, each with tolerationSeconds: 300. So when a node's power fails at 10:00:00:

TimeWhat happens
10:00:00The node stops sending heartbeats.
about 10:00:50The node controller's grace period (40 to 50 seconds by default, depending on version) runs out. The node is marked NotReady / Unknown, and the unreachable:NoExecute taint is added. Services stop sending traffic to its pods once those pods are marked not ready.
about 10:05:50The 300-second toleration runs out. The pods are marked for deletion, and their Deployment or ReplicaSet creates replacements on healthy nodes.

About 6 minutes with fewer replicas. If that is too long for an app, lower its tolerationSeconds (for example to 30). Too low, and a short network blip causes needless pod churn. StatefulSet pods are special: a replacement with the same name is not created until the old pod is confirmed gone, which needs the node to come back, the node object to be deleted, or a manual force delete.

7. Pods Near or Far from Other Pods

Pod affinity rules look at other pods, not node labels. Each rule has a topologyKey: the node label that defines "the same place".

topologyKey"Same place" means
kubernetes.io/hostnameThe same node
topology.kubernetes.io/zoneThe same zone (one data centre in a cloud region)
  • podAffinity: "put me in the same place as pods with label X". Example: put a cache next to the app that calls it, to cut network delay.
  • podAntiAffinity: "never (or preferably not) in the same place as pods with label X". Example: no two replicas of the API on one node, so one node failure cannot take them all.
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: api
      topologyKey: kubernetes.io/hostname

Worked example: the hard rule trap. The Deployment has 3 replicas and the rule above. The cluster has 2 nodes. Replica 1 goes to node 1, replica 2 to node 2. Replica 3 has no legal node: it stays Pending forever (or until a third node appears). Worse, during a rolling update with maxSurge: 1, the new pod also needs a node with no app: api pod, so a rollout on a 3-node cluster with 3 replicas gets stuck. For most apps, use the preferred form or, better, a topology spread constraint (next section).

Pod affinity is expensive for the scheduler in big clusters, because it must check pods on every node. Use it with care in clusters with thousands of nodes.

8. Topology Spread Constraints and Skew

A spread constraint says: "keep pods with this label evenly spread across these domains, within a tolerance". The tolerance is maxSkew.

topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule    # hard; "ScheduleAnyway" makes it a soft preference
  labelSelector:
    matchLabels:
      app: api

How the check works. For each candidate domain, the scheduler asks: if I put the new pod here, would (pods in this domain + 1) - (pods in the emptiest domain) be more than maxSkew? If yes, every node in that domain is filtered out.

Worked example. 3 zones. Existing app: api pods: zone-a 3, zone-b 2, zone-c 1. The minimum is 1 (zone-c). maxSkew = 1.

Place new pod inSkew if placedAllowed?
zone-a(3 + 1) - 1 = 3No
zone-b(2 + 1) - 1 = 2No
zone-c(1 + 1) - 1 = 1Yes

The pod goes to zone-c. Keep adding pods and they fill zones evenly: a, b, c, a, b, c...

Useful facts:

  • You can have two constraints, one per zone and one per node (kubernetes.io/hostname). Both must pass.
  • Only scheduling is checked. When pods are deleted (scale-down, a node dies), the spread can become uneven, and nothing moves pods back. A tool called the descheduler can evict pods to rebalance.
  • With DoNotSchedule, if a zone has no free room, pods can go Pending even while other zones have space. That is the rule doing its job: decide whether you prefer "even" or "running".
  • The cluster autoscaler understands these rules and can add a node in the right zone.

9. Priority and Preemption

Some pods matter more than others. A PriorityClass gives pods a number:

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: business-critical
value: 100000
globalDefault: false
description: "Customer-facing APIs"

Pods use it with priorityClassName: business-critical. Pods without one get priority 0 (unless a class is marked globalDefault). Built-in classes system-cluster-critical (2000000000) and system-node-critical (2000001000) are for cluster parts like DNS and networking; your own classes may go up to 1000000000.

Priority does two things:

  1. Queue order. Pending pods with higher priority are tried first.
  2. Preemption. If a high-priority pod fits nowhere, the scheduler looks for a node where deleting some lower-priority pods would make room. It picks the node and victims that cause the least damage (lowest priorities, fewest pods, and it tries not to break PodDisruptionBudgets).

Worked example. One node, 4 CPU allocatable, full with four batch pods (priority 0) of 1 CPU each. An API pod (priority 100000) needs 2 CPU.

  1. Filter: no node fits. Preemption starts.
  2. Removing 2 batch pods frees 2 CPU, which is enough. Those 2 are the victims.
  3. The victims get their normal graceful shutdown (SIGTERM, then up to terminationGracePeriodSeconds). The API pod's status.nominatedNodeName is set to the node while it waits.
  4. When the room is free, the API pod is scheduled there. The 2 batch pods (if owned by a Job or Deployment) are recreated and wait as Pending.

Set preemptionPolicy: Never on a class whose pods should jump the queue but never kick others out. And be careful: if every team marks its pods "critical", priority means nothing.

10. When a Node Runs Short: Eviction Order

Scheduling uses requests, but pods can use more memory than they request (up to their limit). If many do at once, the node runs low. When free memory drops below the hard threshold (default 100 Mi), the kubelet evicts pods until it is back above. It ranks pods by:

  1. Is the pod using more than its request? Those go first.
  2. Then by priority: lower first.
  3. Then by how far above its request it is: more first.

Worked example. Three pods on a node under memory pressure, all priority 0:

PodRequestUsingAbove request?Eviction order
api1 Gi900 MiNo3rd (last)
worker512 Mi1.5 GiYes, by about 1 Gi1st
cronnone (BestEffort)300 MiYes, by 300 Mi2nd

The lesson: a pod that stays within its memory request is the safest pod on the node. This order is linked to the QoS classes described in Workloads. Eviction is different from an OOM kill inside the container's own limit; that case is walked through in Scenario: A Pod Keeps Getting OOMKilled.

11. Reading a FailedScheduling Message

When a pod is Pending, kubectl describe pod shows an event that counts, for every node, why it was filtered out:

Warning  FailedScheduling  default-scheduler  0/6 nodes are available:
  1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: },
  2 Insufficient memory,
  3 node(s) didn't match pod topology spread constraints.
  preemption: 0/6 nodes are available: 1 Preemption is not helpful for scheduling,
  2 No preemption victims found for incoming pod, 3 Preemption is not helpful for scheduling.

Read it line by line. The numbers add up to the node count (1 + 2 + 3 = 6):

PhraseMeaningUsual fix
Insufficient cpu / memoryRequests do not fit in what is left of allocatableLower requests if they are too high, add nodes, or check for a typo like memory: 64G instead of 64Mi
untolerated taint {key: value}The node is tainted and the pod has no matching tolerationAdd the toleration, or this pod should not go there
didn't match Pod's node affinity/selectorNo node has the labels you asked forCheck spelling with kubectl get nodes --show-labels
didn't match pod anti-affinity rulesEvery node already has a pod you said to avoidMore nodes, fewer replicas, or the preferred form
didn't match pod topology spread constraintsPlacing here would break maxSkewRoom in the emptiest domain, or ScheduleAnyway
had volume node affinity conflictThe pod's disk lives in another zoneSee Storage: use WaitForFirstConsumer binding
Preemption is not helpfulEven removing lower-priority pods would not help on that node (for example, a taint blocks it)Fix the filter reason first

If there is no FailedScheduling event at all, check that a scheduler is running and that the pod's schedulerName is right, and whether the pod has schedulingGates (a pod with gates waits until another controller removes them). A step-by-step playbook for Pending and every other stuck pod state is on Debugging Pods.

12. A Full Example (Validated)

A customer-facing API with 6 replicas: amd64 only, prefers zone-a, spread evenly across zones and across nodes, not too sensitive to brief node failures, and protected by priority. This manifest passes kubeconform -strict against the Kubernetes 1.31 schemas.

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: business-critical
value: 100000
globalDefault: false
description: "Customer-facing APIs"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 6
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      priorityClassName: business-critical
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: kubernetes.io/arch
                operator: In
                values: ["amd64"]
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 50
            preference:
              matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values: ["zone-a"]
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: api
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: api
      tolerations:
      - key: node.kubernetes.io/unreachable
        operator: Exists
        effect: NoExecute
        tolerationSeconds: 60
      - key: node.kubernetes.io/not-ready
        operator: Exists
        effect: NoExecute
        tolerationSeconds: 60
      containers:
      - name: api
        image: registry.example.com/api:1.4.2
        resources:
          requests:
            cpu: 500m
            memory: 512Mi
          limits:
            memory: 512Mi

Notes: the zone rule is hard, the node rule is soft (so a missing node never blocks the rollout). The zone preference (weight 50) and the zone spread pull in different directions; with maxSkew 1 the spread wins, and the preference only breaks ties. Memory request equals the limit, so the pod is never "above its request" in the eviction ranking of section 10.

13. Common Pitfalls

  • No requests at all. The scheduler thinks the pod needs nothing and may pile many on one node. Those pods are also first in line for eviction.
  • Requests far above real use. Nodes look full while CPUs idle; you pay for empty machines and new pods go Pending.
  • Toleration without affinity when you wanted dedicated nodes. The pod may land anywhere.
  • Hard anti-affinity with replicas >= nodes. Extra replicas, and rollouts, get stuck Pending.
  • Expecting the scheduler to rebalance. It never moves running pods. Use the descheduler, or restart a rollout.
  • Labels with typos. topology.kubernetes.io/zone vs failure-domain.beta.kubernetes.io/zone (old, removed). Check real labels with kubectl get nodes -L topology.kubernetes.io/zone.
  • Priority for everyone. If every pod is "critical", the batch work you wanted to sacrifice is the same priority as the API.
  • Very low tolerationSeconds. A 10-second network blip then reschedules every pod on the node, which can overload the rest of the cluster.
  • Forgetting DaemonSets in the math. Logging, monitoring and networking agents run on every node and use part of its allocatable room.

14. Practice Problems (with Solutions)

Problem 1: does it fit?

Node allocatable: 3800m CPU, 14 Gi memory. Pods on it request 2500m and 9 Gi in total. A new pod requests 1500m and 4 Gi. Does it fit?

Solution

CPU: 2500 + 1500 = 4000m > 3800m. No, it does not fit, even though memory (13 Gi of 14 Gi) would. The event would say Insufficient cpu.

Problem 2: scoring

A pod requests 2 CPU and 4 Gi. Node X: allocatable 8 CPU / 16 Gi, requested 2 CPU / 8 Gi. Node Y: allocatable 16 CPU / 64 Gi, requested 12 CPU / 16 Gi. Which wins with LeastAllocated?

Solution

X: CPU (8 - 4) / 8 = 50, memory (16 - 12) / 16 = 25, average 37.5. Y: CPU (16 - 14) / 16 = 12.5, memory (64 - 20) / 64 = 68.75, average 40.6. Y wins on this rule (the balanced-allocation scorer, which prefers similar CPU and memory use, would push back toward X; the final total depends on all scorers).

Problem 3: skew

Zones hold 4, 4 and 2 pods of an app with maxSkew 1 on zones. Where can the next pod go? And the one after that?

Solution

Minimum is 2. Zone 1: 5 - 2 = 3 (no). Zone 2: 3 (no). Zone 3: 3 - 2 = 1 (yes). Next pod goes to zone 3, making 4, 4, 3. The one after: minimum is 3; zone 1 or 2 gives 5 - 3 = 2 (no); zone 3 gives 4 - 3 = 1 (yes). Also zone 3, making 4, 4, 4.

Problem 4: how long without the pods?

A node loses power. The grace period before it is marked unhealthy is 50 seconds. Your pods have tolerationSeconds: 60 for unreachable. Roughly when are replacements created?

Solution

About 50 + 60 = 110 seconds after the power loss, instead of about 350 seconds with the default 300.

Problem 5: who is evicted?

Memory pressure on a node. Pod P1: priority 1000, request 1 Gi, using 2 Gi. Pod P2: priority 0, request 2 Gi, using 1.8 Gi. Pod P3: priority 0, request 256 Mi, using 512 Mi. In what order are they evicted?

Solution

Step 1, above request: P1 (yes) and P3 (yes) come before P2 (no). Step 2, priority among P1 and P3: P3 (0) before P1 (1000). Order: P3, then P1, then P2. P1 uses the most above its request, but its higher priority protects it.

Problem 6: the stuck rollout

A 3-node cluster runs 3 replicas with required pod anti-affinity on hostname. The Deployment uses maxSurge: 1, maxUnavailable: 0. A rollout never finishes. Why, and what are two fixes?

Solution

The surge pod needs a node with no app pod, but all 3 nodes have one, and maxUnavailable 0 means no old pod may be removed first. Fixes: set maxUnavailable: 1, maxSurge: 0 (remove one old pod before adding a new one), or replace the hard rule with a topology spread on hostname using ScheduleAnyway, or the preferred anti-affinity form. (Adding a 4th node also works.)

How Containers Really Work

There is no "container" object inside the Linux kernel. A container is an ordinary process with three things added: a limited view of the system, limited resources, and its own files. This page builds each piece by hand with real commands, then puts them together into a working container without Docker. Every output shown was produced on a real Linux machine (kernel 6.12, cgroup v2).

1. The Big Idea in One Picture

When you run docker run nginx, the kernel starts a normal process, just like when you type nginx in a terminal. The difference is that the process is started inside a box made of three kernel features:

                       +-----------------------------------------------+
                       |              one ordinary process             |
                       |                  (e.g. nginx)                 |
                       +-----------------------------------------------+
                          |                    |                    |
              NAMESPACES  |        CGROUPS     |      ROOT FILESYSTEM
          "what can I see?"   "how much can I use?"   "which files are mine?"
           own PIDs, own        memory.max = 512M      image layers stacked
           network, own         cpu.max = 1 CPU        with overlayfs, plus a
           hostname, own        pids.max = 100         thin writable layer
           mounts, users

        + security filters: capabilities, seccomp, AppArmor/SELinux, user namespaces
  • A namespace gives a process its own private copy of one kind of system resource (process IDs, network, hostname, mounts...). Other processes outside it see their own copy.
  • A cgroup (control group) is a group of processes that the kernel counts and limits together: memory, CPU time, number of processes, disk I/O.
  • The root filesystem is the set of files the process sees at /. For a container, it comes from the image, stacked with overlayfs.
Intuition: a virtual machine is a separate house with its own foundation (its own kernel). A container is a room in a shared house: it has its own door, its own furniture, and a meter on its power use, but it shares the foundation, the pipes, and the wiring (the host kernel) with every other room.

Because a container is just a process, you can see it from the host. On a Docker host, ps aux | grep nginx shows the container's nginx with a normal host PID. That one fact explains a lot: containers start in milliseconds (no OS to boot), they are as fast as normal processes, and a kernel bug can affect all of them at once.

2. Namespaces: What a Process Can See

Linux has eight kinds of namespaces. A container usually gets a new one of each kind except, sometimes, user and time.

NamespaceIsolatesWhat the container sees
mnt (mount)The list of mounted filesystemsIts own /, its own /proc, its volumes
pidProcess ID numbersIts first process is PID 1; host processes are invisible
netNetwork interfaces, IPs, routes, ports, firewall rulesIts own eth0 and lo; port 80 is free even if the host uses it
utsHostnameIts own hostname (Docker uses the container ID)
ipcShared memory and message queuesIts own /dev/shm segments
userUser and group IDsCan be "root" (UID 0) inside while being an unprivileged UID like 100000 on the host
cgroupThe view of the cgroup treeIts own cgroup looks like the root
timeBoot and monotonic clocksCan have its own uptime (rarely used)

Every process points at one namespace of each kind. You can see them as links in /proc:

$ ls -l /proc/self/ns
lrwxrwxrwx 1 box box 0 Nov 22 14:20 cgroup -> cgroup:[4026531835]
lrwxrwxrwx 1 box box 0 Nov 22 14:20 ipc -> ipc:[4026532324]
lrwxrwxrwx 1 box box 0 Nov 22 14:20 mnt -> mnt:[4026532292]
lrwxrwxrwx 1 box box 0 Nov 22 14:20 net -> net:[4026531840]
lrwxrwxrwx 1 box box 0 Nov 22 14:20 pid -> pid:[4026532325]
lrwxrwxrwx 1 box box 0 Nov 22 14:20 uts -> uts:[4026532323]
...

The number in brackets is the namespace's ID. Two processes with the same number for net share one network stack. This is exactly how a Kubernetes pod works: all containers in a pod join the same network namespace (so they talk over localhost), while each keeps its own mount namespace (its own files).

Three system calls do all the work:

  • clone() with flags like CLONE_NEWPID starts a new process in new namespaces.
  • unshare() moves the calling process into new namespaces.
  • setns() joins an existing namespace. This is what docker exec and nsenter use to put a new shell inside a running container.

3. Lab: Your First Namespaces with unshare

The unshare command (part of util-linux, present on almost every Linux system) runs a program in new namespaces. You need root (or a user namespace) for most of these.

A private hostname (uts namespace)

$ hostname
grok-bot-vm-187681928
$ sudo unshare --uts bash -c 'hostname box-in-a-box; hostname'
box-in-a-box
$ hostname
grok-bot-vm-187681928          # the host did not change

Private process IDs (pid namespace)

$ sudo unshare --uts --pid --fork --mount-proc bash -c \
    'hostname box-in-a-box; sleep 100 & ps -e -o pid,comm; true'
    PID COMMAND
      1 bash
      3 sleep
      4 ps

Inside, bash believes it is PID 1, the first process on the machine, and sees only 3 processes. The host still sees all of them, with normal large PIDs.

  • --fork is needed because a process cannot change its own PID; the new namespace applies to its children.
  • --mount-proc creates a mount namespace and mounts a fresh /proc. Without it, ps would read the host's /proc and still show every host process. Tools like ps and top just read files in /proc.

A process has two PIDs

From the host, the kernel file /proc/<pid>/status shows both numbers:

$ grep NSpid /proc/416988/status
NSpid:	416988	1          # 416988 on the host, 1 inside its namespace

This is why kill on the host needs the host PID, and why a container's process shows up in the host's top.

An empty network (net namespace)

$ sudo unshare --net bash -c 'ip -brief addr'
lo               DOWN

A brand-new network namespace has only a loopback device, and it is even switched off. No eth0, no routes, no internet. The next section shows how a container runtime wires it up.

4. Network Namespaces, veth Pairs, and Bridges

To connect a network namespace to the outside, runtimes use a veth pair: two virtual network cards joined by a virtual cable. A packet sent into one end comes out of the other. One end goes inside the container (and is renamed eth0); the other end stays on the host and is plugged into a bridge, a virtual network switch (Docker's is called docker0).

   container A netns          container B netns
   +--------------+           +--------------+
   | eth0         |           | eth0         |
   | 172.17.0.2   |           | 172.17.0.3   |
   +------|-------+           +------|-------+
          | veth pair                | veth pair
   -------|--------------------------|----------- host netns
       vethA1                     vethB1
          \__________ docker0 _______/        bridge, 172.17.0.1
                         |
                    host eth0  --- NAT (iptables/nftables MASQUERADE) ---> internet
  • Containers on the same bridge talk directly through the bridge.
  • To reach the internet, the host rewrites the container's private source address to its own (NAT, see IP Addressing & Routing).
  • docker run -p 8080:80 adds a rule: "packets arriving at host port 8080 go to this container's IP, port 80."

Lab: build it by hand

# 1. create a named network namespace and a veth pair
sudo ip netns add red
sudo ip link add veth-host type veth peer name veth-red
# 2. push one end into the namespace
sudo ip link set veth-red netns red
# 3. give both ends addresses on a small private network and switch them on
sudo ip addr add 10.200.0.1/24 dev veth-host
sudo ip link set veth-host up
sudo ip netns exec red ip addr add 10.200.0.2/24 dev veth-red
sudo ip netns exec red ip link set veth-red up
sudo ip netns exec red ip link set lo up
# 4. run a web server inside "red"
sudo ip netns exec red python3 -m http.server 8000 --bind 10.200.0.2 &
$ sudo ip netns exec red ip -brief addr
lo               UNKNOWN        127.0.0.1/8 ::1/128
veth-red@if5     UP             10.200.0.2/24 fe80::a097:c3ff:fe68:b59d/64

$ curl -s -o /dev/null -w "HTTP %{http_code}\n" http://10.200.0.2:8000/
HTTP 200                         # reached through the veth cable

$ curl http://127.0.0.1:8000/
curl: (7) Failed to connect to 127.0.0.1 port 8000 after 0 ms: Could not connect to server
                                 # the host's own port 8000 is empty: the server
                                 # lives in a different network namespace

Clean up with sudo ip netns del red (deleting the namespace also deletes the veth pair). This is, in small, what Docker's bridge network and a Kubernetes CNI plugin do for every container and pod.

5. PID 1 and Signals: Why Containers Ignore Ctrl+C

The first process in a PID namespace is special. On a normal Linux machine, PID 1 is the init system (systemd). The kernel protects it: a signal sent to PID 1 from outside is ignored unless the process has installed a handler for it. The only exceptions are SIGKILL and SIGSTOP, which cannot be blocked.

Inside a container, your app is PID 1. Most programs never install a handler for SIGTERM; they rely on the default action ("exit"). As PID 1, that default does not apply. We can prove it:

$ sudo unshare --pid --fork --mount-proc sleep 300 &
$ grep -E "NSpid|SigCgt" /proc/416988/status
NSpid:	416988	1
SigCgt:	0000000000000000          # no signal handlers installed
$ sudo kill -TERM 416988; sleep 1; ps -p 416988 -o pid,cmd
    PID CMD
 416988 sleep 300                 # still running: SIGTERM was ignored
$ sudo kill -KILL 416988          # SIGKILL always works
$ ps -p 416988 -o pid,cmd
    PID CMD                       # gone

And with a handler:

$ sudo unshare --pid --fork --mount-proc sh -c \
    'trap "echo got SIGTERM, cleaning up; exit 0" TERM; while :; do sleep 0.2; done' &
$ sudo kill -TERM <its host pid>
got SIGTERM, cleaning up

Why it matters: docker stop and Kubernetes both send SIGTERM, wait a grace period (10 s for Docker, 30 s by default in Kubernetes), then send SIGKILL. An app that ignores SIGTERM as PID 1 always waits the full grace period and then dies abruptly, dropping in-flight requests. The exit code is then 137 (128 + 9 for SIGKILL), which people often mistake for an out-of-memory kill.

A second duty of PID 1 is reaping zombies. When any process exits, its parent must collect its exit status. If the parent died, the orphan is handed to PID 1. A real init system collects these; a typical app does not, so finished processes pile up as zombies.

Fixes:

  • Handle SIGTERM in your app (stop accepting work, finish what is in flight, exit).
  • Use the exec form CMD ["node", "server.js"], not CMD node server.js. The shell form starts /bin/sh -c as PID 1, which does not pass signals on to your app.
  • Or run a tiny init as PID 1: docker run --init, or tini as the entrypoint. It forwards signals and reaps zombies. See Docker Fundamentals: best practices.

6. cgroups: What a Process Can Use

Namespaces hide things. They do not stop a process from eating all the memory or CPU. That is the job of cgroups. Modern systems use cgroup v2: a single tree of folders mounted at /sys/fs/cgroup. Each folder is a group. You put a process in a group by writing its PID into the group's cgroup.procs file, and you set limits by writing to other files in the folder. Children of a process stay in its group.

/sys/fs/cgroup/                        root of the tree
├── system.slice/                      system services (systemd)
└── kubepods.slice/                    everything Kubernetes runs
    ├── kubepods-burstable.slice/
    │   └── kubepods-burstable-pod<uid>.slice/       one folder per pod
    │       ├── cri-containerd-<id>.scope/          one folder per container
    │       │     memory.max   memory.current   memory.events
    │       │     cpu.max      cpu.weight       cpu.stat
    │       │     pids.max     cgroup.procs
    │       └── ...
    └── kubepods-besteffort.slice/ ...

The files you will meet most:

FileMeaningSet by
memory.maxHard memory limit. Above it, the kernel reclaims what it can, then OOM-kills a process in the group.docker run --memory, Kubernetes limits.memory
memory.currentMemory used right now by the group, including page cache from files it read or wrote(read only)
memory.eventsCounters: how often the limit was hit (max) and how many OOM kills happened (oom_kill)(read only)
memory.statBreakdown: anon (heap, stack), file (page cache), and more(read only)
cpu.max"quota period": may use quota microseconds of CPU every period microseconds. 50000 100000 = half a CPU.docker run --cpus, Kubernetes limits.cpu
cpu.weightRelative share when CPUs are busy (1-10000, default 100). Not a cap.Kubernetes requests.cpu
pids.maxMost processes and threads the group may have. Stops fork bombs.docker run --pids-limit

CPU math. --cpus=1.5 becomes cpu.max = "150000 100000": 150 ms of CPU time per 100 ms window, spread across any number of cores. A program with 4 busy threads uses that 150 ms in just 37.5 ms of wall time, then is throttled (frozen) for the remaining 62.5 ms of each window. That is why a container can be slow while showing low average CPU. The full story with numbers is in Processes & CPU Scheduling.

7. Lab: Memory, CPU, and Process Limits

A real OOM kill

This Python program allocates 10 MiB at a time and fills it, so the memory is really used:

# hog.py
import time
chunks = []
for i in range(1, 1000):
    chunks.append(bytearray(10 * 1024 * 1024))   # 10 MiB, zero-filled
    print(f"allocated {i*10} MiB", flush=True)
    time.sleep(0.02)

Make a cgroup with a 100 MiB limit (and no swap), move a shell into it, and run the program:

$ sudo mkdir /sys/fs/cgroup/demo
$ echo 100M | sudo tee /sys/fs/cgroup/demo/memory.max
$ echo 0    | sudo tee /sys/fs/cgroup/demo/memory.swap.max
$ sudo bash -c 'echo $$ > /sys/fs/cgroup/demo/cgroup.procs; exec python3 hog.py'
...
allocated 80 MiB
allocated 90 MiB
Killed
$ echo $?
137

$ cat /sys/fs/cgroup/demo/memory.events
low 0
high 0
max 37
oom 1
oom_kill 1

$ sudo dmesg | tail -1
Memory cgroup out of memory: Killed process 416702 (python3) total-vm:116940kB,
anon-rss:102016kB, file-rss:5764kB, shmem-rss:0kB, UID:0 pgtables:260kB oom_score_adj:0

Read the evidence: the limit was hit 37 times (max 37; each time the kernel tried to free memory), then it gave up and killed the process (oom_kill 1). The kernel log names the group (oom_memcg=/demo in the full message) and shows the process held about 100 MiB of anonymous memory. The rest of the machine was not affected at all. This is exactly what happens when a Kubernetes container shows OOMKilled; the OOMKilled scenario walks through debugging one.

Page cache counts, but does not kill

In the same 100 MiB group, write a 300 MiB file:

$ sudo bash -c 'echo $$ > /sys/fs/cgroup/demo/cgroup.procs
    dd if=/dev/zero of=big.bin bs=1M count=300 status=none; echo dd-exit=$?
    grep -E "^(anon|file) " /sys/fs/cgroup/demo/memory.stat
    cat /sys/fs/cgroup/demo/memory.current'
dd-exit=0
anon 237568                  # 0.2 MiB of real program memory
file 100003840               # 95 MiB of cached file data
104026112                    # memory.current: 99 MiB, right at the limit

The group sat at its limit, yet nothing was killed. File cache is "clean" (a copy of data already on disk), so the kernel simply drops old cache pages to make room. Only memory that cannot be dropped, like a program's heap, leads to an OOM kill. Lesson: memory.current near the limit does not mean danger by itself; look at anon.

CPU throttling, measured

$ echo "50000 100000" | sudo tee /sys/fs/cgroup/mini/cpu.max     # half a CPU
$ sudo bash -c 'echo $$ > /sys/fs/cgroup/mini/cgroup.procs
    exec timeout 3 sh -c "while :; do :; done"'                   # spin for 3 s
$ grep -E "usage_usec|nr_periods|nr_throttled|throttled_usec" /sys/fs/cgroup/mini/cpu.stat
usage_usec 1582407           # about 1.5 s of CPU used in 3 s: half a CPU
nr_periods 38
nr_throttled 30              # throttled in 30 of 38 windows
throttled_usec 1465648       # about 1.5 s spent frozen

A process limit

$ echo 20 | sudo tee /sys/fs/cgroup/mini/pids.max
# inside the group, try to start 30 background sleeps:
/bin/sh: can't fork: Resource temporarily unavailable
$ cat /sys/fs/cgroup/mini/pids.events
max 1

Clean up with sudo rmdir /sys/fs/cgroup/demo once no process is left in it.

8. The Root Filesystem: Layers and overlayfs

An image is made of layers. Each layer is a set of file changes: files added, changed, or deleted, usually from one Dockerfile step. Layers are read-only and shared: ten containers from the same image use one copy on disk.

To give a container one normal-looking /, the runtime stacks the layers with overlayfs, a filesystem built into Linux that merges several folders into one view:

  what the container sees  ->  merged/      (one combined view)
                                  ^
  container layer (writable) -> upperdir/    changes made by this container
  image layer N   (read-only)  \
  ...                           > lowerdir/  stacked; upper ones win
  image layer 1   (read-only)  /

  read a file   : take it from the highest layer that has it
  change a file : "copy-up" - copy the whole file into upperdir, then change it
  delete a file : put a "whiteout" marker in upperdir that hides the lower copy

Lab: overlayfs by hand

$ mkdir -p ovl/{lower,upper,work,merged} && cd ovl
$ echo "v1 from image" > lower/app.conf
$ echo "keep me"       > lower/readme.txt
$ sudo mount -t overlay overlay -o lowerdir=lower,upperdir=upper,workdir=work merged

$ echo "changed in container" | sudo tee merged/app.conf   # change a file
$ sudo rm merged/readme.txt                                 # delete a file
$ echo "new" | sudo tee merged/new.txt                      # add a file

$ ls -l merged
-rw-r--r-- 1 box  box  21 Nov 22 14:21 app.conf
-rw-r--r-- 1 root root  4 Nov 22 14:21 new.txt

$ ls -l lower; cat lower/app.conf          # the "image" is untouched
-rw-r--r-- 1 box box 14 Nov 22 14:21 app.conf
-rw-r--r-- 1 box box  8 Nov 22 14:21 readme.txt
v1 from image

$ ls -l upper                              # all changes live here
-rw-r--r-- 1 box  box    21 Nov 22 14:21 app.conf
-rw-r--r-- 1 root root    4 Nov 22 14:21 new.txt
c--------- 2 root root 0, 0 Nov 22 14:21 readme.txt

Look at the last line: the deleted file became a character device with number 0, 0. That is the whiteout marker. It hides lower/readme.txt from the merged view without touching the lower layer.

Three practical results:

  • Deleting in a later layer does not shrink an image. RUN rm big.tar in a new Dockerfile step only adds a whiteout; the bytes are still in the earlier layer. Delete in the same RUN step that created the file, or use a multi-stage build (Advanced Docker).
  • Copy-up copies the whole file. Changing one byte of a 2 GiB file in a lower layer first copies all 2 GiB into the container layer. Databases and other heavy writers should write to a volume, which bypasses overlayfs.
  • The container layer dies with the container. docker rm deletes upperdir. Anything worth keeping must be in a volume.

9. An Image, Pulled Apart by Hand

An image is not magic either. Under the OCI image specification (the open standard Docker and others follow), it is three kinds of plain files, each named by the SHA-256 hash of its contents (its digest):

  1. A manifest (JSON): lists the config and the layers by digest.
  2. A config (JSON): the default command, environment variables, working directory, and the history of build steps.
  3. Layers: compressed tar archives of files.

We can download Alpine Linux 3.20 from Docker Hub with just curl:

$ TOKEN=$(curl -s "https://auth.docker.io/token?service=registry.docker.io&scope=repository:library/alpine:pull" | jq -r .token)
$ R=https://registry-1.docker.io/v2/library/alpine
# the tag "3.20" points to an index with one manifest per CPU type; we pick the amd64 one
$ curl -s -H "Authorization: Bearer $TOKEN" \
       -H "Accept: application/vnd.oci.image.manifest.v1+json" \
       $R/manifests/sha256:c64c687cbea9300178b30c95835354e34c4e4febc4badfe27102879de0483b5e | jq .
{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "config": {
    "mediaType": "application/vnd.oci.image.config.v1+json",
    "digest": "sha256:bf8527eb54c3680e728d5b4b383a8ba730d72dae7236fbc8dff97ed6b224a731",
    "size": 612
  },
  "layers": [
    {
      "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "digest": "sha256:25f1d6b1951ac8eb3740558fe94cb83d377bdadf95fd9f98b50d2e1b96130471",
      "size": 3630321
    }

  ...
}

The config (trimmed):

{
  "architecture": "amd64",
  "os": "linux",
  "config": {
    "Env": ["PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"],
    "Cmd": ["/bin/sh"]
  },
  "rootfs": { "type": "layers", "diff_ids": ["sha256:08bc4e53...a4a2"] },
  "history": [
    "ADD alpine-minirootfs-3.20.10-x86_64.tar.gz / # buildkit",
    "CMD [\"/bin/sh\"]"
  ]
}

And the single layer is a normal tar file whose hash matches its name:

$ curl -sL -H "Authorization: Bearer $TOKEN" $R/blobs/sha256:25f1d6b1...0471 -o layer.tgz
$ sha256sum layer.tgz
25f1d6b1951ac8eb3740558fe94cb83d377bdadf95fd9f98b50d2e1b96130471  layer.tgz
$ tar tzf layer.tgz | head -4
bin/
bin/arch
bin/ash
bin/base64
$ tar tzf layer.tgz | wc -l
517
  • Because names are hashes, a layer can be checked after download (a changed byte changes the hash), and two images that share a base layer download and store it only once.
  • A tag like 3.20 is a movable label; a digest is fixed forever. Pin by digest (alpine@sha256:...) when you need the exact same bits every time.
  • Cmd in the config is what CMD in a Dockerfile writes. When you run the image, the runtime reads it to know which program to start.

10. Who Does What: docker, containerd, runc, kubelet

   You                      Kubernetes
   docker run ...           kubelet (on every node)
        |                        |  CRI (Container Runtime Interface, gRPC)
        v                        v
     dockerd  ------------>  containerd   (or CRI-O)     pulls images, unpacks layers,
                                 |                         sets up overlayfs snapshots
                                 v
                          containerd-shim                  one per container; keeps it
                                 |                         running if containerd restarts
                                 v
                               runc                        OCI runtime: reads config.json,
                                 |                         then exits once the app starts
                                 v
   clone(new namespaces) -> join cgroup -> mount rootfs (pivot_root)
   -> drop capabilities, apply seccomp -> exec your program (it becomes PID 1)
  • runc does the real kernel work from this page. It reads an OCI runtime config.json (namespaces to create, cgroup limits, mounts, the command) and makes the system calls.
  • containerd manages images and containers' lifecycles. Docker uses it under the hood, and so do most Kubernetes clusters (Kubernetes removed its built-in Docker support, "dockershim", in version 1.24; images built with Docker still run fine because they follow the same OCI format).
  • Other OCI runtimes can replace runc: crun (faster, written in C), gVisor (runsc, a user-space kernel for stronger isolation), and Kata Containers (each container in a tiny VM).

11. Security Layers and Their Limits

Namespaces and cgroups are about visibility and fair use. They are not a strong security wall on their own, because every container talks to the same kernel. Runtimes add more layers:

LayerWhat it doesDefault in Docker
CapabilitiesRoot's powers are split into about 40 pieces (for example CAP_NET_ADMIN, CAP_SYS_ADMIN). A container gets only a small set.About 14 kept; dangerous ones like CAP_SYS_ADMIN dropped
seccompA filter on system calls. Calls the app should never need (like loading kernel modules) are refused. See System Calls for the kernel side of this door.A default profile blocks dozens of risky calls
AppArmor / SELinuxRules on which files and resources a process may touch.On if the host supports it
User namespaces"root" inside maps to an unprivileged user outside, so an escape lands as nobody.Off by default; on in rootless Docker and Podman
Read-only root filesystemThe container cannot change its own files.Off; use --read-only or readOnlyRootFilesystem: true
Big warning: --privileged turns almost all of this off: all capabilities, no seccomp, access to host devices. A process that is root in a privileged container is effectively root on the host. Mounting the Docker socket (/var/run/docker.sock) into a container is just as powerful, because it can ask Docker to start a privileged container.

When you run code you do not trust (for example, code written by users or by an AI agent), add a stronger boundary: gVisor, Kata Containers, or a micro-VM like Firecracker.

12. Capstone: A Container from Scratch

Now put every piece together: the Alpine layer from section 9 as the root filesystem, a cgroup with limits from section 6, and namespaces from section 2. No Docker involved.

# 1. root filesystem: unpack the image layer
mkdir rootfs && tar xzf layer.tgz -C rootfs

# 2. cgroup: 50 MiB of memory, 20 processes, half a CPU
sudo mkdir /sys/fs/cgroup/mini
echo 50M            | sudo tee /sys/fs/cgroup/mini/memory.max
echo 20             | sudo tee /sys/fs/cgroup/mini/pids.max
echo "50000 100000" | sudo tee /sys/fs/cgroup/mini/cpu.max

# 3. join the cgroup, create namespaces, switch root, start a shell
sudo bash -c "echo \$\$ > /sys/fs/cgroup/mini/cgroup.procs
  exec unshare --mount --uts --ipc --net --pid --fork \
       --mount-proc=$PWD/rootfs/proc \
       chroot $PWD/rootfs /bin/sh -c 'hostname mini; hostname; head -2 /etc/os-release; ps; true'"

Output:

mini
NAME="Alpine Linux"
ID=alpine
PID   USER     TIME  COMMAND
    1 root      0:00 /bin/sh -c hostname mini; hostname; head -2 /etc/os-release; ps; true
    5 root      0:00 ps

(The trailing ; true keeps sh alive as PID 1; without it, sh would replace itself with ps.) The host runs some other Linux, but this shell sees Alpine's files, its own hostname, only its own processes (it is PID 1), an empty network with just lo, and it is capped at 50 MiB, 20 processes, and half a CPU (the pids.max and cpu.max tests in section 7 ran in this exact cgroup). That is a container.

What real runtimes add on top: pivot_root instead of chroot (so the old root can be fully unmounted and escaped from less easily), a populated /dev, a veth network, overlayfs instead of a plain folder, dropped capabilities and seccomp, user namespaces, and logging.

13. Practice Problems

Try each one before reading the answer.

Problem 1: what is shared?

A Kubernetes pod has two containers: app listens on port 8080 and sidecar wants to call it. Which namespaces do they share, and what URL should the sidecar use? Can the sidecar read /app/config.yaml from the app's image?

Answer: Containers in a pod share the network namespace (and the IPC namespace; the PID namespace only if shareProcessNamespace: true). So the sidecar calls http://localhost:8080. Each container has its own mount namespace and root filesystem, so the sidecar cannot see the app's image files. To share files, mount the same volume (for example an emptyDir) into both.

Problem 2: CPU quota

A container has limits.cpu: 2 and runs a program with 8 busy threads on a 16-core node. The period is 100 ms. What is in cpu.max? How long does the program run in each period before it is throttled?

Answer: cpu.max = "200000 100000": 200 ms of CPU time per 100 ms. Eight threads burn 8 ms of CPU per 1 ms of wall time, so the quota is gone after 200 / 8 = 25 ms. The program is frozen for the other 75 ms of every period. Any request that arrives then waits.

Problem 3: why is the image still big?

A Dockerfile has RUN curl -o /tmp/data.tar big-file-url (800 MB), then RUN tar xf /tmp/data.tar -C /opt, then RUN rm /tmp/data.tar. The image is still about 1.6 GB. Why, and how do you fix it?

Answer: Each RUN makes a layer. Layer 1 holds the 800 MB tar, layer 2 the unpacked files, and layer 3 only a whiteout that hides the tar. The bytes stay in layer 1. Fix: download, unpack, and delete in one RUN step (RUN curl ... && tar ... && rm ...), or do it in a build stage and COPY --from only /opt into the final stage.

Problem 4: read the exit code

A pod is stopped during a deploy. It always takes exactly 30 seconds to go away and ends with exit code 137. kubectl describe says Reason: Error, not OOMKilled. What is going on?

Answer: 137 = 128 + 9: it was killed with SIGKILL. Since the reason is not OOMKilled, the kubelet sent it after the 30-second grace period. The app ignored SIGTERM, most likely because it runs as PID 1 with no handler, or behind a shell started with CMD in shell form. Fix: handle SIGTERM, use exec form, or add tini/--init.

Problem 5: will it be killed?

A container has memory.max = 512 MiB. memory.stat shows anon = 180 MiB and file = 320 MiB, and the app now copies a 2 GiB file. Will it be OOM-killed?

Answer: Very likely not. The 320 MiB is page cache that the kernel can drop, and copying a file mostly adds more clean cache, which gets reclaimed as needed. Only 180 MiB is memory that cannot be reclaimed. The risk comes if anon grows toward 512 MiB (or if files are written to a memory-backed tmpfs, which counts as memory that cannot be dropped).

14. Common Pitfalls

  • Thinking a container is a small VM. It shares the host kernel. A kernel bug or a privileged container affects the whole host.
  • Reading /proc/meminfo or nproc inside a container to size things. These often show the host's memory and CPUs, not the cgroup limits. Read /sys/fs/cgroup/memory.max and cpu.max, or use runtimes that are cgroup-aware (recent JVMs, Go 1.25+ for CPU limits, GOMEMLIMIT for memory).
  • Shell-form CMD. /bin/sh becomes PID 1 and swallows SIGTERM, so every stop waits the full grace period.
  • Writing heavy data inside the container layer. Copy-up and overlayfs make it slow, and it disappears with the container. Use volumes.
  • Deleting files in a later Dockerfile step to save space. It only adds a whiteout.
  • Blaming every exit code 137 on memory. 137 only means SIGKILL. Check the reason and memory.events.
  • Mounting the Docker socket or using --privileged "just to make it work". Both give away the host.

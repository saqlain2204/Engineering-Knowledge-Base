Agent and LLM Memory

How agents remember across turns, sessions, and users.

What types of memory do agents need, and how do short-term and long-term differ?
  • Working memory - current turn scratchpad: plan, last tool result, draft output (in-context).
  • Short-term (episodic) - session/thread scope: message list, rolling summary, task state this visit.
  • Long-term (semantic) - cross-session: user preferences, prior resolutions, extracted facts (vector DB, SQL, graph).
  • Procedural - how to act: system prompts, playbooks, fine-tuned weights (org/agent level).
  • Shared/collective - product-wide docs and runbooks (often overlaps with RAG).

Short-term is fast and lossless until the context window fills; long-term is larger but needs explicit write, index, and retrieval. Context window is RAM; persistent memory is disk - you page data in deliberately.

What short-term session memory patterns exist and when do you use each?
  • Full buffer - append all messages; simple, lossless until overflow. Best for short chats and eval replay.
  • Sliding window - keep last k turns or n tokens; cheap but drops early constraints unless pinned elsewhere.
  • Token-aware trimming - drop middle or large tool payloads first; preserve system + first user message + recent tail.
  • Scratchpad - structured working notes (goal, constraints, done, next) the agent updates; survives aggressive summarization better than buried prose.
  • Typed state (LangGraph) - fields like messages, plan step, artifacts; nodes read/write schema instead of parsing free-form chat.
How does summarization extend session memory, and what are its main risks?

When raw history exceeds the token budget, older turns compress into a rolling summary while recent messages stay verbatim. Update every N turns: previous summary + new messages → new summary, with prompts that preserve constraints, decisions, open tasks, and IDs while dropping small talk. Hierarchical summaries (session → daily → profile) scale further. Summarization is lossy compression - silent amnesia is the top failure mode. Mitigate by pinning immutable facts to long-term store before summarizing, keeping verbatim tool errors and numeric outputs, logging summary diffs, and using structured JSON facts instead of prose when precision matters.

How does vector memory work for long-term agent recall?

Write path: select candidates (post-extraction), chunk with metadata (user_id, session_id, timestamp, type), embed with a consistent model, upsert to vector store.

Read path: embed current query (+ optional plan), similarity search with mandatory metadata filters, re-rank (cross-encoder, MMR), inject top-k with citations and timestamps.

Vector memory answers "what past text is similar to now?" not "what is objectively true?" - pair with structured stores and consolidation for high-stakes facts. Always scope by user_id/tenant; cross-user leakage is a severe privacy failure.

When should you use structured memory instead of (or alongside) vector memory?
  • Key-value user profile - exact fields like timezone, language, shipping_address_id; load every session (~500-1500 tokens).
  • Episodic event log - append-only events (purchases, ticket IDs); query by time/type without semantic guesswork.
  • Knowledge graph - entities and relations for multi-hop CRM/ITSM questions; higher setup cost.
  • Hybrid - canonical fact in SQL, narrative episode in vector index linked by fact_id; vector finds context, SQL confirms current truth.

SQL/KV excels at exact lookup and transactions; vectors excel at fuzzy text recall but lack native truth maintenance. Use structured memory for numbers, IDs, and facts that must not drift.

How do extraction and consolidation pipelines decide what enters long-term memory?

Extraction triggers: end-of-session batch, per-turn "remember this" classifier, post-tool outcomes, explicit user commands.

Extract stable user-specific facts as JSON (type, text, confidence); exclude chit-chat and debug output. Gate writes: no PII without consent, no secrets, no unverified model guesses labeled as facts; use proposed vs confirmed for sensitive data.

Consolidation merges new facts with existing store: recency wins on explicit updates, confidence/source ranking, optional LLM merge pass, human review queue on contradictions. Anti-pattern: embedding every assistant reply creates a self-reinforcing hallucination index - prefer user-verified or tool-grounded content.

What retrieval strategies should you combine when assembling memory for a turn?
  • Always-on profile - small KV bundle every request for baseline personalization.
  • Query-conditioned vector search - embed current message; tune k and similarity threshold on eval set.
  • Recency bias - timestamp decay or "last 7 days" filter for support context.
  • Importance scores - weight facts that affected money/account at write time.
  • Tool-based lookup - expose search_memory / get_user_profile so the agent fetches only when needed (saves tokens).
  • MMR / reranking - reduce redundant near-duplicate episodes; cross-encoder for precision.
  • HyDE / query expansion - bridge vocabulary mismatch between question and stored text.
What's the difference between session memory and persistent memory?

Session (thread): message list, summaries, tool artifacts, LangGraph checkpoint state keyed by thread_id - dies or archives when the thread ends.

Persistent: user profile across threads, org knowledge, learned outcomes ("last order #12345 shipped") - survives devices and sessions.

Promotion pipeline: detect durable fact in session → validate and dedup → write to long-term index → optionally pointer in session summary. Keep threads isolated (multi-tab = parallel narratives); cross-thread recall is persistent memory's job. On login, merge anonymous session memory into user profile with conflict rules and audit log.

How does agent memory differ from RAG, and when do you need both?
DimensionRAGAgent memory
SourceCurated docs, wikis, corporaConversations, tool results, extractions
UpdateBatch ingest, versioned releasesContinuous per session/user
ScopeUsually shared/org-widePer-user or per-agent
Truth modelAuthoritative documentsProbabilistic; needs consolidation
Eval focusCitation accuracy, groundingRetention, forgetting, contradiction

Production copilots commonly layer: RAG (policies, API docs) + memory (preferences, past cases) + session (current ticket, tool traces). Prompt order: system policies → RAG with citations → user memory → session summary → recent messages. RAG alone suffices for static, single-session Q&A; memory is required for returning users, multi-day tasks, and personalization RAG corpora cannot capture.

What LangChain memory abstractions exist and when are they appropriate?
  • ConversationBufferMemory - full history, unbounded until external trim.
  • ConversationBufferWindowMemory - last k turn pairs.
  • ConversationSummaryMemory - LLM-compressed history.
  • ConversationSummaryBufferMemory - hybrid: recent raw + summary of older content within token budget.
  • VectorStoreRetrieverMemory - vector-backed episodic recall per query.
  • Entity memory - structured tracking of people/places via extraction.
  • RunnableWithMessageHistory - separates chain logic from session backend (Redis, SQL) via session_id.

New agent projects should prefer LangGraph checkpoints + explicit store modules for clearer state and replay; LangChain memory remains useful for simple LCEL chat wrappers.

What do LangGraph checkpoints and Store provide for agent memory?

Checkpoints persist graph state (messages, custom fields, pending sends) at super-step boundaries - session replay tapes for thread survival, human-in-the-loop pause/resume, time-travel debugging. Backends: MemorySaver (dev), PostgresSaver (production). Same thread_id resumes; new thread starts fresh. Checkpoints are not automatic cross-session user memory unless nodes write to a store.

LangGraph Store is the filing cabinet across threads: namespaced tuples like (users, user_id) with optional embed search on values. Intuition: checkpoints = session tape; Store = durable user/org memory.

How do you handle PII, privacy, and security risks in agent memory?
  • Cross-tenant leakage - mandatory user_id filters on every vector/SQL read; integration tests per tenant.
  • PII minimization - store IDs not full payment details; redact SSN/cards/API keys before embed; tier memories (public, internal, sensitive).
  • Prompt injection via memory - attacker plants instructions in stored text retrieved later; wrap retrieved content in untrusted delimiters, separate structurally from system instructions, never execute tools based solely on memory.
  • Access control - same auth as API; role-based break-glass for support with logging.
  • Deletion/export - GDPR/CCPA requires purge across SQL, vectors, summaries, checkpoints with tracked IDs (no orphan embeddings).
How do you evaluate an agent memory system?
  • Write accuracy - precision/recall vs labeled extractions.
  • Retention - delayed probe questions after N turns or a new session.
  • Retrieval - recall@k, MRR, nDCG on whether the right memory was injected.
  • Forgetting - false recall on outdated facts after preference updates.
  • Contradiction handling - consistency after update sequences.
  • Task success - end-to-end agent success with vs without memory (ablations).

Benchmark patterns: needle-in-haystack (fact at turn 3, ask at turn 50), multi-session recall, distraction filler turns, mid-session preference updates. Memory fails quietly - combine synthetic CI scripts with sampled production logs. Log whether failures are: never written, written but not retrieved, retrieved but truncated, or retrieved but ignored.

What production patterns keep agent memory reliable at scale?
  • Central MemoryService API - get_context, record_turn, async extract_and_persist, delete_user; agents never touch vector DB directly.
  • Async extraction queue - do not block user latency on extraction LLM calls.
  • Versioned schema - tag embedding_model and schema_version; backfill on model changes.
  • Observability - log retrieved memory IDs/scores, trace summarization (redacted), alert on empty retrieval spikes.
  • Feature flags - gradual rollout; kill switch to disable retrieval without taking down chat.
  • Caching - profile bundle in Redis with invalidate-on-write.
  • Cost controls - cap daily embed ingest per user, cap auto-retrieved tokens, smaller model for extraction vs main agent.

Mantra: writes are async and gated; reads are scoped and logged; deletes are complete and tested.

What are common agent memory failure modes and how do you mitigate them?
  • Summary amnesia - early constraint ignored → pin facts to LTM, structured summary, eval needles.
  • Memory hallucination - agent cites false past events → ground with IDs, show sources, lower temperature on recall.
  • Stale memory - outdated preference applied → TTL, updated_at checks, explicit supersede on conflict.
  • Retrieval miss - user repeats self → HyDE, hybrid search, always-on profile for top facts.
  • Retrieval noise - irrelevant old chats injected → higher threshold, MMR, reranker, tool-based lookup.
  • Cross-user leak - wrong personal data → mandatory filters, per-tenant tests.
  • Injection via memory - hostile stored text steers agent → delimiter wrapping, instruction hierarchy.
  • Token blow-up - latency/cost spikes → hard caps on retrieved chars; trim tool outputs first.
  • Duplicate memories - cluttered index → consolidation job, embedding dedup threshold.
  • Embedding drift - recall drops after model change → version index, scheduled re-embed.
How do you budget context tokens across memory layers?

Memory design is explicit budget allocation: reserve system + tools + output headroom first, then allocate to retrieved chunks (RAG + long-term hits), historical summary + recent raw messages, and working turn content. Every retrieved token has cost and attention-dilution risk ("context rot") - stuffing the full window degrades instruction following. Treat context like a cache with eviction (LRU messages, TTL facts, priority boost for user-stated constraints). Prefer targeted retrieval over maximal history; compare token cost vs success lift in ablations to justify complexity.

How should forgetting, TTL, and user deletion work in production memory?

Not all memories live forever: apply TTL on marketing context, session-scoped goals, and stale inventory facts. Consolidation should supersede contradictions (recency or confidence wins) rather than accumulate conflicting entries. User deletion must be complete across SQL profile rows, vector index entries, cold-storage summaries, LangGraph checkpoint tables, and caches - track memory IDs at write time so nothing is orphaned. Offer opt-out of persistent personalization without necessarily deleting the account. Document retention in privacy policy and obtain consent for cross-session memory.

Reasoning Models & Test-Time Compute

For years, the way to get a smarter model was to train a bigger one. Reasoning models add a second dial: let the model spend more compute while answering, by thinking longer, trying several times, or checking its own work. This page builds the idea from zero, works the math by hand, and measures each method with small simulations you can run. All numbers in the tables come from the Python code on this page.

1. The Big Idea: Two Ways to Spend Compute

Think about a student in an exam. Two things decide how well they do:

  • How much they studied before the exam. For a model, this is training compute: more data, more parameters, longer training.
  • How much time and scratch paper they use during the exam. For a model, this is test-time compute (also called inference-time compute): the work done each time it answers a question.

A normal chat model answers a hard math question the way a student blurts out the first number that comes to mind. A reasoning model first writes a long private scratchpad: it breaks the problem into steps, tries an approach, notices a mistake, backs up, checks the result, and only then writes the final answer.

Intuition: some questions are hard to answer in one go but easy to check, like "what is 4,913 divided by 17?" or "does this code pass the tests?". For such questions, spending more effort at answer time pays off a lot, and checking lets you pick the good attempts.

Since 2024, this has become a main direction in AI: reasoning models (from many labs, including open-weight ones such as DeepSeek-R1 and Qwen's QwQ and Qwen3 "thinking" modes) score far higher on math, coding, and science tests than models of similar size that answer directly.

3. Why Thinking Out Loud Helps

A transformer does a fixed amount of work per token: one pass through all its layers. A rough rule is about $2 \times N$ floating-point operations per token for a model with $N$ parameters. For a 7-billion-parameter model:

  • Answer in 1 token: about $2 \times 7 \times 10^9 = 1.4 \times 10^{10}$ operations. That is all the "thinking" the model can do.
  • Think for 1,000 tokens first: about $1.4 \times 10^{13}$ operations, a thousand times more work on the same question.

The written tokens also act as memory. Each new token can look back at everything already written, so the model can store partial results and build on them, the way you write down carries in long multiplication.

Worked example: 47 × 38

Asked to answer in one token, a model must produce "1786" from pattern-matching alone. Asked to think first, it can write:

47 x 38 = 47 x 40 - 47 x 2
        = 1880 - 94
        = 1786
Check: 1786 / 38 = 47. Correct.

Each line is an easy step the model is very likely to get right, and the last line catches mistakes. This is why the classic prompt "Let's think step by step" (zero-shot chain of thought) helped older models on math and logic. Reasoning models are trained so that this behavior is built in, longer, and better. The basic prompting tricks are in Prompt Engineering.

4. Three Ways to Spend Test-Time Compute

1. SEQUENTIAL: think longer in one chain
   question -> [step][step][check][oops, back up][step][check] -> answer

2. PARALLEL: many independent tries, then pick one
                 /-> try 1 -> answer 42 \
   question ----+--> try 2 -> answer 41 --+-> pick: majority vote, or best verifier score
                 \-> try 3 -> answer 42 /

3. SEARCH: grow partial solutions step by step, keep only the promising ones
   question -> step 1 options (a)(b)(c) -> score each -> keep best 2
            -> step 2 options from each -> score -> keep best 2 -> ... -> answer
  • Sequential is what a reasoning model does inside one response. It is good when later steps depend on earlier ones and the model can notice its own errors.
  • Parallel works with any model. It is easy to run at the same time on many GPUs, so it adds cost but little extra waiting time.
  • Search needs a way to score partial work (a process reward model). It can be the most compute-efficient, but it is the most complex to build.

Research on scaling test-time compute (Snell et al., 2024) found that the best mix depends on difficulty: for easier questions, letting the model revise its own answer works well; for harder ones, broader search helps more. Choosing the method per question used about 4 times less compute than plain best-of-N for the same accuracy.

5. Self-Consistency: Majority Voting, Measured

Self-consistency (Wang et al., 2022): sample $N$ chains of thought at a temperature above 0, take the final answer from each, and return the answer that appears most often. No verifier is needed, only a way to compare final answers (easy for a number, hard for an essay).

Why should voting help? If the right answer is the single most likely answer, then with more samples its share in the vote gets closer to its true probability, and it wins more and more often. Wrong answers usually differ from each other, so they split the vote.

Simulation

We model a question as a list of possible answers with probabilities, draw $N$ samples, take the plurality (ties broken at random), and repeat 20,000 times:

import random
from collections import Counter
random.seed(0)

def sample(dist):
    r, acc = random.random(), 0
    for ans, p in dist:
        acc += p
        if r < acc:
            return ans
    return dist[-1][0]

def vote_acc(dist, n, trials=20000):
    ok = 0
    for _ in range(trials):
        c = Counter(sample(dist) for _ in range(n))
        top = max(c.values())
        winners = [a for a, v in c.items() if v == top]
        ok += random.choice(winners) == "right"
    return ok / trials

A = [("right", 0.4)] + [(f"wrong{i}", 0.1) for i in range(6)]          # errors are scattered
B = [("right", 0.3), ("trap", 0.45)] + [(f"wrong{i}", 0.05) for i in range(5)]  # one common mistake

Two lessons:

  • Case A: the model is right only 40% of the time, yet with 33 votes it is right 98% of the time. Its errors are scattered, so they never agree with each other.
  • Case B: the model makes one common mistake more often than it is right. Voting makes things worse: from 30% down to 16%. More samples just make the trap win more reliably.
Rule: voting fixes random errors, not systematic ones. If a model has a consistent misconception (a classic trick question, a wrong fact it learned), no number of votes helps. You need a better model, more information (for example retrieval), or a real verifier.

6. Best-of-N and Verifiers

Best-of-N: sample $N$ answers, score each with a verifier, return the highest-scoring one. How good this is depends almost entirely on the verifier.

Perfect verifier

For code with good unit tests, or math with a known answer, the check is (almost) perfect. Then best-of-N succeeds if any of the $N$ samples is right. If each sample is right with probability $p$, independently:

$$P(\text{at least one right}) = 1 - (1-p)^N$$

With $p = 0.4$: $N=1$ gives 0.40, $N=2$ gives $1 - 0.6^2 = 0.64$, $N=4$ gives $1 - 0.6^4 = 0.87$, $N=8$ gives $1 - 0.6^8 = 0.983$.

Noisy verifier

A learned reward model makes mistakes. We simulate that: a right answer gets score $1 + \text{noise}$, a wrong one $0 + \text{noise}$, where the noise is Gaussian with spread $\sigma$, and we keep the sample with the top score.

def best_of_n(p, n, sigma, trials=20000):
    ok = 0
    for _ in range(trials):
        best = None
        for _ in range(n):
            good = random.random() < p
            score = random.gauss(1 if good else 0, sigma)
            if best is None or score > best[0]:
                best = (score, good)
        ok += best[1]
    return ok / trials

A good verifier gets almost all the benefit. A weak one still helps, but slowly: with 64 samples it is still wrong 11% of the time, because among many wrong answers, one will get a lucky high score.

Watch out at large N: a learned reward model has blind spots. The more samples you draw, the more likely one of them exploits a blind spot (for example, a confident tone or a long answer that "looks" correct). This is reward hacking at inference time. With weak verifiers, accuracy can even go down after some N. Keep a held-out check with a trustworthy grader.

7. pass@k: Measuring "Right in k Tries"

Benchmarks for code and math often report pass@k: the chance that at least one of $k$ samples is correct. pass@1 is plain accuracy. pass@k with large $k$ tells you what best-of-N with a perfect checker could reach.

The naive way (draw exactly $k$ samples, check, repeat) is noisy. The standard unbiased estimator (from the Codex paper, Chen et al., 2021) draws $n \ge k$ samples per problem, counts the $c$ correct ones, and computes:

$$\text{pass@}k = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}$$

In words: the chance that a random group of $k$ out of the $n$ samples contains no correct one is (ways to choose $k$ from the $n-c$ wrong ones) / (ways to choose $k$ from all $n$). One minus that is the chance of at least one correct.

Worked example

You draw $n = 10$ samples for a problem and $c = 3$ pass the tests.

  • pass@1 = $1 - \binom{7}{1} / \binom{10}{1} = 1 - 7/10 = \mathbf{0.30}$. (Same as 3/10.)
  • pass@3 = $1 - \binom{7}{3} / \binom{10}{3} = 1 - 35/120 = \mathbf{0.708}$.
  • pass@5 = $1 - \binom{7}{5} / \binom{10}{5} = 1 - 21/252 = \mathbf{0.917}$.

Average this over all problems in the benchmark. When comparing two reasoning models, compare pass@1 averaged over several samples per problem; a single sample per problem gives noisy numbers.

8. Step-Level Search with Process Reward Models

An outcome verifier can only judge a finished answer. A process reward model (PRM) scores each step of a partial solution: "is this step correct and useful so far?" OpenAI's "Let's Verify Step by Step" (Lightman et al., 2023) trained one on 800,000 human step labels and found that step-level scores picked correct solutions more reliably than final-answer scores.

With a PRM you can do beam search over reasoning steps: keep the best few partial solutions at each step and extend only those. Here is a tiny walkthrough with beam width 2 (scores are made up for illustration; a real PRM outputs a number between 0 and 1 per step):

Problem: "A shirt costs $40 after a 20% discount. What was the original price?"

Step 1 candidates                        PRM score
  (a) "Original x, 0.8x = 40"              0.92   keep
  (b) "40 + 20% of 40 = 48"                0.15   drop  (common trap)
  (c) "Discount is 20%, so pay 80%"        0.85   keep

Step 2 (extend a and c)
  (a1) "x = 40 / 0.8 = 50"                 0.95   keep
  (a2) "x = 40 x 0.8 = 32"                 0.05   drop
  (c1) "80% of x is 40, so x = 50"         0.93   keep
  (c2) "80% of 40 is 32"                   0.10   drop

Final: both kept paths say 50. Answer: $50.

The trap answer ($48) was cut at step 1, before any compute was spent finishing it. That is the efficiency win of search: bad paths die early. The costs are a PRM to train and serve, and many short model calls instead of one long one.

9. How Reasoning Models Are Trained

Prompting a normal model to "think step by step" helps a little. Reasoning models are trained to think well and long. The common recipe, in plain steps:

  1. Start from a strong pretrained model (see Pretraining).
  2. Optional warm-up with supervised fine-tuning (SFT) on a small set of long, high-quality reasoning examples, so the model learns the format (think, then answer).
  3. Reinforcement learning with verifiable rewards (RLVR): give the model many problems with checkable answers (math with known results, code with tests). Sample several answers per problem, give reward 1 if correct and 0 if not (plus small rewards for following the format), and update the model to make rewarded answers more likely. No human labels each answer; the checker does.
  4. Distill the result into smaller models by fine-tuning them on the big model's reasoning traces.

DeepSeek-R1 (2025) showed this openly: its "R1-Zero" version, trained with RL on rule-checked rewards and no SFT warm-up, learned by itself to write longer and longer chains of thought, re-check its work, and change approach mid-answer. Its distilled small models (for example 7B and 32B versions) beat much larger normal models on math tests.

The GRPO advantage, worked by hand

A popular RL algorithm here is GRPO (Group Relative Policy Optimization). For each problem it samples a group of $G$ answers and scores each one relative to the group:

$$\hat{A}_i = \frac{r_i - \text{mean}(r_1, \dots, r_G)}{\text{std}(r_1, \dots, r_G)}$$

The advantage $\hat{A}_i$ says how much better than average answer $i$ was. Positive means "do more of this", negative means "do less".

  • Rewards $[1, 0, 0, 1]$: mean 0.5, standard deviation 0.5. Advantages $[+1, -1, -1, +1]$. The two correct answers are pushed up, the two wrong ones down, equally.
  • Rewards $[1, 0, 0, 0]$: mean 0.25, standard deviation 0.433. Advantages $[+1.73, -0.58, -0.58, -0.58]$. A rare success gets a big push: the model learns most from problems it can only sometimes solve.
  • Rewards $[0, 0, 0, 0]$ or $[1, 1, 1, 1]$: every answer equals the mean, so all advantages are 0 (in practice a tiny number is added to the standard deviation to avoid dividing by zero). No learning signal. Problems that are always failed or always solved are wasted compute, so training sets are filtered to problems of the right difficulty.

The full derivation of GRPO, PPO, RLOO, PRMs, and RLVR is in Reinforcement Learning: RL for LLMs, and the bigger picture of alignment training is in Post-Training.

10. Controlling the Thinking Budget

More thinking costs more money and time, so you need a dial. Common ways to set it:

  • Effort levels: many APIs accept a setting like low, medium, or high reasoning effort.
  • Token budgets: some APIs let you set a maximum number of thinking tokens.
  • Hybrid models can switch thinking on or off per request (for example a "thinking mode" flag), so one model serves both quick chat and hard problems.

Budget forcing

The "s1: Simple test-time scaling" paper (Muennighoff et al., 2025) showed a simple trick with open models, where you control the raw text:

  • To cut thinking short: once the budget is reached, insert the end-of-thinking marker and force the model to write its answer.
  • To make it think longer: when the model tries to stop, remove the end marker and append the word "Wait". The model often re-checks its work and fixes mistakes.

They fine-tuned a 32B model on just 1,000 carefully chosen reasoning examples and showed that accuracy on competition math rose as budget forcing let it think longer.

Overthinking is real: reasoning models often spend hundreds or thousands of tokens on trivial questions ("what is 2 + 3?"), re-checking an answer that was right the first time. Studies of this "overthinking" show much of that compute adds nothing. Use low effort or no thinking for easy requests.

11. Cost and Latency Math

Use simple, made-up but realistic numbers: output costs $10 per million tokens, and the model writes 80 tokens per second for one request. A direct answer is 300 tokens. With reasoning, the model writes 6,000 thinking tokens and then the same 300-token answer.

SetupOutput tokensCost per requestTime to finish
Direct answer300300 × $10 / 1,000,000 = $0.003300 / 80 ≈ 3.8 s
Reasoning6,300$0.063 (21x)6,300 / 80 ≈ 79 s
Reasoning, 8 samples in parallel + vote8 × 6,300 = 50,400$0.504 (168x)still about 79 s (samples run at the same time)

At 100,000 requests per day, the direct version costs $300 per day; plain reasoning costs $6,300 per day; reasoning with 8-way voting costs $50,400 per day. That is why the right question is not "is reasoning better?" but "which requests are worth it?"

  • Latency: users wait for every thinking token before the answer starts (time to first answer token can be tens of seconds). Stream a progress indicator or a reasoning summary so the app does not look frozen.
  • Serving: long outputs keep a large KV cache in GPU memory for a long time, which lowers how many requests a GPU can serve at once. See Inference Optimization for KV cache math.

12. When to Use a Reasoning Model

TaskReasoning helps?Why
Multi-step math, logic puzzles, planningYes, a lotMany dependent steps; errors can be caught by re-checking
Hard coding tasks, debugging, code with testsYesNeeds planning; tests make best-of-N very strong
Agents that choose tools over many turnsOftenBetter plans and fewer wasted tool calls, at higher cost per turn (see Agents)
Simple facts, extraction, classification, short rewritesRarelyOne step; extra thinking adds cost and delay, not accuracy
Questions needing knowledge the model lacksNoThinking cannot invent facts; use retrieval (RAG)
Real-time chat or voice with tight latencyUsually noTens of seconds of thinking breaks the experience; use a fast model, maybe route hard turns

A common production pattern is a router: a cheap, fast step guesses how hard each request is and sends only the hard ones to a reasoning model (or a high effort setting). The same idea appears in SLMs as model routing.

13. Engineering Tips

  • Do not micromanage the thinking. Reasoning models already think step by step. Long "think like this" instructions often help less than with older models. Give a clear goal, the constraints, and what a good answer looks like.
  • Make answers easy to compare and check. Ask for the final answer in a fixed format (for example, a JSON field or a last line "ANSWER: ..."). This makes voting, verifiers, and evaluation simple.
  • Use the cheapest check that works. Unit tests, schema validation, a calculator, or a SQL dry run are cheaper and more trustworthy than a second LLM judge.
  • Evaluate with several samples. Report pass@1 averaged over multiple samples per question, plus token use and latency percentiles (see Evaluation).
  • Treat the chain of thought as a hint, not a proof. Studies in 2025 found that models do not always mention in their reasoning the real reason for their answer. Use the reasoning to debug, but judge the final answer.
  • Watch the token bill per feature. Log thinking tokens separately from answer tokens; a prompt change can double thinking length without changing the answer.

14. Practice Problems

Try each one before reading the answer.

Problem 1: perfect checker

A coding model passes the hidden tests 25% of the time per sample. You can run the tests on each sample. How many samples do you need to reach at least 90% success?

Answer: Need $1 - 0.75^N \ge 0.9$, so $0.75^N \le 0.1$. $N \ge \ln 0.1 / \ln 0.75 = 2.303 / 0.288 \approx 8.0$. Check: $0.75^8 = 0.1001$, just above 0.1 (success 89.99%, a hair short), so you need N = 9 ($0.75^9 = 0.075$, success 92.5%).

Problem 2: pass@k by hand

For one problem you drew $n = 8$ samples and $c = 2$ were correct. Compute pass@1 and pass@4.

Answer: pass@1 = 2/8 = 0.25. pass@4 = $1 - \binom{6}{4}/\binom{8}{4} = 1 - 15/70 = 1 - 0.214 = \mathbf{0.786}$.

Problem 3: will voting help?

For a question, a model gives answer X 35% of the time, Y 40% of the time, and scattered other answers 25% of the time. X is correct. What happens to accuracy as you add more votes?

Answer: Y is more common than the correct X, so with many votes Y wins almost always and accuracy goes toward 0, below the 35% of a single sample. Voting only helps when the correct answer is the most likely single answer. You need a verifier or a better model.

Problem 4: GRPO advantages

A group of 4 samples gets rewards $[1, 1, 1, 0]$. Compute the advantages. Which sample gets the biggest push, and in which direction?

Answer: Mean = 0.75. Population standard deviation = $\sqrt{(3 \times 0.0625 + 0.5625)/4} = \sqrt{0.1875} = 0.433$. Advantages: correct ones $(1 - 0.75)/0.433 = +0.58$ each; the wrong one $(0 - 0.75)/0.433 = \mathbf{-1.73}$. The single failure gets the biggest push, down: on a mostly-solved problem, the model learns most from the rare mistake.

Problem 5: budget the feature

A support assistant gets 50,000 questions a day. 10% are hard. Reasoning uses 4,000 thinking tokens plus a 250-token answer; a direct answer is 250 tokens. Output costs $10 per million tokens. Compare (a) reasoning for everything, (b) a router that sends only the hard 10% to reasoning, assuming the router is free.

Answer: (a) 50,000 × 4,250 = 212.5 M tokens = $2,125 per day. (b) Hard: 5,000 × 4,250 = 21.25 M; easy: 45,000 × 250 = 11.25 M; total 32.5 M tokens = $325 per day, about 6.5 times cheaper, and easy questions get answered faster too.

15. Common Pitfalls

  • Using a reasoning model for everything. Easy requests get slower and more expensive with no gain. Route or lower the effort.
  • Voting on answers that are not comparable. "42", "42.0" and "The answer is 42" must be normalized first; essays cannot be majority-voted at all.
  • Trusting a weak verifier at large N. More samples give more chances to fool it. Measure accuracy vs N on a held-out set.
  • Expecting thinking to add knowledge. If the fact is not in the model or the prompt, longer thinking only produces longer guesses.
  • Comparing models on one sample per question. Reasoning outputs vary a lot between samples; average several.
  • Ignoring hidden token costs. Thinking tokens are billed even when not shown. Track them.
  • Reading the chain of thought as the true explanation. It is useful for debugging, but it may leave out what actually drove the answer.

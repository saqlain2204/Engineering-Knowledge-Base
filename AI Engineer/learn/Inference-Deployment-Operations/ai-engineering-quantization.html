Quantization Deep Dive

How to store a model's numbers in fewer bits so it fits on smaller GPUs and runs faster, and how to do it without breaking the model. We quantize real arrays step by step and measure the error. All numbers come from the NumPy code on this page.

1. Why Quantize at All

A model is mostly a huge list of numbers called weights. Each weight is usually stored in 16 bits (2 bytes). Memory needed for the weights is simply:

\[ \text{memory} = \text{number of weights} \times \text{bytes per weight} \]

FormatBytes per weight8B-parameter model70B-parameter model
16-bit (FP16/BF16)216 GB140 GB
8-bit (INT8/FP8)18 GB70 GB
4-bit, groups of 128 (see section 5)0.5164.125 GB36.1 GB

(Weights only. The KV cache and activations need extra memory on top.)

There is a second reason. When an LLM writes text one token at a time, the GPU must read every weight from memory for every token. That reading, not the maths, is usually the slowest part (the step is memory-bound). Half the bytes means roughly half the reading. See why decoding is memory-bound.

Intuition: Quantization is like rounding prices to the nearest rupee instead of storing paise. You lose a little detail, the totals are almost the same, and the list gets much shorter.

2. Number Formats in Plain Words

There are two families:

  • Floating point (FP): stores a number like scientific notation, 1.23 × 10-4. Some bits store the digits (the mantissa), some store the power (the exponent). More exponent bits means a wider range of sizes. More mantissa bits means finer detail.
  • Integer (INT): only whole numbers in a fixed range. To store 0.37 you need a separate scale (section 3).
FormatBitsWhat it can holdTypical use
FP3232Huge range, about 7 decimal digits of detailTraining master copy of weights
FP1616Largest value 65,504; can overflowOlder GPU inference
BF1616Same range as FP32, less detailStandard for modern training and serving
FP8 E4M38Largest value 448; more detailWeights and activations on newer GPUs
FP8 E5M28Largest value 57,344; less detailGradients in FP8 training
INT88Whole numbers -128 to 127Weights, activations, KV cache
INT44Whole numbers -8 to 7 (only 16 levels)Weights for small-GPU and laptop inference

"E4M3" means 4 exponent bits and 3 mantissa bits (plus one sign bit). The FP8 limits above come from the FP8 format paper linked at the end.

3. The Core Idea: Scale, Round, Store

The most common method is absmax (symmetric) quantization. In plain words:

  1. Find the biggest absolute value in the group of numbers.
  2. Choose a scale so that biggest value maps to the biggest integer (127 for INT8).
  3. Divide every number by the scale and round to the nearest whole number. Store these integers plus the one scale.
  4. To use the numbers again, multiply the integers by the scale. This is dequantization.

\[ s = \frac{\max |w|}{127} \qquad q = \text{round}\!\left(\frac{w}{s}\right) \qquad \hat{w} = q \times s \]

Worked example (INT8)

Six weights: [0.12, -0.50, 0.33, 0.05, -0.91, 0.70].

  1. Biggest absolute value: 0.91.
  2. Scale: 0.91 / 127 = 0.007165.
  3. Divide and round. For example -0.50 / 0.007165 = -69.78, which rounds to -70.
scale 0.007165
q     [  17  -70   46    7 -127   98]          <- stored as 1 byte each
deq   [ 0.1218 -0.5016  0.3296  0.0502 -0.91    0.7022]
error [ 0.0018 -0.0016 -0.0004  0.0002  0.      0.0022]   max abs error 0.0022

The biggest error is never more than half a step (half of 0.007165 is about 0.0036), because rounding moves a value at most half a step.

Same weights in INT4

INT4 has only 16 levels, so the scale is 0.91 / 7 = 0.13, and each step is much coarser:

int4 scale 0.13
q4   [ 1 -4  3  0 -7  5]
deq  [ 0.13 -0.52  0.39  0.   -0.91  0.65]     max abs error 0.06

The error grew from 0.0022 to 0.06, about 27 times worse. 0.05 became exactly 0. This is why 4-bit needs the extra tricks in sections 5 and 8.

import numpy as np
w = np.array([0.12, -0.50, 0.33, 0.05, -0.91, 0.70])
s = np.abs(w).max() / 127
q = np.round(w / s).astype(np.int8)
w_hat = q * s
print(s, q, w_hat, np.abs(w_hat - w).max())

4. Outliers: One Big Number Ruins the Scale

Now replace the first weight with an outlier, 8.0. The scale becomes 8.0 / 127 = 0.063, about 9 times coarser:

outlier scale 0.062992
q    [127  -8   5   1 -14  11]
deq  [ 8.     -0.5039  0.315   0.063  -0.8819  0.6929]

All the normal weights now share only a handful of levels near zero. 0.05 became 0.063 (a 26% error), and -0.91 became -0.8819. One big number wasted most of the 256 levels on empty space.

Key fact: real LLMs have outliers. Research on 8-bit inference found a few hidden "feature dimensions" in large transformers whose activation values are far larger than the rest, and that naive INT8 breaks those models (see the LLM.int8() paper below). Almost every modern method is a way of dealing with outliers.

5. Granularity: Per-Tensor, Per-Channel, Per-Group

The fix for outliers is simple: use more scales, each covering fewer numbers. Then one outlier only hurts its own small group.

weight matrix (rows = output channels)

per-tensor:   one scale for everything
              [ s ................................ ]

per-channel:  one scale per row
              s1 [ ................................ ]
              s2 [ ................................ ]

per-group:    one scale per block of g numbers in each row (g = 32, 64, 128)
              [ s1 .... | s2 .... | s3 .... | s4 .... ]
              [ s5 .... | s6 .... | s7 .... | s8 .... ]

Real experiment

We built a 1024 × 1024 random weight matrix (normal values, with rows given different sizes, as real layers have), multiplied it by 64 random input vectors, and measured how far the quantized output is from the full-precision output (relative error: size of the difference divided by size of the true output):

MethodRelative output error
INT8 per-tensor1.722%
INT8 per-channel0.789%
INT4 per-tensor30.112%
INT4 per-channel14.348%
INT4 groups of 12811.677%
INT4 groups of 329.618%

Then we added one outlier weight (100 times the typical size) and repeated:

MethodError without outlierError with one outlier
INT8 per-tensor1.722%22.229%
INT8 per-channel0.789%0.980%
INT4 groups of 12811.677%11.638%

One weight out of a million made per-tensor INT8 13 times worse. Per-channel and per-group barely noticed.

Be honest about this toy: these are random matrices with plain rounding. Real INT4 methods (GPTQ, AWQ) are much smarter than rounding, and real weights are not random, so real models lose far less quality than 10% error suggests. Use the table to compare methods, not to predict a real model's score.

The cost of more scales

Each scale is stored too, usually in 16 bits. For 4-bit weights with one 16-bit scale per group of g weights:

Group size gBits per weight including scale
324 + 16/32 = 4.5
644 + 16/64 = 4.25
1284 + 16/128 = 4.125

Group size 128 is a common default: small overhead, most of the accuracy benefit.

6. Symmetric vs Asymmetric (Zero Points)

Symmetric quantization puts 0 in the middle of the range. That wastes levels when the values are lopsided, for example activations after a ReLU-like function are mostly positive.

Asymmetric quantization maps the real minimum to integer 0 and the real maximum to 255, using an extra number called the zero point (z):

\[ s = \frac{\max - \min}{255} \qquad q = \text{round}\!\left(\frac{x}{s}\right) + z \qquad \hat{x} = (q - z) \times s \]

Real run on [-0.5, 0.4, 1.1, 2.3, 3.0, 0.7]:

asymmetric: scale 0.013725  zero point 36
  q   [  0  65 116 204 255  87]
  deq [-0.4941  0.398   1.098   2.3059  3.0059  0.7   ]   max error 0.005882
symmetric:  scale 0.023622
  q   [-21  17  47  97 127  30]
  deq [-0.4961  0.4016  1.1102  2.2913  3.      0.7087]   max error 0.010236

Symmetric used only the levels from -21 to 127; the levels from -128 to -22 were wasted. Asymmetric used all 256 and cut the worst error almost in half. The cost is one extra number per group and slightly more work in the matrix multiply. That is why weights (roughly centred on zero) are usually symmetric, and lopsided activations are often asymmetric.

7. Weights, Activations, and the KV Cache

WhatWhat it isNotationNotes
Weights onlyThe model's learned numbers. Known ahead of time.W4A16, W8A16Easiest. Weights are converted back to 16-bit inside the GPU kernel before the multiply. Saves memory and reading time.
Weights and activationsActivations are the numbers flowing between layers. They change with every input.W8A8 (INT8 or FP8)Lets the GPU do the multiply itself in 8-bit, which is faster for big batches. Harder, because activations have outliers.
KV cacheStored keys and values for past tokens (explained here)FP8 or INT8 KVMatters for long contexts and many users, where the cache can be bigger than the weights.

"W4A16" reads as "weights in 4 bits, activations in 16 bits".

Activation outliers, seen in a real run

We quantized the 64 input vectors to INT8 (one scale per vector, also called per-token), then made one of the 1024 input channels 60 times larger, mimicking the outlier features found in real LLMs:

CaseRelative output error
Normal activations, INT8 per-token0.795%
One outlier channel, INT8 per-token6.530%
Outlier channel kept in full precision, the rest INT80.381%

The last row is the LLM.int8() idea: handle the few outlier channels in 16-bit and everything else in 8-bit. (Its error is even lower than the normal case only because the big outlier channel, now exact, makes up much of the output.)

8. Methods: PTQ, QAT, GPTQ, AWQ, SmoothQuant, NF4, GGUF

When quantization happens

  • Post-training quantization (PTQ): take a finished model and quantize it. Minutes to hours. Most LLM quantization is PTQ.
  • Quantization-aware training (QAT): train or fine-tune while simulating the rounding, so the model learns to tolerate it. Better quality at very low bits, but needs training compute and data.

Many PTQ methods use a small calibration set: a few hundred example inputs run through the model to see which weights and channels matter.

The methods you will meet

MethodIdea in one or two sentences
LLM.int8()8-bit matrix multiply, but the few outlier feature dimensions are pulled out and computed in 16-bit (section 7).
GPTQQuantizes weights one column at a time. After rounding a column, it adjusts the columns not yet quantized to cancel out the error just made, using information from calibration data.
AWQ (activation-aware weight quantization)A small share of weights matter most: the ones multiplied by large activations. AWQ scales those channels up before quantizing so they lose less detail, and folds the inverse scale into the neighbouring operation.
SmoothQuantActivations are hard to quantize (outliers), weights are easy. It mathematically moves part of each activation channel's size into the matching weights, so both become easy, enabling W8A8.
NF4 (from QLoRA)A 4-bit format whose 16 levels are placed to match the bell-curve shape of typical weights, instead of evenly spaced. Used by bitsandbytes for memory-cheap fine-tuning. See Fine-Tuning (QLoRA).
GGUF k-quantsThe file format and quantization family used by llama.cpp for CPU and laptop inference. Names like Q4_K_M or Q8_0 describe the bits and block layout.
FP88-bit floating point instead of integers. Its exponent handles a wide range, so it copes with outliers better than INT8. Needs GPU hardware with FP8 support for the speed benefit.

9. Doing It in Practice

Load a model in 4-bit with Hugging Face Transformers (bitsandbytes)

import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",           # the NF4 format
    bnb_4bit_compute_dtype=torch.bfloat16 # dequantize to BF16 for the maths
)
model = AutoModelForCausalLM.from_pretrained("your-org/your-model", quantization_config=bnb)

Serve a pre-quantized model with vLLM

# a checkpoint already quantized with AWQ or GPTQ: vLLM reads the method from its config
vllm serve your-org/your-model-AWQ

# quantize weights to FP8 on the fly at load time (needs FP8-capable GPU for speed)
vllm serve your-org/your-model --quantization fp8

Make a GGUF file for llama.cpp

# convert to a 16-bit GGUF, then quantize it
python convert_hf_to_gguf.py ./your-model --outfile model-f16.gguf
./llama-quantize model-f16.gguf model-Q4_K_M.gguf Q4_K_M

Many popular models already have AWQ, GPTQ, FP8, and GGUF versions on Hugging Face. Check the model card for how they were made and evaluated.

10. Does Smaller Mean Faster?

Not always. It depends on what limits the GPU:

  • Small batches (few users at once): decoding is memory-bound. Weight-only INT4 or INT8 reads fewer bytes, so tokens come out faster.
  • Large batches: the GPU becomes compute-bound (busy doing maths). Weight-only formats must convert weights back to 16-bit before each multiply, which adds work. Here W8A8 (INT8 or FP8), which multiplies directly in 8-bit, tends to help more.
  • Kernel support: speed needs fast GPU code (kernels) for that exact format on that exact GPU. A format your hardware does not support natively may save memory but run slower.

So measure tokens per second and latency on your own hardware, at your real batch sizes, before and after. See Metrics and capacity planning.

11. Evaluating a Quantized Model

Quantization changes the model, so treat it like a new model release:

  1. Keep a baseline. Run the 16-bit model on the same prompts, same settings, greedy decoding (temperature 0) where possible.
  2. Perplexity on held-out text: a quick "is anything badly broken" check. Lower is better; small rises are normal.
  3. Task evals that match your product: your golden set, plus fragile skills such as maths, code, long context, and strict JSON output. These often break before open chat does.
  4. Compare side by side and look at the examples that changed, not only the averages.
  5. Measure speed and memory at your real load (section 10).

See Evaluation for building eval sets and CI gates.

12. Common Pitfalls

  • Judging only by perplexity. A model can keep perplexity and still lose maths or JSON formatting.
  • Calibration data that does not match your traffic. Calibrating on English news, then serving code, can protect the wrong channels.
  • Assuming a speedup. Measure. Unsupported formats can be slower.
  • Forgetting the KV cache. At long context, weights may be small and the cache may be what runs you out of memory.
  • Quantizing small models too hard. Smaller models often lose more quality at 4-bit than larger ones. Test, do not assume.
  • Mixing up W4A16 and W4A4. Read what is actually quantized.

13. Practice Problems (with Solutions)

Problem 1: quantize by hand

Quantize [0.2, -0.4, 1.27] to INT8 with absmax. Give the scale, the integers, and the dequantized values.

Solution

Scale = 1.27 / 127 = 0.01. Integers: 0.2 / 0.01 = 20, -0.4 / 0.01 = -40, 1.27 / 0.01 = 127. Dequantized: 0.2, -0.4, 1.27. No error here, because every value happens to be a whole number of steps.

Problem 2: will it fit?

You have one GPU with 24 GB of memory. Can a 13B-parameter model fit in 16-bit? In 4-bit with groups of 128? Ignore the KV cache for now.

Solution

16-bit: 13 × 109 × 2 bytes = 26 GB. Does not fit. 4-bit, group 128: 4.125 bits = 0.515625 bytes per weight, so 13 × 109 × 0.515625 = 6.7 GB. Fits, leaving room for the KV cache.

Problem 3: pick the granularity

Your INT8 per-tensor model gives garbage output, and you find one row of a weight matrix has values 50 times larger than the others. What is the cheapest fix to try first?

Solution

Switch to per-channel (one scale per row) quantization. The large row then gets its own scale and stops crushing the others' precision. This costs only one extra scale per row.

Problem 4: memory-bound or not?

A chatbot serves 2 users at a time on a big GPU. A teammate proposes W8A8 to speed it up; another proposes W4A16. Which is likely to help more, and why?

Solution

W4A16. With only 2 users, decoding is memory-bound: the time goes into reading weights. 4-bit weights are a quarter of the bytes of 16-bit. W8A8 mainly speeds up the maths, which is not the bottleneck at such a small batch. Still measure both.

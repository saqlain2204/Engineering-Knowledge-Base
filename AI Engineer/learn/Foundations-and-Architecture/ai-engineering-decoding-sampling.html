Decoding & Sampling: How an LLM Picks Each Token

A language model does not output text. At each step it outputs a score for every token in its vocabulary. Something else must turn those scores into one chosen token, again and again. That "something" is the decoder (or sampler), and its settings (temperature, top-p, penalties, JSON schemas) change answers as much as a better prompt does. This page works through each setting with real numbers, so you can predict what a change will do before you make it.

1. The Generation Loop

Generation is a loop. Each turn of the loop adds exactly one token.

  prompt tokens ─► model ─► one score (logit) per vocabulary token   e.g. 128,000 numbers
                              │
                              ▼
                   decoder: penalties ─► temperature ─► filter (top-k / top-p / min-p)
                              │                         ─► (optional) grammar mask
                              ▼
                   pick ONE token (the most likely, or a random draw)
                              │
             ┌────────────────┴────────────────┐
             ▼                                 ▼
   is it a stop token / stop string     append it to the input
   or did we hit max_tokens?            and run the model again
             │ yes
             ▼
           done

The model part is expensive and the same for every setting. The decoder part is cheap, but it decides which of the many possible answers you get. The model's speed side (prefill, decode, KV cache, speculative decoding) is covered in Inference Optimization. This page is about the choice.

2. The Words, in Plain English

WordPlain meaning
TokenA piece of text the model works with: a word, part of a word, or a symbol (see Tokenization).
VocabularyThe full list of tokens the model knows. Often 32,000 to 260,000.
LogitThe raw score the model gives a token. Any real number. Higher means "more likely". Not a probability yet.
SoftmaxThe formula that turns logits into probabilities that are all positive and add up to 1.
DistributionThe list of probabilities for all tokens at this step.
SamplingPicking a token at random, where likelier tokens are picked more often. Like a weighted dice roll.
GreedyAlways picking the single most likely token. No randomness.
TruncationRemoving unlikely tokens before sampling (top-k, top-p, min-p).
RenormaliseAfter removing some tokens, divide the rest by their new total so they add up to 1 again.
EntropyOne number for "how spread out" a distribution is. 0 means one token is certain. Higher means more choices are open.
EOS"End of sequence": a special token that means "I am done".

3. From Logits to Probabilities, by Hand

We will use one running example for the whole page. The prompt is "The cat sat on the". Pretend the vocabulary has only six tokens, and the model gives these logits:

Tokenmatfloorsofabedroofmoon
Logit z5.04.23.93.52.00.5

Softmax has two steps:

  1. Raise e (about 2.718) to the power of each logit. This makes every value positive, and makes bigger logits much bigger.
  2. Divide each by the total, so they add to 1.
probability(token) = e^z(token) / (sum of e^z over all tokens)
Tokenze^zProbability = e^z / 306.66
mat5.0148.410.484
floor4.266.690.217
sofa3.949.400.161
bed3.533.120.108
roof2.07.390.024
moon0.51.650.005
Total306.661.000

Intuition. Softmax only cares about differences between logits. Add 100 to every logit and the probabilities do not change. A gap of 1 in logits means a factor of e (about 2.7) in probability. "mat" (5.0) vs "floor" (4.2): gap 0.8, so mat is e^0.8 = 2.2 times as likely (0.484 / 0.217 = 2.2).

In code, real systems subtract the largest logit before taking e^z. The answer is the same (only differences matter), but it avoids huge numbers that overflow.

4. Greedy Decoding

The simplest decoder: always take the top token. Here that is "mat", every time.

  • Good: repeatable, and often the best choice for short factual answers, classification, and extraction.
  • Bad: for long text it tends to be dull and can fall into loops ("I think that I think that I think..."). Once a phrase repeats, the model sees the repeat as evidence that repeating is likely, so it becomes even more likely.
  • Also bad: picking the best token now does not always give the best sentence. Section 8 shows a case.

Setting temperature = 0 in most APIs means greedy decoding.

5. Temperature

Temperature T divides every logit before softmax:

probability = softmax(z / T)
  • T < 1 makes the gaps between logits bigger, so the top token gets even more likely. The distribution gets sharper.
  • T > 1 makes the gaps smaller, so rare tokens get more chances. The distribution gets flatter.
  • T close to 0 becomes greedy.

Our example at four temperatures:

Worked check for T = 0.5: the logits become 10, 8.4, 7.8, 7, 4, 1. The gap between mat and floor is now 1.6 instead of 0.8, so mat is e^1.6 = 5 times as likely as floor (0.733 / 0.148 = 5.0).

Real run: 10,000 draws

At T = 1.0, "The cat sat on the moon" happened 65 times in 10,000. That sounds small, but a chatbot answering 1 million requests with long replies makes thousands of such "odd" choices every day, and one odd token early in a reply can steer everything after it. This is why we also cut off the tail (next section).

6. Top-k, Top-p and Min-p

All three remove unlikely tokens, then renormalise the rest. They differ in how they decide what is "unlikely". All numbers below use T = 1.0.

Top-k: keep the k best

With k = 3, keep mat, floor, sofa. Their probabilities add to 0.484 + 0.217 + 0.161 = 0.862. Divide each by 0.862:

mat 0.561   floor 0.252   sofa 0.187   (bed, roof, moon: 0)

Problem: k is fixed. If the model is very sure (one token at 0.99), k = 3 still keeps two bad options. If the model is unsure (20 good options), k = 3 throws good options away.

Top-p (nucleus): keep the smallest set that covers p

Sort tokens from most to least likely and add up probabilities until the total reaches p. With p = 0.9:

TokenProbabilityRunning totalKept?
mat0.4840.484yes
floor0.2170.701yes
sofa0.1610.863yes
bed0.1080.971yes (this one crosses 0.9)
roof0.0240.995no
moon0.0051.000no

Kept total = 0.971. Renormalised: mat 0.499, floor 0.224, sofa 0.166, bed 0.111. The "moon" answer is now impossible.

Top-p adapts: when the model is sure, the set is tiny (maybe one token); when it is unsure, the set grows.

Min-p: keep tokens at least a fraction of the best one

Keep any token whose probability is at least min_p × (top probability). With min_p = 0.1, the bar is 0.1 × 0.484 = 0.0484. mat, floor, sofa and bed pass; roof (0.024) and moon (0.005) do not. Same result as top-p here: mat 0.499, floor 0.224, sofa 0.166, bed 0.111.

Why min-p exists: at high temperature the distribution is flat, and top-p = 0.9 then lets in a long tail of junk tokens (because 90% of a flat distribution is a lot of tokens). Min-p scales with the top token's confidence, so it keeps the tail out even at high temperature. It is popular for creative writing with T above 1.

MethodKeepsAdapts to confidence?Typical value

7. Repetition, Frequency and Presence Penalties

These lower the logits of tokens that have already appeared, to fight loops.

Repetition penalty (multiplicative)

Used by Hugging Face Transformers and many open-model servers. For each token already in the text: if its logit is positive, divide by the penalty; if negative, multiply by it. Both push it down.

Say "mat" already appeared, and the penalty is 1.3. Its logit goes from 5.0 to 5.0 / 1.3 = 3.85. New probabilities:

mat 0.228   floor 0.325   sofa 0.241   bed 0.161   roof 0.036   moon 0.008

One setting moved "mat" from first place (0.484) to second (0.228). Penalties are strong. Values above about 1.2 often damage normal text, because words like "the" and "is" should repeat.

Frequency and presence penalties (subtractive)

Used by OpenAI-style APIs:

new logit = logit - (count of the token so far) × frequency_penalty
                  - (1 if the token appeared at all, else 0) × presence_penalty

Example: "mat" appeared 3 times, frequency_penalty = 0.5, presence_penalty = 0.4. New logit = 5.0 - 3 × 0.5 - 0.4 = 3.1. The frequency penalty grows with each repeat; the presence penalty is a flat "you have used this before" push toward new topics.

8. Beam Search

Greedy picks the best token at each step. But the best sequence may start with a worse token. Toy example with two steps:

First tokenP(first)Second tokenP(second | first)P(sequence)
A0.6x / y / z0.40 / 0.35 / 0.250.24 / 0.21 / 0.15
B0.4x / y / z0.90 / 0.05 / 0.050.36 / 0.02 / 0.02

Greedy takes A (0.6 > 0.4), then x, for a sequence probability of 0.24. But "B x" has 0.36. After A, the model is unsure; after B, it is very sure.

Beam search with beam width 2 keeps the 2 best partial sequences at every step instead of 1:

  1. Step 1: keep A (0.6) and B (0.4).
  2. Step 2: score all 6 extensions; keep the best 2: "B x" (0.36) and "A x" (0.24).
  3. Answer: "B x". Greedy missed it.

In practice, beam search works well for tasks with one right answer and a fixed shape: translation, speech-to-text, short summaries. For chat and open writing it tends to give short, generic, repetitive text, because the most probable text is often the blandest. Chat systems use sampling instead. Real beam search also divides the score by length (a length penalty), because longer sequences multiply more probabilities and always look worse.

9. The Order a Real Sampler Uses

When you set several options at once, they run in a fixed order. A common order (Hugging Face Transformers uses this one) is:

logits
  ─► 1. penalties (repetition / frequency / presence)
  ─► 2. grammar mask, if you asked for structured output (section 11)
  ─► 3. temperature (divide by T)
  ─► 4. top-k  ─► 5. top-p  ─► 6. min-p   (each removes tokens)
  ─► 7. softmax over what is left, then one random draw (or argmax if greedy)

Order matters. Temperature runs before top-p, so a higher temperature lets more tokens through the same top-p. With our example and p = 0.9:

  • T = 1.0: running totals 0.484, 0.701, 0.863, 0.971. 4 tokens kept.
  • T = 2.0: running totals 0.328, 0.548, 0.737, 0.892, 0.965. 5 tokens kept, and "roof" is now possible.

Exact order differs a little between servers (vLLM, llama.cpp, Hugging Face). If a result surprises you, check your server's docs for its order.

10. Seeds, and Why Temperature 0 Can Still Change

Sampling uses a random number generator. Fix the seed and, on the same machine with the same software and the same input, you get the same draws. That is useful for tests.

But even greedy decoding (T = 0) on a busy server can give different answers to the same prompt. Reasons:

  • Floating-point order. Computers round after each addition, so (a + b) + c can differ from a + (b + c) in the last digit. GPU code adds numbers in different orders depending on how many requests are batched together. A tiny change can flip the top token when two logits are almost tied, and after one different token, the rest of the reply differs.
  • Batching changes with load. Your request is grouped with whatever else is running at that moment (see Batching and Scheduling), so the batch size, and so the adding order, changes from call to call.
  • Model or server updates. An API model name can point to a new version.

So for evaluation, do not assume one run is "the" answer. Run important evals several times, and compare averages (see Evaluation). Some servers offer a "batch-invariant" mode that removes this effect at some speed cost.

11. Structured Outputs and Constrained Decoding

Programs often need the model to return valid JSON, like {"approved": true}. Asking nicely in the prompt works most of the time. "Most of the time" breaks programs. Constrained decoding makes invalid output impossible.

The trick: a mask on the logits

At each step, a small checker knows which tokens are allowed next under the rules (the JSON schema or a grammar). Before sampling, every forbidden token's logit is set to minus infinity. e^(-infinity) = 0, so it can never be picked.

Worked example. The model has written {"approved": and the schema says the value must be a boolean. Without a mask, the model's top choices are:

Next tokenProbability before maskAllowed by schema?After mask and renormalise
"yes"0.60no (a string, not a boolean)0
true0.25yes0.25 / 0.40 = 0.625
false0.15yes0.15 / 0.40 = 0.375

Without the mask, 60% of replies would break your parser. With it, 0% do.

How the checker knows what is allowed

  1. The JSON schema (or a grammar, such as GBNF in llama.cpp) is compiled into a state machine: a small map of "where am I in the format, and what may come next".
  2. For each state, the library works out which vocabulary tokens are allowed. This is the hard part, because one token can cover several characters (like ": or true,). Libraries such as XGrammar, llguidance and Outlines precompute and cache these masks so the check costs well under a millisecond per token.
  3. After each chosen token, the state machine moves forward.

Where you meet this: OpenAI-style "Structured Outputs" with a strict JSON schema, vLLM's structured output options, llama.cpp grammars, and tool calling (the tool arguments are JSON; see Agents).

Valid is not the same as correct. The mask guarantees the shape, not the truth. In the example, the model really wanted to say "yes", which was approval. The mask turned that into true (62.5%) or false (37.5%): it can turn a confident answer into a coin flip. Give the model the format in the prompt too, so its own top choice is already valid.

Field order matters

The model writes JSON left to right. If your schema is {"answer": ..., "reasoning": ...}, the model must commit to the answer before it writes any reasoning. Put reasoning first and answer last, so the answer can use the reasoning tokens (the same idea as in Reasoning Models).

12. When Generation Stops

The loop ends on the first of these:

  • EOS token. The model picks its "end" token. The API reports finish_reason: "stop".
  • Stop string. You gave a list like ["\n\nUser:"]; the server stops when the text contains one, and usually cuts it off.
  • max_tokens. The length limit. The API reports finish_reason: "length". The answer is cut mid-sentence, and JSON will be invalid even with constrained decoding, because the closing } was never written.

Always check finish_reason in code. Treat "length" as an error or a retry with a bigger limit, never as a normal answer.

13. Choosing Settings per Task

TaskSettings to start withWhy
Extraction, classification, routingT = 0 (greedy), structured outputOne right answer; you want the same answer every time
Code generationT = 0 to 0.3, top-p 0.95Small changes break code; a little randomness helps when you retry
Chat assistantT = 0.7, top-p 0.9 to 0.95Natural variety without odd words
Creative writing, brainstormingT = 1.0 to 1.3, min-p 0.05 to 0.1More variety; min-p keeps the junk tail out
Several tries, then pick the best (best-of-n, self-consistency voting)T = 0.7 to 1.0Tries must differ, or the vote is pointless
Reasoning modelsUse the model card's settingsMany are trained and tested at a fixed temperature (often 0.6 to 1.0); greedy can make them loop

Change one setting at a time, and measure on an eval set. Your feelings about a few outputs are not a measurement.

14. A Complete Sampler in 30 Lines

This NumPy code does everything above except grammars. Run it and it prints {'mat': 4984, 'floor': 2269, 'sofa': 1662, 'bed': 1085, 'roof': 0, 'moon': 0}: with top-p 0.9, roof and moon can no longer be drawn (compare the 229 and 65 in section 5).

import numpy as np

def softmax(z):
    e = np.exp(z - z.max())          # subtract max: same answer, no overflow
    return e / e.sum()

def sample(logits, seen_counts, rng, temperature=1.0, top_k=0, top_p=1.0,
           min_p=0.0, rep_penalty=1.0, freq_penalty=0.0, presence_penalty=0.0):
    z = logits.astype(float).copy()
    # 1. penalties, only for tokens already generated
    for tok, count in seen_counts.items():
        z[tok] = z[tok] / rep_penalty if z[tok] > 0 else z[tok] * rep_penalty
        z[tok] -= count * freq_penalty + (count > 0) * presence_penalty
    # 2. greedy
    if temperature == 0:
        return int(np.argmax(z))
    # 3. temperature
    p = softmax(z / temperature)
    order = np.argsort(-p)                       # most likely first
    keep = np.ones_like(p, dtype=bool)
    # 4. top-k
    if top_k > 0:
        keep[order[top_k:]] = False
    # 5. top-p: keep tokens until the running total reaches top_p
    cum = np.cumsum(p[order])
    cutoff = np.searchsorted(cum, top_p) + 1
    keep[order[cutoff:]] = False
    # 6. min-p
    keep &= p >= min_p * p.max()
    # 7. renormalise and draw
    p = np.where(keep, p, 0.0)
    return int(rng.choice(len(p), p=p / p.sum()))

tokens = ["mat", "floor", "sofa", "bed", "roof", "moon"]
logits = np.array([5.0, 4.2, 3.9, 3.5, 2.0, 0.5])
rng = np.random.default_rng(0)
draws = [sample(logits, {}, rng, temperature=1.0, top_p=0.9) for _ in range(10_000)]
print({t: draws.count(i) for i, t in enumerate(tokens)})   # roof and moon: 0

15. Common Pitfalls

  • Tuning temperature and top-p at the same time. They interact (section 9). Change one, measure, then the other.
  • Using greedy for long creative text. It gets dull and can loop. Use sampling with truncation.
  • Heavy repetition penalties. Above about 1.2 they start banning normal words and even needed code symbols (brackets, indentation), so code breaks.
  • Trusting "temperature 0 = same answer forever". Batching, hardware and model updates change answers. Pin model versions and run evals more than once.
  • Ignoring finish_reason. A reply cut by max_tokens looks fine at a glance but is incomplete or invalid JSON.
  • Constraining without prompting. If the prompt does not describe the format, the mask fights the model and quality drops. Describe it in the prompt and enforce it with the schema.
  • Answer field before reasoning field in a JSON schema. The model commits before it thinks.
  • Letting end users set any temperature. Keep sampling settings in server config per use case, and expose only safe ranges.

16. Practice Problems (with Solutions)

Problem 1: softmax by hand

Three tokens have logits 2, 1, 0. What are their probabilities? (e = 2.718, e^2 = 7.389.)

Solution

e^2 = 7.389, e^1 = 2.718, e^0 = 1. Total = 11.107. Probabilities: 7.389 / 11.107 = 0.665, 2.718 / 11.107 = 0.245, 1 / 11.107 = 0.090.

Problem 2: temperature

Same logits (2, 1, 0), temperature 0.5. What is the new probability of the first token?

Solution

Divide by 0.5: logits become 4, 2, 0. e^4 = 54.6, e^2 = 7.39, e^0 = 1. Total = 62.99. First token: 54.6 / 62.99 = 0.867 (up from 0.665). Lower temperature made the top token more certain.

Problem 3: top-p

Sorted probabilities are 0.40, 0.30, 0.15, 0.10, 0.05. With top-p = 0.8, which tokens are kept, and what is the renormalised probability of the first one?

Solution

Running totals: 0.40, 0.70, 0.85. The third token pushes the total past 0.8, so the first three are kept (total 0.85). First token: 0.40 / 0.85 = 0.471.

Problem 4: min-p

Same probabilities, min-p = 0.3. Which tokens survive?

Solution

The bar is 0.3 × 0.40 = 0.12. Tokens at 0.40, 0.30 and 0.15 pass; 0.10 and 0.05 do not. Three tokens survive.

Problem 5: presence and frequency

The token "great" has logit 3.0 and has appeared 4 times. frequency_penalty = 0.3 and presence_penalty = 0.5. What is its new logit?

Solution

3.0 - 4 × 0.3 - 1 × 0.5 = 3.0 - 1.2 - 0.5 = 1.3.

Problem 6: the broken pipeline

An extraction job uses a strict JSON schema, yet 2% of replies fail to parse. Logs show those replies are all exactly 512 tokens long. What happened, and what do you change?

Solution

They hit max_tokens = 512 (finish_reason: "length"), so the JSON was cut before its closing brace. The schema cannot help, because generation simply stopped. Raise the limit for these inputs, shorten the output (fewer or shorter fields), and treat "length" as a retry case in code.

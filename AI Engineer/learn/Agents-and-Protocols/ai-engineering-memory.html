1. Why Memory Matters

Large language models are stateless functions: each API call receives a context window and produces tokens. Without an explicit memory layer, the model cannot recall prior sessions, user preferences, or outcomes of tool calls unless you resend that information every turn. Agents that plan over dozens of steps, collaborate across sub-agents, or serve returning users need memory to bridge the gap between finite context and long-horizon tasks.

What breaks without memory

  • Repeated questions: users re-explain preferences every session.
  • Lost tool context: intermediate SQL results, API payloads, or file paths vanish after truncation.
  • Inconsistent personas: tone, role, and constraints drift when system prompts compete with truncated history.
  • Failed multi-step tasks: agents forget sub-goals after summarization errors or window overflow.
  • No learning from outcomes: successful trajectories are not distilled into reusable knowledge.

Memory as a systems problem

Memory is not "store everything in the prompt." It is a pipeline: write (what to remember), store (where and in what shape), retrieve (what to inject now), and forget (TTL, dedup, user deletion). Each stage has cost, latency, and privacy implications. Production agents treat memory as infrastructure alongside auth, logging, and eval.

Intuition: Context window is RAM: fast but small. Persistent memory is disk: larger but slower and needs indexing. Good agent design pages data in and out of RAM deliberately rather than hoping the model "remembers."

Refer: Generative Agents (Park et al.) · LangGraph memory concepts · AI Agents overview

2. Memory Taxonomy

Memory types overlap in practice, but separating them clarifies design decisions and eval scenarios.

TypeScopeTypical storeExamples
Working memoryCurrent turn / stepIn-context scratchpad, tool outputsCurrent plan, last API response, draft code
Short-term (episodic)Session / threadMessage list, rolling summaryConversation so far, task state this visit
Long-term (semantic)Cross-sessionVector DB, knowledge graphUser likes dark mode, prior ticket resolutions
ProceduralAgent / orgPrompts, playbooks, fine-tuned weightsHow to file expenses, escalation policy
Shared / collectiveTeam or productDocument index, wiki RAGProduct docs, runbooks, codebase embeddings

Human memory analogies (use carefully)

  • Episodic: "What happened in our chat Tuesday" - timestamps and narrative.
  • Semantic: "User is allergic to shellfish" - facts without source episode required.
  • Procedural: "Always verify OTP before refund" - how to act, not what was said.

Analogies help stakeholders; implementations should use explicit schemas and retrieval policies, not metaphor alone.

Read vs write paths

  • Implicit read: full message history in context (no separate retrieval).
  • Explicit read: query memory store each turn (vector search, SQL, graph traversal).
  • Implicit write: append messages to thread (automatic).
  • Explicit write: model or pipeline calls save_memory with structured facts (gated).
Design rule: Separate conversation log (audit trail, replay) from memory index (curated facts for retrieval). Not every message should become a retrievable memory.

3. Context Economics

Every token in context has a price: API cost, latency, and attention dilution. Memory design is budget allocation across system prompt, tools, retrieved chunks, summaries, and recent messages.

Token budget layers

  1. Reserved: system instructions, safety policies, tool schemas (often 2k-8k+ tokens).
  2. Working: latest user message, current tool results, agent scratchpad.
  3. Retrieved: RAG chunks, long-term memory hits, similar past episodes.
  4. Historical: raw messages or compressed summary of older turns.
  5. Output reserve: headroom for model completion (critical for long tool JSON).

Cost drivers

FactorEffect
Context lengthLinear to superlinear cost on many providers; slower prefill
Retrieval widthMore chunks = better recall risk, worse precision and cost
Re-summarizationExtra LLM calls each N turns; amortize with incremental summaries
Embedding index sizeStorage + search cost; not billed per LLM token but affects infra
Checkpoint frequencyLangGraph state persistence I/O per node

Context rot

Models attend more reliably to recent and salient tokens. Stuffing 100k tokens "because the window allows it" often degrades instruction following and tool selection. Prefer targeted retrieval over maximal history.

Intuition: Treat context like a cache with eviction policy (LRU for messages, TTL for facts, priority boost for user-stated constraints). Miss rate = agent asks again or hallucinates. 
# Rough budget planner (tokens)
BUDGET = 128_000
RESERVE = {
    "system": 3_000,
    "tools": 4_000,
    "output": 4_096,
}
retrieved = min(8_000, BUDGET - sum(RESERVE.values()) - 12_000)
history_cap = BUDGET - sum(RESERVE.values()) - retrieved
# history_cap goes to summary + recent raw messages

4. Short-Term Memory Patterns

Short-term memory keeps the current session coherent. Implementations range from naive message buffers to structured state machines.

4.1 Full buffer

Append every message (user, assistant, tool) to a list; send all until window fills. Simple and lossless until truncation. Use for short support chats and dev debugging.

4.2 Sliding window

Keep last k turns or last n tokens. Drop oldest messages. Risk: lose constraints stated early unless copied to summary or long-term store.

4.3 Token-aware trimming

Trim from the middle or drop tool payloads first (often largest). Preserve system + first user message + recent tail. Libraries like LangChain trim_messages implement role-aware rules.

4.4 Scratchpad / working notes

Agent maintains explicit notes the model updates via tool or structured output:

{
  "goal": "Book flight ORD to SFO under $400",
  "constraints": ["depart after 9am", "one carry-on"],
  "done": ["searched flights", "filtered 3 options"],
  "next": "confirm user pick, call book_flight"
}

Scratchpads survive better than prose buried in chat when you summarize aggressively.

4.5 State machine memory (agents)

LangGraph and similar frameworks store typed state (messages, plan step, artifacts). Nodes read/write fields instead of parsing free-form chat. Reduces ambiguity for multi-step workflows.

PatternBest forMain risk
Full bufferShort threads, eval replayWindow overflow
Sliding windowHigh-volume chatEarly context loss
ScratchpadTool-heavy agentsStale notes if not updated
Typed stateWorkflows, approvalsSchema rigidity

5. Summarization and Compression

When raw history exceeds budget, compress older turns into a summary while keeping recent messages verbatim. Summarization is the most common short-term memory extension and a frequent source of silent information loss.

5.1 Rolling summary

Maintain summary string updated every N turns:

  1. Input: previous summary + messages since last update.
  2. Prompt: "Update summary; preserve user constraints, decisions, open tasks; drop small talk."
  3. Store new summary; optionally archive dropped messages to cold storage.

5.2 Hierarchical summaries

Session summary, daily summary, user profile summary. Higher levels aggregate lower levels. Enables long horizons without one giant paragraph that mixes unrelated facts.

5.3 Structured compression

Instead of prose, extract JSON facts during compression:

{"facts": [
  {"key": "budget", "value": "$400", "source_turn": 2},
  {"key": "destination", "value": "SFO", "source_turn": 1}
], "open_tasks": ["confirm flight"]}

Easier to query and validate than narrative summary.

5.4 Map-reduce for long documents

For ingesting logs or transcripts into memory: chunk, summarize each chunk, then summarize summaries. Distinct from per-turn chat summarization but same compression idea.

5.5 Quality safeguards

  • Pin immutable facts to long-term store before summarizing (user ID, legal opt-outs).
  • Keep verbatim copies of tool errors and numeric outputs when precision matters.
  • Log summary diffs for debugging "agent forgot X" reports.
  • Use a stronger model for summarization if the worker model is small.
Information theory view: Summarization is lossy compression. The objective is sufficient statistics for future decisions, not faithful prose. Define what must be preserved (constraints, commitments, identifiers) explicitly in the summarizer prompt or schema.

6. Vector Memory

Long-term semantic memory often uses embeddings: text (or multimodal) vectors stored in a vector database for similarity search at query time.

6.1 Write path

  1. Candidate selection: which messages or facts enter the index (post-extraction).
  2. Chunking: split long episodes; attach metadata (user_id, session_id, timestamp, type).
  3. Embedding: model choice must match query embedding model.
  4. Upsert: store vector + payload; handle updates and deletes.

6.2 Read path

  1. Form query from current user message + optional agent plan.
  2. Similarity search with filters (user, time range, memory type).
  3. Re-rank (cross-encoder, LLM ranker, MMR for diversity).
  4. Inject top-k into context with citations and timestamps.

6.3 Metadata filters (critical)

Always scope retrieval by user_id or tenant. Cross-user leakage is a severe privacy failure. Combine vector score with metadata:

filter = {
    "user_id": current_user,
    "memory_type": {"$in": ["preference", "fact"]},
    "created_at": {"$gte": "2025-01-01"},
}
results = index.query(vector=emb, top_k=20, filter=filter)

6.4 Embedding models

ConsiderationGuidance
DomainCode and support tickets may need specialized embedders
DimensionHigher not always better; match index limits
MultilingualUse multilingual embeddings if users mix languages
RefreshRe-embed entire index when changing models

6.5 Stores

Chroma, Pinecone, Weaviate, Qdrant, pgvector, Redis vector, LanceDB. Choice depends on scale, hybrid search needs, and ops maturity. pgvector suits teams already on Postgres for structured + vector in one place.

Intuition: Vector memory answers "what past text is similar to now?" not "what is objectively true?" Pair with extraction validation and structured stores for high-stakes facts.

7. Structured Memory

Facts with known shape belong in databases, not only embedding space. Structured memory enables precise queries, constraints, and audits.

7.1 Key-value user profile

CREATE TABLE user_memory (
  user_id UUID,
  key TEXT,
  value JSONB,
  confidence FLOAT,
  source TEXT,
  updated_at TIMESTAMPTZ,
  PRIMARY KEY (user_id, key)
);

Examples: timezone, preferred_language, shipping_address_id. Load entire row set or top keys each session.

7.2 Episodic event log

Append-only events: {type: "purchase", item_id, at}. Query by time or type. Good for "what did we do last month?" without semantic guesswork.

7.3 Knowledge graph

Entities (User, Account, Ticket) and edges (opened, assigned_to). Supports multi-hop questions and consistency checks. Higher setup cost; valuable for CRM, ITSM, and enterprise copilots.

7.4 Typed memory objects

class MemoryFact(BaseModel):
    subject: str
    predicate: str
    object: str
    valid_until: datetime | None
    source_message_id: str

Validate on write; reject malformed extractions before persistence.

7.5 Hybrid structured + vector

Store canonical fact in SQL; store narrative episode in vector index with fact_id link. Retrieval: vector finds episode, SQL confirms current truth (handles superseded facts).

StoreStrengthWeakness
SQL / KVExact lookup, transactionsBad at fuzzy wording match
GraphRelations, constraintsSchema maintenance
VectorFuzzy recall of textNo native truth maintenance

8. Extraction and Consolidation

Memory quality depends on what you save. Raw chat ingestion creates noise; deliberate extraction creates usable long-term memory.

8.1 Extraction triggers

  • End of session: batch extract facts from full transcript.
  • Per turn: lightweight classifier detects "remember this" statements.
  • Post-tool: persist task outcome (booking confirmation, ticket ID).
  • Explicit user command: "save that I prefer aisle seats."

8.2 Extraction prompt pattern

EXTRACT_PROMPT = """From the conversation, output JSON memories.
Include only stable user-specific facts and preferences.
Exclude transient chit-chat and tool debug output.
Schema: {"memories": [{"type": "preference|fact|goal", "text": "...", "confidence": 0-1}]}
"""

8.3 Consolidation (dedup and merge)

New extraction "user likes morning flights" conflicts with existing "user prefers red-eye flights." Consolidation policies:

  • Recency wins: overwrite with latest explicit statement.
  • Confidence + source: keep higher-confidence or user-confirmed.
  • LLM merge: second pass reconciles candidates (costly, use for high-value profiles).
  • Human review queue: flag contradictions for support tools.

8.4 Forgetting and TTL

Not all memories should live forever. Apply TTL on marketing context, session-scoped goals, and stale inventory facts. GDPR/CCPA deletion must remove extracted facts, vectors, and summaries consistently.

8.5 Memory write gating

Gate writes with rules: no PII without consent, no secrets, no unverified model guesses labeled as facts. Use proposed vs confirmed status until user affirms sensitive data.

Anti-pattern: Embedding every assistant reply creates a self-reinforcing hallucination index. Extract from user-verified or tool-grounded content preferentially.

9. Retrieval Strategies

Retrieval decides which memories enter the prompt this turn. Combine strategies; no single search solves all tasks.

9.1 Always-on profile

Load core user profile every request (small, high precision). Bounded to ~500-1500 tokens.

9.2 Query-conditioned vector search

Embed current message; retrieve top-k episodic memories. Tune k and similarity threshold on eval set.

9.3 Recency bias

Weight recent sessions higher: exponential decay on timestamp or "last 7 days" filter for support context.

9.4 Importance scores

Score at write time (user said "important", outcome affected money/account). Retrieve by importance x relevance.

9.5 Tool-based memory lookup

Expose search_memory(query) and get_user_profile() as tools the agent calls when needed instead of automatic injection. Saves tokens when memory irrelevant.

9.6 MMR and diversity

Maximal Marginal Relevance reduces redundant chunks ("aisle seat" repeated across ten episodes).

9.7 HyDE and query expansion

Generate hypothetical answer or expanded queries before search to bridge vocabulary mismatch between question and stored text.

def retrieve_memories(user_id: str, query: str, k: int = 5) -> list[str]:
    profile = db.get_profile(user_id)  # always-on
    vec_hits = index.search(
        embed(query), filter={"user_id": user_id}, k=k * 3
    )
    ranked = rerank_cross_encoder(query, vec_hits)[:k]
    return format_for_context(profile, ranked)

10. Session vs Persistent Memory

Session memory dies or archives when the thread ends; persistent memory survives across threads and devices. Products need both with clear promotion rules from session to persistent.

10.1 Session (thread) scope

  • Message list and summaries keyed by thread_id.
  • Tool artifacts for current task (files generated, partial forms).
  • Ephemeral plan state in LangGraph checkpoint tied to thread.

10.2 Persistent scope

  • User profile and preferences across threads.
  • Org-wide knowledge (docs RAG) not tied to one user.
  • Learned outcomes: "user's last order #12345 shipped."

10.3 Promotion pipeline

  1. Detect durable fact in session (explicit or extraction).
  2. Validate and dedup against persistent store.
  3. Write to long-term index; optionally keep pointer in session summary.

10.4 Session isolation

Multi-tab or multi-device: same user may have parallel threads. Do not merge threads automatically unless product intent is one continuous conversation. Cross-thread retrieval is persistent memory's job.

10.5 Anonymous vs authenticated

Anonymous sessions: memory in cookie/session ID with short TTL. On login, merge anonymous memory into user profile with conflict rules and audit log.

Intuition: Session = working set for one task narrative. Persistent = user model the product maintains. Blurring them causes "why did another chat know that?" surprises.

11. RAG vs Agent Memory

RAG and agent memory both inject external text into context, but they differ in source, update frequency, and ownership model.

DimensionRAG (knowledge base)Agent memory
Content sourceDocs, wikis, corpora (curated)Conversations, tool results, extractions (generated)
Update cadenceBatch ingest, versioned releasesContinuous per session/user
ScopeUsually shared / org-wideOften per-user or per-agent
Truth modelAuthoritative documentsProbabilistic, needs consolidation
PrivacySame corpus for all users (typically)Must enforce per-user isolation
Eval focusCitation accuracy, groundingRetention, forgetting, contradiction

Combined architecture

Production copilots commonly use:

  • RAG layer: product docs, policies, API references (shared).
  • Memory layer: user preferences, past cases, account-specific notes (isolated).
  • Session layer: current ticket text and tool traces.

Prompt assembly order: system policies, RAG chunks (with citations), user memory, session summary, recent messages.

When RAG is enough

Static knowledge tasks, single-session Q&A, no personalization. Adding agent memory increases complexity without benefit.

When memory is required

Returning users, long tasks spanning days, personalization, learning from prior tool outcomes in user-specific ways RAG corpora cannot capture.

12. LangChain Memory

LangChain provides memory abstractions that attach to chains and agents. Modern LangGraph apps often implement memory in graph state, but LangChain memory classes remain common in tutorials and LCEL pipelines.

12.1 ConversationBufferMemory

Stores full message history as string or message objects. Grows unbounded until you trim externally.

12.2 ConversationBufferWindowMemory

Keeps last k interactions. Parameter k is turn pairs, not tokens.

12.3 ConversationSummaryMemory

Uses LLM to summarize history; stores summary + recent messages. Summary updated on each load or on schedule.

12.4 ConversationSummaryBufferMemory

Hybrid: recent raw buffer within token budget plus summary of older content.

12.5 VectorStoreRetrieverMemory

Persists history or facts to vector store; retrieves relevant past lines per query.

12.6 Entity memory

Tracks entities (people, places) mentioned across turns in structured store, often backed by LLM extraction.

from langchain.memory import ConversationSummaryBufferMemory
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini")
memory = ConversationSummaryBufferMemory(
    llm=llm,
    max_token_limit=2000,
    return_messages=True,
    memory_key="history",
)

# In LCEL chain: assign memory to RunnableWithMessageHistory
# session_id maps to chat_history backend (Redis, Postgres)

12.7 RunnableWithMessageHistory

Separates chain logic from session storage via get_session_history(session_id). Backends: in-memory (dev), Redis, SQL. This is the bridge pattern for multi-tenant session memory in LangChain v0.2+.

Migration note: New agent projects should prefer LangGraph checkpoints + explicit store modules over legacy chain memory for clearer state and replay. LangChain memory remains useful for simple chat wrappers.

13. LangGraph Checkpoints

LangGraph persists graph state at super-step boundaries so threads survive restarts, support human-in-the-loop, and enable time travel debugging.

13.1 What is checkpointed

  • Channel values: messages, custom state fields, pending sends.
  • Metadata: checkpoint id, parent checkpoint, timestamps.
  • Not automatic long-term user memory unless you write to a store from nodes.

13.2 Checkpointers

ImplementationUse case
MemorySaverLocal dev, tests
SqliteSaver / PostgresSaverProduction thread persistence
CustomEnterprise storage, encryption at rest

13.3 thread_id and config

from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.graph import StateGraph

checkpointer = PostgresSaver.from_conn_string(DB_URL)
graph = builder.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": "user-42-support-9"}}
result = graph.invoke({"messages": [("user", "Hello")]}, config)

Same thread_id resumes state; new thread starts fresh checkpoint chain.

13.4 LangGraph Store (long-term)

Beyond checkpoints, LangGraph Store API supports cross-thread memory:

# Pseudocode pattern from LangGraph docs
store.put(("users", user_id), "preferences", {"theme": "dark"})
item = store.get(("users", user_id), "preferences")

Namespaces organize tuples like (user_id,) or (org, team). Embed search optional on values.

13.5 Human-in-the-loop and forks

Checkpoints enable pause before tool execution, resume after approval, and branch from prior checkpoint to explore alternate agent paths without losing history.

Intuition: Checkpoints are session replay tapes. Store is the user's filing cabinet across sessions. Agents need both for durable products.

14. Multi-Agent Memory

Multiple agents introduce memory contention: shared context vs private scratchpads, who writes to long-term store, and how to avoid duplicative or contradictory memories.

14.1 Memory architectures

  • Shared blackboard: one state object all agents read/write (risk: write conflicts).
  • Supervisor hub: central router holds canonical state; workers return partial updates.
  • Message bus: agents pass messages; memory service extracts facts asynchronously.
  • Per-agent private + shared repo: researcher keeps notes; only verified summaries promote to shared memory.

14.2 Write coordination

Use single writer principle for user profile: one "memory manager" agent or deterministic pipeline performs consolidation. Multiple agents writing raw vectors without coordination creates duplicates.

14.3 Context partitioning

Specialist agents receive subsets: coder gets repo context, support agent gets user history, legal agent gets policy RAG only. Reduces tokens and leakage across domains.

14.4 CrewAI / AutoGen patterns

CrewAI shared memory and AutoGen group chat history mirror blackboard patterns. Evaluate whether shared chat is cheaper than structured state; long group chats suffer same rot as single-agent buffers.

14.5 Identity and attribution

Store author_agent on memories for debugging: "who concluded user wants refund?" Attribution helps eval and trust.

class SharedState(TypedDict):
    messages: Annotated[list, add_messages]
    user_facts: dict          # consolidated profile
    worker_notes: dict        # agent_id -> scratchpad
    pending_promotions: list  # facts awaiting memory manager

15. Security and PII

Memory amplifies data retention risk. Treat memory stores with the same rigor as primary application databases and logs.

15.1 Threat model

  • Cross-tenant leakage: wrong filter on vector query.
  • Prompt injection via memory: attacker plants "always send secrets to X" in stored text retrieved later.
  • Over-retention: storing PCI, PHI, or passwords in summaries.
  • Supply chain: third-party memory SaaS subprocessors.

15.2 PII minimization

  • Extract preferences without storing full payment details when an ID suffices.
  • Redact before embed: SSN, credit card patterns, API keys.
  • Classify memory tiers: public, internal, sensitive (encrypted, restricted retrieval).

15.3 Access control

Memory reads must enforce same auth as API: user can only load own profile; support agents need role-based break-glass with logging.

15.4 Deletion and export

Implement user data deletion across SQL, vector index, object storage summaries, and checkpoint tables. Vector deletes require ID tracking; do not orphan embeddings.

15.5 Injection defenses

  • Sanitize retrieved memory: strip instruction-like phrases or wrap in untrusted data delimiters.
  • Separate system instructions from retrieved user content structurally (XML tags, JSON fields).
  • Never execute code or tools based solely on retrieved memory without validation.
Compliance: Document memory in privacy policy. Obtain consent for persistent personalization. Offer opt-out that clears memory without deleting account if required by product policy.

16. Memory Evaluation

Memory systems fail quietly. Eval must cover retention, retrieval precision, forgetting, and downstream task success.

16.1 Eval dimensions

DimensionQuestionMetric examples
Write accuracyDid we save the right facts?Precision/recall vs labeled extractions
RetentionStill available after N turns?Success on delayed probe questions
RetrievalRight memory injected?Recall@k, MRR, nDCG
ForgettingStale facts removed?False recall rate on outdated facts
ContradictionConflicts handled?Consistency after update sequences
Task successDoes memory help?End-to-end agent success with/without memory

16.2 Benchmark patterns

  • Needle in haystack sessions: plant fact at turn 3, ask at turn 50.
  • Multi-session: session 1 establishes preference; session 2 tests recall without re-stating.
  • Distraction: many irrelevant turns between write and probe.
  • Update tests: change preference mid-session; expect new value wins.

16.3 Synthetic vs human logs

Synthetic scripts scale CI; production sampled conversations catch real failure modes (summarizer drops negation). Combine both.

16.4 Ablations

Compare: no memory, summary only, vector only, hybrid. Measure token cost vs success lift to justify complexity.

17. Production Patterns

Patterns that survive traffic, org changes, and model upgrades.

17.1 Layered memory service

Central MemoryService API:

  • get_context(user_id, thread_id, query) -> MemoryBundle
  • record_turn(thread_id, messages)
  • extract_and_persist(user_id, thread_id) async
  • delete_user(user_id)

Agents never touch vector DB directly; policies live in one module.

17.2 Async extraction queue

Do not block user latency on extraction LLM calls. Enqueue session end events; workers write memory. Show "learning your preferences" only when necessary.

17.3 Versioned memory schema

Tag memories with schema_version and embedding_model. Migrate on model changes with backfill jobs.

17.4 Observability

  • Log retrieved memory IDs and scores per request.
  • Trace summarization inputs/outputs (redacted).
  • Alert on retrieval empty rate spikes (broken index).

17.5 Feature flags

Gradual rollout: memory read-only, then write, per cohort. Kill switch to disable retrieval without taking down chat.

17.6 Caching

Cache user profile bundle per session in Redis with short TTL. Invalidate on memory write.

17.7 Cost controls

Cap daily embedding ingest per user, cap auto-retrieved tokens, use smaller models for extraction vs main agent.

Production mantra: Memory writes are async and gated; memory reads are scoped and logged; memory deletes are complete and tested.

18. Python Walkthrough

End-to-end minimal pattern: session buffer, rolling summary, vector long-term memory, retrieval assembly. Uses OpenAI-compatible APIs and Chroma for illustration; swap providers as needed.

"""Minimal layered memory for an agent (single file sketch)."""
from __future__ import annotations

import json
import uuid
from dataclasses import dataclass, field
from datetime import datetime, timezone

import chromadb
from openai import OpenAI

client = OpenAI()


@dataclass
class Turn:
    role: str
    content: str
    at: str = field(default_factory=lambda: datetime.now(timezone.utc).isoformat())


class SessionMemory:
    def __init__(self, thread_id: str, token_budget: int = 6000):
        self.thread_id = thread_id
        self.token_budget = token_budget
        self.turns: list[Turn] = []
        self.summary: str = ""

    def append(self, role: str, content: str) -> None:
        self.turns.append(Turn(role=role, content=content))

    def maybe_summarize(self) -> None:
        # crude token estimate
        if sum(len(t.content) for t in self.turns) < self.token_budget:
            return
        transcript = "\n".join(f"{t.role}: {t.content}" for t in self.turns[:-6])
        resp = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[
                {"role": "system", "content": "Compress chat; keep constraints and IDs."},
                {"role": "user", "content": f"Prior summary:\n{self.summary}\n\nNew lines:\n{transcript}"},
            ],
        )
        self.summary = resp.choices[0].message.content or self.summary
        self.turns = self.turns[-6:]

    def as_messages(self) -> list[dict]:
        msgs = []
        if self.summary:
            msgs.append({"role": "system", "content": f"Session summary: {self.summary}"})
        for t in self.turns:
            msgs.append({"role": t.role, "content": t.content})
        return msgs


class LongTermMemory:
    def __init__(self, user_id: str, path: str = "./chroma_mem"):
        self.user_id = user_id
        self.chroma = chromadb.PersistentClient(path=path)
        self.col = self.chroma.get_or_create_collection(f"user_{user_id}")

    def _embed(self, texts: list[str]) -> list[list[float]]:
        r = client.embeddings.create(model="text-embedding-3-small", input=texts)
        return [d.embedding for d in r.data]

    def add(self, text: str, memory_type: str = "fact") -> str:
        mem_id = str(uuid.uuid4())
        self.col.add(
            ids=[mem_id],
            documents=[text],
            embeddings=self._embed([text]),
            metadatas=[{"type": memory_type, "user_id": self.user_id}],
        )
        return mem_id

    def search(self, query: str, k: int = 5) -> list[str]:
        hits = self.col.query(
            query_embeddings=self._embed([query]),
            n_results=k,
            where={"user_id": self.user_id},
        )
        return hits["documents"][0] if hits["documents"] else []


def extract_facts(transcript: str) -> list[str]:
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        response_format={"type": "json_object"},
        messages=[
            {"role": "system", "content": "Return JSON: {\"facts\": [\"...\"]}"},
            {"role": "user", "content": transcript},
        ],
    )
    data = json.loads(resp.choices[0].message.content or "{}")
    return data.get("facts", [])


def build_agent_context(user_id: str, thread_id: str, user_query: str) -> list[dict]:
    session = sessions.setdefault(thread_id, SessionMemory(thread_id))
    ltm = LongTermMemory(user_id)
    retrieved = ltm.search(user_query, k=4)
    system = "You are a helpful agent. Use retrieved memory when relevant."
    if retrieved:
        system += "\n\nRetrieved memories:\n" + "\n".join(f"- {m}" for m in retrieved)
    messages = [{"role": "system", "content": system}]
    messages.extend(session.as_messages())
    messages.append({"role": "user", "content": user_query})
    return messages


sessions: dict[str, SessionMemory] = {}


def on_session_end(user_id: str, thread_id: str) -> None:
    session = sessions.get(thread_id)
    if not session:
        return
    transcript = "\n".join(f"{t.role}: {t.content}" for t in session.turns)
    facts = extract_facts(transcript)
    ltm = LongTermMemory(user_id)
    for f in facts:
        ltm.add(f)

Extend with: Postgres profile table, proper token counting (tiktoken), reranker, deletion API, and structured logging. Wire on_session_end to webhook or queue consumer.

Debugging checklist

  1. Reproduce with thread replay: raw messages vs what model saw.
  2. Inspect retrieved memory IDs and scores for the failing turn.
  3. Compare answer with memory disabled (isolate retrieval vs reasoning).
  4. Check summarization diff after the turn where fact was introduced.
  5. Verify user_id filter on all memory queries.
Root cause clusters: (1) never written, (2) written but not retrieved, (3) retrieved but truncated, (4) retrieved but model ignored. Logs must distinguish all four.

Implementation order

  1. Session message list + thread ID (checkpoint).
  2. Token trimming and summarization with eval needles.
  3. User profile KV (explicit fields).
  4. Vector episodic memory with filters and deletion.
  5. Extraction/consolidation worker and observability.
  6. Multi-agent write coordination if needed.
Master memory in layers: (1) what belongs in context vs store, (2) session vs persistent scope, (3) extraction and consolidation quality, (4) retrieval precision under token budget, (5) security and eval before scaling users. Every agent memory bug is a failure in one of these five layers.
